# 2026-10-18｜SGLang 前缀缓存与 CPU 调度开销

## 范围与证据边界

本记录来自前缀缓存教学与代码逻辑讨论，保存可检验的调优假设。**所有条目尚无候选实现的同条件性能证明。**

- 审阅的上游 SGLang 提交：[`a3abea35609eeeff7e165486dd614963af211161`](https://github.com/sgl-project/sglang/tree/a3abea35609eeeff7e165486dd614963af211161)。
- 主要讨论 Python UnifiedTreeCore / UnifiedRadixCache 的 FULL 缓存路径，普通 LRU；其他组件、会话、优先级与分层缓存需单独核对。
- 对话中另有一个旧镜像 GLM W8A8C8 教学实例，其源码版本为 `ce0a8fea5f4245839d174b2b8c55692be1810a7f`。该实例不是本仓库普通 W8A8 或 Flash 研究线的当前合同 / 基线；本记录也没有重新连接其运行文件。
- 没有证据认定 LRU 是目标 GLM 的主要瓶颈。调度阶段墙钟可能包含等待，不能整段归为树操作。

## 已核对的当前流程

```text
缓存访问 / 匹配
  → 更新相关节点与路径的最近访问编号

需要回收槽位
  → 从可淘汰叶子集合生成本次候选
  → 按策略优先级建最小堆
  → 弹出候选并回收其槽位
  → 必要时加入新变成叶子的父节点
  → 达到所需回收量后结束本次流程
```

一次淘汰流程内部复用同一个堆；不是每弹出一个叶子都重新建堆。普通 LRU 的新旧顺序、回收资格和槽位数量是不同的维度。

- 仍有活跃请求使用的路径受到保护。
- 缺 4 槽不等于删除 4 个节点，一个叶子可以关联多槽 / 多页。
- 回收通常把槽交回进程内 allocator，不会自动向驱动释放预分配池。
- 这些操作主要维护索引与状态，不应描述为搬动整份 KV。

## CACHE-001

**持久维护淘汰候选，减少反复建堆**

- **状态 / 类型**：源码已定位，改法待验证；数据结构候选。
- **当前**：每次启动 FULL 淘汰时，遍历可淘汰叶子并构造候选堆。候选为 M 时建堆约 O(M)，每次弹出约 O(log M)，另有资格检查与状态回收成本。
- **候选改法**：比较持久候选索引、可维护的优先队列或严格适用条件下的 LRU 顺序结构，避免每次启动都全量组织。
- **收益来源**：候选多、频繁小批淘汰时，可能减少重复列表 / 元组构造和 heapify。
- **新增代价**：访问刷新、保护 / 解锁、分裂、删除、父节点成为叶子时维护索引；惰性失效方案还会有陈旧项和额外内存。
- **回退场景**：访问非常多、淘汰极少，平时维护的总成本可能超过省下的建堆。
- **正确性边界**：新成为候选的父节点应按原有访问记录进入正确位置，不能简单当成“刚使用”追加队尾。会话 / priority 与多组件规则需要保持；若改近似策略，必须明确另立对照。
- **最小验证**：固定树形、页大小、访问与回收事件序列，扫描候选规模及每次回收量。记录访问维护 + 建堆 + 弹出 + 回收的总 CPU 时间，再检查设备空洞与 E2E。
- **否定条件**：维护总成本更大，或局部降低完全未影响目标关键路径且不满足其他明确目标。

教学例子：1 万次交替访问、只启动 1 次淘汰时，持续调整顺序可能多做约 1 万次维护来省 1 次建堆。操作次数不能直接换算成微秒；还要考虑候选规模和一次操作的成本。

## CACHE-002

**批量回收，保留空槽余量**

- **状态 / 类型**：待验证假设；回收目标与触发策略候选。
- **当前基点**：回收量满足本轮需求后结束；叶子 / 页粒度可能使实际回收超过缺口。
- **候选改法**：用高低水位或批量目标保留一段空槽余量，减少连续的小次淘汰。
- **教学例子**：连续请求各需 4 槽，与其反复启动回收，可比较一次腾出 16 槽、后面直接分配的方案。这些数字不是推荐参数。
- **收益来源**：减少淘汰启动和候选组织次数。
- **新增代价**：提前清掉可能再次命中的缓存，增加未来重算；某次较大的淘汰也可能拉长当前请求等待。
- **更可能适用**：持续内存压力、分配需求较稳定；突发结束后长时间无分配时可能多清了缓存。
- **最小验证**：固定回收排序，只改水位 / 批量机制。同时测启动次数、回收时间、被驱逐量、后续命中与重算、TTFT / ITL。
- **否定条件**：CPU 省时被额外 Prefill 或尾延迟抵消。

## CACHE-003

**抽样近似 LRU，少看候选**

- **状态 / 类型**：待验证假设；改变淘汰选择的近似算法。
- **候选改法**：在可回收叶子中直接抽取小样本，从样本里选最旧候选；可比较跨轮保留少量候选的设计。
- **教学例子**：10 万候选只看 32 个。32 不是建议值，也不保证能选中全局最旧节点。
- **收益来源**：用选择精度换较低候选检查与组织成本。
- **新增代价**：可能淘汰更有用的缓存，减少后续命中；抽样索引本身也要维护。
- **实现前提**：必须能够直接抽样。先把所有候选遍历成列表再抽样，可能仍保留主要 O(M) 成本。不能抽中受活跃保护的节点；每次回收后候选资格会变化。
- **最小验证**：同一访问 trace 比较严格 LRU 与不同采样量，固定页与容量，记录总 CPU、驱逐选择、命中 / 重算与服务指标；固定随机种子并重复。
- **否定条件**：节约的维护时间小于额外重算，或候选索引成本使检查量并未下降。
- **外部参考**：[Redis 官方近似 LRU](https://redis.io/docs/latest/develop/reference/eviction/#approximated-lru-algorithm)。这是思路参考，不代表 SGLang 当前已采用这一方案。

## CACHE-004

**对照已有 LFU / SLRU / priority / T-LRU**

- **状态 / 类型**：上游已有能力，目标负载适用性待验证；策略对照，不是新发明。
- **思路**：除了“谁最久没用”，还可按命中频次、已证明的复用历史、请求优先级或下一轮 TTFT 预算选择保留对象。
- **收益来源**：减少一次性流量挤掉常用前缀，或将保留空间分给更影响服务目标的历史。
- **新增代价**：统计和参数维护；过去热门、现在已冷的前缀可能保留过久。保留价值需用真实到达 trace 验证。
- **边界**：策略偏好不能覆盖活跃请求的硬保护。优先保留也不等于永久固定。普通 LRU / LFU / SLRU 与 T-LRU 的目标不完全相同，按冻结合同分别评价。
- **最小验证**：优先比较当前版本已提供的策略，固定模型 / 权重、容量、页、并发与到达顺序。先复核策略是否受目标组件 / 后端支持，再比较缓存命中、重算、TTFT / ITL 与达标吞吐。
- **否定条件**：仅命中率提高，但目标延迟、吞吐或容量约束变差。
- **依据**：[固定版本的策略及参数说明](https://github.com/sgl-project/sglang/blob/a3abea35609eeeff7e165486dd614963af211161/docs/docs/advanced_features/radix_eviction_policy.mdx)。

## CACHE-005

**合并同批共享路径的访问记录刷新**

- **状态 / 类型**：源码已定位，改法待验证；元数据更新候选，可能涉及近似语义。
- **当前**：每次匹配结束沿 best-match 节点回溯祖先写最近访问记录。多个共享前缀请求可能重复更新相同祖先。
- **候选改法**：先统计重复程度；仅在能保持可观察访问顺序、回收资格和组件约束时合并更新。若降低刷新频率，则明确将其视为近似 LRU。
- **收益来源**：减少深路径上反复写相同元数据和 Python 遍历。
- **新增代价**：批内记录 / 去重成本，以及刷新延迟改变淘汰选择、命中和重算的可能。
- **最小验证**：记录路径深度与重复祖先更新次数；分别使用深共享路径和浅独立路径，检查中途淘汰、锁生命周期、MTP 与会话边界。
- **否定条件**：去重比原刷新更贵，或策略变化引起不可接受的重算 / 延迟。
- **源码**：本笔记开头的 `_match_post_processor`。

## CACHE-006

**简单缓存场景的轻量匹配路径**

- **状态 / 类型**：源码已定位，改法待验证；Python 执行路径候选。
- **当前**：通用 matcher 每次构造组件 validator 与局部函数，并在遍历节点时用 `all([v(node) for v in validators])` 检查组件有效性。
- **候选改法**：对语义已确认的 FULL-only、无 HiCache 场景比较轻量分支，减少临时对象 / 回调；复杂场景继续走通用路径。先核对目标版本是否已有等价快速路径，避免重复实现。
- **收益来源**：高请求速率、设备步骤短、单组件路径中可能存在可见的 Python 固定成本。
- **新增代价**：分支维护与正确性覆盖。机械改成生成器不保证更快；短路还须确认 validator 无副作用。
- **最小验证**：隔离纯匹配 CPU 成本与完整请求路径，覆盖空 key、页对齐、节点分裂、部分命中、namespace / salt、MTP bigram、多组件和 HiCache。
- **否定条件**：目标路径原本很少执行、局部成本未下降，或 E2E 无目标相关改善。
- **源码**：[`_match_prefix_helper`](https://github.com/sgl-project/sglang/blob/a3abea35609eeeff7e165486dd614963af211161/python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py#L893)。

## CACHE-007

**减少可避免的索引拼接与复制**

- **状态 / 类型**：源码已定位，所有权待验证；索引表示 / 更新候选。
- **当前**：路径索引收集后用 `torch.cat` 拼接；发布缓存等位置还有强制独立复制。这些操作处理索引，不等于搬运整块模型 KV。
- **候选改法**：区分只读且生命周期可保证的索引与必须拥有独立存储的副本；前者可比较单段复用、批量拼接或增量路径。
- **收益来源**：减少反复索引分配、复制和小操作提交。
- **新增代价 / 风险**：别名被下游原地改写；异步使用尚未完成时缓冲已复用；分裂、淘汰后仍持有旧视图。不能看到 `copy=True` 就直接删除。
- **最小验证**：统计实际拼接次数、段数、字节和提交 / 同步时间；覆盖单段 / 多段、分裂、异步取消、结束和回收。
- **否定条件**：所有权无法安全复用，或生命周期维护比复制更贵。
- **源码**：[`collect_full_device_indices`](https://github.com/sgl-project/sglang/blob/a3abea35609eeeff7e165486dd614963af211161/python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py#L1075)、[缓存发布时复制](https://github.com/sgl-project/sglang/blob/a3abea35609eeeff7e165486dd614963af211161/python/sglang/srt/mem_cache/unified_radix_cache.py#L1195)。

## 进入实验前先补的最小证据

1. 目标模型、量化、框架镜像 / commit、硬件与并行合同。
2. 请求到达、输入 / 有效输出目标、冷热缓存、图与 MTP 条件。
3. 树深、叶子数量、命中 / 插入 / 淘汰调用次数、每次回收量。
4. 访问维护、匹配、建堆、弹出、索引操作的独占 CPU 时间。
5. 对应 CPU 工作是否暴露在设备关键路径；预期改变哪段等待。
6. 正确性保护用例、重复基线与噪声、接受 / 否定条件。

当前下一步是补观测与稳定基线；本笔记不把修改任何线上配置或启动 benchmark 当作已经完成的工作。
