# M001：drain 当前队列候选的正确性与 CPU 实测

已实现并实测一个独立候选：保留 cap32，只收集当前已排队请求，不再等待稍后到达的请求。安装版及其包文件没有修改。它在本轮两条短输入和错开到达的混合输入中改善了 CPU 分词完成时间；长输入的墙钟结果受限流影响，尚未接受。它没有成为服务配置、全局最优实现或物理极限结论。

## 实现和固定环境

[候选](candidates/L013/drain_available.py)只覆盖 `_dynamic_batch_loop` 的收集部分：首请求仍 await 队列，随后用 get_nowait 收集至 cap/预算/空队列。`_process_dynamic_batch`、encode、kwargs 分流、future 完成和取消检查均继承实际安装类。候选 SHA-256 为 `439ed10f5937910caa8232fcc924394d4e18fa9b448b8df7cca9fd0b8f787275`；文件保留冻结前的 UNTESTED 注释，已验证范围以回执和下述结果为准。没有向生产应用补丁。

安装源码 `ce0a8fea5f4245839d174b2b8c55692be1810a7f`、镜像 `sha256:c5cf2deb674cd1c8aba10a70d8dcb3e413d3739f6a54808c568e11d711d2e263`；真实完整 SGLang get_tokenizer、13 个源码和 4 个模型/tokenizer 文件哈希前后核对。CPU venv 重用镜像包文件，排除可选 torch_npu 与启动 .pth；Transformers5.12.1、tokenizers0.22.2、Jinja3.1.6、Torch2.10.0+cpu，Rust 并行关闭。

每个任务容器限制 1 CPU、4GiB、64pids，禁网、只读根、删除 capabilities，只读挂载四个文件，无权重或 NPU 设备。cgroup v1 quota/period 均为100,000us；没有物理核绑定或峰值校准。四个新容器全部按精确 ID/标签清理，现有服务 ID、启动时间和重启计数前后不变。没有生成请求。

## 先验证语义和批次反例

[L013 原始结果](results/L013-R001.json)通过 36 个带记录的场景、42 次操作，共172个预期请求状态：162份完整结果、6次取消、4次注入异常及后续恢复。覆盖单请求、2×512/3×32768同时到达、重复使用、不同kwargs、入队前/入队后/worker内取消、异常恢复、34请求跨cap和8次错开到达。直接实际 tokenizer 的完整字典和固定 ID 作为 oracle；batcher 取消后 worker 线程全部退出。

8次错开到达均观测到原类分组 `[3]`，候选 `[2,1]`。这不是完全相同的调度语义：候选会放弃合并稍后到达的请求，可能增加调用、减小批次。带 delegating wrapper 和方法记录器的 L013 仅作正确性，时间戳用于观察到达，不能作为性能数据。

## 干净计时

L014移除 tokenizer wrapper 和方法替换，直接使用实际原类/候选，双方 cap32、字段窗口2ms不变。每case12个block，交织 A/A（两个独立原类 actor）与 A/B（原类/候选），种子7911随机化顺序。每actor预热3批，每次间隔0.1s；48行/case、共144行，384份计时请求结果全部与完整字典/固定ID相同。

三组输入来自同一 manifest：2×512、3×32768，以及短512/短512/长32768按请求延迟 `[0,0,0.001]` 注入。任务在第一次yield前创建；双方相同的小型 async wrapper 各记录两个时间戳，计入区间，输出/哈希核验在区间外。记录整批wall、包含worker的processCPU、逐请求入队至完成、实际入队/完成offset及每区间cgroup差值。没有Spy或性能采样回调。

短输入CPU中位数1.640/1.608ms，配对比1.0434 [1.0142,1.0885]，仅略离开A/A [0.9785,1.0114]，不作跨环境稳定收益承诺。长输入CPU比1.0139 [1.0087,1.0194]与A/A [0.9945,1.0182]重叠。混合输入CPU中位数48.735/47.483ms，比1.0340 [1.0179,1.0532]，超过本轮A/A [0.9881,1.0097]。这些都是CPU类与注入器结果，不证明原生分词算法本身减少了等同比例的必要工作。

## 逐请求结果与不确定性

混合输入首条短请求的入队至完成中位数 **50.918→3.080ms**，配对比17.0489 [16.1190,18.4029]，A/A [0.9875,1.0086]；第二条50.913→3.070ms；长请求49.609→46.112ms。拆批让短请求可在长输入完成前返回，这是CPU前处理完成时间，不能命名为模型TTFT或端到端加速比。完整逐请求指标见[分析](analysis.json)，没有只选择首请求作为总收益。

请求延迟是目标值，实际到达并非完全相同：A/B中第三请求的offset中位数原类1.430ms、候选1.511ms；范围分别1.142–1.473ms与1.266–1.857ms。全部实际时间戳已保留。因此结论限于这个受事件循环影响的合成生成器，不是对任意相同线上到达轨迹的保证。

长输入限流共3个区间，原始throttled_time总计2,122,090ns，其中A/B原类2,104,960ns、候选5,720ns；另A/A原类11,410ns。不能删掉这些行或将4.057ms的中位数差全部归因给候选。长输入的wall因果结论保持INCONCLUSIVE。

## 当前结论和下一步

L013仅接受覆盖范围内的CPU功能正确性；L014总体INCONCLUSIVE，保留短/混合相对默认cap32的局部效果。尚未在同一配对实验中与cap1等最佳已有路径比较，也未校准驻留输入直接分词的可达下界，所以不登记“最佳全局实现”，不宣称逼近物理峰值。未知线上流的吞吐、队列公平性、大突发和不同tokenizer仍可能改变取舍。

当前没有本任务Ascend PD＋MTP服务器基线，HTTP/frontend是否启用动态分词、reasoning parser、PD传输、MTP接受长度、TTFT/ITL和NPU吞吐均未测。整体仍 **E0**，accepted_baseline=null。进一步M001调优应先确认目标PD前端相关性，并与cap1对照；本阶段转向M031的实际Ascend/PD/EAGLE验证与接受路径核验，保持MTP主线。
