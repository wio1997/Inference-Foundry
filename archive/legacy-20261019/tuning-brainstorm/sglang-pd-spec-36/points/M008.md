- 类型：config。
- 主线：PD 分离 + 推测解码保留；Ascend 实际配置待运行合同确认。
- 本文是用途、假设与最小实验设计，不是已取得加速的报告。

## 它干什么

让等待队列优先处理更能复用已有前缀的请求，争取少做重复 Prefill。

## 当前怎么做

LPM 等现有策略匹配前缀并调整顺序。固定版本对部分策略在队列过大时退回 FCFS；配置名不等于每轮实际采用的策略。

## 成本在哪里

多做匹配、排序与树访问；缓存收益可能被 CPU 或低复用请求的等待抵消。

## 这次考察的优化思路

对照现有 FCFS 与 LPM，判断业务共享前缀是否足以支付排序成本；不把缓存命中直接当成调度策略收益。

## 什么条件下可能适用

主要在 P；缓存开启、重复前缀确实驻留，且实际活动策略可观察。

## 新增成本与回退场景

前缀几乎不共享；大队列回退；冷请求排队恶化或树状态变化带来额外维护。

## 不能破坏的语义和生命周期

同一到达序列与相同缓存初态；每请求完整结果不变，防止饿死；D MTP 参数不动。

## 最小实验

**基线**

冻结请求顺序与 warm/cold 缓存初态，记录 active policy。

**唯一改动因素**

只把 P 的策略从当前 FCFS 改为已支持 LPM，或反向对照。

**用例**

- 全部不同前缀
- 多数共享长前缀、少数冷请求
- 小队列与越过源码回退阈值的受控回放

**预测**

共享负载可能减少实际 P token；无共享应暴露额外排序成本。

**指标**

- 匹配/排序 CPU
- 实际执行 P token
- 冷请求等待尾部
- 满足 SLO 的吞吐

**否定条件**

实际策略回退却宣称 LPM 收益无效；P 计算节省无法覆盖额外等待则不采用。

**第一个可执行动作**

查每轮 _determine_active_policy 返回及缓存初态，不只读取启动参数。

**最低执行层级**

活动策略 → 队列回放 → 服务对照

## 逼近物理极限的分析

**必要工作**

选择执行顺序、识别可复用前缀并维护公平性；任何未命中输入的计算仍必要。

**资源与依赖边界**

最理想可省计算由实际可复用且能留存的前缀决定；排序开销加等待必须支付，不能使用无限缓存/未来信息 oracle 当现实能力。

**怎样校准可达上界**

在固定到达流和容量上用离线可知前缀回放给出乐观上界，再测在线策略的实际命中、CPU 与尾延迟；明确 oracle 不可部署。

**怎样判断剩余空间**

若在线命中已接近该负载上界，转减少匹配/排序维护；若差距在容量/路由则转对应机制，而非只增加策略复杂度。

**条件特化与回退**

按共享前缀族数量、复用距离、队列长度、冷请求比例与 P 负载分区；D MTP 固定以免后端压力混淆。

**何时停止当前方向**

在冻结公平/TTFT 目标内候选策略无法进一步减少必要计算或 CPU 等待，报告帕累托边界，不声称一个排序适合所有请求流。
