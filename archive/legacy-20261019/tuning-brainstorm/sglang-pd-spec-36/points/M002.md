## 它干什么

多个进程分工处理请求，让分词、调度和输出能够同时工作；IPC 是它们之间递交消息的通道。

## 当前怎么做

TokenizerManager 建立消息通道；DetokenizerManager 按请求保存输出状态并把 token 转成文本。固定源码已有按解码选项分组的批量 decode，还会过滤空 token 段。

## 成本在哪里

消息打包、传递、唤醒和反分词都花 CPU。慢客户端可能堆积输出；模型快不等于用户收到得快。

## 这次考察的优化思路

先对照已有批量反分词能力，判断逐请求解码是否形成输出瓶颈；空段跳过已经实现，不再作为新点。

## 什么条件下可能适用

当前 tokenizer 支持批量 decode，且多个请求同时产生输出；不能假设某一模型无边界问题。

## 新增成本与回退场景

批量等待延迟首段；某些 tokenizer 特殊字符跨段解码有兼容风险。

## 不能破坏的语义和生命周期

完整拼接文本、特殊 token 处理、reasoning/tool 字段、结束与取消各只交付一次；按请求保序。

## 最小实验

**基线**

记录当前反分词配置及每条消息大小，其他流式粒度不变。

**唯一改动因素**

仅对照现有 batch decode 开关，不同时改 SSE 聚合或 IPC 格式。

**用例**

- 1 与 3 路正常读取客户端
- 含中文、多字节字符和空输出段
- 其中一路缓慢读取或中途取消

**预测**

多路输出的反分词 CPU 降低；若瓶颈是客户端则设备侧吞吐不变。

**指标**

- 反分词 CPU/输出 token
- IPC 队列停留
- 输出积压字节
- 客户端逐段到达间隔

**否定条件**

文本边界错误即否定；只减少 CPU 却未缩短目标输出延迟，只记录局部收益。

**第一个可执行动作**

按请求关联调度发送、反分词接收、HTTP 写出时间，先确认延迟发生在哪一段。

**最低执行层级**

IPC 路径核验 → 输出回放 → 慢客户端对照

## 逼近物理极限的分析

**必要工作**

每个请求的输出必须有序送达，必要字符边界和完成信号必须保留。

**资源与依赖边界**

至少传递服务合同要求的输出字节；延迟下界含消息依赖及实际链路服务时间。IPC、反分词、HTTP 串行部分不能用一个最大值代替。

**怎样校准可达上界**

分别用已生成 token 回放反分词、固定消息回放 IPC、固定文本回放 HTTP，量三段最好稳定服务率和排队拐点。

**怎样判断剩余空间**

对比无排队段与真实路径，多余打包/复制、空消息和唤醒若仍显著继续拆；慢客户端受合同限制，不能靠丢输出缩短。

**条件特化与回退**

按输出段大小、并发、客户端读取速率、reasoning/tool 字段与 MTP 每轮接受长度区间特化；同一协议内比较。

**何时停止当前方向**

达到目标输出节奏且主要剩余时间由实际消费速率或必要解码解释；任何聚合改变流式合同必须单列取舍，不能记为等价极限。
