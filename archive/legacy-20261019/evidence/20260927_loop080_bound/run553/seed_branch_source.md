# Run553 — source correction: successor seed is conditionally device-resident

Read-only installed-source audit; no service, NPU or code mutation. Run551/552 correctly left seed device completion open, but Run551's prose could be read as if `_copy_draft_token_ids_to_cpu` always delivered the next seed. The installed frozen launcher enables `--async-scheduling` (`scripts/serve.sh:113`). The actual next-step seed path has conditional branches and must be recorded dynamically.

Record the actual branch and event generation rather than assuming either outcome.

The vLLM parent `_prepare_input_ids` at `framework/vllm/vllm/v1/worker/gpu_model_runner.py:1761–1890` has an async path: for shared requests it writes `prev_sampled_token_ids` to `input_ids.gpu` and, when scheduled draft positions exist, scatters `self._draft_token_ids` on device. On a new-request/prefill mix it first uploads CPU prompt IDs. This is a real potential seed producer path. The installed Ascend runner calls it during `_prepare_inputs` before handoff; the handoff binds the resulting actual `input_ids[:96]` and positions. The DCP `rebuild_async_spec_decode_inputs` branch (`vllm_ascend/worker/dcp_utils.py:249+`) can alternatively rebuild positions on device or synchronize a previous valid-sampled-count side-stream event for a CPU correction when with-prefill conditions require it. It explicitly discards its `draft_token_ids` argument, so passing that tensor to the DCP helper is not a provenance certificate. Which branch executes for the selected residual/seed call remains unmeasured.
