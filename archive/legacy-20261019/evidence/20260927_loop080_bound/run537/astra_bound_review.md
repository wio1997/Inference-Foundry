## 2. A correct four-level model

Declare an execution class A and initial state I0, including allowed pre-window work/reuse, storage, representation, numerical semantics and required external completion. Define `T*_A` as the infimum full Product makespan over legal variants in A. Current is one observed legal implementation point; it is not a constraint on the alternative dependency graph.

For one candidate work/placement variant v, a safe relaxation is:

`L(v) = max(resource-load floors, necessary-path floors, legal release/completion floors)`.

For resource k with a *genuine cumulative capacity upper envelope* `service_k(T) <= C+_k T + B_k`, the load term is `max(0, W-_k(v)-B_k)/C+_k`. A path term is a sum of valid service lower bounds only across proven nonoverlapping precedence edges, in a consistent clock/time scope. Load and path terms generally combine by max, not sum. A stronger resource-constrained DAG relaxation can couple them.

The architecture-wide floor requires `L_A = inf_v L(v)` over all allowed variants, or a common relaxation proved for every variant. Choosing the most expensive current graph yields no architecture-wide bound. Adding minima for mutually incompatible work/traffic variants invents an impossible design; instead keep a Pareto set of compute, traffic, memory capacity, communication and dependencies. Recompute versus retain, batching versus latency, replicated weights versus communication, and speculative breadth versus useful output must be represented jointly.

A certified positive L_A implies `TPS*_A <= 49152/L_A`. A fully demonstrated feasible implementation provides an achieved point and an upper latency observation; repeated formal measurements provide the project's performance statistic, not a deterministic bound. An empirical costed schedule can be published sooner as a **conditional predictive interval**, with validation error and unmeasured costs explicit. Calling it an Engineering/Aggressive hardware maximum would overstate it.

For duration intervals and one genuinely feasible schedule, simulated `[T_low,T_high]` maps monotonically to `[49152/T_high,49152/T_low]`; this remains predictive unless the node envelopes, contention, semantics and full-window calibration justify stronger language. Bounds on the optimum require separate lower relaxation and feasible construction, rather than a range formed from independently optimistic node medians.

V3.27's19-node status ledger is a certification workflow, not the executable semantic/resource DAG. A strict positive work subset plus matching capacity can give a weak finite ceiling without closing all19 nodes. Conversely, certifying all current native graph identities would not prove their serialization necessary. Keep endpoint-specific prerequisites; do not make every empirical estimate wait for the complete universal proof.
