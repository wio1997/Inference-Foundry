## Resource and Scheduling evidence

- Each trace has 2,825 CANN kernel rows and 264 ordered `COMMUNICATION` tasks. Across the eight ranks the CANN `Computing` occupancy is narrowly **38.30–39.01 ms** for this first padded88 prefill call. The union of compute-only intervals is smaller on ranks with compute/communication overlap; do not confuse the two.
- CANN `Stage` spans **460.78–495.56 ms**. The exposed categories differ sharply: ranks1/3/5/6/7 label about **409–452 ms** as communication-only; rank4 labels only **62.5 ms** as communication-only and **375.6 ms** as Free. Rank0/2 split the time between Free and communication. The eight Host forward calls returned over **574–627 ms** after the earliest rank entered the wrapper and were synchronized by about the same 627 ms mark. These are profiler-perturbed durations, not normal original path costs.
- Run334 matched the exact same 264 collective names in order across all eight exported traces. The **latest task start** came from rank4 for **214/264** collectives, rank0 for49, rank7 for1. Median rank start spread was **1,436 µs** (max34,388 µs), while median end spread was only **20.4 µs** (max35.5 µs). Median latest-start-to-latest-end window was13.75 µs; summing those windows gives3.756 ms **within this perturbed trace**. These patterns strongly indicate that hundreds of milliseconds reported as HCCL task duration include inter-rank arrival/rendezvous wait. A task start is not independently proven input-data-ready, so neither 3.756 ms nor the CANN communication union is an HCCL resource floor or removable Product time.
- Run335 additionally matched all264 Host `Enqueue@Hccl*` events to their correlation-ID `Dequeue` and ordered CANN task on all eight ranks. The latest Host enqueuer was exactly the latest device-task starter for **264/264** tasks (rank4 214, rank0 49, rank7 1). Host enqueue spread median was **25.774 ms**; latest enqueue to latest device start median **79 µs**; rank4 enqueue-to-dequeue median **9.5 µs**. This localizes the observed profiler-window rendezvous to **Host submission progress**, without proving that the same rank would lag in unprofiled service or that all wait is removable.
- Run165's earlier **one-rank** profiler had 39.6 ms compute, 2.86 ms communication and401.7 ms Free on a warmed83-token forward. Run333's all-rank profiling redistributed apparent idle/wait among CANN categories. The comparison reinforces that profiler task labels cannot by themselves establish a Scheduling-aware or Hardware/Resource Bound.

## Decision

Run333/334 are useful for correcting the Performance Model's **collective DAG semantics**: each collective must join all rank arrivals, then consume measured no-wait link service; early ranks' waiting belongs to scheduling/producer imbalance and must not be added again as intrinsic communication. The 38–39 ms compute occupancy is a profiled fixed-shape work observation, not compulsory compute or an attainable full-prefill floor. Current Formal remains Run99 median571.681 tok/s; Hardware/Resource, Scheduling-aware attainable and Product E2E numeric bounds remain unknown.

Next obtain a low-perturbation all-rank arrival/producer timing around natural 83-token prefill collectives and a same-topology HCCL Test or chain for their real payloads. The measurement should separate true after-last-arrival service from Host submission skew, then feed a resource-constrained prefill DAG; only a complete incremental b=2–4 preparation cost and correctness gate could justify live slot refill. Do not directly optimize a task because its profiled HCCL duration is long.
