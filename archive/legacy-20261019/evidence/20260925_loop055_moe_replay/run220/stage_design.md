# Run220 interleaved stage-completion design

Run219 passed one-layer graph output substitution and Runtime checks, but its C/D phases were single-call, ordered and Host-submission-only. The frozen next discriminator is a same-service, eight-rank, repeated first88 layer0 MoE completion comparison. Retain the original graph capture A and execute four graph and four eager cohorts in the order G1,E1,E2,G2,G3,E3,E4,G4, each 12 requests x 1024 output after legal warmup48. Keep the exact same dataset and service configuration. Each cohort triggers exactly one [11,4096] BF16 layer0 call per rank, checks aliases and context, and records pre-call synchronization plus post-call synchronization wall time. The graph path refreshes persistent input, replays, returns graph output; eager path calls the original op and returns its output. The capture graph and storage persist across cohorts and are reused only after the previous 12-request cohort has fully completed. Record eight-rank activation, all Runtime records, generated counts, and per-rank paired completion times.

Pass criteria: all 8 rank records for all 8 diagnostic cohorts, legal requests, Runtime pass and no graph errors; compare rank-max and per-rank medians across paired graph/eager cohorts. A material stable saving requires graph completion lower than eager in all four pairs at the slowest-rank envelope by at least 0.5ms. The 0.5ms threshold is a screening gate, not an E2E claim. A failure rejects extension of this graph path under the current shape and stream semantics. A pass only allows a bounded multi-layer feasibility design; graph capture cost, shape bank, exact output oracle and formal E2E remain separate gates.

No profiler, client TPS, or simple sum of per-layer savings will be treated as a product verdict. Stop service and restore borrowed source files to exact SHA after the run.
