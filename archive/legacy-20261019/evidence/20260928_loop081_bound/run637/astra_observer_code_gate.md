## Exact installed Event semantics and reuse answer

Installed container `dsv4ab` torch_npu version.py reports `2.10.0.post4`, git `5dd8ef3f9b375b5ae4a83538d5785754148c3302`. Installed Python streams.py SHA256 `241741b356db5006797dbec119007afb33b73b0e1753bfb06ab27c989c5bfac4`; installed NPUEvent.h confirms lazy native creation on first record and device ownership acquired from that stream.

The official implementation at the exact reported commit is [NPUEvent.cpp](https://raw.githubusercontent.com/Ascend/pytorch/5dd8ef3f9b375b5ae4a83538d5785754148c3302/torch_npu/csrc/core/npu/NPUEvent.cpp). `record(stream)` creates the native event only when `!is_created_`, checks the device, then launches a new record task. This is source evidence matched to package metadata, not binary provenance or live execution proof.

**Same-event warm generation 0 followed by measurement generation 1 on the same device/stream is acceptable as the source design.** The warm generation must finish at an already-existing premeasurement terminal drain; post-drain query verifies it. No warm timing or wait may still depend on generation 0. Each measurement event is then recorded once and never rerecorded before export. Warm-only independent events cannot establish that a different measurement event has undergone its lazy initialization. If independent pools are used, every actual measurement event must itself receive its warm record. A second measurement pool is unnecessary for this bounded design.

First-record all intended events outside Graph capture, before the measured Product workload and at a lifecycle location whose existing drain really covers all bound streams. Allocating/first-recording a fresh pool in each measured cohort builder would include initialization in Product preparation, even if outside a Runtime timer. A worker-persistent pool needs explicit cohort ownership and generation retirement. A Python preallocated list does not prove zero remaining runtime allocation or zero observer cost.

Official [CANN event record documentation](https://www.hiascend.com/document/detail/zh/canncommercial/80RC22/apiref/appdevgapi/aclcppdevg_03_0082.html) describes record reuse and overwritten capture for relevant event creation APIs. That older documentation is corroboration only; do not transfer its platform or API availability to the installed environment without checking the exact flags/runtime path. Do not substitute ExternalEvent or add reset, wait, or Graph nodes.

### Hidden synchronization in timing reads

At the exact torch_npu commit, `elapsed_time()` calls `emptyAllNPUStream()` and `aclrtSynchronizeEvent()` for both endpoints before reading elapsed time. `recorded_time()` also empties queues and synchronizes. Therefore export is **not an API-without-synchronization operation**. If accepted, it must happen only after the existing terminal device drain and positive query for every measured event, with no concurrent next-cohort enqueue. These calls should then wait for no unfinished workload, but still incur Host/API cost. If the requirement is literally no additional synchronization API calls anywhere, this timing API fails that requirement and another acquisition interface is required.

Export outside the Runtime timer but before output publication still perturbs Product E2E. Prefer deferred export after measured request completion; otherwise account for diagnostic publication overhead and admit no formal performance transfer. Do not hide the overhead behind the Runtime stop timestamp.

All8 packet admission: hashes, instrumentation/contract versions, rank/device, cohort request multiset, cycle ledger, acceptance decisions/counts, output ledger, warmup/measured boundary, Graph mode and observer env must join.
