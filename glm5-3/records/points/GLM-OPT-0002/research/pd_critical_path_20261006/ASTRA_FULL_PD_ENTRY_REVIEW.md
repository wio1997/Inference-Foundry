## Facts and decisive counterexamples

1. **The boundary improves semantic placement.** AsyncLLM.add_request processes rendered/raw inputs, assigns internal identity, preserves cloned native params, then fans out n>1 (283–418). Native Responses excerpts resolve prior messages before rendering and invoke generate for each built-in-tool turn. Moving P work after native resolution avoids reconstructing Responses history and chat templates in the gateway. Gateway v11 still owns routing/response-owner affinity; it must route generation to D API owners, never accidentally to the P API because of historical complete-request placement configuration. Keeping D API state is necessary but does not by itself prove background cancellation.

2. **Fanout cancellation is a real new ownership interval.** `_add_request` runs once per child, sequentially. An await for P on child 2 can occur after child 1 was admitted. generate's `q` is assigned only after the entire add_request returns; its cancellation/error cleanup is guarded by `q is not None` (570–645). The hook must own cleanup of already admitted siblings, pending P requests, exported-but-unclaimed KV and OutputProcessor registrations before that return. A bare try/finally closing HTTP is insufficient. Registering the collector earlier inside _add_request does not make generate's local q assigned.

3. **Streaming input disproves universal framework one-shot canonicality, but public reachability must be established.** `_add_streaming_input_request` sends each chunk through `_add_request` (501), and also sends its final sentinel through it (517). The sentinel was constructed with token IDs [0] (463–470); it is not a new generation prompt. Scheduler `_update_request_as_session` (1371–1405) constructs the actual context from retained computed output plus the incoming chunk, discarding the prior final sampled token. Thus the chunk's token IDs at _add_request are not the full next prompt. Scheduler.add_request (2213–2234) handles duplicate IDs as StreamingUpdate rather than new connector requests; the shown session-update method does not replace kv_transfer_params or call connector.on_new_request. Blind P-prefilling each chunk/sentinel is incorrect. StreamingUpdate definition and complete session consumers are still required. Streaming input is distinct from ordinary SSE output, which alone does not trigger this issue.

4. **There is a useful but limited release primitive.** AsyncLLM.notify_kv_transfer_request_rejected (744–768) sends abort_immediately with KV metadata and optional DP rank. Core.add_request (478–483) admits then aborts. Mooncake.request_finished (2012–2027) queues an empty receive for unconsumed remote-prefill metadata, allowing native worker completion to release P blocks. This supports cleanup when valid export metadata and destination ownership are known. It does not prove cleanup if P exported but its response/metadata was lost, D is unavailable, or a duplicate cleanup races a real receive. Those cases need an explicit ownership/reconciliation policy and native lifecycle evidence. Do not reuse the public/live D request ID for a synthetic rejection without proving collision behavior.

5. **Token IDs are necessary, not sufficient.** EngineCoreRequest also carries prompt_embeds, prompt_is_token_ids, mm_features, LoRA, cache_salt, DP rank and resumable state (input_processor excerpt 379–394). The current target's actual supported prompt forms must be established from installed model/API configuration; do not invent multimodal/pooling support, and do not silently remove a supported form. A P completions endpoint must be proven to preserve already canonical IDs without adding BOS, truncating, normalizing, or applying different defaults. Same model name is insufficient: actual GLM-5.3 artifact/config, adapters and position/cache semantics must match. Frozen model excerpts cover weight mapping/indexer details, not the full supported-input contract.

6. **KV metadata alone does not deliver prefill-dependent API results.** Prompt logprobs require tracing P computation and D OutputProcessor/serving consumption. Keeping D sampling authority does not recreate logprobs for prompt positions skipped through external KV. No bridge is shown. Pooling also reaches _add_request, but is not a generation request; core validates supported pooling tasks. Do not send PoolingParams into a max1 generation helper. Whether pooling is actually exposed/supported here is unknown.

7. **Validation is not completed solely by reaching this hook.** Passing EngineCoreRequest bypasses the process_inputs branch. Core.preprocess_add_request subsequently constructs Request and initializes grammar (969–994); additional failures can occur after P export. Full installed prompt/output-length validation, completions token-input processing and Request conversion were not supplied. P max1 acceptance does not establish D's original prompt+output budget validity. Run245 KV-capacity failure is not proof of request-length equivalence or full-context runtime capacity after the 2GiB adjustment.

## Gap ranking and Top 3 code questions

Largest verified functional gap: valid generation requests can bypass PD in v2/v3; v3 geometry fallback repeats that defect. Within the proposed replacement, rank the blockers:

1. Ownership across admission/fanout/cancel/failure. **Question:** who owns each pending/exported/admitted child, and which idempotent terminal action releases every native resource even when metadata delivery fails?
2. Canonical-context and prefill-result completeness. **Question:** what exact model input/state and prefill outputs must cross P→D for ordinary calls, prompt logprobs and live streaming-input continuation?
3. Validation and consumer coverage. **Question:** which installed legal endpoints/continuations reach this path, which checks remain downstream, and how are D owner, child identity, cache salt and independent P/D DP routing preserved?

These are ordered review questions, not three active performance hypotheses. Largest removable performance Gap remains unknown.

## Smallest reliable implementation scope

Use the resolved native request boundary for one-shot generation, retaining the existing native P connector bootstrap. Give each child a private P identity/export and explicit admission ownership; initially avoid shared P exports across n children because native release reference-count semantics have not been shown. Preserve original D params and cache identity, copying mutable token/parameter structures rather than aliasing them. Independent P/D DP bindings must not assume equal numeric rank or identical engine ownership.

This is smaller and more reliable than expanding the gateway whitelist or reimplementing Responses state on P, but **no smaller one-hook solution is proven to meet the entire contract**. Session input requires an intentional owner-aware continuation design at the actual assembled-context boundary. Prefill-dependent outputs require their own native bridge. Do not convert these unsupported implementation cases into product exclusions or D-local fallback. A one-shot first slice is a development milestone only.

Before coding, read the installed ParentRequest and OutputProcessor add/abort/collector consumers, StreamingUpdate and Request conversion/hash functions, InputProcessor length/params validation, completions token-input serving/renderer, Responses background task/cancel ownership, and connector worker empty-receive/send-ack handling. Existing snippets do not certify them.

## Minimal functional distinguishing experiment

First, CPU-only fault-injected harness against the proposed boundary with fake P/export and EngineCore sinks: n=2, cancellation after child1 admission during child2 export; export succeeds but response delivery fails; known metadata followed by D rejection; duplicate cleanup; cache_salt and distinct request/rank identities; two streaming chunks followed by sentinel. Assert explicit ownership, exact original D params, no leaked registrations/exports, no sentinel P work, and assembled-context correctness. A blanket hook already fails the streaming counterexample by source inspection; no NPU run is needed to rediscover it.

After the missing consumers and ownership design close, use one bounded real functional fixture on the ready target, not a throughput benchmark: canonical short Chat/tools/grammar, Responses previous/background cancel, n>1, prompt-logprobs if legal, streaming input if exposed, and a context-boundary rejection. These distinct branches cannot be certified by one happy-path request. Verify exact token/model/cache identity, real P export→D transfer for each generation turn, valid public output/usage/state, and terminal P/D resource release. Include one injected cancel before metadata and one after export. Do not equate cancellation of an HTTP client with native KV release. No performance credit.

## Stop List and likely misreadings

Stop gateway helper whitelist expansion, all D-local fallback, counting strict rejection alone as complete functionality, reusing one export across n children without release semantics, treating chunk/sentinel tokens as complete prompt, cloning public response ownership onto P, or removing native max1 bootstrap based on appearance. Stop performance runs aimed at proving this functional boundary.

Most likely misreading: “after tokenization” means every `_add_request` contains a complete canonical prompt. Streaming sessions refute it. Other traps: all legal requests have only token IDs; D authority automatically preserves prompt logprobs; generate cancellation covers work before add_request returns; rejection-notify covers lost metadata; P max1 validity implies original D budget validity; loaded weights or larger KV establish complete PD correctness. None is proven.
