# C64：不重启服务的较长负载与瓶颈采证

2026-10-08，按用户“先低成本、后集中做高成本”的要求，保持 4P2D 服务及参数不变，完成 1024 请求 C64 测试。没有重启容器、升级驱动或改变 MTP/图模式；本轮硬件和 CPU 采样均已停止，代理最后检查健康且在途请求为 0。

结论：C64 仍不满足 SLA；设备证据支持优先检查 D 执行效率，同时追查 KV 交付等待。现有证据不支持把请求槽位不够作为主要瓶颈，不能把增加 seq 或继续扫 70/72/80 当作已证实的解决办法。算子、通信或图回退的具体贡献仍需进一步区分。

## 性能与 SLA

每请求服务侧输入 80,012、输出 600 token；1024/1024 成功、无缺失计时。输入吞吐含缓存复用，P/D 不重复计费输入，输出不累计 P 的内部首 token 或被拒绝的 MTP 草稿。

| 请求数 | 1024 | 960 选中请求 | — |
| 输入 token/s | 246,131.63 | 260,627.33 | 越高越好，前提是 SLA 通过 |

稳态窗口长度条件 max(all E2E)/(window/3)=0.2955，通过；这不是 SLA 通过或统计置信区间。输入 UUID/行号隔离后缀，所有输入逐条重分词且无本轮/与六轮历史的完整重复。数据量和盐值与原 384 请求 C64 不同，因此不能把新旧差异解释成参数收益或监控开销的因果 A/B。

正式窗口 P/D 本地 prefix 命中均为 92.7861%；P 本地加外部复用为 92.9461%。D 外部命中 100% 是本地 miss 对应 KV 被交付，不是用户 prefix 命中 100%。每个 endpoint/engine 聚合值一致，无 counter reset；聚合计数不能证明逐请求命中率都未超过某阈值。

全程实际 HTTP 并发均值 62.095、峰值 64，92.62% 时间处于配置上限；首 token 到结束的并发均值 43.010、峰值 64。说明配置 C64 不是“64 个请求始终同时 decode”。

## 请求等待与执行证据

| 观测 | 结果 | 解释边界 |
|---|---|---|
| P 各节点正式请求数 | 257 / 255 / 254 / 258 | 入口分配均匀；EP 实际工作量不能仅按入口数判断 |
| P 平均 queue | 0.271–0.325 秒 | 有排队，但不是本轮全部 TTFT 的解释 |
| P 平均 prefill | 2.401–2.502 秒 | P 本身仍有明显处理时间，需要降 TTFT |
| D 平均 queue | 1.570 秒 | queue 定义包含等待，不等于算力请求槽位不足 |
| D 平均 prefill / decode | 0.207 / 14.115 秒 | decode 是请求阶段总时长，不能当纯 kernel 时间 |
| D MTP5 接受率 | 61.0894% | accepted/draft tokens；平均每 draft iteration 的 accepted+bonus 约 4.0545 token，仅本档实测 |
| P 稳态 sampled running | 各 engine 峰值 3；均值约 1.29–1.38 | 未观察到上限 8 触顶；2 秒采样可能漏掉短峰值 |
| D 稳态 sampled running | 每 engine 峰值 4–6，均值约 2.69–3.01 | 未观察到上限 32 触顶 |
| P 等待原因标签 | 有间歇性 capacity 队列 | running 未触及 8 不等于没有容量约束；可能涉及 token 预算等调度条件 |
| D 等待原因标签 | sampled capacity=0，等待均标 deferred | 标签不直接等于网络堵塞，需结合 scheduler 状态和 KV 事件 |

这些是各自阶段的聚合均值和采样代理值，不能相加当成同一请求的端到端延迟，也不能用 sampled running 代替真实连续在设备执行的 batch。

既有 PD 日志覆盖 1024 个请求、2048 组双 TP START/END，返回码全部为 0。逐请求两个 TP 调用耗时取最大值：P50 约 1.390 秒、P90 约 2.473 秒、最大约 5.696 秒；prepare 平均仅约 14.46 ms。这说明 KV 交付调用中的耗时值得优先拆解，但 call_ms 包含内部等待、不同 TP 可重叠，不是纯网络传输时间，更不能直接除字节数声称链路带宽。日志按时间筛选，边界精度约 1 秒。

CPU 进程采样只覆盖正式窗口后半段。该重叠区间 EngineCore 约 1 核/进程，TP0 worker 约 1.9 核/进程，采到的 leader 调度等待较低。整机 CPU 不满不排除单线程瓶颈；leader 等待低也不排除其他几百线程的内部等待。没有采调用栈，不能将 EngineCore 近 100% 单核直接判定为关键瓶颈。

## 省时间的后续顺序

1. 本轮先停止盲扫更多高并发点。C64 的稳态 TPOT 仍需下降约 22.6%、TTFT 约 33.6% 才到门槛；当前没有证据说明仅改并发 70/72/80 可以补齐。后续在延迟改善后，按通过/失败区间取中点搜索，而非穷举所有整数。
2. 降低“加大 max_num_seqs”优先级：本轮没有观察到 P 的 8 或 D 的 32 被用满，但 P 存在 capacity 队列，不能排除 token 预算等其他容量限制。P token 预算仍可保留 12288 的候选，但需 scheduled tokens/切块证据，不能把 seq 和预算一起改后直接归因。
3. 下一批需要重启的工作集中准备：D 优先做 MTP3 对 MTP5 的受控对照，并预先配置可关闭的短窗诊断/必要 profiler 能力，避免为每项观测单独重启。配置 profiler 不代表在正式容量测试中开启重型采集。P 调参按其 prefill 证据安排，不同时改 P/D 多项去猜原因。
4. KV 交付调用耗时是明确的后续取证点：利用本轮已有 request/TP 对应关系区分数据未就绪、传输、同步与完成等待，再决定 connector/通信参数。不要把 deferred 或长 collective 时间直接判成网络带宽不足。

当前运行中的 D 进程没有图诊断环境变量；核实 gate 后确认单靠创建文件不能在线开启。此前只读预检中“可直接 touch 激活”的推断已纠正，因此本轮未尝试无效开关、未重新量化 q1 NONE 比例。旧 q1 诊断仍是独立问题证据，不能直接抵扣本轮 TPOT。

本轮是采证和收窄优化范围，不是已经完成优化。未找到满足全部 SLA 的新配置；高成本变更尚未执行。结果与私有证据哈希见 [RESULTS.json](RESULTS.json)、[SERVING_METRICS.json](SERVING_METRICS.json)、[PROVENANCE.json](PROVENANCE.json)。
