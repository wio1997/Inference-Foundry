# C64/C72 的瓶颈诊断与 SLA 容量验证

状态：2026-10-08 核对现有采集能力后制定。C72 尚未实测；本文件不报告预测吞吐，不声称已经定位硬件瓶颈。本轮只读检查本地冻结数据和脚本，没有运行新压测。

## 当前证据能回答什么

- C64 与 C96 均未通过全部 SLA；C96 全程吞吐更高，但 TTFT/TPOT P50 更差。不能据此数学证明中间 C72 必然失败，也不能插值声称 C72 达标。批处理、图形状和调度会使性能不严格单调。
- C64 稳态 TTFT P50 5.7885 秒、TPOT P50 22.9 ms，需要分别降低约 30.9% 和 21.4% 才到 4 秒/18 ms 门槛；因此仅将并发改成 72 没有现有证据支持其补齐缺口。
- 现有 P/D queue、prefill、decode 的 histogram 增量说明压力位置，不是逐请求关键路径；不能把不同请求的 stage P50 相加解释端到端 P50。
- 原 capture_metrics.py 对五个服务端点每 2 秒抓取指标，其中 D head 端点包含多个 engine 标签。每轮必须验证 D0/D1 的 16 个 engine 标签覆盖，不能把一个 HTTP 端点误认为只监控了一台，也不能反过来假定 head 永远完整覆盖。
- 原硬件 sampler 主要读 npu-smi info 的 HBM 占用，生命周期为启动后的固定 360×5 秒；未覆盖正式性能窗口。不能据此补造推理期计算利用率、带宽或功耗。
- 原 metrics snapshot 仅在整个抓取前记一个时间戳，没有各端点抓取起止时间；尚不能精确将跨主机细粒度事件与客户时间线对齐。2 秒采样也无法解释 100–150 ms 级步间空洞。

## 下一轮的具体设计

1. 固定原 4P2D 配置、80,012 服务侧输入/600 输出、缓存热度、路由、代码与 MTP。先 C64→C72，再逆序 C72→C64 复测，减少测试顺序/温度/缓存残留混杂；后缀按全局 run UUID 加行号生成并与历史输入检查重叠。各轮分别预热与核验，不循环重放少量后缀刷高命中。
2. 使用持续补充请求、指定并发上限的负载，确认实际达到目标并发。供给量保证平台段，而不是固定 384 请求就收工。初始至少以数分钟平台段为目标，并根据实测最长 E2E 延长，检查原生窗口条件；最终候选增加重复测量。每轮同时保留全程和稳态的全部 SLA 分位，不挑选有利窗口。
3. 六台同时运行低开销硬件/主机采样与逐 engine 服务指标采集，覆盖预热、正式开始、稳态、停止补充、排空及 counter settle。每次 fetch 记录开始/结束、成功/超时、样本覆盖率，记录客户端和服务端阶段边界。
4. 先做无重型 profiler 的容量测试；另做匹配配置和负载的短 profiling，覆盖普通 decode 与新请求进入时刻，同时采迟到 rank 及等待 rank。不能只抓“看起来最慢”的一个 rank，也不能把 profiler 干扰后的 TPS 直接作为容量结论。
5. 如果 C72 吞吐上升但全部 SLA 未通过，它只提供瓶颈证据；不是达标配置。如果出现更好 batch 效率且延迟下降，需要复测确认。C80 仅在 C72 有收益或需要进一步定位拐点时补测；优化后再找最大达标并发。

## 必须对齐的四类证据

| 层级 | 采集项 | 要回答的问题 |
|---|---|---|
| 客户端 | 请求 ID、send/first token/end、输入/输出 usage、逐流式事件时间、失败、实际 HTTP 与 decode 并发 | SLA 是否真实达标；输入/输出 token/s；慢请求和慢 token 在何时发生。流式 chunk 可能含多个 token，不能把 chunk 间隔冒充逐 token 时间 |
| P/D 调度 | 每 engine running/waiting 及 waiting reason、实际 scheduled token/request 数、prefill/chunk 数、queue/preemption、KV blocks/cache counters、MTP accepted/draft/verify 计数 | 请求槽位、token 预算或 KV 容量是否触顶；是否负载不均；实际 batch 与有效输出怎样变化。部分字段需新增有界采样日志，不假定全是现成 Prometheus 指标 |
| 请求跨端时间线 | 同一 request ID 的 P 接收/排队/执行完成、KV 发布/传输/可用、D 接收/等待/执行/首输出、代理转发 | 谁在等谁；D waiting 是没有 KV 还是没有调度/设备资源。记录阶段重叠，不将所有 elapsed 简单相加 |
| 六台主机和 NPU | 每芯片 AI Core/Cube、HBM 使用与带宽、功耗/频率可用项；CPU 单线程/线程亲和/runqueue；通信字节、重试和错误 | 设备忙在计算、内存还是通信；是否主机供给不足；是否少数 rank 拖住整组。记录设备到 host/rank/DP engine 映射与缺失项 |

冻结环境的 npu-smi watch 帮助确认支持 power、AI Core、AI CPU、control CPU、memory、memory bandwidth、NPU、AI Cube 等指标。下一轮先验证各宿主驱动对实际字段的支持，再选择约 1 秒间隔的轻量采样；HBM 占用不是 HBM 带宽，内存预留比例不是计算利用率。HCCS/RDMA 计数按所用物理链路、计数器语义和 reset 状态解析，不将标称带宽或 collective elapsed 当作实测传输带宽。

主机记录 UTC 和 monotonic 时间；跨主机先测时钟偏差及不确定度，精度不足时只能做粗粒度对齐，不能宣称毫秒级因果。使用现成时钟同步状态核验，不为取样擅改系统时间。

## 如何形成可证伪的瓶颈结论

| 假设 | 至少要看到的支持证据 | 不能仅凭什么判断 | 随后的针对性 A/B |
|---|---|---|---|
| P 计算或带宽受限 | P 队列持续增长，执行时间增长，关键 kernel/带宽占据临界路径，设备持续有工作 | P queue 大或 NPU 单个利用率高 | 根据实际 scheduled-token 分布调预算；必要时单侧 TP/DP 实验 |
| P 调度预算/槽位受限 | 多次触达 token/seq 上限，存在可执行等待请求，且不是 KV 不足/同步依赖 | 仅看到 max_num_seqs 配置值小 | 预算或 seq 单独变更，确认等待下降且尾延迟不恶化 |
| D 图回退/主机调度空洞 | 相同全局 step 的 q、graph mode、host launch gap、kernel 空洞、rank 进入差与客户端慢区间对齐 | 旧 2P2D 的 NONE 关联直接套到新 4P2D | 独立验证 q1 修复；MTP 档对照时同步观察 NONE 频率和每步成本 |
| MoE/TP 通信受限 | collective 的进入与完成、传输字节/链路计数及 kernel 时间支持通信在关键路径 | 早到 rank 的 collective 很长；它可能只在等迟到 rank | 兼容的通信路径/算法或拓扑对照，查看传输而非仅等待时间是否下降 |
| KV 交付受限 | 同一请求 P 已完成而 D 的 KV 尚未 ready，期间确有传输/存储等待，随后阻塞解除 | D queue 大、D external hit 100% | 对应 connector、传输分片/并发/缓存路径实验，保留 token accounting 正确性 |
| 主机 CPU 或负载不均 | runnable/CPU 调度延迟、某 engine/worker 的队列偏斜与 NPU 断供同段出现 | 六台平均利用率低、两台 D 请求数均匀 | 定向线程亲和/调度均衡，验证最慢 rank 和尾延迟改善 |
| 客户端/代理供给不足 | 未达到目标并发，客户端/代理 CPU 或连接路径延迟限制发起/读取 | 服务端吞吐没增长 | 修正压测供给或代理约束，服务配置先不改 |

结论按“观察→定位→机制假设→单变量/必要联动 A/B→结果”留档。多个瓶颈可以随并发改变；若只能确认等待位置而不能确认原因，必须标未定位，不强行选一个参数。NPU 低利用率同样可能来自通信或同步，不能自动判作有可售容量。

## 最终交付应有的两张表

1. 每轮：输入/输出 token/s、全程/稳态全部 SLA、窗口有效性、实际并发、缓存命中与重复检查、错误、配置版本。
2. 每台/每 engine：请求和 token 工作量、running/waiting、资源指标分布与采样覆盖、关键等待位置、证据路径；另外列跨 rank 的共同关键路径，避免用入站请求数代替 EP 实际工作量。

本计划依据本目录已冻结的测试结果及本地采样脚本审计；原始日志、源码和逐步 telemetry 保留私有。实现采集后先验证覆盖和开销，再将正式数据用于性能归因。
