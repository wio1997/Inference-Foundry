# 执行计划研究路线

## 1. 找一个能区分原因的问题

选一段有明确输入/输出/状态边界的计算，按“关键路径可回收时间 × 证据可信度”排序，而非 profiler 累计时长或修改方便程度。框架差异先对齐 workload、精度、缓存和推测解码；发布包尚无可直接归因的 SGLang-vLLM 30% 对照。

当前入口：[GLM-PLAN-0001](studies/GLM-PLAN-0001.md)。证据不足可换片段，不硬填 bottleneck。

## 2. 分离语义问题与执行计划

problem 描述必要工作、数据/状态依赖、资源与条件成本；plan 描述额外顺序和发起优先级。框架 trace 是一种 observed plan，不能把全部串行边变成模型必要依赖。

当前 `execution_lab` 只探索固定操作集合上的顺序/并发。切分、布局、placement 改变需重建并审查 problem 与算子输入输出映射；工具不自动证明不同图的数学等价，也不执行 GLM 内存生命周期管理。

## 3. 校准替身

保留目标机制需要的层宽、dtype、量化布局、KV 访问、专家偏斜、各 rank 消息大小和物理拓扑。裁无关层/迭代，不能默认裁卡数或把 MoE 换为 Dense。检查反复同层的 cache 复用、缩层后的显存/KV 余量、图边界和流水填充变化。

用已有可辨别干预检查替身与原路径的方向和机制是否一致，容限按测量噪声预先约定。失败则替身不能用于该机制排名。MTP 接受率/在线路由反馈不能用冻结轨迹代表完整行为。

## 4. 比较机制不同的计划

候选写明改变哪条额外顺序/资源组织、何处回收时间、什么观测否定它。过滤不合法计划，用带来源成本排序，再实测。未覆盖的竞争需并发成本测量修正；模型中更快不是性能收益。

独立执行器是实验手段。增加 runtime 模块前写清它允许哪种原来无法验证的计划；若只是复制旧执行顺序，无需扩建。CPU replay 与设备 adapter 保持不同结果类型。

## 5. 回到服务

片段机制成立后再决定集成 SGLang、vLLM 或独立 hot path。比较原模型固定状态和动态负载；局部收益不传递时检查瓶颈迁移与额外成本，保留负结果。最终要求见 [MISSION](MISSION.md)，不为局部实验搭完整 HTTP/PD 系统。

## 结束与转向

候选未改变实际路径、结果被噪声淹没或新 Run 不影响下一决定时，停止惯性实验并补决定性证据。可回收时间不值得成本则换机制。无设备证据时只称工具/模型估计已验证，不宣称性能研究完成。
