# GLM多机多卡、可变PD部署的调度极限判据与逼近方案

日期：2026-10-01（Asia/Shanghai）。当前是方案设计阶段。本文件定义如何判断方向和剩余空间，没有访问运行机器、采集profile、实现调度器或得到数值极限。V2、资源驻留、自研控制层与PD配比均是可检验候选；先用当前证据选择有价值的问题，再决定实际重构路径。

用户目标：完整GLM推理服务功能、可变输入输出与动态请求、多机多卡及可变PD配置，在当前现有正确算子实现下探索最大性能。当前两台同规格、卡配置相同的910C服务器；结合前文按每台8卡16芯作计划解释，实际实例/rank映射尚未恢复。1P3D只是未来部署例子，实例数、每实例并行与物理放置独立描述，不把1P1D、1P3D或当前两台设为永久边界。

用户进一步明确：本阶段判断与交付以当前两台服务器及实际具备的实验条件为边界。需要新增服务器或其他未具备资源的方案，标为当前不可实施并给出当前结论，不等待硬件、不把未来扩容实验列为本阶段未完成项。框架保留未来部署扩展能力；当前最优解只在现有资源可行域中寻找，其中包括授权范围内能通过代码重构实现的新组织，不限于Stock现成配置。

## 1. 可判断的极限：条件明确、结论分层

不存在一个脱离硬件预算、负载、功能语义和延迟要求的通用最高TPS。可比较问题由以下信息定义，单次比较需要清楚，后续研究可以改变并扩展：

| 信息 | 必须区分的内容 |
|---|---|
| 功能与模型 | 当前GLM/量化/算子身份，完整服务语义；功能清单从框架恢复，不是排除未列能力的白名单 |
| 资源 | 服务器/芯/内存/链路与共享关系、rank映射、实际软件与patch |
| 部署变量 | P/D池实例数量、各实例TP/EP/PP/CP等并行与容量、placement、connector与路由 |
| 执行变量 | batch/chunk、动态准入、MTP、Graph、buffer/queue、状态提交、传输、输出及控制结构 |
| 负载 | 输入/输出与前缀条件、请求功能参数、到达过程、终止/取消、cache初态和暖态 |
| 性能对象 | 有限请求包的完整wall，或动态负载下满足延迟/失败条件的有效服务容量；冷启动与稳态分开 |

优先沿用实际服务的SLO。没有既有数值时先报告吞吐、TTFT/TPOT及尾延迟、失败/拒绝和资源效率的折中曲线，不偷偷设一个有利的单一评分。服务容量需要考察队列是否持续增长、请求是否真正交付，不能只看成功子集的token/s；实际允许的拒绝/超时规则同样进入合同。

结论有三层：局部步骤/机制、某个部署下的完整服务、同资源下跨部署与执行组织的搜索。前一层的界不自动成为后一层的界。有限负载的makespan界也不自动证明在线SLO容量极限。

## 2. 极限的数值标准

对一个声明清楚的合法调度类和同一完整工作包，设：

- U：已经真实运行、满足当前模型/服务状态与输出合同的可执行方案耗时；正式测量报告重复结果和波动。
- L：在相同条件下，由必要工作、值/状态依赖、释放时间和资源限制推导出的乐观最短耗时下界。
- T*：该合法类中最好的可能耗时。若L确实有效，则L ≤ T* ≤ U。

对相同有效输出数量Q，最优吞吐落在Q/U到Q/L之间。当前方案潜在吞吐提升不超过U/L−1；当前耗时可缩短的比例不超过1−L/U。区间与成本/测量/时钟不确定性一起报告。

持续服务的对应判据是：已实测达标且队列稳定的有效吞吐R，与覆盖声明合法类的乐观容量上界B，给出R≤R*≤B，剩余可能提升不超过B/R−1。B需要由同一负载下必要服务需求和共享资源约束建立，并覆盖允许的batch/shape/复用/部署选择；测得某阶段饱和速率本身不是全系统B。无法得到有效B时，报告已实现性能前沿及容量极限unknown，不用有限包的L强行替代。

例如，假设同一完整工作包的有效U=50s、有效L=48s，那么剩余吞吐提升最多约4.17%。这是说明判据的算例，不是当前GLM的测量。可以据此报告“在声明范围内，剩余提升上限约4.17%”，无需AI凭经验说到顶。

“接近极限”的工程阈值可以按用途调整，报告剩余百分比比固定一个停止阈值更有价值；阈值必须考虑证据不确定性。一次KEEP、几次尝试失败、util很高或trace空隙变少都不是极限证书。即使在某个区间已很接近，也可以继续搜索其他结构或部署。

测得的最小算子耗时并不天然是严格数学下界。需要标明条件成本、适用shape/资源区间、校准与置信口径；证据只支持经验模型时，结论写成条件界或经验饱和，不伪装成严格证明。未知成本可以在乐观界中置零、未知非必需边可以暂略，这会使L更弱，不能因此宣称可实现。

## 3. 下界必须覆盖允许探索的代码与配置

E_must来自模型值、KV/状态版本、writer/consumer、buffer生命周期、通信匹配与有效输出的必要关系。当前Python、stream或Graph顺序只是当前组织，不能全部冻结成E_must。对尚未确认能删除的边保留不确定性；可执行候选始终需要满足真实依赖。

可用的乐观界包括必要依赖最长链、各资源的必要工作量界、请求释放到输出链及阶段容量界，取相容下界的最大值。界可以逐步建立；无需先完成全硬件容量证明，也不需要完美DAG才能做能区分假设的原型。

需要防止把合法类缩窄：

- 固定Stock的节点数、shape、batch、MTP深度、verify次数和buffer数量，只能产生该受限结构的条件界。
- 当前用户允许改变上述组织，甚至重写控制层；较宽界必须覆盖这些选择，或明确它们尚未覆盖。
- batch/K/并行/布局变化后，shape条件成本、工作量和状态路径可能变化；重新建模，不能继承旧L或把旧gap直接乘cycle数。
- 不同采集的接受/路由/输出轨迹未证明一致时，不拼成同一工作包。记录未来轨迹可作事后诊断，在线候选不能提前读取未来接受、路由或token。

多rank不能只用rank0。匹配同一次collective的组/序号，辨认输入就绪、提交、实际开始、到达偏差和完成；最长rank及前驱可能随step改变。HCCL持续时间可能包含等同伴，不能全部冻结为通信service，也不能全部视为可删除等待。

资源重叠要联合校准。两个任务孤立耗时a、b，不代表并行就只需max(a,b)；可能竞争内存、执行单元或链路。现有算子无需改写，但调用shape、发起时机及资源竞争都进入调度模型。

## 4. 从单部署扩展到可变PD

本阶段合法配置θ受现有硬件、资源容量、当前算子和授权改造范围约束。超出可行域的配置不参加本阶段极限证明，也不成为阻塞项；当前可行但尚未测试的方向才属于本阶段搜索未知。未来资源到位后另开研究域。

用θ表达合法部署和执行组织，用Lθ、Uθ描述各自的范围。跨配置最优不是“已测配置里最大的TPS”就算到顶；它还涉及未测试的θ。

只有当同一工作包、同资源和功能合同下，Lθ对全部声明的合法θ有效时，才有minθ Lθ ≤ 全局最优耗时 ≤ minθ Uθ。已测子集的min Lθ不能作为未测配置的全局下界。未测方向缺乏有效乐观界时，跨配置极限仍是unknown。

不要求暴力扫描所有组合。用成本与容量模型筛选可能影响最佳结果的区域，对高价值未知选择区分性实验；只有有效乐观界能排除一个区域，不应因粗糙预测或一次失败永久封死探索。可用分区、区间敏感性、原型或其他搜索方法，Agent自主选择。

PD分析至少连接请求准入→P工作→状态就绪/交接→目标D绑定/执行→有效提交/客户端交付。P/D可以有不同配置；P的首token若已交付，还要测交接停顿与后续token，不能让TTFT掩盖D启动等待。

P、传输和D的容量要换成相同负载口径，例如同一请求分布下的有效请求/s，再研究系统瓶颈。不能直接比较prefill输入token/s与decode输出token/s。共享资源时也不能把三个孤立容量当成可同时达到。

多D路由应考虑KV/prefix位置、可用cache、预期工作、排队和传输代价；何时选择D、是否重路由/迁移/复制都由真实成本与状态契约选择。某端局部提速若只是让另一端队列变长，不算系统收益。增加总服务器的部署收益与同拓扑代码收益分别报告。

例如D空闲时，先辨认到达负载、P供给、传输、D提交/容量和各rank等待。若证据指向P供给不足，就检查当前资源内可行的合批、准入、路由、并行/角色分配或混部方案，以完整服务表现裁决。若当前配置仍供需失衡，可以结论为“当前两台服务器与该负载下，这套PD分配不合适”，给出当前最佳可运行方案及依据。需要额外P/服务器的改进只记当前不可验证/不可实施，不因此拖延当前结论；配置失衡不自动成为所有PD或所有代码的理论极限。

## 5. vLLM prof提供什么证据

官方vLLM v0.27.0支持配置profiler并通过/start_profile、/stop_profile或benchmark的profile开关采集worker trace；官方同时说明profiling会扰动性能，详细stack/shape/memory等选项增加开销。[vLLM v0.27.0 profiling](https://docs.vllm.ai/en/v0.27.0/contributing/profiling/)

Ascend需要映射到真实torch_npu/CANN采集，而非照搬CUDA/Nsight结论。官方服务级prof可观测Request、KVCache、ModelExecute、BatchSchedule、Communication，解析request/cache/batch数据及设备任务；其symbols配置与安装版本、实际runner绑定，V1 hook不自动覆盖重写后的V2/GLM路径。[Ascend service profiling](https://docs.vllm.ai/projects/ascend/en/latest/developer_guide/performance_and_debug/service_profiling_guide.html)

profile_run()启动容量/dummy探测、chunk调度成本预测和真实服务/设备trace不是同一件事。尤其启动dummy可能人为平衡MoE，不能代替真实路由负载测量。实际0.27的image/commit/patch、profiler wrapper与输出完整性仍要恢复，不能把main或文档功能认作本机已生效。

多实例PD需要覆盖所有相关P/D引擎与客户端/proxy链；一个入口的profile调用是否广播由实际proxy/engine实现决定。每份证据需要host/engine/role/rank/device、代码与部署身份、request/step/transfer/collective关联信息。跨机时钟必须有误差估计；没有可靠对齐时，用关联ID和因果约束，不能直接拼微秒级绝对时间。

CPU函数range可能只包住异步enqueue。Graph replay的Host耗时不是图内设备makespan；未采到native task也不能推断设备一定空闲。缺少事件、rank或重写路径hook标为unknown，不记成零开销。

## 6. 用Profile逼近极限的工作方式

以下是可重排、合并或并行的方法，核心是每一步产生能改变判断的证据：

1. 恢复Current的完整合同与可运行证据，读已有log/profile；先测低扰动的端到端表现、请求/状态计数和队列，不从重型全程trace开始。
2. 选择当前最大可信gap或影响路线的未知。沿实际消费者追到Host准备、enqueue、Graph、TP/EP、MTP、PD与输出的必要前驱，区分等待原因。
3. 用短窗口profile、少量成本/干扰测量或结构原型，补足该问题缺失的证据。多rank问题用相应rank证据，PD问题用真实交接；不用单rank平均掩盖最慢路径。
4. 为候选说明改掉哪些额外顺序/重复工作、增加哪些成本、预期影响哪个完整链路；有用的原型可以先做，未经验证的收益仍叫假设。
5. 在可驻留资源下比较预加载执行策略，或仅重建受影响资源。正式性能关闭重型profile，保持相容请求/cache条件与有效工作量；样本/复核深度按噪声和误判成本选。
6. 用实际E2E更新U，更新受改动影响的L和合法类覆盖。KEEP之后继续找剩余gap；REJECT保留失败因果，不以低信息重跑替代研究。

原型或微测不自动证明产品收益。正式性能用未被重型观察器污染的结果；必要时进行匹配的OFF/ON/OFF或其他适用对照估计观察器影响，不强制每Run都采完整profile。

昂贵启动是实验设计因素。controller可以在一次bootstrap内复用相容权重、组、arena和Graph，预加载候选，在合法step/drain及各rank一致的epoch切换；这是待核验/实现的能力。拓扑、地址、cache ABI或captured代码变化按依赖重建，不承诺任意热重载。profiling停止后的导出开销另记，不能混入稳态吞吐，也不能因暂时沉默盲目重跑。

简单事实采集、短profile控制、解析与汇总可交zcode --prompt，研究Agent负责依赖/资源判断与独立验收。多机共享现场由一个controller协调，离线分析可以并行。当前仍是规划，不执行服务操作。

## 7. 什么情况下可以说接近极限

| 状态 | 合法结论 | 下一步 |
|---|---|---|
| 局部L/U闭合，产品链不完整 | 这个机制/步骤的条件空间很小 | 查其他关键链和端到端暴露成本 |
| 某部署完整界闭合，其他配置未知 | 当前部署、负载及合法类下剩余≤x% | 保留该成果，研究可能更好的部署/组织 |
| 跨声明配置类的有效界闭合 | 在声明资源、功能、负载与合法类内接近极限 | 按用途扩展负载、资源或算法/算子研究；当前阶段不自动转kernel |
| 无完整有效L，候选多次不改善 | 暂未发现更好方案，极限未知 | 定位影响结论最大的未知，或记录低信息/预算原因 |

不能声称所有未来输入、所有PD拓扑都存在同一个最优参数。完整功能是产品目标；测试负载用于证据覆盖，不成为产品输入限制。最终报告哪些条件下接近、剩余可能提升多少、哪些配置/功能/负载尚未覆盖，以及哪些观测可能改变结论。

文档维护以恢复和裁决为目的：FRAMEWORK_SCHEDULING_BOUND记合法类、必要边/成本/资源、L/U与覆盖；PERFORMANCE_MAP记实测关键链/gap/unknown；RESULTS记真实E2E、观察器身份与裁决；HANDOFF记Current和下一个有区分力的问题。可以合并初始内容，不要求先填齐所有报告才研究。

## 8. 延续Foundry的有效规则

原仓库FRAMEWORK_SCHEDULING_BOUND已经区分E_must/E_safe、可执行U与乐观L，并明确完整Product数值界未识别；它还记录HCCL同伴等待、跨rank提交偏差、计算/通信并发更慢，以及局部收益未转化为E2E的反例。复用这套证据方法，按GLM与可变PD重建具体模型，不照搬旧固定cohort、DSpark轨迹或数值。[原Framework文档](https://github.com/wio1997/Inference-Foundry/blob/064f4474b1eafd5985469bad1f0bab3233a8f417/FRAMEWORK_SCHEDULING_BOUND.md)

V2抽取、自研动态执行核心、资源驻留和不同PD配置是否值得实施，由上述gap与区分性证据选择。本方案既不以“改了很多代码”证明路线正确，也不以缺少严格数值界阻止有价值的新结构探索。
