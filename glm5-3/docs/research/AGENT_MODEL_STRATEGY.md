# GLM PD调度极限研究的Agent模型与协作方案

日期：2026年10月1日。本文是后续执行配置建议，没有切换当前会话模型、创建新任务、调用模型评测或访问运行机器。用户当前选择ultra，本轮完整分析保留这一偏好。

用户后续明确关注模型成本、代码大改与漫长启动/测试，目标为支持可变输入输出及PD部署的GLM专用框架。推荐更新为成本感知组织：后续持续主线先选6.1 Sol high，重要结构或复杂依赖问题按需使用Sol ultra，Astra只用于有望减少昂贵返工或长机器实验的独立判断。当前会话ultra不因该建议而自动更改。

用户同时明确完整服务功能都要，不能靠手工功能白名单限定交付。模型角色、方案和采样计划都围绕功能完整的GLM执行框架；兼容路径也需要观察与优化，不能只比较过滤后的固定shape热路径。

## 选择依据与已知边界

[OpenAI官方6.1 Sol说明](https://developers.openai.com/api/docs/models/gpt-6.1-sol)将它定位于复杂编码与专业工作，兼顾能力和成本，并建议与Astra在实际任务上比较。[Astra说明](https://developers.openai.com/api/docs/models/gpt-6-astra)将其定位于最困难的推理、编码和研究工作。[官方模型选择指南](https://developers.openai.com/api/docs/guides/model-selection)建议用相同输入比较模型与推理设置。以上支持把Astra与6.1 Sol作为候选，不证明任何一个在本项目上一定最好。

当前宿主工具元数据列出`gpt-6.1-sol`和`gpt-6-astra`均支持high和ultra等推理设置。公开API页面列出的effort为low/medium/high/xhigh/max；宿主产品的ultra不能直接写成API参数，也不能未经核验等同于max。本方案不判断用户当前线程的具体model id或ultra内部实现。实际执行记录有效模型、推理设置和工具能力，身份无法核验时写unknown。

较高推理强度适合复杂依赖、互相矛盾证据、Runtime结构与研究转向；它不能替代源码和实验，也不保证比high得到更好的E2E结果。模型选型看有价值的决策、有效实现和误判率，不看文档长度或假设数量。

[官方API标准价格](https://developers.openai.com/api/docs/pricing)在短上下文档给出6.1 Sol输入/输出每百万token为$2/$10，Astra为$10/$50；相同token数时后者是5倍。缓存、长上下文和处理模式会改变口径；这不是用户Codex订阅或Zcode的直接账单，不能由此计算本项目实际费用。high/ultra也没有可直接套用的固定费用倍数，取决于产品计量与实际调用/推理用量。

## 每个角色的探索权

主负责人、实现Agent和独立复核者均可质疑历史结论、发现未列出的方向、提出结构性重构、要求更有区分力的测量，以及报告原任务前提不成立。不能规定Astra只思考、Sol只能实现，或让实现Agent必须接受已写方案。职责分工用于明确当前产物和机器操作所有权，不限制研究思路。

方案、合同和候选都是有版本的当前判断。新的证据可以改变路径、实验范围、模型角色和执行边界；稳定的是用户目标、当前不改写算子计算实现、真实请求执行、证据可追溯和性能比较有效。

对同一现场，模型分析和离线代码调查可以并行。会改变同一服务、源码或资源的动作由一个明确的现场负责人协调，保护现有PD实验；独立资源可以并行实验。协调不等于要求所有技术动作逐项获得另一模型批准。

## 何时使用独立复核

按判断风险和信息价值选择：例如GLM MTP与DSpark迁移是否成立、拟删除的依赖是否必要、Graph地址与状态是否安全、HCCL等待的归因、PD交接是否闭合、局部收益能否转化为E2E，以及是否已经没有有价值的调度空间。普通采集、索引整理和已明确的实现不必重复进行完整架构审查。

复核者先读必要事实、源码diff和raw evidence，再给独立判断。需要防止锚定时，先提供问题与证据，不先给主Agent的结论；不要求每次盲审。双方意见相同不是证明，意见不同也不立即阻断；定位分歧依赖并安排有信息价值的检查或实验。

## 如何判断选型是否合适

使用项目自然产生的真实checkpoint，不另外搭一套庞大模型评测框架。按需要让候选读同一份模型/软件/配置身份、当前结果、相关源码和最大unknown，比较其下一动作建议或实现。先固定评分事实，再看模型输出。

关注：是否正确识别GLM专属依赖；是否把未知写成已知；是否提出能排除错误归因的实验；是否能实现并验证；是否误报KEEP或全局上限；一次有效决策或可保留实现的耗时、调用和总成本。方案的质量最终由可验证事实与项目进展判断。评估不要求候选模型都实际运行同一份昂贵benchmark，也不以短期单个任务确定永久排名。

只在必要checkpoint保存模型/effort、输入证据、输出结论、复核或实验结果及更换角色的理由；可附在HANDOFF/RESULTS，不新增繁重维护流程。

## 总研究成本与漫长启动

目标是降低一次有效结论或可保留实现的总成本，包含模型调用、上下文重复、代码返工，以及模型加载、分布式初始化、cache分配、compile/capture、warmup、实验和恢复的机器时间。不能仅比较high/ultra的一次回答费用，也不能默认更贵模型总会节省机器实验。

升级推理或使用Astra时说明它需要解决的具体不确定性：例如某个GLM MTP/PD契约是否成立、V2抽取是否会重写多次、昂贵测试失败是否源于错误假设、是否误判已到极限。预计只会复述已知内容时不调用。优先复用同一真实事实包和raw evidence，不给每个角色重复灌入整仓库与全部历史。

离线代码调查、明确接口的实现和证据分析可并行；一个现场负责人协调共享PD/NPU。新增模型数量没有固定配额，委派要有具体收益。长实验运行期间可以做独立工作，但不能让多个executor同时改服务或污染性能样本。

机器验证不按每个编辑机械重启。结构/状态检查与短连续执行先排除便宜可发现的错误；重要接口成立后跑真实PD，再按问题选择正式代表负载和重复测量。顺序可调整，检查深度按风险决定，不能用离线检查替代模型状态和真实E2E。

驻留服务、预置执行变体、稳定arena和合法机制切换可能减少加载与warmup成本，但需在相同权重/通信组/cache与Graph依赖下设计，不能把任意Python热重载当安全切换。需要重启的变更集中进一次明确版本的启动，启动后收集相关证据；有价值的失败也归档，避免盲目反复重跑。TP/EP/PP或地址/捕获结构变化按实际依赖重建，Graph跨进程不直接复用live设备地址。

## Zcode的地位

Zcode默认接收简单、边界明确且可独立验收的任务：环境事实采集、指定源码定位、日志/样本提取、数据汇总、文档索引、现成benchmark/profile/controller和小范围实现。调用使用`zcode --prompt`。现成shell任务的prompt是一条完整命令；文档或代码任务给出输入、输出、允许修改范围和验收条件。实际命令、路径、输出和参数按现场核验。

Zcode不是模型角色表中默认的研究裁判；其实际模型/runner未知时不猜。主负责人负责实验设计及独立验收，核验内层执行、raw evidence和适用的清理恢复。重试不能覆盖已有Run或干扰活跃PD任务。简单任务委派成本明显超过任务本身或Zcode不可用时，可直接完成并简记原因。
