# D侧动态日志线索与候选源码来源链

## 结论和限制

在**日志时间戳按UTC解释、与客户端控制器时钟近似对齐**的假设下，对已归档的SG D侧脱敏服务日志按正式32K/64K冷、热前后快照包络筛选，许多 `Decode batch` 记录的同一行同时显示较高full使用率和非空prealloc队列。这个现象加强了**容量或准入路径值得优先验证**的理由，但还不是已证实的池容量阻塞、单请求等待或两框架TTFT差的根因。

该日志是后来128K失败预热时保存的历史D服务日志；发布版经过文本/结构化脱敏，SHA与原版不同，尚未逐字段证明时间、计数与原日志保真。日志时间戳没有时区、仅秒精度；两个主机间时钟未校准，窗口归属因此是**条件性的，未经确认**。快照包络也包含负载前后时间，不是精确请求起止点。日志只在某些decode batch输出，行数不是请求数、事件独立重复或墙钟覆盖比例；格式里的`TP0 EP0`也未单独证明PP0或唯一进程。

## 按假设UTC落入包络的日志行

每行所选日志仅按原显示字段判断：H为显示的`full token usage ≥ 0.90`，Q为`#prealloc-req > 0`，J为同一条日志同时满足H和Q。usage只有两位小数；这里比较的是**显示值**，不宣称真实硬件使用率的精确阈值。各行分别是两个冷/热窗口、非独立重复；不能跨行相减得性能效应。

|假设窗口|Decode batch 日志行 N|H 高显示值行|Q 队列非空行|J 同行满足|样本内队列中位数|显示usage中位数|
|---|---:|---:|---:|---:|---:|---:|
|32K cold|66|48|47|45|6|0.95|
|32K hot|66|49|47|47|6|0.95|
|64K cold|157|142|134|134|11|0.95|
|64K hot|156|140|133|133|11|0.95|

例如32K cold中，Q非空的47条日志里45条显示H（约95.7%）；Q为空的19条里有3条显示H（约15.8%）。64K cold分别为134/134和8/23。这是**选中日志行的描述性关联**，不是请求概率、排队时间比例、独立重复或因果效应；这些窗口能否对应正式运行仍未知。45/66同样只是按batch输出的日志行联合占比，不是45条正式请求。P/D样本不能配对，队列中可能包含旧事件、健康流量、重试或其他工作；高使用率和队列同一行出现不证明它是准入失败的直接原因。当前摘要内四个窗口均无“显示恰为0.90且Q非空”的行，但显示精度、pool映射、记录版本及实际可驱逐、锁定、预留/required仍未证明。候选源码对prealloc有多个门，队首阻塞、Mamba/metadata/请求槽、调度与时间戳/重入也须排查。

64K这组行Q中位为11、32K为6，与[057的简化容量算术](057-kv-resource-and-early-policy.md)在方向上值得联合调查；但**不能说64K真实拥塞时间更长或该差异导致其客户端TTFT**。显示usage的中位数是对已舍入值的统计，不代表更高仪器精度。60秒分箱中的两个p50独立计算，不能把两个p50当成同一事件；同线联合计数另行提供。缺失分箱表示未观察到足够样本，不是0负载。

### 关于取窗与日志来源

- 以UTC+0假设解释首个/末个已选decode日志行，与已归档启动/后续采集收据的数值顺序相容；以UTC+8假设时则不相容于通常的同进程时序，并且四个包络中没有匹配行。**这只是两个假设的敏感性检查，不是时区、进程身份或时钟误差校准。** 未知时区、偏移或日志轮转/拼接会改变全部窗口归属，不能只把少量边界行标为不确定。
- `full token`记录数除以已报告的345856容量，所有所选日志行均与两位显示usage在0.0051内一致；这只能说明算术一致，并不证明该字段与某请求的allocatable是同一资源池。
- 发布版日志SHA `c26fe6559c4b6c406414f42c80e200347ac581c581d64101bc6d1b8e1d308efa`；归档收据记录的原版SHA不同。复算仅读取匹配`TP0 EP0`和严格字段的日志行，输出汇总，不输出原行、请求/响应、标识或绝对时间。原日志和发布版字段逐条保真与截断/轮转仍未核对。

## G181 候选代码：来源链增强，现场导入仍未知

两端历史launch记录中的candidate原件摘要分别与本机保留原件字节一致；原candidate中的运行包SHA与本机原tar字节一致。tar内integrated清单SHA与两端launch记录一致，清单的source-tree SHA与本机6336项完整源清单一致。`req_time_stats.py`、D `decode.py`、common/Ascend/Mooncake receiver和metrics reporter六个目标成员各为唯一普通文件，tar成员SHA与完整源清单相等，也不在integrated覆盖项中。

这是**启动候选包/源清单的来源链**，不是G181正式轮目标文件的现场逐字节或真实import证明：runtime是独立宿主bind mount、容器rootfs只读不约束宿主内容，实际Python搜索路径还可能遮蔽候选。`early`分支、各资源门和时间戳细节仍只能按候选解释；不能用后来的G316文件SHA倒灌G181现场。
