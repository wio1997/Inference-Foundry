# Ascend 推理性能分析：算子融合、低活动与理论界

> 阶段性报告，基于一台 Ascend 910C 服务器上已冻结的 vLLM-Ascend 与 DeepSeek V4.1 Flash W8A8 推理配置。分析目的在于找到值得深入调查的结构和性能问题；目前没有修改目标推理实现，也没有验证任何候选的加速收益。

## 一、先看结论

- **基线：**32K 输入、1K 输出、并发 8、约 90% 前缀命中的两轮无 profiler 测试，合计输出 16,384 tokens，按两轮整体耗时合计计算约 **519.84 输出 tokens/s**。这是该负载的观测值，并非模型或硬件的理论上限。
- **待查的低活动点：**在部分目标层采样及严格筛选出的可比组里，融合 MoE 任务 `DispatchFFNCombine` 的 AIC MAC 活动代理偏低。它是继续调查的候选，不能据此认定该模块是整机或全模型的最低利用率模块，也不能认定原因为通信等待。
- **融合方向：**已发现 Engram 查表输入连续化、KV 归一化与 RoPE 和缓存写入、主模型与 Indexer 的量化复用等结构候选。各候选均受数据身份、数值语义、事件依赖和资源争用约束；当前没有兑现的加速幅度。
- **理论上界：**已有依赖和资源窗口的条件模型，尚缺可证明覆盖此设备与实现范围的硬容量、实际必要工作量及初态，因此**目前不能给出严格的数值 TPS 上界**。

## 二、基线与测量边界

| 项目 | 口径 |
|---|---|
| 模型和精度 | DeepSeek V4.1 Flash，W8A8；部分模块可采用混合精度 |
| 服务 | vLLM-Ascend；分析对象为本次冻结配置 |
| 单次负载 | 8 个并发请求，每个输入 32,768 tokens，目标输出 1,024 tokens |
| 前缀命中 | 每轮聚合命中 235,904 / 262,144，约 89.99% |
| 基线结果 | 两轮共 16 个成功请求、16,384 个输出 tokens，整体耗时相加约 31.517 秒，约 519.84 输出 tokens/s |
| 性能采集 | 另有开启 profiler 的诊断采样；其任务区间不等同于无 profiler 的线上耗时 |

吞吐分母是两轮各自从最早发送到最晚完成的整体窗口之和，不是各请求延迟相加；这是**输出**吞吐，不含输入 tokens。两轮首条有效 SSE 响应各自约为 0.30–1.10 秒，但留存数据不能严格证明首条含首个生成 token，也无法拆分服务端排队、prefill、采样和网络返回，不能把它直接称作精确 TTFT 或 prefill 时间。

如果用同一整体窗口作分母，两轮 **524,288 输入 tokens / 31.517 秒 ≈ 16,635 输入 tokens/s**；这包含命中前缀，且分母包含生成阶段，不是单独的 prefill 计算速率。两轮前缀查询数减命中数合计 52,480，除以同一总窗口约为 **1,665 查询差额/s**；这只是计数差额的归一化，不能代替实际执行的 token 数、prefill 用时或硬件计算吞吐。

此结果仅适用于所述模型、并发、上下文长度、缓存命中情况与配置。不同的输出长度、请求分布、草稿接受情况、批次结构、缓存状态和设备竞争都会影响数值。两轮样本也不足以确定长时间稳定吞吐或尾部延迟。

## 三、融合与结构重组：已查到哪里

排查结合冻结源码及已保存的目标层 profile，覆盖注意力输入和缓存、Indexer、MoE、HC、Engram、输出与草稿模型中的一批路径，考虑了两算子、多算子、跨模块并行和拆分重组。**覆盖的是已检查的源码分支与被采到的窗口，不是对所有分支、请求、动态形状和图重放的穷尽证明。**

| 候选 | 已有事实与可研究结构 | 不能跳过的条件 |
|---|---|---|
| Engram 输入查表 | 一次单独诊断中，1,513 条有效输入元数据显示非连续 `int32` 视图的 stride 为 `[48,1]`；现有查表源码可使用行 stride，值得研究从视图直接读取，避免中间连续化 | 采样日志达到大小上限，826 条 begin 有唯一正常返回配对；覆盖不完整。还需绑定实际后端、存储与异步生命周期、图重放以及数值一致性；省去逻辑复制不必然减少实际访存 |
| KV norm → RoPE → 缓存写入 | 在 1,280 个选定目标层范围中，均找到形状、类型及顺序相容的三个独立设备任务；一个样本进一步关联到同一 attention 前向范围内的对应 API | 尚无可绑定的 tensor/storage 身份，不能仅凭相邻任务断言同一数据边。合并时必须保持整行归约、旋转配对、缓存槽位与持久状态、数值舍入和事件顺序 |
| 主 Q 与 Indexer 量化 | 某些目标层范围中有两次形状相容的动态量化，源码中存在可接收预量化结果的路径，值得研究共享量化结果与 scale | 尚未证明实际输入为同一张量、数值和量化范围一致，不能认定重复计算或可直接复用 |
| attention/FFN 前后处理 | 源码中部分混合结果在限定条件下可先于其他系数就绪，值得研究拆分并行与之后合流 | 保留残差的全部消费者、归约和舍入、缓冲别名以及跨流同步；源码条件不等于历史运行分支已绑定 |
| Indexer 与注意力 | 值得研究结果发布、可丢弃预取以及按完整行流水 | 必须保留候选不足时的补齐、TopK 的排序和 tie 语义及跨层消费者；已有分块排序、跨块合并和部分流水不可重复算作新增收益 |
| 目标模型采样验证 | 源码中可研究将 target logits 取行、转 FP32 和所需副本初始化组合 | 仅在确认原始值没有消费者、别名和生命周期安全时才可考虑省略副本；entropy 验证或原始 logprobs 可依赖原值，历史执行和收益未知 |

对 Indexer 权重缩放的一个候选：在投影结果已按 BF16 舍入、实际缩放标量恰好为 1/64、按指定 IEEE 最近偶数舍入且没有不兼容的下溢处理时，CPU 数值模型遍历全部 65,280 个有限 BF16 编码后，先在 BF16 缩放再转 FP16 与原 FP32 缩放后转 FP16 的位模式一致。这只覆盖最终 FP16 可见结果；历史标量编码、设备舍入、张量身份和 packed 分支尚未绑定，不能据此断言实际设备等价或提速。

在部分层可研究把 SP 输入 gather 放到 Q_a/KV 投影之后：按保存维度、假设张量均为 BF16，原输入一行是 10,240 字节，两个投影结果合计 3,584 字节。这只是逻辑张量大小，不是网络流量或节省。Indexer source 层还需要本地 query 的原 hidden；其中同时负责 KV 压缩的层还需要全局 cache hidden 或经证明等价的信息。CP/PCP 行域、通信组、权重一致性和精度等价仍须证明，不能直接删掉原 gather。

对这一候选，保存的量化描述和解析源码进一步表明：如果实际配置和映射与快照一致，Q_a 和 KV 投影会选择非量化线性方法，但历史运行实例尚未绑定。一个现有采样中，与 Q 和 KV 投影形状相容的任务分别有 3 行和 24 行，提示必须分别处理 query 和 cache 的行域；不能仅凭形状证明它们属于同一数据链。

保存的 SP 和 legacy CP 源码都按 TP rank 对 token 行做连续切分。若两边 token 数、顺序和 rank 映射一致，可研究直接在本地生成本 rank 的 Q_a，不必先收集所有 Q_a；KV 仍需要全局 cache 所需的数据。真实通信组、行顺序和张量尚未绑定，空 query rank 也不能随意退出集体通信。

对 EP3 第 36 层的一个诊断范围，现已将 attention 输入 AllGather 和三个后续投影分别关联到同一 host 层范围、调用栈、flow 和设备任务。其形状与本地 Q、全局 KV 和本地 Indexer 权重投影相容；这比仅比较形状更强，但尚未绑定张量存储、历史源码哈希和跨 rank 行顺序，不能断定数据链或重组收益。

进一步核对该 AllGather 的通信标识：它在同一采集数据库里唯一匹配到一个标为 TP 的 8 rank 组记录，类型枚举显示 BFP16。但相关主机调用没有导出输入形状或 dtype，也没有张量存储标识；通信计数不等于物理网络字节，不能据此认定它与投影使用同一张量。

更外层的 PyTorch 调用记录显示两个 BF16 缓冲形状为 [8184,5120] 和 [1023,5120]；若历史接口与现安装源码一致，它们分别是 gather 输出和输入。记录中还出现以 [8184,5120] 为输入的 slice，但缺少切片参数、输出形状及张量身份，不能证明它产生了后续投影的 [8180,5120] 输入。对原始 op-range 的三个时间相近候选进行有界检查，也没有找到可用于比较 storage 的 tensor 字段；该结论只覆盖这些候选。

关于 KV 融合的计算顺序：在无 bias 的理想实数模型里，若 RoPE 一个旋转对的两个 norm 权重不同，且该次旋转的正弦不为零，逐维权重与旋转一般不能直接交换。例如一对输入 `(1,0)`、权重 `(1,2)`、余弦和正弦 `(3/5,4/5)`，权重后旋转为 `(3/5,4/5)`，旋转后权重为 `(3/5,8/5)`；共同的 RMS 分母不改变差异。这是构造反例，不代表实测权重或证明无法按原顺序融合。真实精度和舍入仍需验证。

对 Q/KV 共同输入的源码补查：在特定 legacy CP 非空分支且 metadata 由同一 builder 正常构造时，局部 Q 的输入行是全局 KV 输入的连续子视图，可研究共享读取或投影重组。但历史样本尚未绑定该分支；本次冻结量化描述将这两个投影标为 FLOAT，不能据此说存在可以消除的重复动态量化。

同一 CP 源码用全局 RoPE 缓冲区的切片给局部 Q，避免对共享缓存再次 gather 后覆盖尚未被 KV 消费的数据。重组须保留缓存别名和读完成顺序；这是一项已有防护，不是观察到的运行故障。

对 Engram 的 826 条正常配对调用进一步复核，有 168 对相邻调用在同进程、同线程下记录了相同的 storage wrapper token，offset 依次为 0 和 24。若留存的观察器源码就是实际运行版本，这支持它们观察到同一个 Python 包装对象；但尚未绑定具体层、设备消费者或事件，函数返回也不等于设备异步读取完成，不能因此认定两次查表可以安全合并。

路由候选的适用性修正：冻结的视觉路由 Python 回退函数对部分文本行会以查表 ID 覆盖动态 TopK，理论上可研究只计算选中专家 gate。但已有镜像构建信息为 A3，冻结的 A3 硬件 profile 支持对应视觉融合算子；**如果历史进程使用该源码和 profile，这条 Python 回退就不会被选中**。配置中缺省 hash 层数按冻结解析链也会归零。历史进程的实际对象和源码身份尚未绑定，所以不能绝对排除其他运行情况；当前应将这一回退视为参考结构，不计作已命中的基线优化机会，并转向已有复合算子及上下游依赖。图像行仍依赖动态选择。

对保存的 A3 原生融合算子源码进一步检查：在无分组、存在哈希表且为文本行的分支中，算子已经按表选择专家并跳过动态 TopK，但仍先为整行专家计算 score。若实际命中该分支且完整 score 没有其他消费者，可以研究提前选取并只计算所需 score；当前尚未绑定历史哈希表、具体二进制和数值契约。原生算子的权重归一化使用 `sum + eps`，与 Python 回退的 `clamp_min` 公式不能直接互换；这一源码差异本身不证明实际发生了精度问题。

在保存配置未经运行期注入、按冻结代码构造且无哈希表的条件下，文本路由需要按全部专家的 score 加 bias 做动态 TopK，不能直接套用按表只计算所选专家的方案。另一条可研究的结构是将 gate 按专家块计算，与局部 TopK 合并后得到全局 TopK，以减少中间 logits 的物化；仍须保留全部专家对排序的影响、tie/NaN 和浮点次序，并确认 logits 的其他消费者及 dispatch 接口。源码条件不等于历史调用已绑定。

分块合并还有一个具体的正确性约束：[CANN 8.0 Sort 文档](https://www.hiascend.com/document/detail/en/canncommercial/800/apiref/ascendcopapi/atlasascendc_api_07_0842.html)描述等分时保留输入顺序。若原先专家 0、1、2 分数相同、取前两个，按块重排为 0、2、1 后再稳定排序会选出 0、2，改变原结果。若该文档语义适用于历史算子，局部和全局合并都必须保留原始全局 tie 顺序；历史版本、NaN 和数值一致性仍需核对。

冻结源码的条件路径还包含逐层查表、必要时的跨 rank 通信和逐层 ready 事件，mask 则有独立事件。联合读取必须保留相应通信、数据发布和 buffer 生命周期；现有对象观察与设备事件来自不同采集，不能把它们拼成已证实的运行依赖链。

以上是**分析候选**，不是已经修改或验证的融合方案。部分复合算子本身已经包含多个步骤，例如采样到的 `DequantSwigluQuant`；不能把其中反量化、SwiGLU 和量化重复算成三项尚未实现的融合收益。单纯减少任务数，也可能损失已有的并行或增加 Cube、Vector、搬运资源争用。

已登记的 32 条融合与重组边界、既有复合调用及覆盖缺口，见 [融合扫描清单](FUSION-INVENTORY.md)。清单包含条件候选和语义未知项，不代表所有组合已经可以实现。

## 四、局部采样：优先调查什么

### 4.1 融合 MoE 的 AIC 活动代理

对选定的 16 rank、四个调度批次摘要及对应层范围，得到 1,280 个目标层 scope 的 MC2 任务关联。进一步按同一批次、层、算子名、物理形状、数据类型和格式筛选，要求参与该组的 8 个 rank 具有相同签名且任务数量一致；6,862 个签名组中有 4,930 组满足物理完整条件，其中 1,596 组具备有效 AIC 周期和指标。

为减少八卡同形状筛选造成的遗漏，另看 EP3 单卡一个摘要的 40 个目标层：1,580 条已匹配设备任务的时间区间并集为 353.614 ms，MoE 复合任务的区间并集为 156.640 ms，约占 44.30%。这是带 profiler、选定任务的区间比例，不是请求耗时或整机忙时；同步事件和部分身份缺失记录不在这个并集中，不能分解计算、通信或等待。

将同口径扩展到 16 张卡、每卡两个采样摘要，共 32 个卡与摘要组合：MoE 都是各组已选任务中区间并集最长的单个类型，占各组所选并集约 40.44%–90.79%。每组按本卡时间单独计算，不要求其他卡形状一致；这不是 32 次独立线上试验。被排除的同步事件、未关联任务和 profiler 扰动仍限制结论，无法据此算出 MoE 的线上耗时占比。

昇腾官方较早版本的 [op_summary 说明](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta1/devaids/Profiling/atlasprofiling_16_0067.html)将 Task Wait Time 定义为任务之间的间隔。一个 273.565 ms 的所选 MoE 设备记录，其导出的 Wait Time 为 1.111 µs，同流前一条已导出任务到它的间隔为 1.080 µs；这是同源数值对照，不能解释 MoE 内部等待，也不能证明该旧版说明就是本次 9.2 导出器的实现。

对同一长 MC2，已保存的通信分析文件中没有与它的导出数值时间区间相交的条目；两个文件的时钟、采集覆盖以及融合核内部通信尚未闭合，因此这不能证明没有通信或等待。昇腾提供离线解析接口，但重新解析会写入 profile，本次保留原始采集未重跑。

上述 4,930 个物理完整组里，672 组同时满足 AIC 与 AIV 各自的指标有效条件，924 组仅满足 AIC，3,294 组仅满足 AIV，40 组两项均未满足。两个榜单有交集，不能将数量相加；这些是已选任务组数，不能当成整机利用率或模型覆盖率。

排序还有一个重要限制：此前按原始 MatMul 名称列出的最低值，可能来自不同物理形状，不能当作该名称所有任务的统一利用率。例如一个摘要中最小组输出形状为 `[643,32]`，而最常出现的同名完整组输出为 `[643,1280]`；这两类不应当作等工作量。即使固定形状和八卡签名，MC2 各层有效专家路由仍可能不同。搬运任务的 vector 比例低也不能单独代表任务整体空闲。

另一次按形状分组的审计发现，部分同名算子的最低值落在少数组成的物理签名上。例如一个选定批次中，同名 RoPE 的最低 AIV 显示比例来自 4 个层组，而组数最多的另一形状有 40 个层组。形状及每卡任务数不同，该比较只说明按名称取最低可能偏离主形状，不表明实际空闲或可获得的收益。

解释 MoE 工作量时，仅知道专家接收行数的总和也不够：相同的总行数可能集中到一个专家，也可能分散到多个专家，而参考源码按专家分别调度。历史逐专家计数和实际容量仍未绑定；这个例子不证明某种分布实际发生或带来多少耗时。

在上述合格范围内，四批各自最低的 AIC MAC 活动代理均出现在 `DispatchFFNCombine`，对应层分别为 14、14、0、15；按 AIC 周期加权分别约为 **0.489%、1.627%、0.137%、2.786%**。这是对已采样任务的指标排序，不是全芯片利用率，AIC 与 AIV 也不应混为一个分母。不同专家实际接收的行数、有效 token 和路由工作量尚未绑定，因而即使形状相同也不能认定实际工作相同。

对其中一个摘要的第 15 层和第 36 层固定签名进一步比较：第 15 层八卡周期加权比例约 2.786%，但其中一张卡的记录约为 46.65%；该卡任务约 5.02 ms，另外七张卡约为 24 ms。第 36 层八条约为 3.50–4.74 ms。这是带 profiler 的选定任务，不是端到端延迟；不同卡的工作量、时钟同步和相互等待关系未绑定，不能由差异认定某张卡拖慢其他卡或认定通信是根因。

对其中一张卡的第 36 层进一步读取其他流记录，发现四条与 MC2 区间相交的 Notify_Wait，可在采集数据库里关联到一个 allGather 操作编号，而该 allGather 的整体通信记录出现在 MC2 结束后。这说明仅检查整体通信记录的时间范围会漏掉相关调度记录；现有证据没有绑定等待对象与 MC2 的数据依赖，也没有校准跨轨时钟，不能据此认定通信导致 MC2 变慢。

四条所选 Notify_Wait 均在 MC2 开始后启动、结束晚于 MC2 结束至少约 458 µs。在导出时间轴和完成边界可信的条件下，可排除 MC2 完成必须等待这四条记录全部完成；仍不能排除其他等待或争用。相同 notifyId 在该通信操作内多次出现，无法只凭 ID 唯一配对。官网对这些字段和通知操作有说明，但其版本与本次采集未完全一致。参见 [CANN 9.0 profiler 表定义](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/devaids/Profiling/atlasprofiling_16_1144.html) 和 [CANN 9.1 通信行为说明](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910beta3/API/hcclug/docs/zh/user_guide/perf_analysis/profiling_op_behavior.md)。

对另一张卡的一条长 MC2 记录，CSV 将 vector 比例显示为 0，但同一采集数据库原值约为 0.041%，MTE2 比例约为 13.34%。因此不能以显示值 0 断定所有流水没有活动；MTE2 比例也不是墙钟占比、实际带宽或内部等待原因。

这个长样本所属的主机调度范围记录了 5,144 个调度 token，MC2 的物理输入为 643 行，8×643 恰为 5,144；但另一组调度总数为 8,180，8×1,023 为 8,184。形状与调度计数之间不能套用统一乘法恢复每卡有效行，更不能由此推算每专家接收数量或长任务原因。

该样本中，路由算子的 [643,6] 输出与后续 MoE 融合算子的相应输入在形状和类型上相容；输入布尔向量及整数输出只记录了形状。没有存储身份或元素值，无法确认实际有效 token、路由结果或各专家工作量。

该第 15 层中，高比例卡仅占所报八卡 AIC 周期权重约 0.969%，所以全组加权结果主要由其余七张卡决定；这解释统计结果，不能解释各卡差异的成因。对该卡的一个设备任务间隔回查，同线程的 gate 主机调用在导出时间线上持续约 2.05 ms，与间隔高度重合。另一张卡的对照中，gate 主机调用约 1.11 ms，但其两个设备任务的记录间隔约 1.34 µs，说明主机调用长并不必然伴随同样长的设备间隔。跨域时钟校准、采集完整性及调用内部活动未证实，尚不能断定这些调用导致设备等待或线上变慢。

已有 EP3 的 tensor-info 切片经安装版解析器检查，有 40 组描述符的形状与目标 MoE 兼容，但不能唯一定位第 15 层任务，解析字段也不提供专家计数的元素值。解析器和采集生产者的版本尚未完全绑定，其他记录来源仍可能包含更多信息；现阶段不能据此判断专家负载分布。

换用 AIV 的 vector 显示比例单独排名时，四批最低合格组均为 `TensorMove`，显示值为 **0.0%**；因此 MC2 不能称作所有指标下的最低任务。显示值可能受精度和舍入影响，不证明该任务或设备空闲，也不意味着它是全模型最低利用率模块。两个排名使用不同核心和分母，不能混为一个榜单。

对其中一条任务回查同次采集的数据库，高精度 vector 比例约为 **0.0231%**，并非零；另有 MTE2、MTE3 导出字段分别约为 **42.0%** 和 **46.6%**。唯一关联的调用栈指向注意力输出投影路径中的 copy；冻结源码位置相容，但历史加载文件和张量地址仍未证。这只是一条样本，几个流水字段不能相加当作利用率、墙钟时间或带宽，也不能据此归因瓶颈。

同一份重型采样中，一个 rank 的第 14 层与第 39 层相关 MC2 显示约 **160.37 ms** 和 **8.29 ms**；这提示值得追查，但 profiler 对时间的扰动未限定，不能把差异当作线上延迟差或可实现加速。对两个 rank 的两个选定层，已关联的外部同步与集合通信事件均在对应 MC2 开始前结束；这排除了这些**已记录区间直接与所选 MC2 区间相交**，但不能排除之前通信的间接影响、其他流、未记录事件或复合算子内部等待。

对该 rank 的一组调度摘要，40 层均有关联的 MC2 设备记录，且所选记录在同一 stream 上按层顺序不相交；调度摘要不是客户端请求 ID，缺少跨流数据和完成事件的绑定，因此还不能判断长 MC2 是否位于客户端关键路径。

另一份历史采样的单卡窗口中，按导出表筛选的 18 条 `hcom` 记录与 1,188 条计算核心记录没有时间交集。此统计排除了身份缺失的汇总行和部分其他类型，通信行也可能是嵌套记录，不能排除其他流活动或 MC2 内部通信，更不能说明通信无法隐藏或证明串行依赖。

相同筛选扩展到两张卡各三个历史锚点窗口：六个窗口里的已选通信与计算区间均不相交；部分锚点的层角色没有独立验证。这个结果不扩大为全程结论，也没有找到可用来证明实际重叠的对照窗口。

指标解释也很关键：某条样本的 `cube_utilization` 显示接近 98%，其 MAC 活动代理却约 0.3%。核对安装版解析公式后，前者不能直接当作有效矩阵计算的利用率；两个数也不能相减得到等待时间。记录中没有能够分解内核内部阶段的 PC 采样，目前无法在计算不足、数据搬运、轮询或其他原因之间作出结论。 即使假设矩阵计算和搬运比例采用完全相同的计数空间，这两个整体比例也不能唯一确定二者的重叠，更不能算出等待时间。

对已保留的同 rank、同层 `MIX_AIC` 任务分别比较导出的 AIV vector 比例：MC2 低于 attention 和 HcPre 的配对各为 **1,280/1,280**，低于 Indexer 为 **256/256**。这是指定字段的采样比较；不同算子工作量和部分 block 配置不同，无法据此判断整机利用率、算子效率或等待原因。

### 4.2 KV 缓存写入的采样分布

在 1,280 组已选 norm、RoPE、scatter 三任务中，scatter 在 **1,207 组**中的单任务时间比另两项分别更长。对 `T=8180` 的 640 组，scatter 在每组三任务时间和中所占比例的中位数为 **79.43%**；这只是选定任务的 profiler 区间比例，不是端到端时间比例。

同一 rank、同一批次中，两个所报形状、类型、格式和 block 数一致的 scatter 样本分别为 **16.68 µs** 与 **265.06 µs**。多个导出视图的时间一致，但不是相互独立的硬件计时；真实槽位、缓存初态及计数口径未知。这个差异支持继续排查，不能据此认定 HBM 是瓶颈或预测融合收益。

对 T=8180 的 640 组选定任务作事后分组：31 个短 scatter（小于 50 µs）之前，选中 rotary 结束到 scatter 开始的记录间隔为 **283.480–1834.480 µs**；609 个长 scatter（大于 200 µs）之前的相同间隔为 **0.0195–0.04075 µs**。这两个区间在该采集中完全分离，但样本不是独立请求，阈值也是事后选择；间隔可能包含其他任务或未记录活动，不能据此认定设备空闲、间隔导致时长变化或预测融合收益。

在各自同层 scope 的已匹配设备记录中，31 个短 scatter 均未与其他 track 任务交叠，609 个长 scatter 均与一条量化 Matmul 的记录区间交叠；短组同层也有该类 Matmul，只是选中的最近一条出现在 scatter 之后。这仍是同次采集的时序关联，且任务时长本身会影响交叠机会；scope 外任务和未匹配同步事件没有纳入，不能据此认定资源争用或设备空闲。

对同一张卡的两个短、长样本，进一步查看各自同流记录：短样本的 RoPE 到 scatter 间隔约 1.69 ms，所查 trace/DB 中没有其他已导出的同轨任务；对应两次主机 launch 的同线程记录间隔约 1.69 ms。长样本的设备间隔约 0.02 µs，主机 launch 间隔约 432 µs。采集完整性、同步对象和调用内部活动仍未闭合，不能从这些数字认定下发、同步或设备侧的具体根因。

对主机间隔改用“所有相交记录”而非只查“完整落在间隔内的记录”后，短样本约 **99%** 的主机 launch 间隔落在前一个 RoPE 的 dequeue 记录内；长样本约 **96%**。此前仅查到短 tiling API，不能据此说间隔内缺少主机调用记录。调用范围覆盖不区分线程计算、等待或 profiler 开销，也不能证明设备整体空闲。

该次保存的采集配置中，CPU 线程和 OS 运行时采集项为关闭；所查目标工作线程的 Dequeue 记录也没有调用栈。现有 API 区间因而不能拆分为 CPU 执行、线程等待、调度或采集开销；导出器还有 step 范围和频率相关告警，不能据此否定整份采集。当前安装包中有与短、长 Scatter 任务 dtype 相符的候选二进制，但导出的任务与 trace 未绑定实际二进制或 tiling key；原始切片未解码。

对同卡同摘要的 29 个短样本和 11 个长样本，每个 scatter 按时间选择同层最近的量化 Matmul：scatter 时长中位分别为 **17.70 / 261.08 µs**，两个事件从最早开始到最晚结束的记录跨度中位分别为 **330.08 / 324.50 µs**。配对只依据时间，跨度包含可能的空隙，也没有绑定 tensor 或同步关系，因此它不是模块耗时、关键路径或融合收益；这个对照表明不能单从 scatter 的时长比较端到端结果。

当前 stage 中的自定义 scatter 源码显示，批量和分片路径对负索引的处理先后不同：某批量路径先搬入更新数据再跳过负索引写出，分片路径可能先判断再搬运。重复索引及 cache 视图 stride 也影响语义；历史样本实际使用的二进制、tiling、索引值及 stride 均未绑定，不能把其中任何一项认定为短长差异的原因。

对上述两个 scatter 样本进一步检查，同一采集数据库中的任务与 PMU 记录能够唯一关联，记录的周期值与导出 CSV 一致。周期与时间字段的比值，在数值上与采集设备信息中的 AIV 核数和频率相符；但字段单位和导出公式尚未证实，不能把长任务的其余时间直接称为等待。源码中，条件 KV 分支将归一化返回值的视图用于原地 RoPE，随后转换或连续化可能产生副本；这些源码条件仍未与所选设备任务的张量身份绑定。

同一次 EP8 第 14 层的选定任务中，norm、RoPE 和 scatter 的设备记录区间分别与另一条不同流的量化 Matmul 区间相交；scatter 的区间约 258 µs，其中约 239 µs 与该 Matmul 记录重叠。冻结源码存在 Q/KV 多流重叠设计，但该样本尚未直接绑定到相应源码分支或张量。区间重叠不证明有效计算同时进行或没有资源争用；它提示融合如果破坏原有流水，不能直接把整段 scatter 时长视作可节省的端到端时间。

进一步比较同一个已关联层范围内的其他任务：1,280 组中，每组都有一条匹配的 `SparseFlashMla`，其中 **1,223 组**的该任务区间比对应 scatter 更长；另有 256 组各匹配到一条 Indexer 任务，**256 组**均比对应 scatter 更长。余下组没有匹配到唯一 Indexer 记录，不代表设备没有执行。它们处于不同 stream、可能重叠，因此不能将耗时相加，也不能据此认定请求关键路径或收益；这是重型 profiler 下的选定批次，只用于调整排查优先级。调度记录显示其中两组也包含投机 token 描述符，不能将这些批次整体称作纯 prefill。

在上述层范围内进一步按同一设备记录比较区间，1,280 组 scatter 均先于对应的 SparseFlashMla，256 组 scatter 均先于匹配的 Indexer；这些选中配对没有区间重叠。256 组 Indexer 和 SparseFlashMla 处于同一 stream，Indexer 均先结束；条件源码分支支持 Indexer 结果供 attention 使用，但对应运行时张量和分支尚未绑定。其他流仍可能有任务，记录间隔不是设备空闲时长。

对同一 rank 的短、长 scatter 两个样本追查下发时间：短样本前两个设备任务之间的间隔分别为 **1,290.900 µs** 和 **1,693.280 µs**，其中从前一设备任务结束到下一次 host `launch` 开始分别为 **1,173.675 µs** 和 **1,563.175 µs**。按导出时间戳相减，关联的前一个 host API 在设备任务结束后仍持续约 **1,162.235 µs** 和 **1,544.635 µs**；长样本的三次 launch 则均早于第一项设备任务的导出起点。**主机与设备时钟转换及误差尚未独立校准，这些跨域差值仅描述导出时间戳，不能视为精确物理时延。**这支持优先检查 host API 调用和 profiler 扰动，但 API 墙钟时长不能区分有效工作、等待或线程抢占；记录缺失也不能证明设备空闲。

进一步检查两张卡、两组摘要中八个选定层的 **32 对** Indexer → attention 任务，每对之间都有一条同流的索引整理设备任务；三者部分 INT32 输入输出形状相容。已查数据库字段没有可绑定的 tensor 地址或 event 对象，形状和顺序不能证明它们使用同一张量，也不能证明同步关系；其他流及未导出活动仍可能存在。

这 32 条整理任务的 profiler 区间中位数为 **182.93 µs**；逐对计算它占 Indexer 结束到 attention 开始区间的比例，其中位数为 **98.06%**。这是重型采样、选定任务的区间比较，不是端到端占比或可节省时间。冻结源码中对应的候选整理逻辑包括可见性过滤和排序；若将过滤移到 TopK 前，必须证明不会改变被选结果，不能默认两种顺序等价。已有 QLI 接口接收长度和掩码参数，但其内部语义与上述设备任务的源码绑定仍需核实。

对另一批已选 Indexer 的短、长三条记录，数据库都显示其他流有可关联到 allGather 的通知等待，尽管先前的算子 CSV 查询未找到其他流的计算 kernel。短轮和长轮都有这些等待，不能仅凭它们的存在解释时长差，也不能由此证明 Indexer 被通信阻塞。

该采集中还找到了 Indexer metadata 生产任务；三条目标之前各有形状相容的候选记录，但记录没有保存可用的长度元素，候选也没有与目标 tensor/replay 身份绑定。因此目前仍不能确定各轮实际 key 长度或据此解释耗时差异。

冻结源码中，metadata 生产结果可先复制到共享缓冲，再供后续路径使用；生产者和消费者不必是同一存储。要证明数据关系，需要绑定复制、缓冲生命周期与具体重放；现有记录还不能还原这些关系或实际长度。

现有三轮中各两条 metadata 任务之后，分别找到了同线程 host copy 和对应的同流设备 copy 记录；这与源码路径相容，但没有源、目标地址和相应源码栈，仍不能证明这些复制就是目标 Indexer 使用的 metadata。

冻结的索引整理源码中，TopK=512 且请求长度输出时，最多 1024 行在整理中统计长度，超过 1024 行则另对结果统计。按行切分以改变分支需要证明语义一致：在 INT64 位置计算不溢出的数学模型下，当位置和某个索引均为 INT32 最大值时，前一种统计会计入该值，而该值又是最终输出中的无效标记，后一种统计不会计入。这只是极端输入的条件性源码反例，尚未证明真实模型允许或出现该输入，也未绑定历史运行的长度输出、编译语义和实际分支；不能据此判断实际故障或性能收益。

进一步读取所保存的原生 Indexer 源码：在指定 mask 分支、`L≥Q` 及实数行条件下，若该行位置 `p` 等于 `L−Q+i`，其可见范围与后处理使用的范围一致；这里 `L` 是序列长度，`Q` 是查询行数，`i` 是行号。实际调用的这些逐行值、源码与运行二进制尚未绑定；即便范围一致，排序、无效槽、输出地址及其他消费者也必须保留，不能因此直接删除整理任务。

继续追查输入生成源码，在普通 GPU 构造路径中，若这三个值属于同一真实请求和同一次 metadata 构造，`p = L−Q+i` 由位置和长度的生成方式成立；满足相同条件的 causal CP 连续切片也保持该关系。特殊重建、额外切片和历史任务的实际 metadata 身份尚未确认。所选 32 条 Indexer 记录的导出属性均为空，不能借用另一轮样本来推定其 mask 模式。

这 32 条记录可在已保存数据范围内关联到四组调度摘要；调度总行数与其物理形状按 8 分片的算术结果相符，但这不证明实际切片、有效行或设备上的逐行位置和长度。两组总行数相同的批次有不同请求构成，不能只凭相同 shape 认定实际工作相同。

32 条所选整理任务都能关联到同次采集的 PMU 和 CSV 字段；两个 rank 的 `aiv_scalar_ratio` 中位数约为 **87.49%** 和 **87.21%**。这些是导出字段而非经校准的墙钟分解，导出路径和计数覆盖仍需核实，不能据此断定 scalar 计算造成瓶颈、其他流水空闲或可获得提速。

当前安装的 CANN 9.2 存在以 PMU 计数除以任务周期的候选公式，这些样本的比例和周期在算术上与其一致；但原始分子和历史数据库是否走了该公式尚未独立绑定。按冻结 helper 的逻辑分块规则，若实际使用 48 个程序实例，则所选的三种行数分别只有 38、41、43 个实例分到数据块；这不是物理核心闲置的证据。即便设想均衡分配，单实例最大整块数仍相同，因此也不能凭这一现象预测提速。

同线程的主机 API 嵌套记录显示，短样本中两个外层调用分别持续 1,305.920 µs 和 1,685.320 µs，其已记录子 CANN API 的时间并集分别为 13.980 µs 和 12.240 µs。未被记录覆盖的时间不能分类为等待或计算；这次采集没有启用相应的主机 CPU 和 OS runtime 采样项，数据库也没有 CPU 调度事件表。

当前安装的 CANN 9.2 profiler 源码中找到一条按周期、频率、block 数和核数换算时间的公式，在假定频率和核数后与这两条样本的计数数据数值相容。不过历史采集数据库的生成路径和该字段单位尚未绑定，同版也存在其他计算路径，因此不能据此推断设备有效执行或内部等待时长。

### Attention 输出写回的补充核查

在同一采集、相同物理签名和第 0 层选出的 EP8–15 八条 `TensorMove` 中，数据库保存的向量 ratio 均非零，约为 **0.022438%–0.026090%**，而 CSV 对应显示均为 0.0；MTE2 和 MTE3 字段也非零。它们是同一次 profiler 采集的不同表示，不能当作独立测试。字段单位、导出链和采样精度尚未完全确认，不能据此认定实际带宽、设备空闲或低利用率原因。

冻结源码的 attention 自定义算子要求写入调用方传入的 output。让最终投影结果直接写入该缓冲区是一个待验证的结构候选，须保持必要归约、通信、别名、同步及图执行语义；历史采集尚未绑定实际张量存储与最终 producer/consumer，因此不能确认融合可行或估算收益。

同一个 EP8 第 0 层的样本中，copy 前一条同流设备任务关联到 `wo_b` 路径的 Matmul；copy 后的 record/wait 事件分别关联到 reduce-scatter 的主机调用范围。结合冻结源码和形状，这支持“投影 → copy → reduce-scatter”的候选数据路径，但没有 tensor/storage 身份来证明数据边。所选 WAIT 的事件对象及配对 record 未绑定，不能把其区间认定为通信耗时、设备空闲或可隐藏时间。

进一步沿同一次 host 调用的 flow，可以关联到一条 hcom reduce-scatter 记录和一条 AI CPU 任务。导出时间线上，hcom 记录区间落在此前选中 WAIT 区间内；不同轨道的时钟转换及误差、WAIT 的 event handle 与配对 record 均未独立绑定，因此这只是采集中的时间关系，不能证明 WAIT 在等待该通信或据此计算可隐藏的耗时。

官方 CANN 文档提供 BF16 矩阵乘与 reduce-scatter 复合接口；现存源码还有另一模型使用该类接口的例子。但当前 DeepSeek 的部分结果先写入 attention 输出、通信在后续模块进行，若跨边界组合，必须重新证明输出消费者、通信组、分片及舍入。不同版本对通信模式的说明不同，不能由其他模型源码断定历史 9.2 运行支持或性能收益。参见 [CANN 9.1 接口](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-transformer/aclnnMatmulReduceScatterV2.md) 和 [CANN 8.5 接口](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/850/API/aolapi/context/ops-transformer/aclnnMatmulReduceScatterV2.md)。

继续追查同次调用，已把通信前后两条流上的多个 RECORD/WAIT 任务分别关联到主机事件 API，顺序与双向同步相容；但 event handle 未保存，尤其通信流尾部有两条候选 RECORD，无法确定另一流的 WAIT 实际等待哪一条。不同轨道的约 1 微秒时间差也没有时钟精度保证。

该权重描述中 `wo_a.weight` 和 `wo_b.weight` 各 43 条均标记 `FLOAT`。进一步对 EP8 第 0 层一个具体样本核对后，其 Matmul 设备任务通过唯一 flow 关联到 `unquantized_gemm → linear → matmul` 主机调用，主机输入记录为 BF16，设备任务也报告 BF16 输入和输出。此证据限定在该调用，不证明底层指令、累加精度或其他层实际执行路径；整模型使用 W8A8 不能推出每个线性层均使用 INT8。

输出写回的值也随并行分支变化：冻结源码中的 DSV4 专用行并行函数本身返回局部结果，另一个条件分支可能在 attention 之后做 reduce-scatter。因此在研究将投影直接写入原 output 时，必须先确定原 output 在该分支应包含局部值还是已归约值，并保留后续通信；现有源码接口未传目标 out，不代表设备上的所有其他接口都不支持。

## 五、理论极限：可以怎样严格表述

昇腾 MindIE 文档提到一种仅用于负载均衡分析的理想化设置，并明确不能用于正式业务；它适用其他指定硬件和模型。即使能测出这种合成条件的吞吐，也不能自动将其当作保持本任务真实模型语义的不可超越上界，仍须证明必要工作量和硬件容量。参见 [MindIE 负载均衡限制](https://www.hiascend.com/doc_center/source/zh/mindie/21RC2/mindiellm/llmdev/mindie_llm0427.html)。

先区分上下界的方向：对**同一有限工作负载、相同测量窗口和允许的实现集合**，若这两轮基线执行满足所要求的输出契约并属于允许集合，那么已观察到的约 519.84 输出 tokens/s 可作为该有限实验的性能最优值的一个观测下界；实际时钟与计数误差仍需计入。它并不保证稳定复现，也不是单请求 TPS、长期稳态吞吐或理论上界。严格数值上界则还需要下述不可避免工作量和硬容量证据，当前未知，所以尚不能给出有数字的完整上下界区间。

理想模型允许合法的融合、分块和重叠；必须保留由输入输出语义证明的依赖。对给定负载和清楚定义的时间窗口，若能证明某资源至少要完成工作量 `W_min`，且任何时长为 `t` 的窗口最多完成 `b + P_max × t`，则有：

```text
T ≥ max(0, W_min − b) / P_max
```

其中 `P_max` 是覆盖该资源、数据类型、并发机制和整个窗口的**硬容量上界**，`b` 是已证明的窗口初始在途或突发信用。多个可并行资源的下界通常取最大值；有依赖的阶段需按依赖图分析关键路径，只有已证明不可重叠的部分才能直接相加。计算、访存和通信可能共享资源，不能既假设无限并行，又忽略资源争用。

如果同一完整工作窗口必须产生 `N` 个输出 tokens，且已严格证明它的时长不小于 `T_min > 0`，则该窗口的平均输出吞吐不超过 `N / T_min`。这个结论只适用于所定义的窗口、工作量和初态；单个算子的理想时间不能直接倒数成整服务的 TPS 上界，跨窗口流水也需要正确计入在途工作。

一个**计算模型示例**：假设单设备只使用 24 个 INT8 Cube 核、频率恒为 1.8 GHz，每核每周期最多 8,192 次 MAC，且必须按普通稠密算法完成 `3×1280×32768 = 125,829,120` 次 MAC，那么只计计算、假设无开销时约需 **0.356 µs**。核数与频率来自 profiler 元数据，每周期算力使用 [Ascend 工具的估算公式](https://github.com/Ascend/msprof-analyze/blob/6b8f431d4724043f44a39eef000fd5c6600784d8/msprof_analyze/cluster_analyse/cluster_kernels_analysis/operator_mfu/chip_peak_flops.py)；尚未证明它们是这台设备的物理硬上限或覆盖所有合法执行方式。旧采样中按输入形状筛出的 1,920 条矩阵任务中位数约 42 µs，但输出语义、实际有效行与上述算法没有逐条绑定，且 profiler 有扰动。这两个数字用于展示建模及缺口，不能据此声称已证明的差距或可实现的加速。

另一个直接关联到历史样本的 **BF16 投影条件模型**：该次 EP8 Matmul 设备记录对应形状 `[8184,1024] × [1024,5120]`，其 host 调用记录 BF16 输入。若限定普通稠密算法，逻辑工作是 **42,907,729,920 MAC**。再假设仅有 24 个 Cube 核参与、频率硬上限 1.8 GHz、每核每周期最多 4096 个 BF16 MAC、无在途信用且不使用其他资源，纯计算时间条件下界为 **242.489 µs**；这条任务的重型 profiler CSV 区间为 **320.893 µs**。24、频率和 4096 尚未证明是覆盖实际设备、全部资源和实现的硬容量；普通稠密工作量也不是任意合法算法的必需工作。两数之比只是条件模型与采样区间的比较，不是已验证利用率、可达提速或服务 TPS 上界。

设备身份方面，已保存的两份 CANN 软件目标配置 `9381` 与 `9382` 的解析键值，只有 SoC 版本名称不同；因此采集里的 24 AIC、48 AIV 和 1800 MHz 字段不足以区分这两个配置。单个设备的型号查询也不能自动代表全部历史 rank。这是软件配置的比较，不证明两种芯片的实际物理属性相同。

上述时间计算还假设计入的全部工作均须在同一窗口内完成，且不存在需要抵扣的窗前在途工作或突发信用；否则应使用本节的 `b + P_max × t` 形式。稳态平均峰值不能自动当作任意短窗口的硬容量。

若再限定采用 [Ascend Mmad 指令模型](https://asc.gitcode.com/api/appendix/cube_instruction_theoretical_perf_summary.html)、每条指令最多处理这 3 个有效行且不能拼入其他工作，按该模型的 16 行对齐，并进一步假设上述核数、频率和共享资源服务上限均成立，条件时间下界可收紧到约 **1.896 µs**。这比前一个模型限制更强；其他合法分块、拼行或算法重组不受此界约束，也尚未证实历史 kernel 满足这些条件。

同一形状还可以建立**受限冷态输入界**：若矩阵和权重是存储互不重叠、可独立变化的 INT8 输入，要求对所有输入给出完整精确 INT32 结果，输入起初仅以原始字节位于 HBM、没有副本或预计算，且通过指定边界逐字节读取，则存在一个输入要求至少读取 `3×1280 + 1280×32768 = 41,946,880` 个不同字节。若该边界有已证明的硬读取容量 `B` 和初始突发信用 `b`，可得该输入的 `T ≥ max(0,41,946,880−b)/B`。在计算与读取条件都成立的同一窗口，两个时间下界取最大值，允许它们完全重叠。实际模型使用固定权重且可能热缓存，当前既没有绑定这套冷态契约，也没有证明对应的 `B` 和 `b`，故这不是本次请求的 HBM 流量或 TPS 上界。

以本次 scatter 的一个相容形状为例，`8180 × 512 × 2 = 8,376,320` 字节只是 BF16 输入张量的**逻辑容量**。无效或重复槽位、相同的缓存初态、缓存层级及不同合法实现都可能改变实际写覆盖和 HBM 流量。若额外限定目的地址与可观察终态，且证明初态与终态有 `D` 个不同的目的字节位置，那么至少需要覆盖这 `D` 个位置；进一步有匹配的写覆盖硬容量时才可代入上式。当前 `D`、突发信用及对应硬容量均未知，不能据此给出本次请求的正数时间下界。

作为理论方法示例，如果把 scatter 单独定义成接口，假设 8,180 个槽位互异、每个槽位的 512 个 BF16 值都可独立取 256 种值，并要求接收端精确观察最终状态，且窗口前无输入副本或旁路，那么计数论可证明：即使允许融合、压缩和重排，**至少存在一个输入**需要跨指定边界传递 33,505,280 bit 的可区分信息。这是人为限定输入族的最坏情况，不是每个输入均有此工作量；现有证据没有证明这些独立取值在实际模型中可达，也没有证明对应真实 HBM 流量或硬容量。

对索引整理，在所有索引互异且有效、每个位置均可能改变输出、窗口前没有等价摘要的接口域里，所有输入位置都存在必要的信息依赖，但这不要求逐项串行或逐项读取 HBM。若进一步限定算法只能通过二元比较获取次序并需支持全部排列，512 项的最坏情况至少需要 **3,876 个逻辑比较结果**；radix 排序、上游直接生成有序结果等不受该比较模型约束，且这些条件尚未绑定历史运行，不能把它换算为实际时间或 TPS 界。

另外，在一个受限的数据流模型中，512 个有效索引的排序首项可能依赖每一个输入。如果图结构固定、节点最多合并两个输入且边界没有预先算好的摘要，则首项至少需要 9 层逻辑依赖。芯片原语不一定符合二输入假设，上游融合也可改变边界；因此不能把这 9 层直接换成设备时间或 TPS。

当前已经有若干**受限算法和接口条件**下的工作量、信息传递和数据依赖推导，但尚不能证明它们覆盖所有允许的融合、重组和缓存初态；所以它们不是本次整模型的严格数值上界。理论差距也不是可达加速承诺。

## 六、证据与复现口径


本报告公开聚合事实、筛选口径和限制。**原始 profile、请求输入与输出、模型权重、内部运行配置和诊断日志不随本报告发布；因此外部读者不能仅凭仓库独立重放或核验原始采样。** 要独立验证，应在有权使用的等价环境中重新采集，并记录实际硬件、镜像及源码版本、模型和精度、并行方式、请求参数、缓存初态及 profiler 设置。不同配置所得数值不应直接当作同一基线。

可按以下算术和筛选规则复核报告的聚合口径：

1. **输出吞吐**：两轮总输出 tokens 除以两轮整体窗口耗时之和；分别记录每轮成功数、输入输出计数、命中计数和计时边界，不把重型 profile 采样当作基线成绩。
2. **MC2 关联和筛选**：目标层 host scope 通过唯一的 host-to-device flow 关联设备任务，再按任务字段与 kernel 表匹配；按同批次、层、算子名和物理签名分组，要求所比较组的 8 rank 数据完整且各自任务数量相同；AIC 与 AIV 分别筛选。指标不完整的组不填零。
3. **加权活动代理**：`sum(AIC_cycles × aic_mac_ratio) / sum(AIC_cycles)`；明确其分母是已筛选设备任务的 AIC 周期，不能称为全芯片利用率。
4. **F08 分布**：在已关联目标层范围中，按同流、任务顺序及物理签名选出 norm、RoPE、scatter 三元组；逐组比较三个任务区间。先对每组计算 scatter 占该组三任务时长之和的比例，再计算组间中位数。
5. **完整性和干扰**：报告未关联事件、缺字段、日志截断和 profiler 错误；区分设备没有记录、设备无任务、任务内部等待和有效计算活动。保持待验证假说，不从时间邻近或名称相似推出张量身份。

外部资料可用于核对接口和指标语义，但只有确认版本、芯片及执行域匹配后才能用于本机结论。例如 [CANN profiler 字段说明](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta2/devaids/Profiling/atlasprofiling_16_0067.html)、[Ascend C Cube 指令理论性能资料](https://asc.gitcode.com/api/appendix/cube_instruction_theoretical_perf_summary.html) 和 [Ascend C 平台带宽接口说明](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/Utils-API/platform_info/PlatformAscendC/GetCoreMemBw.md)。它们提供核查入口，不能自动证明本次设备的全实现域硬上限。

## 七、尚需解决的问题

- **定位最低利用率模块：**补齐同一口径下相关模块、rank、请求和图重放的覆盖；分别解释设备任务覆盖、AIC/AIV 活动和等待，避免用局部排序代表全模型。

- **收紧上界：**核实设备型号、资源范围、频率和并发规则对应的物理硬容量，证明实际负载不可避免的工作与初态；将可重叠的阶段按依赖图和共享资源建立界。

昇腾 [CANN 9.1 通算融合说明](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910beta1/programug/Ascendcopdevg/docs/guide/%E7%AE%97%E5%AD%90%E5%AE%9E%E8%B7%B5%E5%8F%82%E8%80%83/%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/%E8%8E%B7%E5%8F%96%E6%80%A7%E8%83%BD%E6%95%B0%E6%8D%AE.md) 和 [CANN 8.0 profiler 示例](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/80RC3alpha003/devaids/auxiliarydevtool/atlasprofiling_16_0046.html) 分别描述分块流水和示例中的通信侧阶段：不同块可以重叠，但数据依赖、分块、同步和资源争用会约束掩盖。后者只为对应版本及示例提供字段解释，尚不能直接解释本次 9.2 的 MoE 融合算子内部阶段；既有记录无法据此量化通信被隐藏的时间。


官网接口补查：CANN 9.1 的 [DequantSwigluQuant](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-nn/aclnnDequantSwigluQuant.md) 与 [V2](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-nn/aclnnDequantSwigluQuantV2.md) 产品表对 A3 的支持不同；前者同页约束段也提及 A3。V2 的 mode 1 使用奇偶交错输入，本次保存的 activation wrapper 使用前后两半，不能只凭形状和名称直接替换；重排后的精度、scale、group 和历史调用仍需验证。设备任务同名不证明调用了某公开 API。

另据 [CANN 9.1 msOpProf 指南](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910/devaids/optool/docs/zh/user_guide/msopprof_user_guide.md)，上板 PipeTimeline、instrTimeLine 仅支持 950 且暂不支持通算融合；PcSampling 仅支持 950。指南另有条件性的通算流水图，不能等同于逐指令流水。当前保存的 9.2 工具帮助未列出前三个选项；自定义融合算子的支持及历史版本绑定仍未知，因此这些不是当前已验证的内部阶段证据。
