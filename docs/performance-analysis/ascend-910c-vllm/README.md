# Ascend 推理性能分析：算子融合、低活动与理论界

> 阶段性报告，基于一台 Ascend 910C 服务器上已冻结的 vLLM-Ascend 与 DeepSeek V4.1 Flash W8A8 推理配置。分析目的在于找到值得深入调查的结构和性能问题；目前没有修改目标推理实现，也没有验证任何候选的加速收益。

## 一、先看结论

- **基线：**32K 输入、1K 输出、并发 8、约 90% 前缀命中的两轮无 profiler 测试，合计输出 16,384 tokens，按两轮各自 AISBench 测量窗口之和计算约 **519.84 输出 tokens/s**。这是该负载的观测值，并非模型或硬件的理论上限。
- **待查的低活动点：**在部分目标层采样及严格筛选出的可比组里，融合 MoE 任务 `DispatchFFNCombine` 的 AIC MAC 活动代理偏低。它是继续调查的候选，不能据此认定该模块是整机或全模型的最低利用率模块，也不能认定原因为通信等待。
- **融合方向：**已发现 Engram 查表输入连续化、KV 归一化与 RoPE 和缓存写入、主模型与 Indexer 的量化复用等结构候选。各候选均受数据身份、数值语义、事件依赖和资源争用约束；当前没有兑现的加速幅度。
- **理论上界：**已有依赖和资源窗口的条件模型，尚缺可证明覆盖此设备与实现范围的硬容量、实际必要工作量及初态，因此**目前不能给出严格的数值 TPS 上界**。

### 数据怎么走：两个已保存的样本

以下是带 profiler 的设备记录，不是线上请求时间。箭头表示冻结源码中可成立的条件路径；历史采集尚未绑定张量存储身份和执行分支，因此不能仅凭形状断言这些任务确实首尾相接。

| 路径 | 记录到的数据与单项时长 | 可以得出的分析 |
|---|---|---|
| 注意力 KV 前处理 | 一个 EP8 第 14 层样本依次记录 RMSNorm：BF16 `[8180,512]`，35.920 µs；RoPE：BF16 `[8180,1,1,512]`，36.839 µs；缓存 scatter：BF16 更新 `[8180,512]`，258.095 µs | 条件源码路径中 norm 的结果经过视图送入原地旋转，再按缓存槽写入；可研究融合，但必须保持归约、舍入、缓存写入及跨流依赖。逻辑更新大小约 8.38 MB，不等于实测 HBM 流量或可节省流量。 |
| 融合 MoE | 同次样本中 `DispatchFFNCombine` 的输入包括 BF16 `[1023,5120]`、两组标为 INT8/FRACTAL_NZ 的权重，以及 INT32 `[1023,6]`；第 14 层任务 160.366 ms，第 39 层任务 8.290 ms | 按对应源码条件路径，数据经过路由与量化、跨卡分发、两次分组矩阵乘及激活、归并。内部阶段可分块交叠；专家路由、有效行数、实际通信和每阶段时间未知，形状相同不能说明工作量相同，也不能将长任务归因于通信。 |

在同次采集的 8 张选定卡上，分别对第 14 层和第 39 层的 gate 与 MC2 进行同卡对照：gate 记录分别为 **36.88–46.32 µs** 和 **36.90–46.46 µs**，而 MC2 记录分别约 **160.4 ms** 和 **8.2 ms**。第 14 层的 gate 有 4 卡更长、4 卡更短；因此所选 gate 自身的耗时差不能解释 MC2 约 152 ms 的差距。实际路由分布、有效工作量及中间 tensor 身份未绑定，不能排除它们的影响，也不能据此判断线上耗时或根因。

这两个观察用于确定下一步核查和融合边界，不能把这些单项相加为端到端耗时，也不能与另一轮无 profiler 的吞吐直接相除推导提速。

一个“时间被重叠”的具体例子：同一 EP8 样本的 norm、RoPE、scatter 与另一流的量化矩阵乘，四个设备记录时长相加为 **641.09 µs**，但它们在时间轴上的区间并集只有 **330.93 µs**。其中 scatter 的 258.10 µs 与矩阵乘相交 239.42 µs，约占 scatter 记录的 **92.76%**。这只是所选记录的时间重合，不能证明对应硬件流水一直有效工作、没有争用或属于请求关键路径；融合后依赖和争用可能改变，因此既不能宣称直接省下 258.10 µs，也不能把其余 18.68 µs 当作真实提速上限。

该样本的 RMSNorm 设备记录还列有 FLOAT `[8180,1]` 辅助输出。冻结源码中，无 residual 的特定 wrapper 分支只将主输出返回给后续路径，因此可以研究融合后保留内部行统计、但不对外发布辅助结果；归一化所必需的行归约不能省略。该辅助张量的逻辑大小约 **32 KB**，不是已测或可节省的 HBM 流量；历史分支、其他消费者和接口契约仍未绑定。

在另一批基线 profiler 的 **1,920 个已归属层窗口**中，所选主流矩阵乘与另一流形状相容的 scatter 记录也都出现区间交叠：逐窗计算后，交叠时长中位数为 **22.83 µs**，两条记录的区间并集中位数为 **53.56 µs**。这扩展了时间线观察范围，但两者的实际 tensor、事件依赖及是否争用仍未知；不能将交叠时间称作已经隐藏的通信，也不能据此计算线上收益。

同一批窗口中，按形状与注意力前的顺序选出的主流 RoPE 候选均在该 scatter 记录结束之后开始，间隔中位数为 **0.620 µs**，范围为 **0.520–1.020 µs**。这是一致的导出时间关系，但跨流时间口径、事件对象及数据身份尚未闭合，不能把它解释为 RoPE 等待 scatter 或可消除的等待。

另一组 EP0 第 0 层的同流记录依次出现动态量化、INT8 矩阵乘、`DequantSwigluQuant`、INT8 矩阵乘和加法，首末跨度约 **219.10 µs**。其中前四条已由所记录的主机调用栈和 flow 支持其 shared expert 调用角色；历史加载源码版本及相邻任务的张量身份尚未闭合，不能仅凭顺序认定实际数据边。中间 INT32 `[595,4608]` 的逻辑大小约 10.97 MB，不等于实际 HBM 搬运量。

在两组不同的重型 profiler 批次中，按同卡同层对照了 **32 对**导出签名仅物理行数不同的动态量化任务：595 行增至 1,023 行（约 1.72 倍），任务时长之比的中位数为 **1.24 倍**，范围 **1.03–1.39 倍**。在相同 32 对范围中，另外三条同流、形状相容的第一投影、激活量化和第二投影记录，时长比中位数分别为 **1.369、1.422、1.293 倍**；四个中位数可能来自不同样本，不能相加。除上文所述单个样本的调用角色外，这些任务的实际模块归属尚未逐项绑定，各记录的张量身份也未知。每个任务的有效行和输入内容未知；这只能说明用固定每行耗时线性外推这两档记录不可靠，不能认定固定启动开销、瓶颈原因或线上收益。匿名配对时长可由同目录的聚合和脚本复算。

同一采样范围还有 `HcPre` 和 RMSNorm 两项相邻记录：前者产生 BF16 `[595,5120]`，后者输入形状与之相容。冻结源码的对应路径中，HC 混合结果送往归一化和注意力，但 HC 产生的其他系数还分别供注意力后的残差合并、后续前馈使用。因而研究 HC 与归一化融合或分拆流水时，不能只处理送往归一化的输出；这些系数和原始残差的生命周期也要保持。具体采样尚未绑定这两个任务的 tensor 身份或运行分支。

对同一次重型采样中的 HC 任务，按同卡、同层、同一算子筛出两次签名相同且记录区间不重叠的调用，共 **2,560 对**。在两组 1023 行的 `HcPost` 中，逐对计算第二次/第一次时长，组内中位分别为 **0.863 和 0.856**；其他两组较小形状的中位分别为 **0.974 和 0.998**。对照的 `HcPre` 四组中位为 **0.990–1.029**。这是带 profiler 的所选记录，不能仅凭相同签名认定两次输入或工作量相同，也不能据此归因或预测线上收益。

对其中两组共 **1,280 条 HcPost**，逐条检查同设备、同层范围内经 host flow 关联且有 kernel CSV 的其他已选任务，其导出区间均未与 HcPost 直接相交。这只排除了这些已选记录的直接时间重叠；范围外任务、未导出的事件、前序活动、内部等待与资源争用仍可能影响时长，具体原因尚未确定。

压缩缓存还有跨模块状态约束：在源码的一个两 token 压缩分支中，当前完成行、写入的压缩槽和 RoPE 读取的位置是不同坐标。例如在满足相应有效性条件的假设中，位置 101 的行需结合 ring 中位置 100 的状态，压缩槽为 50，而 RoPE 使用位置 100。重组时不能把这几个数字互换；这是源码条件推导，不是历史请求的实测位置。

对主 Q 和 Indexer Q 的量化复用候选，现有 EP3 第 36 层重采样中，两条动态量化及各自后续投影均已分别关联到主机调用栈和设备任务。两次量化记录的输入都是 BF16 `[1023,1280]`，时长分别为 **19.580 µs** 和 **19.300 µs**。这比仅靠相邻形状推测更能支持两条分支确实存在；但两个输入的 tensor 身份、是否被修改、量化数值规则和存活期还没有绑定，所以不能断言能共享，也不能把 19.300 µs 当作可省时间。

这两条后续 Q 投影的已选设备记录均为 INT8 输入、BF16 输出，并各带 BF16 `[N]` 与 FLOAT `[1023]` 输入；按输出宽度 `N=32768/4096`、全部 1023 行均执行传统稠密运算的假设，两者逻辑乘加量为 **42.91G/5.36G MAC**，时长记录为 **307.92/50.86 µs**。这是条件账本除以带 profiler 的时间，不是实际执行量或硬件吞吐；两次输入的存储身份与有效行仍未知。

该样本中，两次量化之间还记录了主 Q 投影及一次旋转；重组时必须考虑中间读写和同步，不能仅因形状一致就复用缓冲。安装包文档将省略输出类型解释为 INT8，与另一条件路径显式指定 INT8 相容；历史后端是否执行同一确定性量化、两次读到的值是否一致，仍需证明。

这一链条提示一个融合条件：**如果**中间量化按整行最大绝对值计算 scale，且要求逐元素保留原量化结果，那么只看见半行时通常无法最终确定前半行的量化结果，因为后半行可能改变 scale。实现仍可按行或分块处理，或使用暂存、回写、重算等方式；当前采集尚未绑定这次量化的具体语义，不能据此断言历史算子一定遇到此屏障，也不能推算收益。

### 当前排查优先级

| 优先事项 | 已有线索 | 现在还不能回答 |
|---|---|---|
| MoE 复合任务 MC2 | 32 个卡与批次摘要组合中，MC2 都是已选设备任务里区间并集最长的单类；同层 1,280 组中，MC2 的 AIC MAC 导出比例低于 attention 的有 1,219 组，AIV vector 比例低于 attention 的有 1,280 组 | 两类任务工作量和分母不同，不能证明全模型最低利用率，也不能认定是通信等待或估计线上收益 |
| KV 写入与前处理 | norm、RoPE、scatter 的 1,280 组相容任务中，scatter 为单项最长的有 1,207 组；部分 scatter 与其他流的矩阵乘记录重叠 | 尚无张量身份和依赖，不能把任务时长直接相加或当作可节省时间 |
| 理论极限 | 已建立依赖与资源的条件模型，并发现可以收紧的受限算子模型 | 缺少适用设备的硬容量和真实必要工作量，无法声称数值 TPS 上界或与上界的真实差距 |

以上是带 profiler 的既存采样及条件推导，服务基线来自另两轮无 profiler 测试；不能混用两者的时长。

上述排序的覆盖有一个具体缺口：在同一批目标层的关联筛选计数中，**3,840 条通信名称对应的关联记录**因为设备记录缺少名称或任务身份而未纳入可匹配任务，其中 `hcom_allGather`、`hcom_alltoall`、`hcom_reduceScatter` 各 1,280 条。这是被选 flow 的记录计数，不等于 3,840 个独立设备任务，也不能推算遗漏任务的耗时。它说明现有已匹配任务的排名无法覆盖这些通信记录；不能因此断言通信最慢、空闲或是 MC2 的根因。

从同批次已匹配记录再看时间重叠：按单卡、单批次各自的 40 层划成 **32 组**，计算每组 MC2 区间并集与其他已选任务并集的交集，再除以该组 MC2 区间并集，所得比例范围 **0.19%–91.81%**，组间中位数 **71.66%**。每组 MC2 都处于同一 stream，所选同 stream 其他任务没有与 MC2 区间相交；观察到的交集来自其他 stream 的已选记录。组间工作量没有匹配，交集也不证明数据依赖、通信正在传输、关键路径或已获得隐藏收益；未匹配事件和跨轨时钟口径限制同样适用，不能将这个比例当作可节省时间。

### 模块比较中能确认什么

在另一组已归属的 target 40 层采样里，第 0 层按 16 个芯片各 3 个窗口汇总，平均窗口时长约 **1.420 ms**，是该组 40 层中最长。再按配置记录分成 DP0 和 DP1 后，第 0 层每组各有 24 个窗口：两组的窗口时长中位数分别约 **0.829 ms** 和 **2.142 ms**，其中 MC2 单任务中位数分别约 **0.354 ms** 和 **1.662 ms**。两列中位数不一定来自同一窗口，且不同芯片的窗口未证明属于同一请求。

这组数据说明：第 0 层值得继续调查，且不能把 16 芯片平均值当成每个芯片的情况。DP1 的 MC2 在该组选定记录的 AIC 周期分母中占约 **88.51%**，其 MAC 活动代理约 **1.49%**；这是导出计数的加权统计，不能解释成芯片空闲百分比、等待时间或已经找到原因。两组专家有效行数、路由、请求状态及内部阶段均未匹配，不能认定 DP1 较慢是通信造成，也不能推成线上整体速度差距。

同一组 40 层窗口中，1,920 条 `SparseFlashMla` 的 AIC MAC 活动代理为 **3.12%**，但 AIC scalar 活动代理为 **57.35%**；另一个独立分母的 AIV vector、scalar 代理分别为 **2.78%**、**53.03%**。因此只看低 MAC 会漏掉同一任务报告出的其他流水活动。这些值是按对应引擎报告周期加权的计数，不同流水可能并发，不能相加或用差值算空闲；当前也不能仅凭较高 scalar 指标认定控制流是瓶颈。导出工具版本与指标定义的精确绑定仍待核实。

对后文的 INT8 小矩阵乘，也从同次已冻结采样中精确定位了一条：EP8 第 24 层记录时长 **25.980 µs**，其导出 AIC MAC、MTE2、scalar 比例分别为 **11.2%、61.4%、44.1%**。这些流水可以交叠，三项不能相加，也不能把 MTE2 比例当成 HBM 带宽利用率。该条在数据库中的任务标识被复用，尚未绑定具体上层调用与 tensor，因此不能仅凭这些指标断言是搬运、计算还是调度导致了耗时。

进一步按相同物理签名检查全部 1,920 条记录：单任务时长中位数 **25.600 µs**，范围 **23.040–32.739 µs**；按 AIC 周期加权的 MAC、MTE2、scalar 比例分别为 **11.13%、61.44%、46.29%**，三项均有完整的正周期和有效比例。按两个数据并行组分别汇总，任务时长中位数为 **25.4895 µs** 和 **25.7095 µs**。它们仍是同次 profiler 的选定窗口，形状一致不保证有效工作量相同，不代表线上性能或其他算子；指标也不能相加或单独用于归因。

## 二、基线与测量边界

| 项目 | 口径 |
|---|---|
| 模型和精度 | DeepSeek V4.1 Flash，W8A8；部分模块可采用混合精度 |
| 服务 | vLLM-Ascend；分析对象为本次冻结配置 |
| 单次负载 | 8 个并发请求，每个输入 32,768 tokens，目标输出 1,024 tokens |
| 前缀命中 | 每轮聚合命中 235,904 / 262,144，约 89.99% |
| 基线结果 | 两轮共 16 个成功请求、16,384 个输出 tokens，两段 AISBench 窗口相加约 31.517 秒，约 519.84 输出 tokens/s |
| 草稿计数 | 两轮服务计数差值：草稿 token 8,755 / 8,730，接受 6,447 / 6,456；比例约 73.64% / 73.95% |
| 性能采集 | 另有开启 profiler 的诊断采样；其任务区间不等同于无 profiler 的线上耗时 |

冻结服务配置请求 DSpark 草稿、每次最多 5 个候选。两轮的服务聚合计数分别为 **1,751 / 1,746 次草稿**，平均每次接受 **3.682 / 3.698 个**；这些是两个引擎的计数差，不是每个请求的接受率、模型精度或草稿独立耗时。指标抓取窗口与客户端计时窗口并非已证明严格重合，也未与 profiler 中的任务逐请求关联。不能凭该比例直接推算提速；不同提示、输出长度及采样条件会改变结果。

无 profiler 的两轮服务指标快照中，queue、prefill、decode、服务端 TTFT 各自都有 **8 次** histogram 观察增量，两引擎各 4 次。按各自 sum/count 算出的均值如下：

| 服务端指标 | 第一轮均值 | 第二轮均值 |
|---|---:|---:|
| 引擎排队 | 0.032 ms | 0.043 ms |
| prefill 区间 | 374.91 ms | 372.29 ms |
| decode 区间 | 14.663 s | 14.605 s |
| 服务端 TTFT | 750.01 ms | 749.23 ms |

当前容器的 vLLM 源码将 queue 定义为引擎记录的 queued 到首次 scheduled，prefill 为首次 scheduled 到首个生成 token，decode 为首个到最后一个生成 token；preemption 可以包含在后两段内。这是**当前源码口径**，历史服务的实际加载版本尚未绑定。各项是完成请求的聚合观察，既不是设备计算时间，也不能把 8 个请求的时间相加当作墙钟；不同指标的观察与客户端请求未逐个绑定。每轮两个 seed 在 before 之前发送并等待空闲，计数与 8 条正式请求相容，但不能完全排除迟计或其他请求。

如果进一步证实每轮 8 次 queue 观察恰好对应这 8 个客户端请求、各值非负且上述源码口径适用，那么每个请求的该 queue 区间最多为该轮 queue 总和 **0.257 / 0.342 ms**，不足以单独解释客户端首条 SSE 超过 300 ms 的间隔。这只涉及首次调度前的引擎队列区间；进入引擎前、首次调度后的等待、逐步调度开销和网络等仍需独立分析，不能由此认定全部调度开销很小。

对已有的 8 请求重型诊断，客户端记录的首条非空文本 data 行出现在请求开始后 **6.26–9.62 秒**；无 profiler 基线同轮首条已记录 SSE data 行为 **0.30–1.10 秒**。重采请求列表摘要与冻结负载相符，8 条输出与参考匹配，但两个客户端的计时点不同：重采在 JSON 解析后记时，基线在解析前记时；重采还同时开启 profiler 与日志 hook，服务进程、缓存和发起方式也不同。由此不能把差值归因于 profiler 或 NPU，也不能把首个文本块直接称作服务端首 token 时间。现有匿名标识未能将这些客户端响应绑定到具体设备任务。

该诊断还使用了记录层调用的 hook。保存的 hook 源码显示，它会在调用前后写日志并进入 profiler 标记范围；如果历史加载的正是该版本，它可能带来额外主机侧开销。现有无 profiler 基线与诊断并非同一请求，不能把两者的差异单独归因于 profiler，也没有测出 hook 的独立开销。

另外核对无 profiler 基线的客户端流式接收：两轮分别合并 **1,759 / 1,754 个**请求内相邻 SSE 行间隔，中位数为 **65.33 / 65.13 ms**，P99 为 **73.76 / 78.07 ms**；每轮均有 11 个间隔超过事后选定的 100 ms，8 个请求均参与统计。SSE 行可能为空文本或包含多个 token，这些数不是逐 token TPOT；同一请求内的间隔相关，客户端缓冲、网络与服务端阶段也无法从该记录拆开，因此不能用长间隔直接认定设备空闲或调度故障。

约 65 ms 的行间隔与约 14 ms 的客户端 TPOT 代理使用不同分母：对同一请求的首末行时间差，前者除以记录行数减一，后者除以 1,023 个输出间隔。两者数值之比因而是 `1023/(记录行数−1)`，不能把这个差值当成额外的设备或调度等待；也不能把该比值当作已测出的每行 token 数。

从客户端开始 POST 到各自最后一条已记录 SSE 数据的区间看，两轮分别有 **96.35% / 92.13%** 的测量窗口内 8 个请求都处于该区间；按时间加权的区间内请求数为 **7.860 / 7.755**。因此客户端发起时间的错开不能解释大部分窗口没有同时存在 8 个这类区间。这不证明 8 个请求均已由服务端接收、同时执行或占用 NPU，也不说明它们各自处于哪个推理阶段。

吞吐分母是两轮各自 AISBench 窗口之和，不是各请求延迟相加，也不是两轮连续运行的总墙钟：在所核对客户端正常路径下，每轮从最早请求 POST 前的时间点算起，到各请求最后一个非空、非注释、非 `[DONE]` SSE 数据块的最晚记录时间；该时间点在 JSON 解析之前，未包含完整 HTTP 结束或两轮之间的准备和等待。每轮预先向两个 DP 副本发送前缀 seed 的时间也不在这两个窗口中。两轮约 0.30–1.10 秒的首条非 `[DONE]` SSE 数据块不能严格证明含首个生成 token，也无法拆分服务端排队、prefill、采样和网络返回，不能把它直接称作精确 TTFT 或 prefill 时间。

如果用两轮各自 AISBench 窗口之和作分母，两轮 **524,288 输入 tokens / 31.517 秒 ≈ 16,635 输入 tokens/s**；这包含命中前缀，且分母包含生成阶段，不是单独的 prefill 计算速率。两轮前缀查询数减命中数合计 52,480，除以同一窗口之和约为 **1,665 查询差额/s**；这只是计数差额的归一化，不能代替实际执行的 token 数、prefill 用时或硬件计算吞吐。

此结果仅适用于所述模型、并发、上下文长度、缓存命中情况与配置。不同的输出长度、请求分布、草稿接受情况、批次结构、缓存状态和设备竞争都会影响数值。两轮样本也不足以确定长时间稳定吞吐或尾部延迟。

## 三、融合与结构重组：已查到哪里

排查结合冻结源码及已保存的目标层 profile，覆盖注意力输入和缓存、Indexer、MoE、HC、Engram、输出与草稿模型中的一批路径，考虑了两算子、多算子、跨模块并行和拆分重组。**覆盖的是已检查的源码分支与被采到的窗口，不是对所有分支、请求、动态形状和图重放的穷尽证明。**

覆盖台账中有 12 个模板、每个模板各登记两算子、三算子、多算子、拆分重组、跨模块和多消费者 6 类，共 72 条记录。其中 48 条标记为结构扫描，另外 24 条仅标记为已知组合阶段或原始模板的部分覆盖；72 条的语义证明标志均未完成。这些是台账条目，不是 72 个已证可融合的机会，也不代表原始算子图的边已全部展开。不同模板使用的图版本并不统一，跨模块图也尚未并入所有更新后的细化图；因此仍需补齐具体数据边、消费者和动态分支，不能据此宣布全模型扫描完成。

在冻结的 DSpark 非 causal metadata 构造路径中，可研究让索引与长度生成器直接写入图重放使用的两个固定缓冲，减少临时张量到固定缓冲的复制。现有 `indices_output` 或 `buffer` 参数会令指定的 Triton 分支条件不成立，转到另一条仍有复制的路径，不能视作现成的直接写入开关。新接口须保证前一轮异步读取结束后再覆盖，并保证本轮索引和长度对各消费者均可见；图重放地址、空行和并发也需保持。历史样本尚未将生成任务和两次复制绑定为同一次调用，所以不能估算实际可省时间或 HBM 流量。

对其中一个既有采样窗口，索引生成任务之后的同一设备流上紧接两条 `aclnnInplaceCopy` 记录，时长分别为 **0.800 和 0.760 µs**；三条任务的主机出队记录也在同一线程内按序出现。记录没有复制的源、目标、大小或 Python 栈，因此仍不能确认复制的是上述索引与长度，也不能把时长当作融合收益。针对关联队列的有限数据库查询遇到 I/O 错误，需有效一致副本或其他证据才能继续确认。

草稿拒绝后的恢复采样还有随机数依赖：冻结的 PyTorch fallback 为每个请求生成一行随机向量，同一请求的多个草稿位置复用这行向量。改变成每个位置独立生成，可能改变各位置的恢复候选；源码还会在特定条件下推进零草稿请求的独立生成器。重组时需要明确是保持逐 seed 和后续随机状态，还是只要求输出分布等价，并分别证明。这里尚未确认历史运行选择该 fallback，候选差异也不直接证明最终输出变化或性能收益。

进一步核对已保存的两次 profiler 客户端及无 profiler 测量配置，它们都指定了 `temperature=0`。按保存的请求转换和采样源码，若运行时保留该温度、批次没有混入非 greedy 请求且实际 `all_greedy=True`，就会在 greedy 分支返回，不进入上段的随机恢复路径。因此该随机向量约束**不能直接当作当前基线的热点**；历史批次成员和实际 metadata 尚未绑定。即使是 greedy，源码中的 synthetic 模式仍可能生成其他随机数，不能笼统断言没有随机操作。

一个所选 gate 任务还导出了完整形状的第三输出；保存源码中该输出是否写回受标志控制，调用接口要求输出 buffer 不等于已执行完整写回。因此不能直接把该输出的逻辑张量大小算为可节省的内存流量，历史标志和运行内核仍未知。

Engram 的另一处条件性边界是先对完整请求 chunk 计算 hash，再选取本地需要的行。可以研究直接生成所选输出，但不能简单地先丢掉未选输入：它们可能是所选行的 n-gram 历史，或参与可选的跨调用缓存状态。重组还需保留请求边界、缓存写入与可见性、所选行顺序以及 mask 的发布时机；历史是否执行这条路径及其收益尚未确认。

压缩注意力的 ratio-2 池化还有一个更小的内部重组候选：当一个完整 token 组跨越输入分段时，保存源码从 ring 读取旧值、从当前投影读取新值，并在该分支三遍读取 score、两遍计算指数。可研究局部保留并复用这些值，但必须保持旧值读取、ring 更新顺序、数值舍入和后续归一化；非跨段的另一个分支已复用指数。尚未证明历史采样进入该分支或编译后仍有重复读取，不能把源码级操作次数直接算成 HBM 流量或收益。

对两个 token 的池化，稳定 softmax 加权可在实数中改写为 sigmoid 差值表达式；但 CPU FP32 算术模型的一个有限输入反例中，两种写法随后转成 BF16 分别得到 **59.75** 和 **59.5**。这证明数学等价不足以保证该模型下逐位一致；实际 910C 指数、归约、舍入和精度容差尚未绑定，不能据此声称设备上发生了同样差异或重组一定不可行。

末层 HC 混合与归一化还有条件性融合空间。已有一组 Cast、Mul、ReduceSum、Cast、RMSNorm 记录的形状和顺序与源码路径相容；进一步检查发现五条记录共用的连接号在该数据库被大量复用，且按该编号没有找到相应主机 API 关联。因此当前不能仅凭顺序和形状认定它们属于同一次实际张量链，需换用其他身份或调用证据再判断。

对两种 shared expert 投影形状，还可以给出一个有条件的融合约束：如果 INT8 点积以零初值精确累加到 INT32，中途没有缩放、偏置或其他舍入，则 K=5120 与 K=2304 的任意部分和绝对值最多分别为 **83,886,080 / 37,748,736**，不会溢出 INT32。该条件下可改变整数乘加的分组与求和树，而不必保留原加法顺序。历史任务是否满足此整数契约还未验证；之后的激活、逐行量化和舍入仍需单独保留。

对 MoE 已有复合算子的内部重组，保存的源码将两次矩阵计算的输出指向同一工作区。一个条件性地址例子说明，**不能只按相同行号确认是否可以提前写入**：若第一组至少两行，第一输出行宽 4608、第二输出行宽 5120，均为连续无填充 FP16，则第二输出的第 0 行末 1024 字节会覆盖第一输出第 1 行的开头；须等后者对应区间被最后一次读取后才能覆盖。独立缓冲或不同布局可改变这一约束。历史调用的实际行数、布局与二进制尚未绑定，这不是已发现的数据竞争或性能收益。

需要注意，[CANN 8.5 的量化矩阵乘接口文档](https://www.hiascend.com/document/detail/en/canncommercial/850/API/aolapi/context/ops-nn/aclnnQuantMatmulWeightNz.md)允许 A3 在相关组合中使用 BF16/FP32 权重 scale 和 INT32 输出，通用公式包含 scale。不能因为输出为 INT32，就假定整个算子等同于未经 scale 处理的整数点积；历史版本和具体调用的 scale 处理仍待确认。

Indexer 的 INT8 key 和 FP16 scale 在条件源码路径中分开写缓存。若两个输入行写到同一 slot，而两次写的赢家可以不同，仅等待两次写入完成并不能保证最终 key 与 scale 来自同一行；融合成同一 kernel 也不自动提供跨内存原子发布。重复 slot 和具体后端在历史采样中未知，因此这是需要核对的语义边界，不是已发现线上错误。

压缩注意力的非 packed 源码路径还显示：算子 metadata 取自 long-KV 字段，而原始窗口的索引和长度取自 SWA 字段；显式等待使用所选算子 metadata 的对象标识。重排两路计算或 metadata 构建时，需要分别确认这些数据如何就绪及彼此是否一致。SWA 也可能已由同流顺序或其他等待保证就绪，现有证据不能据此断言缺同步或数据竞争。

同一源码的 metadata 构建路径按压缩比使用不同缓存键：SWA 为 `smla:c0`，压缩 long-KV 为 `smla:c1` 或 `smla:c2`。即使两次构建共享字典，命中一个键也不自动命中另一个；但键不同不证明实际对象、存储或任务不同，历史缓存命中与生命周期尚未绑定。

对 Indexer 权重缩放的一个候选：在投影结果已按 BF16 舍入、实际缩放标量恰好为 1/64、按指定 IEEE 最近偶数舍入且没有不兼容的下溢处理时，CPU 数值模型遍历全部 65,280 个有限 BF16 编码后，先在 BF16 缩放再转 FP16 与原 FP32 缩放后转 FP16 的位模式一致。这只覆盖最终 FP16 可见结果；历史标量编码、设备舍入、张量身份和 packed 分支尚未绑定，不能据此断言实际设备等价或提速。

在部分层可研究把 SP 输入 gather 放到 Q_a/KV 投影之后：按保存维度、假设张量均为 BF16，原输入一行是 10,240 字节，两个投影结果合计 3,584 字节。这只是逻辑张量大小，不是网络流量或节省。Indexer source 层还需要本地 query 的原 hidden；其中同时负责 KV 压缩的层还需要全局 cache hidden 或经证明等价的信息。CP/PCP 行域、通信组、权重一致性和精度等价仍须证明，不能直接删掉原 gather。

对于所选第 36 层，如果进一步证明 Q_a 和 Indexer 的原 hidden 消费都能在本地满足，并且全局只需收集 KV 投影，可研究另一种结构：先本地投影，再收集 512 维 KV。这时按 BF16 逻辑张量大小算，候选 gather 输入是原 5120 维 hidden 的 **10%**；前面的 35% 则是假设同时收集 Q_a 和 KV，两者是不同方案。该单卡样本缺少张量身份及其余 rank 的绑定，还须证明 padding、行序、权重和数值等价及其他消费者；10% 不是实测网络流量或提速。

另一项跨模块候选来自 DSpark 辅助状态：在三个目标层均被配置、启用 SP 且各 rank 的行域与通信组一致等条件下，可研究先保留各层本地 mean，再合并通信并恢复三个列表项。实际安装的层列表、运行分支和通信身份尚未绑定；重组须保留每层的快照、行顺序和所有消费者，并重新核对各 rank 之间与其他 collective 的顺序。合并通信可能推迟较早状态的就绪、失去已有重叠，不能按调用次数估算收益。

对同一摘要选出的 8 个层范围，形状相容的局部投影记录中有 7 条是 1023 行、1 条是 1019 行；另一类全局 KV 形状记录均为 8180 行。`7×1023+1019=8180` 只是形状算术，不能证明它们属于同一通信组或对应相同 token。若假设直接将这些行投影后作为一次 gather 的发送缓冲，[CANN 9.1 HcclAllGather 文档](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/commlib/hcclug/docs/en/api_ref/comm_op_interface/HcclAllGather.md)要求各 rank 发送数量一致，就需要核实等长打包或另一种支持变长的协议；这不是原历史通信发生错误的证据。

对这一候选，保存的量化描述和解析源码进一步表明：如果实际配置和映射与快照一致，Q_a 和 KV 投影会选择非量化线性方法，但历史运行实例尚未绑定。一个现有采样中，与 Q 和 KV 投影形状相容的任务分别有 3 行和 24 行，提示必须分别处理 query 和 cache 的行域；不能仅凭形状证明它们属于同一数据链。

保存的 SP 和 legacy CP 源码都按 TP rank 对 token 行做连续切分。若两边 token 数、顺序和 rank 映射一致，可研究直接在本地生成本 rank 的 Q_a，不必先收集所有 Q_a；KV 仍需要全局 cache 所需的数据。真实通信组、行顺序和张量尚未绑定，空 query rank 也不能随意退出集体通信。

对 EP3 第 36 层的一个诊断范围，现已将 attention 输入 AllGather 和三个后续投影分别关联到同一 host 层范围、调用栈、flow 和设备任务。其形状与本地 Q、全局 KV 和本地 Indexer 权重投影相容；这比仅比较形状更强，但尚未绑定张量存储、历史源码哈希和跨 rank 行顺序，不能断定数据链或重组收益。

进一步核对该 AllGather 的通信标识：它在同一采集数据库里唯一匹配到一个标为 TP 的 8 rank 组记录，类型枚举显示 BFP16。但相关主机调用没有导出输入形状或 dtype，也没有张量存储标识；通信计数不等于物理网络字节，不能据此认定它与投影使用同一张量。

更外层的 PyTorch 调用记录显示两个 BF16 缓冲形状为 [8184,5120] 和 [1023,5120]；若历史接口与现安装源码一致，它们分别是 gather 输出和输入。记录中还出现以 [8184,5120] 为输入的 slice，但缺少切片参数、输出形状及张量身份，不能证明它产生了后续投影的 [8180,5120] 输入。对原始 op-range 的三个时间相近候选进行有界检查，也没有找到可用于比较 storage 的 tensor 字段；该结论只覆盖这些候选。

关于 KV 融合的计算顺序：在无 bias 的理想实数模型里，若 RoPE 一个旋转对的两个 norm 权重不同，且该次旋转的正弦不为零，逐维权重与旋转一般不能直接交换。例如一对输入 `(1,0)`、权重 `(1,2)`、余弦和正弦 `(3/5,4/5)`，权重后旋转为 `(3/5,4/5)`，旋转后权重为 `(3/5,8/5)`；共同的 RMS 分母不改变差异。这是构造反例，不代表实测权重或证明无法按原顺序融合。真实精度和舍入仍需验证。

对 Q/KV 共同输入的源码补查：在特定 legacy CP 非空分支且 metadata 由同一 builder 正常构造时，局部 Q 的输入行是全局 KV 输入的连续子视图，可研究共享读取或投影重组。但历史样本尚未绑定该分支；本次冻结量化描述将这两个投影标为 FLOAT，不能据此说存在可以消除的重复动态量化。

同一 CP 源码用全局 RoPE 缓冲区的切片给局部 Q，避免对共享缓存再次 gather 后覆盖尚未被 KV 消费的数据。重组须保留缓存别名和读完成顺序；这是一项已有防护，不是观察到的运行故障。

对 Engram 的 826 条正常配对调用进一步复核，有 168 对相邻调用在同进程、同线程下记录了相同的 storage wrapper token，offset 依次为 0 和 24。若留存的观察器源码就是实际运行版本，这支持它们观察到同一个 Python 包装对象；但尚未绑定具体层、设备消费者或事件，函数返回也不等于设备异步读取完成，不能因此认定两次查表可以安全合并。

保存的 Engram 查表源码还显示，非本分片 ID 会先映射到本地第 0 行，源码表达读取后把该行输出写零。可研究屏蔽无效 ID 的读取，但需保持零值写入、量化格式及事件依赖；当前没有历史运行分支、无效 ID 比例或实际访存证据，不能估算收益。

路由候选的适用性修正：冻结的视觉路由 Python 回退函数对部分文本行会以查表 ID 覆盖动态 TopK，理论上可研究只计算选中专家 gate。但已有镜像构建信息为 A3，冻结的 A3 硬件 profile 支持对应视觉融合算子；**如果历史进程使用该源码和 profile，这条 Python 回退就不会被选中**。配置中缺省 hash 层数按冻结解析链也会归零。历史进程的实际对象和源码身份尚未绑定，所以不能绝对排除其他运行情况；当前应将这一回退视为参考结构，不计作已命中的基线优化机会，并转向已有复合算子及上下游依赖。图像行仍依赖动态选择。

对保存的 A3 原生融合算子源码进一步检查：在无分组、存在哈希表且为文本行的分支中，算子已经按表选择专家并跳过动态 TopK，但仍先为整行专家计算 score。若实际命中该分支且完整 score 没有其他消费者，可以研究提前选取并只计算所需 score；当前尚未绑定历史哈希表、具体二进制和数值契约。原生算子的权重归一化使用 `sum + eps`，与 Python 回退的 `clamp_min` 公式不能直接互换；这一源码差异本身不证明实际发生了精度问题。

在保存配置未经运行期注入、按冻结代码构造且无哈希表的条件下，文本路由需要按全部专家的 score 加 bias 做动态 TopK，不能直接套用按表只计算所选专家的方案。另一条可研究的结构是将 gate 按专家块计算，与局部 TopK 合并后得到全局 TopK，以减少中间 logits 的物化；仍须保留全部专家对排序的影响、tie/NaN 和浮点次序，并确认 logits 的其他消费者及 dispatch 接口。源码条件不等于历史调用已绑定。

对动态路由还有一个条件性重组：若能为每个专家的实际排序分数建立包含浮点误差和 bias 的严格上下界，且已有 K 个不同专家的下界都严格大于某个未完成专家的上界，则这个专家不可能进入 TopK，可以研究提前停止计算该列。等号不能直接使用：相同分数时原实现的 tie 规则可能决定该专家应被选中。生成界、读取范数、同步以及完成选中专家的原始 score 和归一化都有成本；尚未证明实际历史调用可获得这种证书、可以剪掉任何计算或带来收益。

分块合并还有一个具体的正确性约束：[CANN 8.0 Sort 文档](https://www.hiascend.com/document/detail/en/canncommercial/800/apiref/ascendcopapi/atlasascendc_api_07_0842.html)描述等分时保留输入顺序。若原先专家 0、1、2 分数相同、取前两个，按块重排为 0、2、1 后再稳定排序会选出 0、2，改变原结果。若该文档语义适用于历史算子，局部和全局合并都必须保留原始全局 tie 顺序；历史版本、NaN 和数值一致性仍需核对。

冻结源码的条件路径还包含逐层查表、必要时的跨 rank 通信和逐层 ready 事件，mask 则有独立事件。联合读取必须保留相应通信、数据发布和 buffer 生命周期；现有对象观察与设备事件来自不同采集，不能把它们拼成已证实的运行依赖链。

以上是**分析候选**，不是已经修改或验证的融合方案。部分复合算子本身已经包含多个步骤，例如采样到的 `DequantSwigluQuant`；不能把其中反量化、SwiGLU 和量化重复算成三项尚未实现的融合收益。单纯减少任务数，也可能损失已有的并行或增加 Cube、Vector、搬运资源争用。

已登记的 32 条融合与重组边界、既有复合调用及覆盖缺口，见 [融合扫描清单](FUSION-INVENTORY.md)。清单包含条件候选和语义未知项，不代表所有组合已经可以实现。

## 四、局部采样：优先调查什么

### 4.1 融合 MoE 的 AIC 活动代理

对同一 EP8 采集的两个 MC2 样本，进一步检查数据库中同设备的其他流：第 14 层的任务约 160.37 ms，其窗口内有一条 AI CPU 上的 `reduce_scatterAicpuKernel` 导出区间与之交叠约 95.23 ms；第 39 层的对照任务约 8.29 ms，未找到相交的 AI CPU 内核记录。这些是开启 profiler 的两个选定窗口，可能包含未记录活动，且实际路由及工作量尚未绑定。区间交叠不证明二者有依赖、占用同一资源或造成慢任务，也不能当作物理网络传输时间、线上时延或收益。此前按该层 host scope 选出的通信事件与 MC2 不相交；此次扩大到同设备其他流的数据库任务，筛选范围不同。

进一步追踪显示，该 AI CPU 记录关联到一次 `vllm::ascend_sp_reduce_scatter_impl` 主机调用；同次标记将该调用所在 host scope 的层号记为 23，而 MC2 锚点属于第 14 层提交范围。该主机调用还关联另一条通信大算子记录，导出坐标显示它在 MC2 结束约 227.46 ms 后开始。两条关联记录不一定表示同一物理事务，跨轨时钟误差及采集覆盖也未独立确认；因此不能把 AI CPU 的交叠当作该通信大算子或物理链路的交叠，也不能推定与 MC2 的依赖。

再核查该通信大算子关联的 168 条子任务：同库内每条都唯一匹配一条 TASK，按导出时间均不与第 14 层 MC2 相交，最早一条在 MC2 结束约 226.81 ms 后开始；这些子任务不包含前述 AI CPU 记录。这只覆盖该大算子已导出的子任务，不能推广到所有通信或排除内部同步。另外，该库中相同 notify 数字被多个通信算子复用，单靠数字相等不能配对事件或证明依赖。

该通信记录的组键与同库一个组元数据项精确匹配，元数据标注为 TP 组，成员数为 8，和通信记录的 rankSize 一致；设备与组内 rank 记录也相互吻合。这提高了组关联的可信度，但历史 exporter、元数据生成时点和组生命周期尚未完全绑定，不能由此证明同一次 collective 或与 MC2 的依赖。

同次采集扩展到 EP8–15：第 14 层的 8 个 MC2 窗口均与本卡其他流的 AI CPU 记录相交，其中 6 个窗口被一条 `reduce_scatterAicpuKernel` 记录完整覆盖；第 39 层对照的 8 个窗口均未查到相交的同类记录。每卡单独在导出坐标中计算，这些记录不证明同一通信事务、物理传输或资源争用，也不能由此认定慢任务原因；第 14、39 层的实际有效工作量仍未知。

进一步追踪 EP9–15 各卡的相交 reduce-scatter 记录，在各自数据库中都找到一个关联的 `HcclReduceScatter` 主机调用，其 sidecar 将所在提交范围标记为第 23 层；EP9 还有一条关联第 22 层的记录。各库对应通信记录与其 TP 组元数据的组键、成员数和本卡组内 rank 一致。不过，部分连接编号在库内被多个 ID 复用；关联并不证明这些卡在执行同一次 collective，也不能证明它们与第 14 层 MC2 存在数据依赖、资源争用或因果。模型实例、请求以及组元数据的生成和生命周期仍未完全绑定。

按相同规则检查另一批已保存的配对记录：其中一个匿名批次的 EP8–15，8 张卡上第 23 层主机提交范围关联的 reduce-scatter AI CPU 区间都完整覆盖本卡第 14 层 MC2 区间；另两个批次各有 4 张卡完整覆盖、4 张卡没有这对记录的交集。层标签表示主机提交范围，不是设备任务的排他层耗时；这些导出区间也不证明链路持续传输、同一请求或争用。不能把跨流、跨层标签的时长直接相加，也不能把一批记录推广为所有负载。

在上述两个各有 8 卡的批次中，进一步只比较第 23 层提交范围各卡选出的那条 AI CPU 记录自身时长：EP0–3 分别为 **0.176–0.221 ms** 和 **0.204–0.259 ms**，EP4–7 分别为 **27.891–27.981 ms** 和 **24.815–24.891 ms**。每卡单独计算持续时间，没有跨卡时钟相减。相同名称、层标签和批次摘要不能证明这些记录属于同一次 collective、拥有相同数据量或职责；记录时长也不等于物理网络传输时间，因此不能据此判断原因、隐藏量或端到端收益。

进一步在每张卡的既有数据库关联所选任务：两个批次各自的 8 条记录均可关联到 `HcclReduceScatter` 和通信 op，同一批次各卡记录的操作名称、op ID、count、BFP16 类型及 8 rank TP 组成员一致；每个所选 op ID 在各自数据库中仅出现一次。这比仅凭名称和摘要更支持它们属于同组、同类通信的候选关系。跨库 op ID 的生命周期和连接语义尚未完全确认，其中一条连接集合还包含事件记录，因此仍不能断定八条记录就是同一笔物理事务，或者确定通信双方的实际有效数据和时长差异原因。

在这 16 条关联通信 op 中，已有 `communication.json` 分别找到一个名称相符的条目，其 Elapse 字段均与各自数据库 op 区间的时长数值相同。两批次各卡的 Elapse 范围分别为 **0.295–0.308 ms** 和 **0.453–0.481 ms**；导出的 Transit 范围分别为 **0.193–0.213 ms** 和 **0.303–0.343 ms**，Wait 范围分别为 **0.090–0.107 ms** 和 **0.123–0.166 ms**。[MindStudio 通信分析文档](https://www.hiascend.com/document/detail/en/mindstudio/600/msug/msug_000227.html)提供这些字段的参考含义；历史 exporter 与文档版本尚未完全绑定。该结果增强了同库记录匹配，不是独立重复测量，也不能直接用来分解上述 AI CPU 的长区间、证明链路持续传输或计算可隐藏的时间。各字段范围来自不同记录，不能将范围端点相加。

进一步查看每个已选通信 op 的子任务：16 组中，最早的子任务记录起点都早于对应大 op 的导出起点，所以不能只看大 op 区间就排除更早的子任务。按同库导出坐标，14 组的所选子任务起点均在对应 AI CPU 记录结束之后，另外两组有部分起点落在该 AI CPU 区间内。跨轨时间转换、相对误差和 replay 身份尚未确认；这些只是所查子表的坐标关系，不能据此判定实际先后、依赖或其他通信是否重叠。

为核查时间口径，检查了当前安装的 profiler 分析器：它确实会按同设备坐标比较计算任务和通信 op。但所选的 **16 条 AI CPU 记录均未出现在该分析器所用的计算任务信息表中**，因此不能用这段分析器代码证明这些记录与通信子任务的时钟同步或误差。若要升级为实际先后结论，需要该次导出的转换版本、时钟锚点和相对误差界，以及相关 replay 和事件身份。

对后两个批次，事后选取部分有完整覆盖和部分无交集的卡，再分别用同卡第 39 层的 MC2 作时长对照：一批选中记录的第 14 层约 **25.50–25.60 ms**、第 14 层与第 39 层的时长比约 **2.64**；另一批分别约 **22.47–22.53 ms**、**2.79**。两种覆盖情况下都能看到这些量级，因此“本卡选中的这条 AI CPU 记录必须覆盖，才会出现上述量级”不成立。这是事后选样：零交集但第 14 层更短的三张卡未纳入这组对照，不能用它排除其他通信、跨卡依赖或资源争用。

继续检查 EP9–15 每卡该主机调用关联的另一条通信大算子及其 168 条已匹配子任务：按各卡自身数据库的导出时间，都没有与本卡第 14 层 MC2 窗口相交，最早子任务在各自 MC2 结束约 226.75–226.81 ms 后开始。这与 EP8 的限定结果一致；这些子任务不包含之前相交的 AI CPU 任务，不能代表所有通信或排除内部同步。不同轨的时钟和采集完整性尚未独立确认。

[昇腾 CANN 9.1 指南](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910/programug/Ascendcopdevg/docs/guide/%E7%AE%97%E5%AD%90%E5%AE%9E%E8%B7%B5%E5%8F%82%E8%80%83/%E6%80%A7%E8%83%BD%E5%88%86%E6%9E%90/%E8%8E%B7%E5%8F%96%E6%80%A7%E8%83%BD%E6%95%B0%E6%8D%AE.md)指出，部分产品的并发 GM 请求若落在同一 512 字节范围，可能因一致性而串行。对保存的 MC2 专家计数轮询源码作条件地址推导，不同来源与块的轮询起点至少相距 512 字节；但每次读取 32 字节，基址和读写并发未知，不能因此排除地址范围冲突，更不能断定本次慢任务由该机制引起。历史 kernel、shmem 映射与文档版本尚未绑定。

对选定的 16 rank、四个调度批次摘要及对应层范围，得到 1,280 个目标层 scope 的 MC2 任务关联。进一步按同一批次、层、算子名、物理形状、数据类型和格式筛选，要求参与该组的 8 个 rank 具有相同签名且任务数量一致；6,862 个签名组中有 4,930 组满足物理完整条件，其中 1,596 组具备有效 AIC 周期和指标。

为减少八卡同形状筛选造成的遗漏，另看 EP3 单卡一个摘要的 40 个目标层：1,580 条已匹配设备任务的时间区间并集为 353.614 ms，MoE 复合任务的区间并集为 156.640 ms，约占 44.30%。这是带 profiler、选定任务的区间比例，不是请求耗时或整机忙时；同步事件和部分身份缺失记录不在这个并集中，不能分解计算、通信或等待。

将同口径扩展到 16 张卡、每卡两个采样摘要，共 32 个卡与摘要组合：MoE 都是各组已选任务中区间并集最长的单个类型，占各组所选并集约 40.44%–90.79%。每组按本卡时间单独计算，不要求其他卡形状一致；这不是 32 次独立线上试验。被排除的同步事件、未关联任务和 profiler 扰动仍限制结论，无法据此算出 MoE 的线上耗时占比。

昇腾官方较早版本的 [op_summary 说明](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta1/devaids/Profiling/atlasprofiling_16_0067.html)将 Task Wait Time 定义为任务之间的间隔。一个 273.565 ms 的所选 MoE 设备记录，其导出的 Wait Time 为 1.111 µs，同流前一条已导出任务到它的间隔为 1.080 µs；这是同源数值对照，不能解释 MoE 内部等待，也不能证明该旧版说明就是本次 9.2 导出器的实现。

对同一长 MC2，已保存的通信分析文件中没有与它的导出数值时间区间相交的条目；两个文件的时钟、采集覆盖以及融合核内部通信尚未闭合，因此这不能证明没有通信或等待。昇腾提供离线解析接口，但重新解析会写入 profile，本次保留原始采集未重跑。

上述 4,930 个物理完整组里，672 组同时满足 AIC 与 AIV 各自的指标有效条件，924 组仅满足 AIC，3,294 组仅满足 AIV，40 组两项均未满足。两个榜单有交集，不能将数量相加；这些是已选任务组数，不能当成整机利用率或模型覆盖率。

排序还有一个重要限制：此前按原始 MatMul 名称列出的最低值，可能来自不同物理形状，不能当作该名称所有任务的统一利用率。例如一个摘要中最小组输出形状为 `[643,32]`，而最常出现的同名完整组输出为 `[643,1280]`；这两类不应当作等工作量。即使固定形状和八卡签名，MC2 各层有效专家路由仍可能不同。搬运任务的 vector 比例低也不能单独代表任务整体空闲。

另一次按形状分组的审计发现，部分同名算子的最低值落在少数组成的物理签名上。例如一个选定批次中，同名 RoPE 的最低 AIV 显示比例来自 4 个层组，而组数最多的另一形状有 40 个层组。形状及每卡任务数不同，该比较只说明按名称取最低可能偏离主形状，不表明实际空闲或可获得的收益。

解释 MoE 工作量时，仅知道专家接收行数的总和也不够：相同的总行数可能集中到一个专家，也可能分散到多个专家，而参考源码按专家分别调度。历史逐专家计数和实际容量仍未绑定；这个例子不证明某种分布实际发生或带来多少耗时。

在上述合格范围内，四批各自最低的 AIC MAC 活动代理均出现在 `DispatchFFNCombine`，对应层分别为 14、14、0、15；按 AIC 周期加权分别约为 **0.489%、1.627%、0.137%、2.786%**。这是对已采样任务的指标排序，不是全芯片利用率，AIC 与 AIV 也不应混为一个分母。不同专家实际接收的行数、有效 token 和路由工作量尚未绑定，因而即使形状相同也不能认定实际工作相同。

对其中一个摘要的第 15 层和第 36 层固定签名进一步比较：第 15 层八卡周期加权比例约 2.786%，但其中一张卡的记录约为 46.65%；该卡任务约 5.02 ms，另外七张卡约为 24 ms。第 36 层八条约为 3.50–4.74 ms。这是带 profiler 的选定任务，不是端到端延迟；不同卡的工作量、时钟同步和相互等待关系未绑定，不能由差异认定某张卡拖慢其他卡或认定通信是根因。

对其中一张卡的第 36 层进一步读取其他流记录，发现四条与 MC2 区间相交的 Notify_Wait，可在采集数据库里关联到一个 allGather 操作编号，而该 allGather 的整体通信记录出现在 MC2 结束后。这说明仅检查整体通信记录的时间范围会漏掉相关调度记录；现有证据没有绑定等待对象与 MC2 的数据依赖，也没有校准跨轨时钟，不能据此认定通信导致 MC2 变慢。

四条所选 Notify_Wait 均在 MC2 开始后启动、结束晚于 MC2 结束至少约 458 µs。在导出时间轴和完成边界可信的条件下，可排除 MC2 完成必须等待这四条记录全部完成；仍不能排除其他等待或争用。相同 notifyId 在该通信操作内多次出现，无法只凭 ID 唯一配对。官网对这些字段和通知操作有说明，但其版本与本次采集未完全一致。参见 [CANN 9.0 profiler 表定义](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/devaids/Profiling/atlasprofiling_16_1144.html) 和 [CANN 9.1 通信行为说明](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/910beta3/API/hcclug/docs/zh/user_guide/perf_analysis/profiling_op_behavior.md)。

对另一张卡的一条长 MC2 记录，CSV 将 vector 比例显示为 0，但同一采集数据库原值约为 0.041%，MTE2 比例约为 13.34%。因此不能以显示值 0 断定所有流水没有活动；MTE2 比例也不是墙钟占比、实际带宽或内部等待原因。

这个长样本所属的主机调度范围记录了 5,144 个调度 token，MC2 的物理输入为 643 行，8×643 恰为 5,144；但另一组调度总数为 8,180，8×1,023 为 8,184。形状与调度计数之间不能套用统一乘法恢复每卡有效行，更不能由此推算每专家接收数量或长任务原因。

该样本中，路由算子的 [643,6] 输出与后续 MoE 融合算子的相应输入在形状和类型上相容；输入布尔向量及整数输出只记录了形状。没有存储身份或元素值，无法确认实际有效 token、路由结果或各专家工作量。

该第 15 层中，高比例卡仅占所报八卡 AIC 周期权重约 0.969%，所以全组加权结果主要由其余七张卡决定；这解释统计结果，不能解释各卡差异的成因。对该卡的一个设备任务间隔回查，同线程的 gate 主机调用在导出时间线上持续约 2.05 ms，与间隔高度重合。另一张卡的对照中，gate 主机调用约 1.11 ms，但其两个设备任务的记录间隔约 1.34 µs，说明主机调用长并不必然伴随同样长的设备间隔。跨域时钟校准、采集完整性及调用内部活动未证实，尚不能断定这些调用导致设备等待或线上变慢。

已有 EP3 的 tensor-info 切片经安装版解析器检查，有 40 组描述符的形状与目标 MoE 兼容，但不能唯一定位第 15 层任务，解析字段也不提供专家计数的元素值。解析器和采集生产者的版本尚未完全绑定，其他记录来源仍可能包含更多信息；现阶段不能据此判断专家负载分布。

换用 AIV 的 vector 显示比例单独排名时，四批最低合格组均为 `TensorMove`，显示值为 **0.0%**；因此 MC2 不能称作所有指标下的最低任务。显示值可能受精度和舍入影响，不证明该任务或设备空闲，也不意味着它是全模型最低利用率模块。两个排名使用不同核心和分母，不能混为一个榜单。

对其中一条任务回查同次采集的数据库，高精度 vector 比例约为 **0.0231%**，并非零；另有 MTE2、MTE3 导出字段分别约为 **42.0%** 和 **46.6%**。唯一关联的调用栈指向注意力输出投影路径中的 copy；冻结源码位置相容，但历史加载文件和张量地址仍未证。这只是一条样本，几个流水字段不能相加当作利用率、墙钟时间或带宽，也不能据此归因瓶颈。

同一份重型采样中，一个 rank 的第 14 层与第 39 层相关 MC2 显示约 **160.37 ms** 和 **8.29 ms**；这提示值得追查，但 profiler 对时间的扰动未限定，不能把差异当作线上延迟差或可实现加速。对两个 rank 的两个选定层，已关联的外部同步与集合通信事件均在对应 MC2 开始前结束；这排除了这些**已记录区间直接与所选 MC2 区间相交**，但不能排除之前通信的间接影响、其他流、未记录事件或复合算子内部等待。

同一摘要下选取八张卡的第 14、39 层同流任务，要求完整导出签名、核心和 block 配置在每张卡两层相同且各层唯一，得到 18 组签名。MC2 的八个逐卡时长比为 **19.344–19.516**；其余 17 组共 136 对为 **0.794–1.286**。这排除这些选中任务都按 MC2 的倍率变化，但不覆盖其他流、未匹配任务或 MC2 内部；签名相同也不代表有效工作量相同，不能据此认定根因。

把观察扩至四个已选摘要、两个输入行数及各 40 层后，分别比较两组八卡的每层 MC2 时长中位数：1023 行的组间比值范围 **0.990–8.528**，其中 33 层前一组更长；643 行为 **1.174–10.331**，40 层前一组更长。每层所选记录的导出签名一致，但不同组的实际输入、专家工作量和运行条件未知，不能认定是硬件组差异或线上速度差。

另一个可检验的条件：如果两层属于同一通信组、全组有效专家行总数相同，并且每卡时长仅由专家行数按两层共用的非负截距线性关系决定，那么前述 19.34 倍差异要求短层所选八卡承担不超过全组约 **5.17%** 的有效专家行。实际分布和这些假设均未证明；合成路由反例表明总行数相同仍可能出现这种局部偏斜，不能将该比例当作实测或根因。

对该 rank 的一组调度摘要，40 层均有关联的 MC2 设备记录，且所选记录在同一 stream 上按层顺序不相交；调度摘要不是客户端请求 ID，缺少跨流数据和完成事件的绑定，因此还不能判断长 MC2 是否位于客户端关键路径。

进一步在 32 个选定的单卡范围中，分别计算 40 条 MC2 之间 39 个间隔与其他已选任务区间的交集。同流其他任务覆盖各组间隔的 **8.52%–68.56%**；把其他流的已选任务也算入，覆盖为 **11.34%–97.05%**。这说明不能把 MC2 之间的整段间隔都称作调度空闲，但未覆盖部分也不等于空闲或等待：事件记录、缺失身份的任务和未选择的活动不在统计内；跨流区间重叠也不能证明资源有效并行。

另一份历史采样的单卡窗口中，按导出表筛选的 18 条 `hcom` 记录与 1,188 条计算核心记录没有时间交集。此统计排除了身份缺失的汇总行和部分其他类型，通信行也可能是嵌套记录，不能排除其他流活动或 MC2 内部通信，更不能说明通信无法隐藏或证明串行依赖。

相同筛选扩展到两张卡各三个历史锚点窗口：六个窗口里的已选通信与计算区间均不相交；部分锚点的层角色没有独立验证。这个结果不扩大为全程结论，也没有找到可用来证明实际重叠的对照窗口。

指标解释也很关键：某条样本的 `cube_utilization` 显示接近 98%，其 MAC 活动代理却约 0.3%。核对安装版解析公式后，前者不能直接当作有效矩阵计算的利用率；两个数也不能相减得到等待时间。记录中没有能够分解内核内部阶段的 PC 采样，目前无法在计算不足、数据搬运、轮询或其他原因之间作出结论。 即使假设矩阵计算和搬运比例采用完全相同的计数空间，这两个整体比例也不能唯一确定二者的重叠，更不能算出等待时间。

对已保留的同 rank、同层 `MIX_AIC` 任务分别比较导出的 AIV vector 比例：MC2 低于 attention 和 HcPre 的配对各为 **1,280/1,280**，低于 Indexer 为 **256/256**。这是指定字段的采样比较；不同算子工作量和部分 block 配置不同，无法据此判断整机利用率、算子效率或等待原因。

### 4.2 KV 缓存写入的采样分布

在 1,280 组已选 norm、RoPE、scatter 三任务中，scatter 在 **1,207 组**中的单任务时间比另两项分别更长。对 `T=8180` 的 640 组，scatter 在每组三任务时间和中所占比例的中位数为 **79.43%**；这只是选定任务的 profiler 区间比例，不是端到端时间比例。

同一 rank、同一批次中，两个所报形状、类型、格式和 block 数一致的 scatter 样本分别为 **16.68 µs** 与 **265.06 µs**。多个导出视图的时间一致，但不是相互独立的硬件计时；真实槽位、缓存初态及计数口径未知。这个差异支持继续排查，不能据此认定 HBM 是瓶颈或预测融合收益。

对 T=8180 的 640 组选定任务作事后分组：31 个短 scatter（小于 50 µs）之前，选中 rotary 结束到 scatter 开始的记录间隔为 **283.480–1834.480 µs**；609 个长 scatter（大于 200 µs）之前的相同间隔为 **0.0195–0.04075 µs**。这两个区间在该采集中完全分离，但样本不是独立请求，阈值也是事后选择；间隔可能包含其他任务或未记录活动，不能据此认定设备空闲、间隔导致时长变化或预测融合收益。

另一类 Q 投影与 RoPE 的候选重排中，1,920 个同窗样本里，所选 scatter 相对投影结束的尾部均长于对应 RoPE 记录时长，两者差为 **4.899–14.940 µs**。这仅说明所选记录的时间长度相容：冻结源码在 RoPE 之前等待辅助流，跨流时钟、张量就绪、依赖及争用仍未闭合，不能据此认为现有执行可以提前或获得收益。

在各自同层 scope 的已匹配设备记录中，31 个短 scatter 均未与其他 track 任务交叠，609 个长 scatter 均与一条量化 Matmul 的记录区间交叠；短组同层也有该类 Matmul，只是选中的最近一条出现在 scatter 之后。这仍是同次采集的时序关联，且任务时长本身会影响交叠机会；scope 外任务和未匹配同步事件没有纳入，不能据此认定资源争用或设备空闲。

同次采集的另一组 `T=4760` 数据中，按同摘要、8 卡和 40 层选出 **320 个 scope**，三条前处理任务的导出物理签名一致。其中 EP3 的 40 条 scatter 记录中位数为 **16.13 µs**，EP0 对应 40 条为 **152.21 µs**。按事后阈值分组，41 条短记录均未与同 scope 已匹配的其他轨任务相交，279 条长记录均与量化 Matmul 记录相交；短组也各有同名 Matmul 记录。这说明上述关联并非只见于 `T=8180` 样本，但两组仍属于同一次 profiler 采集，实际有效槽位、工作量和资源状态未知，不能将交叠认定为变慢原因。

对同一批数据再看从 norm 开始到 scatter 结束的三个事件跨度：短 scatter 组中位数约 **1233.88 µs**，长组约 **197.58 µs**。该跨度包含两个任务间隔，不是三个算子耗时之和；短任务前的间隔较大，因此不能只凭 scatter 单项较短就认为这段前处理更快。它也不是整层或整请求时长，间隔原因尚未确定。

对其中同层的两条短、长 scatter 点查，设备记录分别为 **14.56 µs** 和 **149.64 µs**，导出的 AIV 总周期字段分别约为 **100.42 万**和 **100.17 万**。它们说明这两个导出周期数本身没有相差约十倍；但历史计数的单位、归一化和与墙钟的关系尚未绑定，不能据此认定两次有效工作量相同，或把多出的时间判为等待。已查记录也没有实际 slot 值、stride 或 tiling key。

对同一张卡的两个短、长样本，进一步查看各自同流记录：短样本的 RoPE 到 scatter 间隔约 1.69 ms，所查 trace/DB 中没有其他已导出的同轨任务；对应两次主机 launch 的同线程记录间隔约 1.69 ms。长样本的设备间隔约 0.02 µs，主机 launch 间隔约 432 µs。采集完整性、同步对象和调用内部活动仍未闭合，不能从这些数字认定下发、同步或设备侧的具体根因。

对主机间隔改用“所有相交记录”而非只查“完整落在间隔内的记录”后，短样本约 **99%** 的主机 launch 间隔落在前一个 RoPE 的 dequeue 记录内；长样本约 **96%**。此前仅查到短 tiling API，不能据此说间隔内缺少主机调用记录。调用范围覆盖不区分线程计算、等待或 profiler 开销，也不能证明设备整体空闲。

当前安装的 CANN 9.2 profiler 源码中找到一条按周期、频率、block 数和核数换算时间的公式，在假定频率和核数后与这两条样本的计数数据数值相容。不过历史采集数据库的生成路径和该字段单位尚未绑定，同版也存在其他计算路径，因此不能据此推断设备有效执行或内部等待时长。

### Attention 输出写回的补充核查

在同一采集、相同物理签名和第 0 层选出的 EP8–15 八条 `TensorMove` 中，数据库保存的向量 ratio 均非零，约为 **0.022438%–0.026090%**，而 CSV 对应显示均为 0.0；MTE2 和 MTE3 字段也非零。它们是同一次 profiler 采集的不同表示，不能当作独立测试。字段单位、导出链和采样精度尚未完全确认，不能据此认定实际带宽、设备空闲或低利用率原因。

冻结源码的 attention 自定义算子要求写入调用方传入的 output。让最终投影结果直接写入该缓冲区是一个待验证的结构候选，须保持必要归约、通信、别名、同步及图执行语义；历史采集尚未绑定实际张量存储与最终 producer/consumer，因此不能确认融合可行或估算收益。

同一个 EP8 第 0 层的样本中，copy 前一条同流设备任务关联到 `wo_b` 路径的 Matmul；copy 后的 record/wait 事件分别关联到 reduce-scatter 的主机调用范围。结合冻结源码和形状，这支持“投影 → copy → reduce-scatter”的候选数据路径，但没有 tensor/storage 身份来证明数据边。所选 WAIT 的事件对象及配对 record 未绑定，不能把其区间认定为通信耗时、设备空闲或可隐藏时间。

进一步沿同一次 host 调用的 flow，可以关联到一条 hcom reduce-scatter 记录和一条 AI CPU 任务。导出时间线上，hcom 记录区间落在此前选中 WAIT 区间内；不同轨道的时钟转换及误差、WAIT 的 event handle 与配对 record 均未独立绑定，因此这只是采集中的时间关系，不能证明 WAIT 在等待该通信或据此计算可隐藏的耗时。

官方 CANN 文档提供 BF16 矩阵乘与 reduce-scatter 复合接口；现存源码还有另一模型使用该类接口的例子。但当前 DeepSeek 的部分结果先写入 attention 输出、通信在后续模块进行，若跨边界组合，必须重新证明输出消费者、通信组、分片及舍入。不同版本对通信模式的说明不同，不能由其他模型源码断定历史 9.2 运行支持或性能收益。参见 [CANN 9.1 接口](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-transformer/aclnnMatmulReduceScatterV2.md) 和 [CANN 8.5 接口](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/850/API/aolapi/context/ops-transformer/aclnnMatmulReduceScatterV2.md)。

9.1 接口文档还要求左矩阵为二维连续输入；对 A2/A3 的 BF16 路径规定使用 AIV 通信，并对 bias、scale 等参数有限制。现有样本未保存可确认的输入 stride 或张量身份，也尚未证明历史 9.2 实例支持同样接口，因此这些是融合候选需要满足的条件，不是已确认的融合方案或资源争用。

继续追查同次调用，已把通信前后两条流上的多个 RECORD/WAIT 任务分别关联到主机事件 API，顺序与双向同步相容；但 event handle 未保存，尤其通信流尾部有两条候选 RECORD，无法确定另一流的 WAIT 实际等待哪一条。不同轨道的约 1 微秒时间差也没有时钟精度保证。

该权重描述中 `wo_a.weight` 和 `wo_b.weight` 各 43 条均标记 `FLOAT`。进一步对 EP8 第 0 层一个具体样本核对后，其 Matmul 设备任务通过唯一 flow 关联到 `unquantized_gemm → linear → matmul` 主机调用，主机输入记录为 BF16，设备任务也报告 BF16 输入和输出。此证据限定在该调用，不证明底层指令、累加精度或其他层实际执行路径；整模型使用 W8A8 不能推出每个线性层均使用 INT8。

另一张卡的同层采样中，两级输出投影分别关联到主机调用栈和设备任务：第一步的 BF16 形状为 `[8184,1,4096] × [1,4096,1024] → [8184,1,1024]`，第二步记录为 BF16 `[8184,1024]` 与权重 `[5120,1024]` 产生 `[8184,5120]`。调用位置与冻结源码的第一投影、reshape 和第二投影路径相容，为研究两级投影分块衔接提供了依据；中间张量身份、reshape 是否复制、实际 stride 和后续通信仍未绑定。任何重组还须保留原有中间 BF16 舍入和必要同步，不能仅由相邻形状推断收益。

进一步检查该次调用链，两个投影之间确有 `reshape` 和嵌套的 `view` 记录，随后出现形状相容的线性投影；这些调用栈与保存源码位置相符。已检查的记录没有可关联的 tensor storage、stride 或 offset，因此仍不能据此断定两次投影共享存储、reshape 没有复制，或中间值可以直接分块交付。

输出写回的值也随并行分支变化：冻结源码中的 DSV4 专用行并行函数本身返回局部结果，另一个条件分支可能在 attention 之后做 reduce-scatter。因此在研究将投影直接写入原 output 时，必须先确定原 output 在该分支应包含局部值还是已归约值，并保留后续通信；现有源码接口未传目标 out，不代表设备上的所有其他接口都不支持。

## 五、理论极限：可以怎样严格表述

昇腾 MindIE 文档提到一种仅用于负载均衡分析的理想化设置，并明确不能用于正式业务；它适用其他指定硬件和模型。即使能测出这种合成条件的吞吐，也不能自动将其当作保持本任务真实模型语义的不可超越上界，仍须证明必要工作量和硬件容量。参见 [MindIE 负载均衡限制](https://www.hiascend.com/doc_center/source/zh/mindie/21RC2/mindiellm/llmdev/mindie_llm0427.html)。

先区分上下界的方向。把目标明确限定为这两轮各 8 个请求、每轮对应的暖缓存初态及输出契约，并把性能函数定义为 `16,384 / (第 1 轮 AISBench 窗口 + 第 2 轮 AISBench 窗口)`，允许的实现集合若包含两轮已观察执行，那么该集合的性能最优值至少不低于这次执行在**同一函数口径**下的表现。约 519.84 tokens/s 是该条件下的观测参考；两轮分别约 522.37 和 517.35 tokens/s。现有客户端计数和与冻结参考文本逐条一致支持该记录，但不直接证明完整模型精度契约、两轮运行时每项配置或缓存初态与另一实验相同；计时与计数误差未形成严格数值区间。不能把 519.84 当成连续 16 请求墙钟吞吐、长期稳定可达值、不同缓存初态下的可行下界、单请求 TPS 或理论上界。严格数值上界还需要下述不可避免工作量和硬容量证据，目前未知。

要给这个**两窗口合并口径**建立上界，若能分别证明任意合法实现的两轮耗时至少为 `L₁`、`L₂`，则有 `TPS ≤ 16384/(L₁+L₂)`。相加的是基线指标定义中的两段窗口，不代表同一轮中的计算、访存与通信必须串行。若允许第一轮为第二轮提前准备数据，第二轮的下界必须把这些已准备数据计入初态；目前两个所需下界尚未证实。

融合还要保留所要求的数值边界：在一个明确限定的 RMSNorm → RoPE 理想算术示例中，删除中间 BF16 舍入会改变最终 BF16 结果。这个构造不代表历史设备出现误差，也不排除在融合内保留舍入或满足其他精度合同。

理想模型允许合法的融合、分块和重叠；必须保留由输入输出语义证明的依赖。对给定负载和清楚定义的时间窗口，若能证明某资源至少要完成工作量 `W_min`，且任何时长为 `t` 的窗口最多完成 `b + P_max × t`，则有：

```text
T ≥ max(0, W_min − b) / P_max
```

其中 `P_max` 是覆盖该资源、数据类型、并发机制和整个窗口的**硬容量上界**，`b` 是已证明的窗口初始在途或突发信用。例如在受限的热态原始权重读取模型里，若必要不同字节为 `D`、初态可供应量上限为 `C`、同一通路的短窗突发信用为 `β`、硬速率上限为 `B`，则条件时间界是 `T ≥ max(0,D−C−β)/B`。其中已跨边界的初态数据计入 `C`，仍需跨边界的在途信用由 `β` 处理，不能重复抵扣；只有证明 `β=0` 才能省略它。实际 169 的这些量均未证实。

多个可并行资源的下界通常取最大值；有依赖的阶段需按依赖图分析关键路径，只有已证明不可重叠的部分才能直接相加。计算、访存和通信可能共享资源，不能既假设无限并行，又忽略资源争用。

一个帮助理解分块与依赖的受限模型：假设每个块必须依次搬入、计算和搬出，分别固定用时 `a、b、c`；三阶段各用独立资源，同一阶段一次处理一个块，允许跨块完全重叠且不能继续拆块或合并。对 `n` 个块，最短时间恰为 `a+b+c+(n−1)max(a,b,c)`，既包含首块准备和末块排空，也包含中间流水。实际硬件若共享带宽、允许更细分块或改变算法，需重新建模；这不是本机的数值上界。

多种实现还可能在计算和访存间互相替代：分别取全体实现中的最少计算量和最少访存量，有时两项都会是零，无法表示二者不可能同时为零。如果能够对所有合法实现证明联合约束，并分别证明资源容量，就能结合这些约束给出更紧的条件时间下界；本任务尚未证明适用于整模型的联合工作量或硬容量。

如果同一完整工作窗口必须产生 `N` 个输出 tokens，且已严格证明它的时长不小于 `T_min > 0`，则该窗口的平均输出吞吐不超过 `N / T_min`。这个结论只适用于所定义的窗口、工作量和初态；单个算子的理想时间不能直接倒数成整服务的 TPS 上界，跨窗口流水也需要正确计入在途工作。

一个**计算模型示例**：假设单设备只使用 24 个 INT8 Cube 核、频率恒为 1.8 GHz，每核每周期最多 8,192 次 MAC，且必须按普通稠密算法完成 `3×1280×32768 = 125,829,120` 次 MAC，那么只计计算、假设无开销时约需 **0.356 µs**。核数与频率来自 profiler 元数据，每周期算力使用 [Ascend 工具的估算公式](https://github.com/Ascend/msprof-analyze/blob/6b8f431d4724043f44a39eef000fd5c6600784d8/msprof_analyze/cluster_analyse/cluster_kernels_analysis/operator_mfu/chip_peak_flops.py)；尚未证明它们是这台设备的物理硬上限或覆盖所有合法执行方式。旧采样中按输入形状筛出的 1,920 条矩阵任务中位数约 42 µs，但输出语义、实际有效行与上述算法没有逐条绑定，且 profiler 有扰动。这两个数字用于展示建模及缺口，不能据此声称已证明的差距或可实现的加速。

再看一个记录输出为 INT32 的小行数样本：选定 1,920 条 `QuantBatchMatmulV3` 的 profiler 时长中位数为 **25.6 µs**；输入含 INT8 `[3,5120]`、NZ 格式 INT8 权重，输出形状为 INT32 `[3,4608]`。如果把它假设为完整稠密的 `3×5120×4608` 乘加，并沿用上一段 24 核、1.8 GHz、8192 MAC/核周期的**假定总硬容量**，则纯计算条件下界为 **0.2 µs**。若进一步限定每条对应指令最多使用 3 行、不能与其他行拼接，并假定该限制适用于全部核，条件下界为 **1.067 µs**。后者只适用于这一更窄的指令域，不能约束允许拼行的方案。

[昇腾 CANN 9.1 的 QuantMatmulWeightNz 接口文档](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/aolapi/context/ops-nn/aclnnQuantMatmulWeightNz.md)给出 INT8 非转置 NZ 权重的形状规则；上述两组采样的 `[144,320,16,32]` 和 `[160,144,16,32]` 分别与逻辑 `[5120,4608]`、`[2304,5120]` 相符。两组也不符合该版本的转置形状规则。对应两档采样的 **128 条投影记录**已逐条唯一回连到设备记录，名称均含 `aclnnQuantMatmulWeightNz`，形状、dtype 和 format 一致。这增强了维度假设的接口依据，但设备名称不是 host API 参数，历史采集使用的 9.2 参数、版本及张量身份未证，不能据此认定实际计算路径。

进一步在单张卡、单层的一个采样中，主机 API 调用栈经唯一 flow 关联四个 shared expert 设备任务，以及一个 MoE 路由融合任务；这些调用栈与冻结源码相应位置相符，为任务角色提供依据。所选 shared 动态量化输入为 BF16 `[595,5120]`，MC2 输入为 BF16 `[643,5120]`，因此不能直接把两者当成完整同形输入复用；切片、填充、重排或共享部分存储仍可能存在。历史加载源码的 hash、tensor 身份与实际行映射尚未闭合，上述绑定不能推广到其他样本。

冻结源码提供一条可排除的解释：如果 shared 的原输入恰是那 643 行、使用 shared-DP 分支并按 8 路 TP 补齐和均分，那么每路量化应为 **81 行**，与看到的 595 行不符。这个矛盾只说明这些条件不能同时成立，并未确定哪一个不成立；另一种 sequence-parallel 路径允许按实际 token 数裁剪，但是否在该次运行发生仍未知。shared-DP 的局部输出后面还需要按源码执行聚合和裁剪，不能把局部结果直接当完整输出。

进一步按已存摘要关联两档调度记录：**4,760 和 8,180** 个调度 token 按 8 路向上取整分别得到 **595 和 1,023 行**，与对应量化记录的行数相容。源码还存在对 routed 输入追加 padding 的条件路径，可能造成两支物理行数不同。但调度器与设备记录来自不同进程，摘要相同、数字相容不等于证明张量、实际分片模式或 padding 长度相同；不能把 643−595 的 48 行认定为已测 padding。

其中 4,760 的调度摘要包含四项，数值分别为 **3,200、1,548、6、6**；两个较小项各记录了 5 个投机 token 描述，另外两项的对应字段为空而不是已证为零。这说明不能仅凭总数确定每张卡的行属于哪些请求或阶段。另一个样本里的 5,144 来自不同摘要和进程，不能直接作为这里的实际补齐值。

对两组各有三个请求的 **8,180-token 调度记录**，保存的调度源码提供了一个条件性解释：若批次输入预算为 8,192、DSpark 长度为 5，且每个请求需额外预留 4 个草稿槽，那么 `8192−3×4=8180`。在指定请求处理顺序且没有其他更紧预算时，源码规则也能算出记录中的两组剩余 prompt 调度量。实际生效配置、处理顺序及动态预算尚未绑定；这不是已证截断原因，也不代表 12 个槽位对应实际设备计算或性能损失。

同一调度器的两次连续已记录调用中，三个匿名请求标识前后匹配。其中一个请求第一次安排 1,652 token 后，调度状态从 29,568 变为 31,220；下一次从 31,220 安排 1,548，到达 32,768。另两个请求第一次分别到 32,768，下一次各安排 6，并各记录 5 个投机 token 描述。这个关联支持分段调度的解释，但调度状态不是设备完成证明，匿名标识也没有与客户端响应绑定；它仍不能证明上述草稿槽就是实际截断原因。

冻结源码中，一条 shared expert 路径将权重 scale 作为该类矩阵乘的第三个参数，后续激活使用 FP32 版本的 scale；在指定 W8A8 加载、BF16 参数和投影维度等条件成立时，它可以解释样本中的 BF16 `[4608]` 输入。但仅凭形状、dtype 和源码不能确认历史调用用了该路径，也不能确定这组实际执行的 NZ 地址映射。

对上文 32 对较大行数采样，也可在同一个纯计算模型下作对照：假设所有物理行均有效、NZ 权重分别等价于逻辑矩阵，并且每任务窗口内完成完整稠密 INT8 乘加。以下“理想值”沿用 **24 核、1.8 GHz、每核每周期 8192 MAC、无突发信用**的假定资源模型：

| 投影形状 | 条件理想计算时间 | profiler 记录时长中位数 |
|---|---:|---:|
| 595×5120 → 595×4608 | 39.67 µs | 76.87 µs |
| 1023×5120 → 1023×4608 | 68.20 µs | 101.86 µs |
| 595×2304 → 595×5120 | 19.83 µs | 58.58 µs |
| 1023×2304 → 1023×5120 | 34.10 µs | 76.10 µs |

这是便于检查量级的**条件模型与记录并列**：硬容量、NZ 映射、有效行、运算和计时初态没有完全绑定，不能将比值称为实际利用率、严格性能差距或可达提速。两档是不同批次，测量还受 profiler 扰动；计算、搬运和其他任务允许重叠。

如果进一步限定 INT8 Mmad 按 16 行计费、尾块不能与其他工作拼接，那么 595 行需按 608 行、1023 行按 1024 行计费。沿用上表假定容量，四个投影的条件理想时间依次变为 **40.53、68.27、20.27、34.13 µs**。这只收紧了该狭窄模型下的计算时间：实际 tile、有效行、指令和容量均未知，不能将小幅修正解释成真实尾块损失，也不适用于允许合法拼行或更换算法的全部实现。分形粒度参考[昇腾 Cube 指令理论模型](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/appendix/cube_instruction_theory_performance_summary.md)。

这不是已经证明的 128 倍或 24 倍提速空间：历史任务的有效行、NZ 到逻辑矩阵的映射、额外 BF16 输入语义、实际指令，以及这些假定容量是不是本机覆盖所有路径的硬上限都未绑定。两组数字的意义是说明**模型对照需要补哪些证据**；搬运、融合、重叠和初态改变后都需重新核查。

另一个直接关联到历史样本的 **BF16 投影条件模型**：该次 EP8 Matmul 设备记录对应形状 `[8184,1024] × [1024,5120]`，其 host 调用记录 BF16 输入。若限定普通稠密算法，逻辑工作是 **42,907,729,920 MAC**。再假设仅有 24 个 Cube 核参与、频率硬上限 1.8 GHz、每核每周期最多 4096 个 BF16 MAC、无在途信用且不使用其他资源，纯计算时间条件下界为 **242.489 µs**；这条任务的重型 profiler CSV 区间为 **320.893 µs**。24、频率和 4096 尚未证明是覆盖实际设备、全部资源和实现的硬容量；普通稠密工作量也不是任意合法算法的必需工作。两数之比只是条件模型与采样区间的比较，不是已验证利用率、可达提速或服务 TPS 上界。

一个用于检查模型假设的反例：所选 copy 记录为 **37.0995 µs**。如果额外假定源和目标的完整读写共 **167,608,320 字节**均在该窗口内经过同一共享通路，且没有突发信用，则该通路须至少提供约 **4.518 TB/s** 才与这条记录相容。历史地址、缓存、通路和计时覆盖尚未证明，所以这不是实测带宽；如果将来已证容量与之矛盾，只能判定这组假设至少有一项不成立，不能直接选择原因。允许融合时也不能强加原 copy 的两次流量。

[昇腾 ToolBox 6.0.RC1 文档](https://www.hiascend.com/doc_center/source/zh/mindcluster/60rc1/toolbox/toolboxug/MindX%20DL%20ToolBox%206.0.RC1%20%E7%94%A8%E6%88%B7%E6%8C%87%E5%8D%97%2001.pdf)说明，其 d2d 测试以读写总量除以时间计算带宽，缓存和预取等可能让该结果超过标称值。这进一步说明逻辑读写量除以时间与实际 HBM 物理流量是不同口径；该旧版资料既不能证明本次采样发生缓存命中，也不能提供本机短窗口硬容量。

进一步考虑固定权重和确定性投影：对上述 BF16 `[8184,1024]` 输入，其可能的输入比特组合数至多 `2^134086656`；假如对应输出是 `[8184,5120]`，那么假设其每个元素都可独立取 256 个值会产生 `2^335216640` 种组合，比可能输入更多。这些独立输出组合不可能全部由该固定投影生成，因此不能只按输出形状把独立 copy 的信息下界套到投影上。假如接收方已拥有相同权重和其他状态、可以逐位等价重算，还可以研究传入约 16.76 MB 的输入并重算约 83.80 MB 的输出；这只是有附加条件的理论构造，不是实测流量或可行性、速度证明。历史投影与 copy 的张量存储身份仍未绑定。

已保存的同族 BF16 MatMul 二进制中存在对应矩阵指令，并列有 17 个 tiling 配置；但无法确认历史任务使用了这份二进制或其中哪一个配置，也缺完整 stride 和实际转置属性。因此，接口 dtype 和形状相容还不足以确定实际指令、同步或每周期容量。

设备身份方面，已保存的两份 CANN 软件目标配置 `9381` 与 `9382` 的解析键值，只有 SoC 版本名称不同；因此采集里的 24 AIC、48 AIV 和 1800 MHz 字段不足以区分这两个配置。单个设备的型号查询也不能自动代表全部历史 rank。这是软件配置的比较，不证明两种芯片的实际物理属性相同。

上述时间计算还假设计入的全部工作均须在同一窗口内完成，且不存在需要抵扣的窗前在途工作或突发信用；否则应使用本节的 `b + P_max × t` 形式。稳态平均峰值不能自动当作任意短窗口的硬容量。

若再限定采用 [Ascend Mmad 指令模型](https://asc.gitcode.com/api/appendix/cube_instruction_theoretical_perf_summary.html)、每条指令最多处理这 3 个有效行且不能拼入其他工作，按该模型的 16 行对齐，并进一步假设上述核数、频率和共享资源服务上限均成立，条件时间下界可收紧到约 **1.896 µs**。这比前一个模型限制更强；其他合法分块、拼行或算法重组不受此界约束，也尚未证实历史 kernel 满足这些条件。

同一形状还可以建立**受限冷态输入界**：若矩阵和权重是存储互不重叠、可独立变化的 INT8 输入，要求对所有输入给出完整精确 INT32 结果，输入起初仅以原始字节位于 HBM、没有副本或预计算，且通过指定边界逐字节读取，则存在一个输入要求至少读取 `3×1280 + 1280×32768 = 41,946,880` 个不同字节。若该边界有已证明的硬读取容量 `B` 和初始突发信用 `b`，可得该输入的 `T ≥ max(0,41,946,880−b)/B`。在计算与读取条件都成立的同一窗口，两个时间下界取最大值，允许它们完全重叠。实际模型使用固定权重且可能热缓存，当前既没有绑定这套冷态契约，也没有证明对应的 `B` 和 `b`，故这不是本次请求的 HBM 流量或 TPS 上界。

以本次 scatter 的一个相容形状为例，`8180 × 512 × 2 = 8,376,320` 字节只是 BF16 输入张量的**逻辑容量**。无效或重复槽位、相同的缓存初态、缓存层级及不同合法实现都可能改变实际写覆盖和 HBM 流量。若额外限定目的地址与可观察终态，且证明初态与终态有 `D` 个不同的目的字节位置，那么至少需要覆盖这 `D` 个位置；进一步有匹配的写覆盖硬容量时才可代入上式。当前 `D`、突发信用及对应硬容量均未知，不能据此给出本次请求的正数时间下界。

作为理论方法示例，如果把 scatter 单独定义成接口，假设 8,180 个槽位互异、每个槽位的 512 个 BF16 值都可独立取 256 种值，并要求接收端精确观察最终状态，且窗口前无输入副本或旁路，那么计数论可证明：即使允许融合、压缩和重排，**至少存在一个输入**需要跨指定边界传递 33,505,280 bit 的可区分信息。这是人为限定输入族的最坏情况，不是每个输入均有此工作量；现有证据没有证明这些独立取值在实际模型中可达，也没有证明对应真实 HBM 流量或硬容量。

对索引整理，在所有索引互异且有效、每个位置均可能改变输出、窗口前没有等价摘要的接口域里，所有输入位置都存在必要的信息依赖，但这不要求逐项串行或逐项读取 HBM。若进一步限定算法只能通过二元比较获取次序并需支持全部排列，512 项的最坏情况至少需要 **3,876 个逻辑比较结果**；radix 排序、上游直接生成有序结果等不受该比较模型约束，且这些条件尚未绑定历史运行，不能把它换算为实际时间或 TPS 界。

另外，在一个受限的数据流模型中，512 个有效索引的排序首项可能依赖每一个输入。如果图结构固定、节点最多合并两个输入且边界没有预先算好的摘要，则首项至少需要 9 层逻辑依赖。芯片原语不一定符合二输入假设，上游融合也可改变边界；因此不能把这 9 层直接换成设备时间或 TPS。

当前已经有若干**受限算法和接口条件**下的工作量、信息传递和数据依赖推导，但尚不能证明它们覆盖所有允许的融合、重组和缓存初态；所以它们不是本次整模型的严格数值上界。理论差距也不是可达加速承诺。

以已有 `[595,5120]` 形状为例，可以构造一个允许融合、压缩、分块与重算的**独立动态量化接口**条件界：假设每行按最大绝对值除以 127 得到 scale，精确输出全部 INT8 值及 scale，输入只在发送侧且接收侧初态固定。将每行最后一个值固定为 127，其他值分别从 0 到 127 取整数，可得到 `2^21320635` 种不同输出。因此，若完整计入所有旁路和控制、时间信道，至少存在一个输入需要跨该接口传递 **21,320,635 bit** 的可区分信息；这不是每个输入的下界。若进一步证明边界的硬容量包络为 `I(t)≤β+Bt`，则该输入族最坏情况满足 `T≥max(0,21320635−β)/B`。历史量化语义、可达输入、接收侧初态和 B、β 均未闭合；若中间量化输出可被融合消去而只观察最终结果，这条独立接口界不自动适用，不能把它当作实际 HBM 流量或整模型吞吐上界。

## 六、证据与复现口径


本报告公开聚合事实、筛选口径和限制。**原始 profile、请求输入与输出、模型权重、内部运行配置和诊断日志不随本报告发布；因此外部读者不能仅凭仓库独立重放或核验原始采样。** 要独立验证，应在有权使用的等价环境中重新采集，并记录实际硬件、镜像及源码版本、模型和精度、并行方式、请求参数、缓存初态及 profiler 设置。不同配置所得数值不应直接当作同一基线。

可按以下算术和筛选规则复核报告的聚合口径：

1. **输出吞吐**：两轮总输出 tokens 除以两轮各自 AISBench 窗口耗时之和；分别记录每轮成功数、输入输出计数、命中计数和计时边界，不把重型 profile 采样当作基线成绩。
2. **MC2 关联和筛选**：目标层 host scope 通过唯一的 host-to-device flow 关联设备任务，再按任务字段与 kernel 表匹配；按同批次、层、算子名和物理签名分组，要求所比较组的 8 rank 数据完整且各自任务数量相同；AIC 与 AIV 分别筛选。指标不完整的组不填零。
3. **加权活动代理**：`sum(AIC_cycles × aic_mac_ratio) / sum(AIC_cycles)`；明确其分母是已筛选设备任务的 AIC 周期，不能称为全芯片利用率。
4. **F08 分布**：在已关联目标层范围中，按同流、任务顺序及物理签名选出 norm、RoPE、scatter 三元组；逐组比较三个任务区间。先对每组计算 scatter 占该组三任务时长之和的比例，再计算组间中位数。
5. **完整性和干扰**：报告未关联事件、缺字段、日志截断和 profiler 错误；区分设备没有记录、设备无任务、任务内部等待和有效计算活动。保持待验证假说，不从时间邻近或名称相似推出张量身份。

外部资料可用于核对接口和指标语义，但只有确认版本、芯片及执行域匹配后才能用于本机结论。例如 [CANN profiler 字段说明](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta2/devaids/Profiling/atlasprofiling_16_0067.html)、[Ascend C Cube 指令理论性能资料](https://asc.gitcode.com/api/appendix/cube_instruction_theoretical_perf_summary.html) 和 [Ascend C 平台带宽接口说明](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/Utils-API/platform_info/PlatformAscendC/GetCoreMemBw.md)。它们提供核查入口，不能自动证明本次设备的全实现域硬上限。

[CANN 8.5 图 Profiling 配置文档](https://www.hiascend.com/doc_center/source/zh/canncommercial/850/API/ascendgraphapi/atlasgeapi_07_0150.html)列出的 Atlas A3 系统互联采集频率为 1–50 Hz；这是该版本中配置项的采集频率范围，不是链路带宽上限，也不证明本次实际使用了该配置。若假定采用均匀的 50 Hz 时点采样，约 25.5 ms 的单次任务只有一至两个采样点，取决于相位；区间累计或其他逐事件工具可以有不同覆盖。因此不能用这一文档推断历史任务必然漏采，也不能把观测带宽当作物理硬容量。

例如，[Ascend C 的一种 AIC/AIV 同步接口](https://asc.gitcode.com/api/SIMD-API/c_api/sync/inter_core_sync/asc_sync_block_arrive.html)对单个同步计数器规定最多累加到 15，并说明通知不会阻塞该流水的后续指令。这是特定协议的条件约束，不能把 15 当作整卡在途任务或字节数上限。页面为持续开发预览版，尚未与历史 kernel 绑定，也不能据此设定本次短窗初始信用或吞吐硬上界。

## 七、尚需解决的问题

- **定位最低利用率模块：**补齐同一口径下相关模块、rank、请求和图重放的覆盖；分别解释设备任务覆盖、AIC/AIV 活动和等待，避免用局部排序代表全模型。

- **收紧上界：**核实设备型号、资源范围、频率和并发规则对应的物理硬容量，证明实际负载不可避免的工作与初态；将可重叠的阶段按依赖图和共享资源建立界。

对已保存的 MC2 INT8 peer 搬运源码作条件性工作量核对：若该源码及其常量确实用于目标调用，且 K=5120，令 R 为各次经容量截断后实际搬运行数之和，该 helper 的 GM→UB 逻辑读取请求为 `5152×R` 字节；按每次调用的行数 `r_i`，读取调用次数为 `sum(ceil(r_i/2))`。同样的 R 可能因行分布不同产生不同调用次数。这里的 32 字节包含预留区，不能都称为有效 payload；公式不代表物理 HBM/网络字节或等待时间。当前 R、历史二进制与执行分支未知，无法用于对实际瓶颈定量归因。计数单位参考 [昇腾 CANN 9.1 DataCopy 文档](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/SIMD-API/basic_api/data_move_guide/gm_and_ub_data_movement.md)，与历史 9.2 未绑定。


对与 Engram 形状相容的两处层间候选区间做同卡同轮配对，48 对中第一处均更长；逐对减去所选大矩阵任务时长差后，三个采样轮次的残差中位分别约 0.050、0.620、0.280 µs。这只是采样范围内的算术对照，残差包含其他活动及未覆盖区间；相关形状没有绑定权重和请求，不能认定矩阵任务造成差异、位于关键路径或对应可节省时间。

对这 48 对中的大矩阵记录，继续比较导出字段的乘积：第一处相对第二处的 `AIC总周期 × MAC比例` 比值，在三轮中的中位数分别约 **1.001、0.999、0.999**；`AIC总周期 × MTE2比例` 的对应中位数约 **1.080、1.062、1.065**，48 对均大于 1。这里只能说保存字段的代数表现不同：MAC 乘积接近不证明运算量相同，MTE2 乘积也不是搬运字节、HBM 带宽或独立耗时，不能据此认定搬运造成时间差。两处权重、有效输入、缓存状态及 profiler 导出语义尚未完整绑定。

将后一乘积分解，48 对的 `MTE2比例` 前后比均在 **1.000–1.0051**，三轮 `AIC总周期` 比值的中位数分别约 **1.077、1.061、1.064**；且每一对的总周期比都大于 1、MTE2 比例比都不小于 1，所以乘积比全部大于 1 已由这两个字段的代数关系决定。它不能当成一条独立的搬运变慢证据。比例仅显示到三位小数，真实误差及计数定义未知；同样也不能由此排除缓存、搬运或其他因素的影响。


F31 的共享接口补查：冻结的 DSpark proposer 在压缩模式传入 `common_ratio_to_sas_metadata`，而 V4.1 metadata builder 的共享入口读取 `common_v41_metadata` 和 `common_v41_batch_metadata`。因此即使假设只让该 builder 转发现有参数，也不能据此认定 V4.1 的跨组共享会生效；还需核对共享范围、每组 block table/slot 和缓冲生命周期。历史运行是否采用这些对象、是否真的重复工作及性能影响均未知。


F31 的构造器选择链进一步收窄：保存的 DSpark 源码将 draft SWA cache 指向 V4.1 backend，draft group 由该 backend 选择 metadata builder；当前 stage 的 `AttentionGroup` 创建逻辑与之相容。在历史确实加载这些对象、cache 属于该 group 且 legacy CP 开启、PCP 关闭的条件下，会选择 V4.1 CP builder；启动参数和当前文件哈希仍不足以证明历史实例及生效配置。


进一步核对 Engram 候选的单个 EP8 采集子树：保存的配置中 `hardware_mem`、`sys_profiling` 为 off，HBM、DDR 和 L2 的相关字段为空；空字段不能直接解释为关闭。在指定的两个目录直属文件名中未发现访存相关名称，原始二进制未解码。当前仍不能判断矩阵任务的数据来自 HBM 还是缓存，不能从 MTE2 活动比例计算实际带宽。昇腾 [CANN 9.1 文档](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/maintenref/troubleshooting/troubleshooting_0516.html)列出了不同访存采集类别，但不能证明本次历史 9.2 已启用或支持它们。
