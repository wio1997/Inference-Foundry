# 129之后的证据复核：下一突破口转向调度交错，尚不放行新模型实验

2026-11-13。**本轮仅分析128/129已有记录，0次模型加载、0次服务器调用；默认保持114，同一版本C4/C8均领先强参考30%的目标仍未完成。**

结论：编译准备确实消除了已定位的慢调用，但没有解决C4整体退化。新增证据把关注点缩小到**冷请求的prefill分批及其与在途decode的交错**。这是一条有数据支持的核查方向，尚不是已经证明、可以立即修改的根因。

## 1. 本轮新增的确定事实

复查了128/129两档各32条正式请求的原始SQLite时间戳、实际输入文本哈希、输出文本哈希，以及rank0已有的状态包装器事件。逐条输入文本相同，每条均1024输入、256输出；时间端点与原复现记录完全一致。完整输入token ID数组不在这批记录中，不能把文本核对写成逐ID核对。

| C4指标 | 128 | 129 | 变化 |
|---|---:|---:|---:|
| 整批耗时 | 28.663819秒 | 31.397200秒 | **+2.733381秒** |
| 输出吞吐 | 285.795836 TPS | 260.914989 TPS | −8.71% |
| 纯prefill调用 | 25次 | 35次 | **+40%** |
| 其中只有一个请求分段的调用 | 2次 | 17次 | +15次 |
| 调度的纯prefill token | 31,488 | 31,488 | 相同 |
| 扣除状态命中后实际送入原模型的对应token | 30,720 | 30,720 | 相同 |
| 每次纯prefill平均调度token | 1,259.52 | 899.66 | −28.57% |
| 状态复用请求 / 跳过token | 2 / 768 | 2 / 768 | 相同 |
| 平均请求首token等待 | 1.187309秒 | 0.936081秒 | 改善 |
| 平均请求首token后至结束 | 2.388931秒 | 2.963663秒 | 退化 |

**工作量没有增加，却分成了更多小批次。** 不能再以“129需要处理更多prompt token”解释这次C4退化。每次纯prefill主机区间常见约0.28–0.32秒；区间包含原模型入队和等待，不能当作隔离的NPU kernel耗时，也不能用“少10次×0.3秒”直接承诺收益。

## 2. 多出来的2.733秒落在哪里

把每条请求分为“开始到首token”和“首token到结束”，分别求和后除以并发数4，再加上未占用的客户端并发槽位时间，恰好等于整批耗时。这里是请求占用时间的账目，不是硬件关键路径分解。

| 折算为整批秒数的分量 | 128 | 129 | 差值 |
|---|---:|---:|---:|
| 首token前请求占用面积 ÷ 4 | 9.498470 | 7.488648 | **−2.009821** |
| 首token后请求占用面积 ÷ 4 | 19.111451 | 23.709305 | **+4.597855** |
| 未占用客户端槽位面积 ÷ 4 | 0.053898 | 0.199246 | +0.145348 |
| 合计 | 28.663819 | 31.397200 | **+2.733381** |

因此，129确实更早给出了首token，但后续完成变慢了。首token后的时间包含其他请求的prefill、decode、通信、调度和HTTP传输，不能统称为“decode算子慢了”。

进一步按同一主机的单调时间对齐，首token后新增的4.597855秒中：

- **3.050142秒**与已记录的纯prefill主机区间重叠；这部分由1.472135升至4.522277秒。
- **1.547712秒**发生在这些主机区间之外。

这是时间重叠证据，**不是证明prefill造成了3.050秒、也不是可直接回收3.050秒的收益估算**。它足以决定下一步查调度交错，但不能排除模型执行、通信、MTP轨迹或客户端到达变化。

C8同样呈现“首token前改善，后续略退化”：前段折算减少1.375908秒，后段增加0.534570秒，空槽增加0.126065秒，合计净省0.715274秒。因此不能把C8全部收益解释成decode加速。

## 3. 哪些解释已经关闭，哪些仍未知

| 解释或方向 | 证据裁决 |
|---|---|
| C4退化是因为prompt工作量增加 | 不支持：两批调度与实际计算的纯prefill token总量相同。 |
| 继续降低状态复制耗时即可解决 | 不支持：复制stream区间仍为数毫秒量级，整批差异为秒级。 |
| 继续补这组卷积状态编译模板就能过线 | 关闭：129已完成干预且受监测迟编译为0，双档门槛仍失败。 |
| HTTP/客户端空槽就是主要损失 | 不支持：该账目只增加0.145秒，远小于整批增加2.733秒；仍不能由此排除活跃请求中的传输成本。 |
| C4的MTP接受率下降导致退化 | **未知**：只有含工程和预热的72请求全程计数，不能分配到正式C4。 |
| C4小批次增多、prefill与已有decode交错更重 | 已观察到；具体触发条件与因果方向仍待源码核查。 |
| 状态复用在一般业务必然有优势 | 未证明：正式C4/C8只分别命中2/16请求，C8继承C4留下的状态。 |

全程MTP拒绝数373→597、批次数660→689是真实记录，但不能将增加的224个拒绝全部算给C4。AIS记录的每请求时间戳数量也不能替代模型步数。129/128相同输入下的完整文本一致为C4 24/32、C8 27/32；这既不是质量通过，也不能仅凭它判定缓存错误。

## 4. 与框架源码的对应关系

129固定源码为`5c4290726beb475ee7ea200580f07a36a71e515f`，128为`432aac4cc9afc8f0b371c74ebb2ac716b5be4e2f`。本轮只读核查，未修改模型或调度代码。

- `DeepInfer/csrc/engine/scheduler.hpp`，`_schedule()`：NORMAL引擎每步选择prefill或decode；在prefill尝试点检查waiting队列和缓存水位。prefill步后decode计数归零，后续仍可能继续prefill。这里不是一个同时混合两种请求阶段的统一token批次。
- 同文件`_schedule_prefill()`：按token预算和显式状态检查点截断请求；到检查点时允许其他已等待请求填剩余预算。**已有填充逻辑不能再作为新功能重复实现。** 当前需要判断的是为什么当时只有一个分段可被选中。
- `DeepInfer/deepinfer/model_executor/models/glm5_next/full_model/sdk_http.py`：HTTP线程排队，模型主线程在`llm.step()`之间接纳请求；队列暂空就结束当轮接纳。客户端已发出请求，不等于请求当时已进入C++ waiting队列。
- 同目录`native_prefill_state.py`：只记录满足契约的纯eager prefill分段；现有事件没有request ID、完整waiting队列和每步MTP计数。因此不能从当前时间线重建唯一的到达/调度因果链。

可能的链条是：请求进入waiting的时间和已有请求完成时间变化 → 较小的prefill批次 → 更频繁打断在途生成 → 之后的完成、到达和MTP轨迹再次变化。**这仍是假设，不能写成已定位bug。** 冷编译的消失可能改变了请求聚合时机，也可能只是两批运行差异；现有证据不能区分。

## 5. 对此前安排的修正

这轮暴露的问题是：把一个真实的局部慢点，当成了足以预测整批收益的依据。修掉慢点后，批次构成和请求交错发生变化，原先的静态减法不再成立。继续追加编译、复制微优化或参数组合，没有足够依据。

后续保留完整混合状态复用这一条框架功能主线，先解决它与原生请求调度的配合。共同编译准备必须同时给vLLM；不能把共同能力包装为DeepInfer独家优势。也不能用114的C4与129的C8拼接达标。

下一项工作限定为**已有源码和证据的调度契约审查，最多90分钟，0模型加载**：

1. 确认HTTP接纳、C++ waiting、状态检查点及异步两批在途之间的实际先后关系；只定位与“小批次/打断在途decode”相关的路径。
2. 判断是否存在可修的无必要串行或过早派发，且不需要增加benchmark请求、预热、内存、虚构到达时间或模型数值试验。
3. 输出一个可证伪的实现提案，或明确“证据不足，不能放行”。若提出改变prefill优先级或聚合方式，必须解释首token延迟/饥饿的代价以及vLLM是否已有对应共同能力；不直接扫interval参数。

这不是新NPU阶段。129阶段已关闭，130/131条件未触发，均未运行。累计裁决截止仍为北京时间11月13日14:53，不因本次分析延长。若后续有可放行提案，必须另列明确干预、必要证据、预算和停止条件；不能把Goal active视为自动获得下一次加载额度。

剩余交付仍包括：一个同版本双档达标候选、共有准备一致的新强参考、同源码特性关闭对照、质量判据下的有效性和可复现发布。**当前没有可信的“再跑一次就结束”依据，也没有新增性能成绩。**
