# 129 候选：补齐共有编译准备，验证混合状态复用收益

2026-11-13。**当前是源码准备完成，NPU 未验证。** 性能仍以 [128 实测](native128-result-20261113.md) 为准：C4/C8 相对强参考 117 为 +25.03%/+43.86%，双档 30% 未通过。默认代码保留 114。

## 问题与证据

128 的 C4 还需净省 1.095376 秒才达到历史参考的门槛。正式区间内状态复制每 rank 合计仅数毫秒，而一次没有状态复制的原模型调用/前序等待约 1.690 秒。继续复制微优化没有足够收益量级。

本次只读已结束作业的实际 rank 编译缓存、固定 SDK 源码和原始流式时间戳，没有加载模型：

| 证据 | C4 慢调用 | C8 慢调用 |
|---|---|---|
| rank0 原模型主机区间 | 约 1.690 秒 | 约 1.740 秒 |
| 新编译模板请求数 | 1 | 5 |
| 对应 kernel | `_copy_conv_state_kernel` 读/写两种方向 | 同左 |
| 8 rank 缓存写入 | 均落在各自慢调用区间内 | 均落在各自慢调用区间内 |
| 区间内流式输出事件 | 0 | 0 |
| 后续完全相同分段对照 | 没有 | 约 0.281/0.288/0.285 秒 |

固定源码 `vllm_ascend/ops/triton/kda/conv_state.py` 中，`REQUESTS` 和 `WRITE_BACK` 均决定编译特化。96 份相关缓存元数据覆盖 8 rank、6 种请求数、2 个方向。原共同准备只覆盖 slot mapping/indexer，没有覆盖这个 kernel。

这是一次干预的充分依据，不是端到端收益已经证明：缓存修改时间只说明产物写入完成，不能当编译开始/结束；C8 后续调用也不是受控重复实验；C4 1.690 秒包含正常计算和等待。不得直接把慢调用时长从正式成绩中扣除。

## 下一次实验只回答什么

`提前编译共有模板 → 正式区间不再发生对应编译 → 原请求批次是否净提速，同时保留合法状态复用`。

先运行一次候选的原工程检查与完整 C4→C8。通过历史双档筛选及有效性检查，才运行同源码关闭状态复用和同期强参考各一次。三组使用相同共有准备；不加单边预热、不挑慢参考、不把 114 的 C4 和 128/129 的 C8 拼起来。新参考可能更快，因此通过旧 117 的门槛不代表最终通过。

本阶段最多 1 次候选加 2 次条件控制，截止与停止规则见 [当前反思和计划](after128-reflection-and-plan-20261113.md)。没有第二候选额度。若编译仍迟到、状态路径失效、收益不足或控制推翻结论，报告对应失败，不自动改名续开参数搜索。
