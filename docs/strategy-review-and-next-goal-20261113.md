# DeepInfer 性能路线复盘与下一轮目标

更新：2026-11-13，北京时间。依据135、137、136实际回执、原始计时及固定源码。本文替代此前三臂启动前的反思；旧文及旧计划已归档。本文为发布时快照，实际归属由现场唯一计划和检查点维护。

**结论：过去的推进确实存在安排问题。已经做出了能运行的原生接入和一个有价值的C8候选，但尚未证明共同优化匹配后的双档30%优势，也没有完成新增机制的因果对照。下一轮应结束这项证据欠账，按结果决定路线去留；不能继续预设“总有一个参数能凑够30%”。**

复盘阶段仅核查已有证据，未新增模型加载。随后已执行R1并启动138参考；实际管理器、容器和模型引擎存活，139/140已部署尚未运行。具体见文末执行更新。原生Goal仍active，目标未完成。

## 二、为什么此前没有收敛

### 1. 把框架名称当成性能收益来源

当前请求路线确实是DeepInfer引擎 → C++ scheduler → Worker → GLM适配层 → 固定SDK模型计算。但GLM入口明确关闭 `DEEPINFER_ZERO_OVERHEAD_SCHEDULING`，Worker的GLM分支在进入通用ZOS执行分支前就返回。

因此，**原生框架接入成立，原有ZOS优势尚未成立。** 参考vLLM也已有异步、设备端token与位置更新、图执行等能力。把现有异步代码换个名字不能算独家技术；贸然打开ZOS开关又会跨越混合缓存、MTP接受数量和异步生命周期契约，不能当成小改动。

双方共用大量模型计算与NPU算子后，额外优势只能来自明确的工作量减少、等待消除、计算通信重叠或更有效的批处理。如果从完全相同的耗时基线只靠消除一部分成本达到1.3倍，至少须消除约23.08%的总时间；这是数学关系，**不是已经测得的可优化空间**。

### 2. 小改动试了很多，关键对照却一直欠着

此前先看候选是否过30%，再决定是否做机制关闭对照。这使得候选不断变，收益归因迟迟没完成。另一些改动虽然触发了，例如减少元数据操作、缩减MTP输入行数，最终吞吐却没有相应提高。

问题不在于应该取消必要验证，而在于**验证没有及时改变采用或否决的决定**。整套模型初始化通常以十几分钟计，正式两档计时只是几十秒；每个无清晰因果问题的新变体都会支付这笔成本。

### 3. 把温缓存收益当成冷请求通用优势

135正式C4只跳过384个纯prefill token，占当档对应调度量约1.22%；C8跳过5120个，占约41.67%。这个分母是“纯prefill调度token”，不是整个模型总算量。C8承接C4留下的状态，重复输入条件必须披露。

这能解释为什么缓存值得保留，却不能单独补齐冷请求的全部差距。继续只增加缓存变体，不是可靠的双档达标路线。

### 4. 预算写了，但通过更名阶段继续探索仍可能失控

上一135/137/136阶段已经花完3次模型加载：候选成功，公平参考和机制控制都没有验收通过。失败产生了信息，但不能当成完整交付。新计划明确保留旧账、限定新增投入，不把“Goal仍active”当作无限重试理由。

参考137比值无效；不能扣掉几段编译时间“修正”分数，因为编译还可能影响到达、分批和MTP轨迹。若仅用这组无效原始计时作量纲说明，C4距1.3倍还差约1.218秒，C8仅有约0.251秒余量。**真实缺口必须由有效新参考重算，这两项不是达标门槛或保守收益保证。** 旧115/117的C8曾有约11.52%的同配方跨批漂移，因此也不能把擦线单批当稳定优势。

优先级作如下裁决：

| 方向 | 判断与下一动作 |
|---|---|
| 完整混合状态复用 + 原生准入配合 | **最接近形成真实特性成果。** 保留135，完成同源码开关对照；停止追加缓存变体。它是当前固定实现间的差异，不能未经全生态核查就说vLLM永远没有同类能力。 |
| C4批次构造与执行依赖 | **若继续研发，先查这个范围的实际成本。** 135的C4已经组成8个四请求组，C8组成4个八请求组；固定C4下再等待“凑更大组”不会凭空多出请求。需要找重复准备或无必要等待，不能再盲调组大小。 |
| 原生稳定decode中的元数据准备、接受数量回传、输出回收 | 只在证明存在足够大的、未被重叠隐藏的成本后放行一个窄改动。当前仍没有足够收益证据，**不直接重做全套ZOS**。 |
| KDA/DSA/MoE数学重写、CPU/NPU逐位追差、MTP置信度变长大改 | 当前性能阶段不做。已有参考算子与高接受率证据，不支持把这些当成眼前30%的捷径。 |
| 状态复制的毫秒级微优化、继续扫参数 | 停止。已有量级不足以解释数秒端到端缺口。 |

135的C4请求占用账目为：首token前7.638秒、首token后18.729秒、空槽0.055秒，合计26.422秒。这只是逐请求时间求和再除并发数，**不是NPU关键路径，也不能把18.729秒都叫decode算子时间**。它说明后续完成阶段值得核查，不授权按比例承诺收益。

旧126抽样图中，某rank约44.19毫秒区间已有43.71毫秒被计算/通信覆盖；该次profile导出失败且不代表当前正式全程。这个有限证据至少不支持“GPU/NPU大段空闲，换调度就能白捡30%”的说法。不开新的大规模profile工程来填满报告。

## 四、两个具体失败如何处理

**137：原因明确。** 共有预编译遗漏卷积状态复制 `index_stride=1` 的专用签名，真实请求触发编译，且落在C4和C8正式计时窗口。最小修正草稿已经覆盖捕获步长及步长1、请求数1–8、读写方向；4项元数据检查通过；后续已部署至138/139/140执行包，NPU结果尚未验收。下一轮将同一修正给所有比较臂，保持模型源码、请求、缓存总预算与采样不变。

**136：失败层已明确，底层触发原因未知。** rank2、3在HTTP服务就绪前出现 `RunAicpuRpcSrvLaunchV2_allgather` AICPU异常及错误507018，运行时报告参数无效；随后两rank退出134，其余由管理器收尾。容器不是OOM，正式AIS结果为0，资源已释放。不能把这归成精度问题、确定硬件损坏或确定超时，也不能声称改一个等待时长就修好了。

只做有界的初始化顺序、已记录设备身份和日志核查，不改系统驱动、不重启他人服务、不盲增超时。若无确定修正，最多在下一比较臂内做一次原配置恢复尝试，必须如实标“原因未闭合的恢复尝试”；再现同因错误即停止该支，不另外加载模型做无边界诊断。

## 六、达到与达不到时分别怎么做

1. **两档都达到且有效性、机制归因与波动证据支持：** 发布限定于本负载、缓存初态及延迟范围的性能结论。单批擦线或漂移足以改变判断时仍写“尚未证实”；本轮不靠反复补测挑出最好成绩。通用质量另列未验收，不能偷换成全面交付。
2. **机制有收益但任一档不到30%：** 按 `D = T_native − T_reference / 1.3` 分别列缺口。新研发必须指出一处能在关键路径上净省至少对应D的成本，并解释新增开销、另一档退化和状态正确性；毫秒微优化不抵充秒级缺口。
3. **控制无收益或有明显延迟代价：** 否决该机制在本负载上的相应主张，保留可运行基线，不继续缓存参数网格。
4. **参考或运行无效：** 给出具体错误、失败时间、资源归属和下一恢复条件；不把0个有效结果写成“还差一点”。

**当前没有证据保证再投入两天就能取得通用、稳定的30%。** 下一轮可以承诺的是有界工作和明确决定，不能承诺不存在的性能空间。若可信上限不足，后续应向用户说明“当前限定路线不足以支撑目标”，保留完整Goal未完成；更换模型、负载、硬件或降低门槛均不得擅自进行。
