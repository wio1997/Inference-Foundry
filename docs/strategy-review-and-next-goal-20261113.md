# DeepInfer 性能任务：当前反思、突破口与下一轮交付

日期：2026-11-13，北京时间。本文依据已回收的测试结果、固定源码和当前作业身份；不把计划当结果。本文为发布时快照；现场进程归属以执行检查点为准，本文文末说明已完成结果与尚未运行的对照。

**判断：此前安排确实缺少收敛。现在主要欠缺的不是另一个算子精度实验，而是证明某项框架机制在同一版本、两档并发上带来净收益。下一轮只完成一个固定三臂对照与路线裁决，不再同时增加优化候选。30%仍是目标，不能提前保证必然达到。**

## 1. 先分清：适配成果、框架特色和30%目标

已有请求确实经过 DeepInfer 引擎、C++ scheduler、Worker 与完整模型执行。默认版本114完成既定72请求及8rank正常退出，这是真实的适配成果。

但当前GLM路径并没有把DeepInfer原有特性全部用起来。本轮重新核查135源码：

- `glm5_full_model_offline.py` 明确设置 `DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0`。
- `worker.py` 的GLM分支直接调用 `glm_adapter.execute_model_step`，绕过后面的通用ZOS执行分支。
- 目前已有两批次在途的异步MTP执行；固定参考也有异步、设备端token/位置更新等能力，不能只因实现名字不同就说是独有。

这些事实意味着：**不能把原生接入完成，等同于已证明DeepInfer完整的零开销调度优势。** 同时，也不能直接打开ZOS开关：GLM的混合状态、MTP接纳数量和异步回收需要匹配，已有源码审查没有证明移植它能补足当前端到端差距。

当前模型计算、NPU算子、图和多项并行优化与参考共用实现。换调度框架本身不保证额外30%。若只靠完全消除某段开销来达到1.3倍，该开销至少须占参考总时间的约23.08%；目前没有这一级别的可消除调度成本证据。这个数学条件不是当前硬件的实测上限。

源码身份和行号见 [本轮证据](../validation/shared-features-20261111/strategy-review-135-three-arm-20261113.json)；固定参考能力审查见 [既有ZOS差异审查](../validation/shared-features-20261111/native-zos-glm-delta-audit.json)。

## 3. 安排上的具体问题

**第一，特性名称先于关键路径证据。** metadata图化、MTP缩行等改动确实命中，但124两档退化，125的C8仅比114高约0.06%。少几行输入、少一次CPU操作，并不等于端到端更快。

**第二，把测到理想数字当成做归因对照的前提。** 此前每个候选必须先双档过30%，才运行新参考和关闭机制的控制。候选变化了多次，最重要的归因仍没完成。这个流程可能筛掉坏候选，却不能回答已有C8改善有多少来自新机制。

**第三，冷请求与复用请求的收益被混在一起。** 129正式C4只复用了2个请求、跳过768个target prefill token；C8复用了16个、跳过5120个token。C8承接C4留下的状态，所以缓存路线天然更有利于后面的复用流量。它不能自动证明冷请求也快，更不能证明任意业务都快。

**第四，小组冻结可能把有价值的缓存收益抵消。** 132的C8出现1请求和3请求的decode组，分别持续约2.095和2.303秒，其他已创建请求直到组结束才接纳。此前“冻结时已排队7/5个”是从对象创建及紧接入队源码作出的推断，不是直接qsize采样。135修正冻结前的可接纳工作判断，并记录直接队列快照；还需看实际是否减少阻挡。

**第五，每个阶段有预算，整个过程仍可能靠另开阶段延长。** 最近核对的7个已完成模型作业，manager生命周期约16.5–18.8分钟，两档正式计时合计约43–48秒，占4%左右。其余包含加载、编译、工程用例、预热、清理，并非全是浪费；但这说明再试一个随意变体的成本很高。解决办法是减少无决策价值的完整加载，不是另造运行平台。

## 4. 突破口的优先级

| 方向 | 现有依据 | 本轮决定 |
|---|---|---|
| 完整混合状态复用，减少重复prefill | 已有真实命中、跳过token和C8改善；独立净贡献尚未测出 | 保留为唯一待裁决的新增机制 |
| 修正冻结前的请求接纳 | 132已有小组冻结及长等待，135有最小源码修正 | 完成正在运行的135，不新增组大小或等待阈值变体 |
| 再优化状态复制 | 129正式C4每rank复制stream区间约2.45–4.57毫秒 | 停止；不能用毫秒级范围解释数秒缺口，且不能跨rank累加当可回收时间 |
| 重写KDA/DSA/MoE数学算子 | 当前无证据能补足该吞吐缺口 | 不进入当前性能阶段 |
| 将原生ZOS完整移植到GLM | 原生分支未接通，但参考也有部分等价机制；当前可回收成本不明 | 作为未完成架构能力记录，不自动启动另一轮移植和验证 |

状态复用缓存的是KDA递推/卷积、DSA相关缓存与必要hidden，仍走正常采样和MTP；不是缓存生成答案。其1GiB状态区从原4GiB预算扣除，普通池剩3GiB，容量代价也要计入。

## 6. 何时接受，何时停止

- **可接受的限定成果**：同一135源码两档都超过匹配137至少30%，有效性成立，新增机制有可解释贡献，并明确负载、温缓存和延迟范围。旧117同时披露；若漂移足以改变结论，标记未证实。
- **机制有效但未到30%**：发布真实收益和剩余秒数，保留可复用成果；不能把Goal标完成。
- **关闭机制反而更快或因果无法解释**：否决该机制在本负载上的交付主张，停止继续改缓存参数。
- **执行/状态错误**：先判实验无效，停止依赖臂；不把失败算完成，也不重启无限精度排查。

三个臂后不自动追加新候选、另开命名阶段或顺手移植ZOS。若仍未达标，下一份成果应明确“当前路线不足以支持30%”及具体缺口，而不是继续以更多试验轮数代表进展。

本轮完成的是可核验的反思、预先记录的对照规则和有终点的计划。模型性能结果仍按实际回收情况报告。
