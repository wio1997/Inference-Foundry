# DeepInfer 性能阶段裁决：124不采用，保留114

2026-11-13，北京时间。范围：Ascend910C / aarch64 / 8 die、GLM-5.3-Flash W8A8、固定AISBench 1024输入/256输出、C4/C8。

**本阶段得出了否决结论，没有拿到新的性能突破。124的新元数据执行路径已实际运行，整批成绩低于保留版本114，因此不合入默认运行路径。双档同时领先固定强参考30%的目标仍未完成。**

## 4. 此次反思需要纠正的具体判断

1. **减少Python构建调用，不等于减少端到端关键路径。** 124仍需复制动态输入、提交图、维护返回对象，还存在首次捕获/校验和回退。没有独立测出这些净成本前，不能由1700次调用减少推导速度提升。
2. **把局部重复工作放进图，并不自动减少模型计算或通信工作量。** 这次保留了全部target/draft计算；原生完成批次数甚至增加。最应寻找的是能少做真实工作或消除串行依赖的干预，而不是继续叠加图包装。
3. **工程门禁应覆盖真实对象关系。** 123缺少三后端/两物理组的真实fixture，浪费一次加载。这是实现前的检查遗漏，不是需要更严的CPU/NPU模型精度容差。
4. **命中、正确性、收益必须分别记账。** 124机制命中和有限工程请求通过成立；输出变化影响未知、吞吐采用条件失败也成立。不能把运行成功写成突破。
5. **预算必须产生去留结论。** 本次保留原14:40:39起点和次日02:40复盘点；123失败后只追加一次有具体根因的124工程修正确认。现在已完成裁决，不开启第三次加载、不调计划容量、不追一个更好分数。

当前没有证据证明新增拷贝、首次捕获、容量回退、调度差异或MTP接受率中的哪一项是唯一退化根因。它们是待验证解释。为了一个已经不采用的候选逐项穷举，正是这次要停止的做法。

## 6. 后续工作的放行条件

**当前没有已经验证、可以承诺达成30%的新突破口。下一步不默认再加载模型。** 方向仍在DeepInfer调度与设备执行交接，但必须从“包装同样的工作”转成“消除已证实的重复工作或串行依赖”。

下一次推进只先做一次**最多45分钟、0次NPU加载**的离线决策：利用已回收的114/117/122/124执行记录和固定源码，针对原生批次形成、SDK输入准备、MTP结果交接三处，选出至多一处固定参考没有的可消除工作。产物必须列明实际调用链、输入/输出所有权、哪些工作可删除、哪些仍必须执行，以及现有证据能否区分它与NPU计算重叠。不要重新整理一遍热点排名或声称不完整trace代表设备空闲。

只有出现**新的具体证据**，并能提出一个范围明确、可否决的改动，才另列实现预算和一次硬件裁决；这不是预授权第三次124试验，也不是保证继续跑就能达标。如果仍只有“可能更快”，结论必须是当前没有足够依据追加昂贵试验。原N0—N4预算不重置，这项离线决定单独记账。

剩余交付分三项：①一个真正改善端到端的固定候选，目前尚无；②同一候选固定C4/C8均达≥30%，当前仅114的C4单批越线；③对应机制贡献、输出边界和必要重复性证据，避免由运行波动产生假优势。当前不能据此给出“两天必完成”的日期。
