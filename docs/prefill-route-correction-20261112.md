# DeepInfer：prefill 路线纠正与下一阶段放行条件

日期：2026-11-12。本文更新此前的 RP6/RP7 决定。目标仍是固定 910C/8 die、相同可用共有优化、正式 AISBench C4/C8 同一候选均领先固定 vLLM 参考至少 30%。该目标未完成。

## 1. 当前判断

**此前的问题不只是测试过多，更在于没有先证明候选能改变足够大的端到端成本。** 最近的实验关闭了一些假设，但仍未形成有硬件证据的独有执行能力。不能把更多模型加载、开关数量或测试轮次当成交付进展。

本轮源码审查得到两个会改变实施顺序的结论：

1. **否决 RP7 的原方案。** 保持当前 AllToAllV 计算路径不变，直接捕获完整 prefill，不满足正确重放的条件。原因已经在源码中出现，无须为此加载模型试错。
2. **纠正“共有优化已核齐”的判断。** 固定 SDK 有 `enable_prefill_mc2`，而最近的 102/104 两侧均未开启。已完成双侧接入和实际通信观察，源码提交 `ba853d0f283246b0079e964418063523c036da07`；硬件仍未验证。这是共有能力，不是 DeepInfer 独有创新。

## 3. 为什么原方案不能直接做

固定源码 `TokenDispatcherWithAll2AllV._preprocess` 使用实际专家路由结果：

```text
本批 topk_ids
  → 专家 token 计数
  → input_splits / output_splits 拷贝到 CPU 并转 NumPy
  → 按这些长度执行 AllToAllV
  → 依赖本批计数的重排与专家计算
```

相关位置为 `token_dispatcher.py` 的 `_preprocess`（约 616–660 行）及 `token_dispatch`，不是固定形状的静态调度描述。捕获时生成的 CPU split 不会因为下一请求的 NPU tensor 内容改变而自动重新计算。将它们固化会有重复使用旧路由长度的风险。

因此，仅稳定 KDA/SFA 元数据地址、固定总 token 数或换一个 graph mode 都不够。原 RP7 明确规定：必须大改后端或改变共有配置才能实现时，停止该分支。本轮已经按该条件停止，未运行该原型。

## 4. 新发现的共有能力实际改变什么

固定 A3 硬件 profile 使用 `FUSED_OR_CAPACITY` 策略；已完成参考104的实际配置中 `enable_fused_mc2=0`。源码会在 token 数不超过 MC2 容量时选 MC2，超过容量时选 AllToAllV。

| 项目 | 最近实测配置 | 新准备的共同配置 |
|---|---:|---:|
| `enable_prefill_mc2` | false | true |
| `max_num_batched_tokens` | 1792 | 1792 |
| TP | 8 | 8 |
| 源码计算的 MC2 总容量 | 48，来自最大 decode 捕获尺寸 | 1792，来自批 token 上限 |
| 每 rank 容量 | 6 | 224，低于该路径 512 上限 |

这里改变的是**现成专家 dispatch/combine 通信路径的适用范围**，没有修改权重、KDA/DSA 数学实现、输出长度或草稿数。原有 HCCL 缓冲保持 400 MiB；真实运行是否兼容仍须验证，不能仅凭上表宣称已通过。

原生新增 `--prefill-mc2`，传入同一个 SDK `additional_config.enable_prefill_mc2`。参考使用对应的 `--additional-config` 字段。两侧安装字节相同的观察代码，统计原始 selector 返回的通信方式，不替换返回值、不读回模型 tensor。

验收观察的是：8 个 rank 上的配置值、实际容量、硬件策略，以及正式请求期间“大于最大 decode 尺寸的目标模型批次”确实选用 MC2。计数必须扣除启动阶段。参数为 true 本身不是生效证据。

## 6. 下一阶段如何收敛

**主方向仍是减少 prefill 的主机提交和运行器准备成本，但先把共有通信条件补齐。** 当前两侧复用同一模型计算、量化权重和大部分设备算子，仅优化 DeepInfer 调度入口不必然能再省 30%。C4 是更紧的性能约束，任何候选都必须解释它能省掉哪些 C4 成本。

| 顺序 | 唯一问题 | 允许的工作与预算 | 放行或停止 |
|---|---|---|---|
| A：共同基线 | prefill MC2 在当前模型/硬件/组合下是否实际可用？ | 复用已准备配置；取得原同组资源后，一次参考加载，通过后一次原生加载；复用原4项工程检查，计分负载不变 | 出错保留具体异常并收尾；不得展开通信参数网格。只改启动脚本不算通过 |
| B：执行路径决定 | MC2 下是否还有足够大的、DeepInfer 能改变的 prefill 主机成本？ | 先用已有 trace 与源码；重算新参考门槛。最多一次完整调用链可捕获性决定，不再纯观测加载，不写第二套调度器 | 如果只能靠大改模型/量化、测试专用缓存或关闭参考优化成立，否决；不因想达到30%而放宽 |
| C：一个候选 | 能否把同一模型的重复主机发射变成可复用的原生执行单元？ | 仅在 B 有具体可省成本和完整状态方案时实现；当前原 RP7 不自动恢复。必须保留首次构建成本、固定地址更新、请求状态隔离与回退 | 一次有界工程验证不通过即停该分支，不能只因最终吞吐未改善就无限加开关 |
| D：正式判定 | 同一候选是否在两个档位都达到目标？ | 只在机制及工程通过后做开/关与新参考对照；接近门槛时才做必要重复，保留负结果 | 两档同一候选、相同条件、质量护栏及自然波动证据同时满足才完成；禁止拼接最好成绩 |

原 6/12 小时投入预算不重置：北京时间 14:40:39 起计；20:40 为路线决定点，次日02:40为单候选投入上限。资源等待单独记录，不当作工程推进，也不据此另开一个“再两天”的承诺。RP7 已提前得到否决结论。上述时间是**决定是否继续投入的截止点，不是30%达标承诺**。

若 B/C 在预算内仍给不出足够的可省成本和可运行候选，应直接交付“该路线未证明能达到30%”及证据，明确需要架构重构的范围。不能靠自动续跑延长一个没有收益依据的方案，也不能擅自把原30%目标标成完成。
