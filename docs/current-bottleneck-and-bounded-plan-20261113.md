# DeepInfer 当前瓶颈、反思与有界交付计划

日期：2026-11-13。目标仍为：910C / aarch64 / 8 die 上，GLM-5.3-Flash W8A8 通过 DeepInfer 原生调度与 Worker 执行；正式 AISBench C4、C8 在**同一个源码版本**上，分别超过匹配共有优化的强 vLLM 参考至少 30%。完整目标尚未完成。

## 1. 我的判断

此前安排确有问题。早期同时处理模型计算语义、状态接入、低精度边界和运行器，后期又容易把局部热点的改善当成端到端路线成立。验证发现了问题，但未始终转化成稳定可交付的版本。这不能用“任务很难”或“已运行很多轮”抵消。

当前应把任务进一步收缩为：**保住已运行的原生模型与共有能力，解决冷请求 prefill 和已有 decode 的调度关系，验证完整混合状态复用是否带来可归因的端到端收益。** 不再重写数学算子，也不继续做 CPU/NPU 逐位精度追逐。

不能保证任何优化必然得到 30%。能够承诺的是每个候选有固定源码、原始数据、有限投入和去留决定；失败不通过换阶段名称继续扫参数。

## 2. 已有数字到底说明什么

下面都是已完成批次的原始 AIS 时间重算结果，不是性能预测。每档 32 请求，1024 输入、256 输出；共计每档 8,192 输出 token。

| 版本 | C4 输出 token/s | C8 输出 token/s | 能得出的结论 |
|---|---:|---:|---|
| 强参考 117 | 228.578 | 415.610 | 历史固定参考；新增共同编译准备后需要新参考。 |
| 保留的默认版本 114 | 306.942 | 501.220 | 相对 117 为 +34.28% / +20.60%，未同时达标。 |
| 混合状态批量复制候选 128 | 285.796 | 597.893 | 相对 117 为 +25.03% / +43.86%，C4 仍不足。 |
| 共同编译准备候选 129 | 260.915 | 630.825 | C8 更快、C4 进一步退化；不作为默认版本。 |

129 相对旧 117 的 +14.15% / +51.78% **只能做历史筛选**，因为旧参考缺少这次新增的共同编译准备。不能拼接 114 的 C4 和 129 的 C8，更不能把 129 的 C8 数字说成整个框架领先 51.78%。

129 的 C4 用时 31.3972 秒；相对旧参考的 30% 门槛，需要降至 27.5684 秒，尚差 **3.8288 秒，即再缩短约 12.2%**。这给候选选择提供了量级：几毫秒的复制优化解决不了数秒的缺口。

## 3. 哪些方向应结束，突破口在哪里

| 方向 | 已有证据 | 下一步判断 |
|---|---|---|
| 继续优化状态复制 | 正式 C4 每 rank 的复制 stream 区间合计约 2.45–4.57 毫秒 | 停止；量级不足。不得跨 rank 相加当可回收时间。 |
| 继续补同一组卷积编译模板 | 129 消除了受监测的服务期迟编译，但 C4 更慢 | 这项局部问题已解决；不能继续据此许诺整体收益。 |
| 重写 KDA / DSA / MoE 数学算子 | 当前有可执行模型，没有证据证明此处能填补当前吞吐缺口 | 不进入本阶段。 |
| 新请求的 prefill 穿插已有 decode | C4 同样的计算 token 被拆成 25→35 次纯 prefill，单请求分段 2→17 次 | 当前唯一进入硬件验证的因果假设。 |
| 完整混合状态复用 | 129 正式 C4 / C8 分别复用 2 / 16 请求，跳过 768 / 5,120 个 target prefill token | 保留；需同源码关闭控制来证明贡献。 |

129 比 128 的 C4 整批慢 2.7334 秒。按客户端占用时间记账，首 token 前折算改善 2.0098 秒，首 token 后增加 4.5979 秒，空槽增加 0.1453 秒。其中 3.0501 秒新增首 token 后时间与纯 prefill 主机区间重叠。这是选择调度方向的证据，**还不是可直接回收的硬件耗时**。

进一步核对，17 次单请求分段中有 14 次确实只有一个请求在等待首 token，其他请求已经在生成。因而“把已有等待请求凑批”的逻辑不能凭空补出批次；几毫秒的收集等待也没有充分依据。要验证的是更明确的请求接纳策略。

## 4. 一个固定候选：请求组准入

132 源码固定为 `8e22eb568a5f8ed1e757da4a5053f3076d66386e`，基于 129。新增默认关闭的 `--native-admission-cohort`；3 个 Python 文件变化，模型数学、权重、采样、C++ 扩展均未修改。

```text
HTTP 请求进入原有有界队列
            ↓
接纳当前可用请求，由 DeepInfer 原生 scheduler / Worker 做 prefill
            ↓
当前组开始 decode → 新请求继续排队，暂不加入模型执行
            ↓
当前组全部结束 → 立即开放下一组
```

组内请求不会被后到的新请求不断延长；没有固定等待时长、硬编码 C4/C8、识别评测题目或缓存生成答案。已接纳请求继续使用原有计算与状态协议。

**这是吞吐优先策略，可能增加新请求的首 token 等待。** 排队时间全部计入 AISBench，不从分母扣除。服务回执明确该模式不是原连续接纳模式。若快了但延迟明显变差，报告必须称为权衡，不能包装成所有在线业务都更优。

“组准入”是通用调度思路，不能仅凭 DeepInfer 多了一个开关就称为独有技术。需要证明的实现差异仍是当前原生路径的完整 target 混合状态与 hidden 复用，并用固定参考的实际能力和同源码关闭控制验证它。共有算子、图、MTP、并行和编译准备继续匹配。

本节规定决策规则；进程与资源的实时归属以现场检查点为准，不能用本文件替代现场核验。

| 步骤 | 验收产物 | 投入上限 / 触发条件 | 结果如何改变决策 |
|---|---|---|---|
| A0–A2：源码与固定包 | 调度契约审查、8 项元数据检查、命令与共有 helper 对照、控制设计 | 已完成；不再重复 | 只允许固定 132 进入硬件，排除参数网格。 |
| A3：132 一次正式候选 | 原始两档 AIS、请求组事件、状态计数、真实 worker / 扩展身份、退出释放 | worker 25 分钟，manager 27.5 分钟；本阶段只 1 次候选 | 两档历史筛选均过且执行有效才进入控制；失败就关闭本候选。 |

已有累计裁决截止仍为**北京时间 11 月 13 日 14:53**，包括加载、等待、失败和恢复，不重新计时。这是作出去留决定的截止，**不是保证 30% 目标必然达成的日期**。若候选失败，不把未触发的两个控制额度挪来试新参数；剩余问题和未完成原因必须明示。

测试共享同一卡组与性能条件，三次模型负载串行；本机的原始结果分析、复现记录整理可以与模型初始化并行。无需新增代理、cron、调度平台或其他模型会话。

## 6. 接受结论所需的最小证据

1. 同一 132 源码、同一正式负载，在 C4、C8 均达到相对新 134 的 1.30 倍；不拼版本。
2. 权重、设备、内存上限、共有优化、输入输出、预热和计时口径匹配；参数不同须说明是否就是被测特性。
3. 真实请求组事件证明策略执行，完整状态计数证明命中和释放；所有请求、rank、容器和占用有终态。
4. 133 用于证明状态复用的贡献；若不能支持因果结论，就如实写“尚未证实”，不能只报两框架比值。
5. 同时披露 TTFT、TPOT、排队等待、文本变化与统计范围。已有 129 对参考每档 25/32 完整文本一致，仅是诊断观测；通用质量尚未验收。没有约定逐位一致门槛，不把自由生成差异直接当缓存错误，也不将请求成功直接当质量通过。
6. C8 继承此前 C4 留下的状态，收益适用范围是当前请求顺序和复用率。不得外推为冷流量、任意业务或全部并发均领先。

## 7. 后续汇报方式

每次只汇报四件事：本次关闭了哪个假设；哪个可交付版本发生了变化；端到端双档和延迟是否更好；剩余门槛是什么。源码检查、已派发、进程存活、报告数量都不计作性能突破。

当前候选只在明确的调度假设上前进。如果这条路线不能同时改善双档，就交付否决结论和可用的 114 基线，指出“普遍领先 30%”尚无证据；不会继续用增加实验轮数代替路线判断。
