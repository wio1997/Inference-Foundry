## 2. 机制确实执行，失败也定位到具体动作

全部 72 请求的事件记录满足：16 个请求组完整开始、结束；没有在已冻结的 decode 组内新增接纳；准入与退出计数闭合；事件没有丢失。组策略不是只设置了参数而没有执行。

C4 形成 8 个四请求组。与 129 相比，纯 prefill 调用 35→25，单请求分段调用 17→2；实际计算的纯 prefill token 保持 30,720。首 token 后的请求占用面积除以并发数，从 23.7093 秒降至 19.3868 秒。它支持“减少交错有助于这批 C4”的方向，但历史单批比较仍不等于隔离的因果收益。

C8 形成的 6 个组依次为 **8、1、7、3、7、6**。关键事件如下：

| C8 组规模 | 冻结组时已在 HTTP 队列、尚未接纳的请求 | 该 decode 组持续时间 | 该组开始前的实际 target prefill token |
|---|---:|---:|---:|
| 1 个请求 | **7 个** | **2.094566 秒** | 0，命中已有状态 |
| 3 个请求 | **5 个** | **2.303167 秒** | 0，命中已有状态 |

这些等待请求确实直到对应组结束后才获准接纳。源码在首次 decode 返回后冻结当前活跃集合，没有在冻结决策中考虑这时已经进入 HTTP 队列的待接纳请求。**本次设计遗漏了已有排队请求对冻结边界的影响。** 热状态路径很快进入 decode，把小组冻结，放大了等待代价。

这组记录直接证明了阻挡行为和对应等待区间；不能据此把两个组的全部时间相加，当成修正后必定可回收的端到端收益。还没有运行另一种调度，不能预测它一定达到目标。
