## 2. 本次真正回答了什么

原假设：把正式请求中的首次卷积状态 kernel 编译移到双方共同的启动准备阶段，可能补足 128 的 C4 缺口。

实际结果分开记录：

- **干预确实执行。** 8 rank 各完成 16 个卷积状态编译模板，覆盖请求数 1–8、读/写两个方向；新增模型 forward 和 kernel launch 均为 0。
- **受监测的服务期编译已消除。** 8 rank 的 slot mapping、indexer、卷积状态 kernel 延迟编译记录均为空；不能外推为所有运行时都没有首次使用成本。
- **旧的大额原模型调用没有重现。** 129 的状态包装器记录中，正式区间没有超过 500 毫秒的主机调用。
- **C8 有方向一致的变化。** rank0 正式 prefill 原模型调用/前序等待区间合计由 2.594 秒降至 1.154 秒；整个 C8 批次少 0.715 秒。不同时间域不能相加，也不能用单批对照证明全部差值来自编译。
- **C4 没有转化为净收益。** 记录到的正式 prefill 调用从 25 次增至 35 次，原模型调用/前序等待区间合计从 8.302 秒增至 9.929 秒。两批都是复用 2 个请求、跳过 768 个目标 token，直接复制仍只有数毫秒。

因此，**“延迟编译是剩余 C4 缺口的充分解释”不成立。** 该问题真实存在且已被修复，但不能再据此承诺完整模型会跨过 30% 门槛。新增的分批变化与时间增加属于已有证据，具体因果尚未证明；不能立即宣布调度器有 bug，或再把问题归到 KDA 数学精度。

含工程和既有预热的全作业计数中，调度批次由 660 增至 689，MTP 拒绝草稿数由 373 增至 597。这些不是正式 C4 的独立计数，不能把它们直接全部归为 C4 退化原因。
