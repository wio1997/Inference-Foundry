# 135 源码修正：冻结前先处理已有排队请求

## 已定位的问题与证据边界

132 的 `after_step` 只依据 decode 阶段和活跃集合冻结请求组，没有读取 HTTP 队列及剩余准入容量。一次短的状态命中可以迅速进入 decode，把当时的小组固定下来，后续请求必须等整组完成。

原始记录中，C8 单请求组开始前约 112–116 毫秒，另外 7 个请求对象已经创建；三请求组开始前约 117–120 毫秒，另有 5 个请求对象创建。它们分别在约 2.095 / 2.303 秒的组结束后才被接纳。

**需要纠正此前报告的证据口径：** `queued_monotonic_ns` 在 `Pending` 对象构造时记录，下一行才执行 `waiting.put_nowait`。源码和时间间隔支持“这些请求已排队”的推断，但 132 没有记录冻结时的精确 `qsize`，也没有单独记录成功入队时刻。不能把 7 / 5 当作直接采样到的冻结点队列长度。请求创建到实际接纳的等待、组规模及性能退化都是实测；这项限定不改变 132 的否决结果。

## 最小修正

原逻辑：首次 decode 返回且有活跃请求 → 直接冻结。

修正逻辑：首次 decode 返回 → 读取当前 HTTP 排队数及剩余 HTTP 活跃请求/总请求额度 → 若有等待请求且有额度，暂不冻结，让原有准入循环再执行；否则冻结。

准入循环保留 `llm.get_num_unfinished_requests() < max_sequences` 等原有容量检查。未完成的原生 terminal reap 可能临时占着引擎容量，因此延后冻结不等于绕过原生引擎的容量限制：模型仍正常推进，由原有检查决定何时可以接纳。

已经冻结的组仍保持有限成员，不因后来的请求不断扩张。没有新增等待计时、组大小参数、C4/C8 特判、输入内容识别或额外预热；已有 `--native-admission-cohort` 开关保持默认关闭。模型数学、权重、采样、状态复用和编译扩展均未改变。

新增有界记录包括：延后冻结次数、决策时的 HTTP 队列快照、剩余 HTTP 准入额度。它们用于直接判断修正是否触发，不用请求对象创建时间推定当时队列长度。队列快照只代表读取时刻，不能保证之后到达的请求也被纳入当前组。
