# DeepInfer / GLM-5.3-Flash 性能攻关复盘与下一阶段计划

日期：2026-11-13，北京时间。范围：910C/aarch64、8 die、GLM-5.3-Flash W8A8；固定 AISBench C4/C8、1024 输入/256 输出。本文没有新增性能成绩，也不声称模型身份变化会自动解决问题。

## 1. 当前完成程度与实际差额

**适配已有可运行、可复现的有限负载版本；同一候选在两档都领先固定强参考至少 30%，并证明 DeepInfer 差异机制的贡献，仍未完成。**

| 正式负载 | 固定 vLLM 参考117 | 保留 DeepInfer114 | 本批优势 | 30%门槛 |
|---|---:|---:|---:|---:|
| C4 | 228.57797 token/s | 306.94205 token/s | +34.28% | 297.15136 token/s |
| C8 | 415.61018 token/s | 501.22023 token/s | +20.60% | 540.29324 token/s |

C8 整批目前 16.34411 秒，目标最多 15.16214 秒：还需净省 **1.18198 秒**，相当于当前时间再减少 **7.23%**，或吞吐再提升 **7.80%**。C4 整批目前 26.68908 秒，保持 30%优势只允许约 **0.87937 秒**的回退。

以上为已有可比批次，不是稳定收益保证。参考115较慢；同配置117的C8吞吐比115高约11.52%。不能挑较慢参考，也不能将不同候选的C4/C8最好分数拼成达标结果。

保留源码：`c4ec8e000d04966574970802ae01db76e57a01b5`。两侧正式请求、预热、实际启动命令和原始时间点见[114复现清单](../validation/shared-features-20261111/native114.json)及[117复现清单](../validation/shared-features-20261111/reference117.json)。图捕获、MTP、EP、共享专家重叠、DSA CP、prefix、prefill MC2等适用共有能力保持原匹配配方。限定负载工程通过不替代通用模型质量认证。

## 2. 之前安排的具体问题

### 将三个不同目标混在一起

“完整模型能在DeepInfer里执行”“把双方共有优化配齐”“证明原生独有机制带来30%优势”是三个阶段。前两个阶段真实有产出，但不能直接记作第三个阶段的完成度。继续补共有开关，也不能自动扩大对同样开启开关的参考的优势。

### 依据特性名称选择方向，早于确认实际执行路径

当前请求确实由DeepInfer引擎、C++调度和Worker驱动，模型执行及部分缓存、采样组件复用固定SDK。这是实际架构，不是vLLM引擎代跑。

但原版DeepInfer ZOS在当前GLM入口被关闭，适配层也不支持直接开启。固定vLLM参考已经具有设备侧token回填、MTP长度修正和异步执行。不能把“ZOS”“异步”“图重放”的名字本身当作新增优势。把原版ZOS完整移植过来，也需要证明它相对现有路径的增量收益。

### 过早将小热点升级为全模型候选

主机函数耗时可能被NPU工作覆盖；事件数量多也不代表它阻塞了NPU。局部实现跑通，只能说明功能命中。

120确实完成了多请求prefill图重放，但相对114的C4/C8吞吐退化约5.43%/46.81%，这条实现路线已经关闭。反复修到出现一个好分数，既浪费投入，也容易误判。

### 对探索和验收使用同一套门槛

探索不应每改一个主机函数就跑完整正式对照；也不应要求在实验前已经证明收益，导致只能继续写审计报告。正确做法是给一个明确假设有限的测量预算，再按结果采用或否决。正式验收仅针对一个已经有机制依据的候选。

本轮因此调整此前“纯观测加载预算已耗尽”的内部安排：**下一阶段允许且仅允许一次有决策价值的114诊断启动**，用于当前配方的关键路径归因，同时观察初始化故障是否再次出现。这不重开121候选、不恢复参数搜索，也不重置原02:40投入复盘点。本轮没有执行这次启动。

### 执行故障侵占了优化主线

121的输出批量化候选在HTTP就绪前失败，正式样本为0。失败发生在通信/初始化阶段；既不能声称该优化性能无效，也不能记为模型精度失败。后续必须将“环境能否完成必要启动”和“优化是否值得做”分别记录。

## 3. 本轮实际做了什么

沿用推理优化、性能评估技能，复核既有结果；完成一次有界启动审查，没有运行模型或NPU测试：

- 核对114/121实际容器命令、8个Worker命令。只消去任务目录/容器名差异后，命令完全相同；镜像、设备映射、CPU/内存/共享内存限制相同。
- 比较完整源码清单和加载扩展哈希：运行源码差异只有HTTP批量输出文件，另有一份对应测试；扩展相同。没有据此假定驱动或所有外部运行条件相同。
- 从已经停止的121容器只读取出3份实际SDK源码并核对哈希：两个runner与已计分117实际源码一致；worker与已有准备源码一致。
- 将失败报告范围缩到 `determine_available_memory → profile_run` 内，发生在其返回和HTTP服务建立之前。显式设置4GiB KV并不跳过这个阶段：SDK仍执行1792 token的dummy profile forward。
- 原始HCCL记录指出 `group_name_21` 的MC2 AICPU资源与 `ringAlignedAllGatherDoubleRingFor91093Executor_device` 路径；rank4/5在stream10/task1报 `RunAicpuRpcSrvLaunchV2_allgather` 参数无效。

**仍未确定：唯一Python发起点、实际通信tensor形状/类型，以及哪个参数或运行状态导致异常。** 异步错误上报可能晚于发起；更早已有STUCK心跳告警，不能把最后的错误时间当作第一处异常。没有证明硬件损坏，也没有证明HTTP改动造成故障。

因此不执行随意的小tensor `all_gather` 来冒充原故障复现。必要诊断必须匹配原MC2路径；本轮审查到此结束，不继续扩成通信框架项目。证据：[启动审查JSON](../validation/shared-features-20261111/native121-startup-audit.json)。

## 4. 突破口在哪里

**优先层次是框架的调度、输入准备、设备执行和结果回收之间，具体干预点尚需一次当前配方测量决定。不是再开几十个算子精度分支。**

要回答的是：C8这16.344秒里面，哪些时间确实在等待DeepInfer可改变的工作，而且没有被NPU计算掩盖？

| 路线 | 已有证据 | 决定 |
|---|---|---|
| 同步/输入准备/结果交接 | 114已有两批在途重叠；旧101显示大部分接受数等待被覆盖 | 只查尚未覆盖的间隙；不把全部主机等待计为可省成本 |
| 原版ZOS整套移植 | 固定参考已有部分等价机制；当前GLM状态/元数据协议不同 | 当前不做大移植；若测量指向某个缺失的具体环节，只实现那一段 |
| HTTP同一步批量输出 | 确有逐token重复处理；尚无临界路径收益证据 | 修复候选保留，不能用它冒充专有算法，也不重开121测到满意 |
| 完整签名prefill图 | 120已实测大幅退化 | 关闭当前路线，不再修第二轮或加单边预热 |
| 直接启用置信度变长MTP | 在满宽5draft预算下，排序仍选中全部draft位置 | 仅开开关无新增分配效果，不作为现成突破口 |
| 重写KDA/FFN/DSA、CPU/NPU逐位追齐 | 无证据说明它们是当前性能门槛的主因 | 不开展；保留必要输出和状态生命周期检查 |

如果测量显示剩余时间主要是双方共有的模型计算和通信，那么当前框架层候选可能没有足够空间在固定负载实现双档30%。应明确报告这个结果，不能承诺“多跑几天一定能到”。降低计算工作量、改并行策略或改测试场景都属于新的技术假设，必须重新说明语义、公平性和代价；不自动扩项。

## 6. 下一轮真正应该新增的成果

验收按三件事：

1. **一个当前配方的关键路径结论**：可改变的时间在哪里、哪些是重叠时间、未知边界是什么。
2. **一个采用或否决决定**：有机制和成本依据才进入实现；无空间也必须及时结束该分支。
3. **若采用，再交一个固定提交及对应C4/C8结果**：数字与机制贡献分别验收。

本轮没有新增性能成绩。当前双档30%及专有归因仍未完成；当前无本任务存活NPU作业，Goal为active不等于机器正在跑。后续是否达标以新证据判断，不能用升级模型、计划数量或消耗token作为进展。
