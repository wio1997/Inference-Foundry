# DeepInfer 性能任务复盘：125之后的路线与投入边界

日期：2026-11-13，北京时间。本文为D1结束时的复盘与计划，文中的“0次加载”对应当时状态。后续126已使用唯一取证加载，图内计算部分可见，但完整导出失败，尚无候选或新性能成绩；见[126阶段记录](native126-diagnostic-status-20261113.md)。以下原计划和预算不重置。

**结论：前面的安排确实有问题。适配接入已有成果，但性能选题仍多次停留在“有重复工作、能减少调用”的层面，没有先证明它限制端到端吞吐。124和125已经说明，局部机制执行成功不等于项目向30%目标前进。下一阶段先补齐目标模型执行图的关键路径证据；不再自动排队尝试小优化。**

## 2. 为什么三周工作没有自然累积成30%优势

### 接入成功与新增性能机制被混在一起

现在实际结构是：

```text
请求 → DeepInfer引擎 / C++调度 / Worker / 原生请求生命周期
                         ↓
             原生调度、异步输出、缓存契约适配
                         ↓
          固定SDK的模型运行器、模型计算和混合状态支持
                         ↓
                CANN / torch-npu / 现成算子
                         ↓
                     Ascend910C
```

DeepInfer确实拥有引擎和调度，未用vLLM引擎代替目标。但目标模型、量化、设备执行与大量算子仍复用固定SDK。这是收敛适配正确性的有效办法，也意味着不能预设换了上层框架就会让相同模型计算快30%。原生调度必须真正减少工作、隐藏依赖或改善资源使用，才有可归因的收益。

两批在途、原生前缀命中记账等已有执行证据；其单独收益尚不能用全部跨框架差值代替。prefix、异步、MTP、图捕获、MC2等共有能力也不能包装成DeepInfer独有。

### 局部工作量证据被过早升级为实现优先级

124元数据图实际执行，却比114的C4/C8低11.45%/9.20%。125保留FULL图并缩小后四步MTP行宽，实际执行成功，C8端到端仅提高0.06%。两项结果都应关闭相应路线，不能换一个参数继续无限延伸。

此前125原型前已经知道输入行数不等于设备耗时，却仍在设备成本占比未知时投入实现和一次完整加载。下一阶段把这个缺口变为真正的放行门槛，而不只是报告里的免责声明。

### 等待时间、采样热点与关键路径没有充分区分

CPU正在等设备时，删掉CPU的等待函数不会让必要的模型计算消失。多个流的等待时长互相重叠，不能相加作为可省时间。已有采样未完整覆盖图内kernel，缺失的记录也不能解释为空闲。

### “完成一轮”过于容易被当成“推进目标”

报告、收集、启动修复和图命中都不是30%验收。后续只计三类成果：关闭一个具体且重要的假设；交付一项有证据支持的实现；推进一个明确验收门槛。失败结论有价值，但不能长期用连续失败替代交付主线。

## 3. 本轮实际关闭了一条路线

本轮核查“把接受数量/混合状态提交放到MTP草稿前，能否解除CPU长等待”。没有重新跑卡，直接分析122的原始设备轨迹，并用API关联ID与主机执行区间确定图身份：模型49的提交落在目标模型执行阶段，模型48落在采样/草稿阶段。

固定源码已经在独立流等待采样完成事件，再提交混合状态更新。设备轨迹中的三个完整循环进一步显示：**状态提交已经在草稿图执行之前完成**。

| 观测量 | 三个循环的中位数 | 能说明什么 |
|---|---:|---|
| 目标模型图的MODEL_WAIT_COMPLETE跨度 | 44.811毫秒 | 大段时间在目标图执行区间内，内部计算/通信/等待尚未拆清 |
| 草稿图的MODEL_WAIT_COMPLETE跨度 | 7.418毫秒 | 草稿段存在，但不能把缩行量直接换算成收益 |
| 状态提交kernel | 8.06微秒 | kernel本身很小 |
| 状态kernel完成到草稿图开始 | 1.316毫秒 | 状态提交没有排在草稿图之后 |

示意顺序：

```text
目标模型图运行 ── 采样结果可用 ── 草稿图运行
                       └─ 独立流状态提交，随后接受数量可用
下一批CPU准备：需要等待真实采样/状态依赖，不等于可删除的冗余等待
```

**裁决：不实现“仅前移状态提交”的候选，不为它加载模型。** 这不证明所有异步机制都已最优，只关闭这一条未经证实的捷径。

边界：122是带诊断开销的rank0局部样本；MODEL_WAIT_COMPLETE跨度包含图内可能的等待，不等于纯算术kernel耗时。这些数值不替代114计分时间，也不直接外推整批收益。

## 4. 下一轮的突破方向与决策规则

**优先方向是目标模型的完整执行计划：先查清图内计算、跨rank通信、依赖等待究竟哪一项占据关键路径，再决定能否通过DeepInfer的分派和执行计划减少或重叠它。** 这是已确认的大段执行区间，不是已经找到根因或已证明会加速。

下一轮只回答一个问题：

> 在维持模型、共有开关和固定负载的条件下，是否存在一条具体、可安全改变、且有希望净省至少1.182秒的执行依赖或重复工作？

放行实现前必须同时具备：

1. **位置**：实际目标图、rank、流、生产者和消费者能对应到源码；不能仅引用函数名或调用次数。
2. **成本**：有覆盖已知的大段执行的证据，区分重叠时间与净关键路径时间，给出收益估计及假设。图内记录仍缺失，就承认缺失。
3. **干预**：说明改变什么排布/依赖/重复工作，为什么数学语义、状态所有权和通信顺序仍成立。
4. **区别**：固定参考是否已有同样可用实现；已有共有能力先按共有能力处理，不计新增独有机制。
5. **预算**：一个候选，一次实现；候选无实质收益便退出，不开参数网格。

如果主耗时是双方相同的必要模型计算，且没有证据可移除或隐藏，就应交付“当前薄接入路线尚无支持双档30%的机制”。不能擅自降低目标，也不能声称再多跑几轮必然达到。

不把长上下文、超大并发、关闭参考优化等换负载办法当当前目标的补救；它们即使展示其他优势，也不能代替固定C4/C8验收。

## 8. 进一步复盘：不能用不断重排计划代替推进

此前至少有四个安排缺点需要具体纠正。

| 缺点 | 当前证据 | 此后如何改变行为 |
|---|---|---|
| 把接入功能当成框架独有优势 | 当前GLM入口关闭原版完整ZOS；已有两批在途，固定参考也有异步、设备token回填和MTP长度修正 | 先写清固定参考缺少的执行机制，再给它性能研发预算；C++、异步、MTP、图捕获这些名称本身不算独有 |
| 根据局部次数或张量规模选题 | 124元数据图、125缩行均真实执行，端到端仍未达到采用条件 | 实现前先算关键路径上能省的时间；候选失败后不自动改容量、阈值或图模式重试 |
| 把等待或不完整profile当作瓶颈 | 状态提交原本就在草稿图前；图内部主要kernel没有采集到 | 必要依赖不能删，缺失区间不能当空闲；只补一次明确缺失的测量 |
| 失败后反复新增阶段 | 已有多次去留裁决，但完整目标仍未达成 | 本阶段沿用已登记T1和六小时截止；一个诊断、一个候选的上限不因改编号或换报告重置 |

这里有两个不同的问题：**适配是否跑通**，以及**是否创造了新的、可归因的性能优势**。前者已经有原生8die、固定负载的实现和运行证据；后者仍在研发。当前主要障碍不是“CANN少一个算子”或“还要把CPU/NPU逐位对齐”，而是没有证实一个足够大的、可改变的剩余性能限制。

“独有”的可验证含义限定为：本次DeepInfer候选新增、固定参考版本未提供等效路径。它不等于技术永远不能移植到vLLM，也不意味着把通用优化写在DeepInfer适配器里就自动构成框架优势。

以当前C8记录计算，需要净省现有总时间的7.23%。如果一个方向只能把其涉及的成本降低一半，那么该成本至少要在整批关键路径上占2.364秒，还没计新开销。一个局部步骤即使快了很多，只要它原本与其它工作重叠，就可能几乎不缩短整批时间。这个门槛用于淘汰投入方向，不是要求先用模型仿真精确预测收益。

## 9. D1已完成什么：确认了测量盲区，尚未确认根因

本次直接核查122的原始分析数据库，而不只看CSV或CPU榜单：

- 目标模型图49有8个`MODEL_WAIT_COMPLETE`记录，合计354.554104毫秒；草稿图48有8个，合计59.084162毫秒。这些仅为采样窗口中的图执行外框。
- 选取一个完整45.267384毫秒目标图区间，关联`TASK`与`COMPUTE_TASK_INFO`后，图内可归属的计算kernel记录为0。区间里只有少量其它任务记录，无法重建45层主要计算与通信。
- 因此继续从这份数据细数CPU等待或少数HCCL项，不能回答主要时间花在哪里。记录缺失也不能证明设备没有工作。
- 固定镜像里的Ascend profiler提供CPU+NPU、Level1采集；Worker支持明确的开始/停止。原采样在图捕获后才开启。下一次只改变采集边界：权重/cache初始化完成后、`compile_or_warm_up_model()`之前开始，覆盖捕获和实际decode重放。
- 配置中出现`capture_torch_profiler`并不证明当前Ascend路径会调用它，不能照搬CUDA配置名。已核查实际Ascend实现，准备使用其真实接口。

最后一项是**有源码依据的采集方案，尚未上NPU验证能够补全记录**；“晚启动导致全部缺失”也还不是已复现的根因。D1完成的是“旧数据是否足够、下一次只补什么”的裁决，不是已经得到目标图成本分解。

## 10. 下一轮执行工单：有条件推进，不按路线列表轮流试

首选调查方向是**目标模型执行图中的跨rank串行等待、通信与计算的依赖，以及DeepInfer能控制的批次分派边界**。这是调查范围，不是已经证明通信是瓶颈，也不是已经批准重构模型图。

| 如果一次完整取证发现 | 允许考虑的最小干预 | 不允许据此推断 |
|---|---|---|
| rank输入准备明显错开，导致全组等待 | 消除已定位的重复准备或提前准备无依赖的输入；保留状态所有权 | 不能把所有HCCL等待都当网络慢，也不重开已否决的metadata图方案 |
| 通信与独立计算串行，存在足够未重叠时间 | 由原生执行计划安排一处安全重叠，复用现有算子；明确生产者、消费者和缓冲寿命 | 不能只开双方都有的overlap/MC2开关，也不默认独立流必然更快 |
| batch边界造成重复工作或实际可避免的空档 | 只改一处有证据的批次/执行边界；重新核对混合状态与MTP契约 | 不能只凭padding行数或设备利用率推算收益 |
| 主要成本是双方相同的必要计算，或数据仍不可归属 | 结束本阶段，保留114，交付当前路线缺少足够机制依据的结论 | 不能宣称30%理论上不可能，也不能自动再加载一次继续找 |
