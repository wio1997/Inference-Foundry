# 128：完整混合状态复用的批量复制候选

2026-11-13。源码`432aac4cc9afc8f0b371c74ebb2ac716b5be4e2f`，基于127源码`605a4bb403eda35acfec700ae0d43854af21616a`。**本轮产出真实隔离补丁，11项主机契约测试通过；没有启动模型，尚无128性能或质量结果。默认仍为114。**

## 为什么准备这一项改动

127确实跳过了重复prefill，但C4无命中时仍需保存状态，当前每条状态逐项提交102次设备复制。已有时间轴不能证明这些复制占了多少时间，也不能证明合并调用就能补足C4需要的1.818秒。

本候选只检验一个实现假设：**保留完整状态复用策略，利用固定SDK已有的批量复制函数减少逐项提交成本。** 模型、量化、跨rank一致性检查、采样、MTP和调度策略均不改；没有新增算子数学实现。

批量复制本身不是DeepInfer独有能力，固定vLLM也已使用。待验证的框架机制仍是DeepInfer管理的完整混合prefill状态复用；不能把“调用了已有批量复制函数”单独包装为独有创新或性能收益。

## 实现改变了什么

固定函数为`vllm.v1.worker.mamba_utils.batch_memcpy`。本轮通过既有协议，从103上已完成、停止的127容器只读取回源码，其SHA-256与此前计分参考117一致：

`23fdaa4e8f63ee8f938eaa1a2b39f803cb04fa6ecd69789563254b1a0691413a`

该函数对每个地址区间执行字节复制。它不替调用者管理Tensor寿命，也不保证多个复制区间互相覆盖时安全。因此补丁同时约束地址、容量和完成事件。

| 项目 | 127 | 128源码候选 |
|---|---|---|
| 每条状态的设备到设备提交 | 102次逐项复制 | 1次批量kernel，另有1次小型主机到设备元数据复制 |
| 大区间 | 各Tensor单独提交 | 固定拆成不超过64KiB的片段；不进行参数扫描 |
| 384行hidden的典型复制计划 | 102个Tensor区间 | 486个互不冲突的字节片段，合并提交 |
| 复制元数据 | 无独立批量表 | 容量518片段，设备预留12,800字节 |
| 总缓存预算 | 4GiB，包括1GiB状态arena | 不变；12,800字节从同一个arena扣除 |
| 保存的Tensor/主机指针寿命 | 普通Tensor复制API | 显式保留到完成事件；等待异常时不先释放 |

依据127实际条目占用，扣除新的元数据区后arena仍余33,697,280字节。这是同布局的容量核算，尚未由128实际NPU运行确认。

固定64KiB分片用于限制现有helper单程序内的循环长度；它不是经实测挑选的最优值。本候选可能仍然变慢，源码中的提交数减少不等于端到端加速。

## 安全边界与必要观测

- 复制前检查连续布局、dtype、设备、地址区间和整数宽度；拒绝目的区间重叠以及跨区间读写别名。
- 设备描述符位于原arena内；在当前stream按序上传、复制。保持原有状态完成事件与跨stream依赖。
- 原始指针对应的Tensor及页锁定主机缓冲保留到复制完成。最多保留4份未完成主机缓冲；达到上限时显式等待并计数，该等待属于候选成本。
- 保留KDA状态、卷积历史、注意力状态、尾部和hidden的原有覆盖范围；可写目标仍须为当前请求私有。没有借本改动改变127的状态定义。
- 加入有界的计划、一致性检查、原forward返回、保存/恢复返回时间记录；复制stream区间在原有drain同步完成后读取，不在每次请求中同步读计时。
- stream区间包含元数据传输和可能的主机发射间隙，不冒充纯kernel时间；事件和记录开销计入候选。没有增加模型请求或单边预热。

这些检查验证本次搬运实现的边界，不能证明127原有的端点复用语义已经完全正确。127的新增输出差异仍是未完成项，不能由11项主机测试替代验收。

仅有1次算力服务器只读调用，用于核对已停止容器中的固定源码；没有启动容器、占卡、加载模型或改变远端配置。隔离补丁只修改两个文件：

- `DeepInfer/deepinfer/model_executor/models/glm5_next/full_model/native_prefill_state.py`
- `DeepInfer/tests/test_native_prefill_state.py`
