## 2. 此前安排的问题

1. **把“适配可运行”与“新增技术领先30%”混在一起。** 双方共享模型执行和大量底层算子，框架更换本身不保证30%增益。现在需要的是减少实际计算或降低关键路径成本。
2. **用局部计数代替端到端收益判断。** 图重放、输入缩行、调用减少都可能真实发生，但已有124/125说明它们不足以补足目标缺口。
3. **只关注受益路径，没把无命中成本当作同等重要的指标。** 127在重复输入上省算，同时给冷请求增加快照、一致性检查和内存管理。两边必须用同一候选一起验收。
4. **阶段有时限，项目却不断重新开阶段。** 一个候选失败后自动换名字、换参数继续，仍然会无限消耗。127阶段已经结束，未触发的控制额度不能挪作诊断或新变体。
5. **结果判断曾过度依赖中间精度或单个统计量。** 本阶段不回到CPU/NPU逐位比较；但新缓存引入的输出分叉也不能只凭“浮点误差”放行。应验证本次状态复用是否保持了计算契约。

## 3. 本轮新证据：C4究竟慢在哪里

将32个请求的时间轴按并发数归一化，可得到准确恒等式：

`整批时长 = Σ首token等待/C + Σ首token后至请求结束/C + 未占用请求槽时间/C`

已核实两臂实际并发上限分别为4和8；各请求均成功且为1024输入、256输出。下面是127减114的变化：

| 时间组成 | C4变化 | C8变化 |
|---|---:|---:|
| 首token前请求时间面积/C | +0.388秒 | −1.220秒 |
| 首token后请求时间面积/C | +2.223秒 | −0.467秒 |
| 未占用请求槽时间面积/C | +0.086秒 | +0.047秒 |
| 整批时长 | **+2.697秒** | **−1.640秒** |

这说明C4损失主要出现在已经开始输出的请求仍未结束的区间。**这不等于“decode算子慢了2.223秒”**：其他请求的prefill、队列等待、MTP轨迹、传输都可能落在该区间。也不能把0.086秒直接归因为服务端调度错误。

C4最初一组4个data ID的平均请求时长从3.340秒变为4.755秒，中间若干组接近原水平，后部又出现拖长。这些是按data ID分组的描述，不能冒充引擎实际batch。

### 一个明确异常，但不足以单独决定修复路线

正式C4开始约0.823秒后，有一次`[640,1024)`的单请求prefill调用：

- rank0主机区间1.684秒；8rank范围1.593–1.765秒。
- 8rank进入该事件的时间差约0.794毫秒，不能用“某个rank很晚才开始”解释。
- 该区间包含计划、一致性通信、原模型调用和状态保存；现有记录没有把各段或NPU执行拆开。不能认定1.684秒都是复制成本。
- 另有7.626秒主机事件发生在正式请求开始之前，属于既有预热范围，不能算入正式C4损失。

C4距离30%门槛需净省1.818秒。在其他时间不变的假设下，即使把上述事件中最长rank的全部1.765秒删掉，整批仍为27.621秒，超过27.568秒门槛约0.053秒。这只是固定其余时间的账面推算；调度与MTP轨迹改变时不是严格因果上限。它足以说明：**现有证据不能支撑“修这一个慢调用就会达标”的下一次加载。**

## 4. 下一阶段唯一值得评审的候选

**目标：把127的完整混合状态复用变成低开销的原生缓存路径，保留114的正常未命中计算。** 不改权重、量化、算子数学语义或正式负载，不按C4/C8档位切实现。

框架负责请求与状态的所有权；模型模块说明需要保存哪些状态；底层继续复用现成NPU实现。现有127每条保存/恢复涉及102次逐项复制，纯prefill还进行跨rank对象一致性检查。这些是源码确认的新增工作，**实际时间占比未知**。

下一次源码评审只回答一个问题：是否能用固定环境已有的批量复制能力和既有请求元数据，形成一个成本更低且契约不变的单一实现。不能把“合并102次调用”直接当作已证明加速；若需要重写kernel、通用快照系统或同时改调度/模型语义，则否决这个最小方案。

必须保留的约束：

- KDA递推状态、卷积历史及可写尾部按请求隔离，不能为了零复制共享可变状态。
- 总缓存仍为4GiB；复制、临时区和保留状态全部计入，不能额外分配掩盖成本。
- 未命中和混合batch仍走完整模型路径；正常logits、采样、MTP和生成持续执行。
- 快照完成事件与原slot复用有明确依赖；不能把尚未完成的复制移到后台后立刻复用源内存。
- 不增加单边预热、不删除慢请求、不使用benchmark请求ID决定命中。

输出分叉与冷侧成本是同一候选的两个准入条件，不另开后端组合搜索。127相对参考的C8完整文本一致数23/32，114是29/32；这不是任务质量分数，但新增分叉尚未解释。后续检查应围绕相同NPU上的保存/恢复数据与首个受影响生成边界，明确区分状态传输错误、上下文不匹配与已有批处理数值差异。不得把全部词表逐位对齐作为新目标，也不得提前豁免真实状态错误。
