# DeepInfer 性能攻关：反思、122诊断结论与下一阶段唯一候选

更新时间：2026-11-13，北京时间。本文接续[性能复盘](performance-reset-20261113.md)，以本次回收的实际结果更新其中待执行部分。当前原生Goal未完成；没有新增正式性能成绩。N2原型已完成，123唯一候选正在原卡组初始化，详见[原型、机制与验收边界](native123-prototype-20261113.md)。

## 1. 结论先说清楚

**当前已实现有限负载下的原生推理适配，但尚未证明同一候选在C4、C8均领先强参考30%，也没有完成框架差异机制的净贡献证明。问题已经从“模型能否运行”转为“原生框架究竟能减少哪一笔端到端成本”。**

| 同条件正式AISBench | vLLM参考117 | DeepInfer保留114 | 已观测优势 |
|---|---:|---:|---:|
| C4 | 228.57797 token/s | 306.94205 token/s | +34.28% |
| C8 | 415.61018 token/s | 501.22023 token/s | +20.60% |

C8还需从16.34411秒减少到15.16214秒，净省1.18198秒；相当于当前吞吐再增加7.80%。C4只能承受约0.87937秒回退。这是已有批次的差额，不能当成稳定收益保证。115到117同配方参考的C8变化约11.52%，因此不能挑较慢参考，也不能只拿某次过线宣称稳定领先。

正式参数与原始计时见[114复现记录](../validation/shared-features-20261111/native114.json)、[117复现记录](../validation/shared-features-20261111/reference117.json)。保留模型源码为`c4ec8e000d04966574970802ae01db76e57a01b5`。

## 2. 为什么此前投入没有持续转化成框架优势

1. **适配、共有能力补齐、独有性能优势三件事混在一起。** 修复接入缺陷有价值，但恢复共有图捕获、MTP、缓存等能力，不等于创造相对同条件参考的新优势。
2. **当前架构复用了很大一段SDK执行路径。** DeepInfer拥有引擎、C++调度和Worker；模型执行仍复用固定SDK的一部分runner、MTP与混合缓存元数据构建。原生入口成立，但不能由此推导整个执行循环已经采用DeepInfer的优化设计。
3. **从热点名称跳到了昂贵实验。** 主机等待可能覆盖设备工作，局部加速也可能被新增拷贝、图准备和状态维护抵消。120的多请求prefill图确实命中，却造成C4/C8吞吐约5.43%/46.81%退化。
4. **用严格但未必有决策价值的检查拖住试验，同样是错误。** 不该追CPU/NPU逐位相等，也不该要求实现前精确证明30%收益；应先完成一个有限、可否决的机制实验，再作正式判定。
5. **执行故障与优化失败未始终分开。** 121在初始化阶段失败、没有正式样本，不能算优化已被性能反证；也不能无限续跑它直到出分。

这部分是安排和技术路线的问题，模型档位升级本身不会弥补。后续只按可运行代码、关闭的假设、同条件结果衡量进展。

## 3. 本次122诊断实际新增了什么

本次使用114模型源码与相同共享优化配方，启动一次有界诊断；没有套用120图改动或121输出批处理。72个请求完成、8个Worker退出码均为0，作业与资源登记已释放。138个回收文件逐个核对SHA-256。启动越过121曾失败的位置，**只证明本次未复现，不能宣称根因修复**。

实际C8开始后采样3个prefill和8个decode步骤；另外8个decode步骤做CPU采样。没有追加诊断请求。带采样批次不计为新的性能成绩。

### 3.1 找到一笔真实重复工作，但还没证明收益

在8个CPU采样步骤中：

| 观察项 | 实际调用 | 采样成本 | 解释边界 |
|---|---:|---:|---|
| MTP后续草稿注意力元数据更新 | 32次 | 累计35.37ms | 每轮5个draft中的后4步；非可全部消除成本 |
| 压缩索引缓存元数据build | 48次 | 累计34.15ms | 包含动态位置、slot、长度等必要更新 |
| GDN/KDA元数据build | 24次 | 累计27.38ms | 涉及padding、请求阶段和递推状态 |

CPU窗口总自耗时441.44ms。这些函数存在嵌套，累计时间不能相加，也不能按比例外推成正式C8可省时间。

从已停止的真实122和已计分117容器各读取5份源码：MTP proposer、SFA CP、Indexer KPool、GDN builder、CP helper，**五份SHA-256全部相同**。

具体源码事实：

- proposer为后续draft步骤逐个组织metadata；其`device_metadata_executor`入口在该段代码只对`dspark`选择，不能当成普通`mtp`已有的快速路径。
- Indexer KPool的`build_for_drafting`仍调用完整`build`；`fast_build`参数被忽略，没有仅凭该开关就能获得的快速构建。
- GDN builder有真实padding、状态、有效请求数分支，不能简单按batch size缓存整份metadata。

这些事实支持考察“减少重复构建”的候选，**不证明该工作只存在于DeepInfer，也不证明它就是当前瓶颈**。同名组件源码相同也不等于两框架全部调度行为相同。

### 3.2 撤回一个可能误导方向的诊断指标

单算子CSV在decode窗口含4635行，Model ID全部为未设置值；同一trace却记录了捕获模型48/49的`MODEL_EXECUTE`及`MODEL_WAIT_COMPLETE`。CSV没有展开对应整图模型计算。

因此“主机区间减去CSV算子占用”不能叫NPU空闲，也不能预测优化空间。此前分析文件中的`visible_device_idle_ms`不用于路线成本判断。**这不是发现NPU有约95%可消除空闲；是发现诊断覆盖不完整。** 不再为完善这张图追加纯观测模型加载。

## 4. 下一阶段唯一候选：原生GLM执行计划复用MTP元数据

目标是在DeepInfer原生调度结果和设备执行之间，减少同一轮5步MTP的重复元数据组织。它是一个**已实现、待NPU验收的新路径**，源码`a4df69bc805a871c3587e007b5224e7b76eaf129`，不是把现成共有开关换个名字。

```text
当前
DeepInfer调度 → SDK输入批次 → 按草稿步重建多组metadata → target/draft图执行
                                  ↑ 每轮继续重复

唯一候选
DeepInfer调度 → 原生GLM执行计划
                  ├─稳定结构：按明确签名复用
                  ├─动态数据：按实际位置/接受数增量更新
                  └─复杂或不支持的批次：回退原路径
               → 同样的target/draft算子与图执行
```

优先只处理稳定的decode批次。权重、量化、注意力公式、MTP草稿数和接受规则不变；不改CANN核心算子。共同优化继续两侧匹配。

**不能缓存掉的动态量**包括：位置、有效长度、接受/拒绝结果、block与slot映射、KDA状态索引。请求加入/退出、slot复用、block跨界、padding变化、prefill混入都必须有明确处理；不支持时回退。不得只按总token数或batch size作缓存键，不能让多步图中的不同草稿状态别名覆盖。

这条路径能否形成增量优势，取决于它实际减少了多少组织、分配或提交工作，新增更新/拷贝开销是否更低。**可消除的关键路径时间和预期提速目前均未知。** 它不能仅凭源码名称或CPU排名获得正式性能验收。
