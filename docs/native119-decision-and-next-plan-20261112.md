# DeepInfer 性能复盘：119图候选否决，保留114基线

2026-11-12，北京时间22:40左右。**完整模型适配已有可运行成果，双档领先30%的性能目标仍未完成。本轮真正关闭的问题是：当前prefill签名图实现虽然能执行，却不适合作为性能候选。**

基线114相对较快的参考117仍为 **C4 +34.28%、C8 +20.60%**。不能用较慢的参考115保留此前单批双档35%的达标印象。119没有缩小差距，当前实现直接否决，不原样重跑、不替换默认源码。

## 2. 图能运行，为什么仍然否决

8个rank各实际捕获4份图、执行26次，其中复用22次；0次状态预热，0个图致命错误。另有29次因元数据clone改变stride而回退eager。因此，“完全没有命中图”已排除，“图命中就一定更快”也被端到端结果否决。

固定工程三请求和fresh槽位复用通过，72个总请求完成、8个Worker均exit0。119与117全文相同为C4 28/32、C8 25/32；与114为28/32、26/32。这只是限定输出观测，没有据此声称正式通用质量验收。

这将下一步问题收缩到**完整模型提交和批次组织之间的衔接**：相同计算量为何变成更多小批次、元数据准备是否阻塞下一批、图复用主要覆盖了哪些实际批次。无需重写KDA/DSA，也不重开CPU/NPU精度搜索。

## 3. 本轮管理器故障及修复

119管理器完成正式计分和Worker关闭后，释放登记仍断言代次118，导致最终状态停在收集阶段。现场日志已确认这是一处复制模板时的遗漏，属于执行实现错误，不是模型精度问题。

本轮核对原manager已退出、原不可变容器已停止、8个已登记Worker均退出，保留原日志和原状态；从已有产物重新运行原来的结果校验，核销本任务119的登记。没有重启模型、重跑benchmark、改原始计时或终止其他进程。manager状态仍记为failed，候选产物校验单独记为passed，不把人工核销包装成原管理器成功。

准备脚本改为核对当前manager的实际generation，已用原119反例确认旧条件失败、新条件接受119并拒绝错误代次/执行者。已执行stage及原失败日志未修改。本任务现无存活NPU作业；现场另有进程，不能把“我方登记已释放”说成“整机全空”。

## 4. 对三周推进方式的反思

1. **把适配正确与获得独有性能优势混为一谈。** 复用模型和CANN算子使计算能运行；共同的MTP、缓存、通信和decode图必须双方开启，补齐这些能力不自动产生独有30%。
2. **局部技术验证过早升级为整机实验。** 图捕获通过、某个函数少调用、某个等待很长，均不是端到端净收益。本轮TTFT改善但吞吐退化就是反例。
3. **完整加载成本太高，候选过滤不够有效。** 119从启动到计分结束约18分钟，正式两档计时合计约53秒。先用已有证据否决低收益方向，比增加并行加载更有效；正式同卡对照也不能互相争设备。
4. **状态与模板维护本身出现错误。** 这次118/119校验遗漏和旧检查点字段未及时更新，说明过程记录多并不代表执行可靠。本轮以真实进程、回执和原始计时重新收口，而不是扩大恢复系统。

保留114已验证基线及116单开关消融成果。119作为失败候选归档。后续以关闭假设、可部署修改和验收结果计进展，不以轮数、报告数量或Goal=active计进展。
