候选的因果链是：

```text
读取当前请求身份、真实native进度和现有状态条目
  → 仅识别队头连续、完整且具备兼容保存状态的请求
  → 在本步预算装不下下一个完整尾段时设置一次调用范围内的队列边界
  → 原生C++ scheduler继续产生完整尾段批次
  → 原有状态复用逻辑独立检查全rank一致性、物理状态和hidden行范围
  → 如果这些检查也满足，才跳过对应target forward
```

这不是把1792改成1536，也没有按C4/C8、数据集或固定prompt特判。预算、CP对齐、输入、量化、MTP、采样和缓存容量均沿用139。

## 2. 实现边界

新增 `NativeTerminalPrefill`，由原生 `LLMEngine.step()` 在调用C++ scheduler的位置使用。通过现有 `Sequence.schedulable` 可写接口，暂时阻止第一个不适合进入本批的后续请求；`finally`在C++ schedule返回或抛异常后立即恢复该标记。

以下条件缺一不可：请求仍处于waiting、纯文本、没有结构化输出准备任务；请求身份及已注册sequence一致；未开始生成；native已有真实非末尾prefix进度；保存状态覆盖当前起点；中间没有必须停留的checkpoint。按native的CP padding计算本步预算。

额外限制：

- 队头冷请求或单请求尾段超过预算时直接走原调度，不制造空批次等待。
- 不改变队列顺序、已计算token数、状态slot、物理缓存或原生MTP进度。
- 不屏蔽已结束请求的清理，不覆盖其它请求原本的不可调度状态。
- 只允许同一个引擎线程操作，不允许重入；边界不跨越模型执行或异步结果回收。
- 若原生实际prefill输出没有保持选定的完整跨度，立即在模型执行前报错。
- 仅rank0使用状态条目作为调度提示；真正是否复用仍由原有各rank共识和状态检查决定，不以rank0提示替代验证。

没有修改C++源码或二进制，复用现有编译绑定；实际目标环境的绑定执行仍需后续验证。该限定路径不需要为这一改动重新编译调度扩展。
