## 1. 已经做到哪里

DeepInfer 原生引擎、C++ scheduler 和 Worker 已实际驱动完整模型，在当前 8 die、固定正式负载上执行并正常结束。现在主要缺的是**性能增益的联合验收和机制归因**，不应重开早期模型公式、量化或 CPU/NPU 精度搜索。

| 固定实现 | C4 相对强参考 117 | C8 相对强参考 117 | 处理 |
|---|---:|---:|---|
| 默认 114 | +34.28% | +20.60% | 保留可回退基线 |
| 状态复用 127 | +21.96% | +34.05% | 冷侧退化，不采用 |
| 批量状态复用 128 | **+25.03%** | **+43.86%** | 机制实际命中，双档目标仍未通过 |

128 完成 72 请求、8 rank 退出 0，作业及占用已释放。以上是历史单批成绩，不是稳定收益结论；不能拼接 114 的 C4 与 128 的 C8。

128 的 C4 需从 28.66382 秒降到 27.56844 秒，**缺 1.09538 秒净收益**，约为当前整批时间的 3.82%。C8 当前有约 1.46070 秒的门槛余量，但也需要同期控制确认。

一般模型质量、另一台机器干净重建不因性能批次成功而通过。本轮不把这些范围扩大成新的研究项目；正式性能结论仍需要与新状态路径直接相关的有效性证据。

## 2. 前面安排中应当纠正的四件事

### 2.1 把适配与性能研发混在一起

初期是让权重、模型计算与 DeepInfer 接线正确；现在是两个已能运行的引擎争取端到端差异。二者都复用大量同一模型和 NPU 算子，不能指望框架名称不同就快 30%。继续写算子或追所有数值差异，可能离当前目标更远。

仅靠消除框架开销得到 1.30 倍吞吐，理论上至少要消除原总时间的 `1−1/1.30≈23.08%`。这是串行成本模型下的必要量级，不是本系统已测出的开销占比；若可消除的框架时间远小于此，即使把它压到零也不够。因此，当前应优先减少真正的模型计算量，而不是把几毫秒的包装成本当作几十个百分点的收益来源。

### 2.2 用局部变化代替可兑现的时间收益

124 的 metadata 图和 125 的 MTP 缩行已经说明：图重放、减少行数或调用次数真实发生，也可能没有足够的整批收益。128 的复制提交减少同样不能直接证明能补 C4 缺口。后续候选先列出能影响多少关键路径时间，再决定是否值得加载模型。

### 2.3 把“热请求收益”与“冷请求代价”拆开看

本协议先 C4、后 C8，缓存保留。128 正式 C4 仅复用 2 个请求；C8 复用 16 个请求，跳过 5,120 个目标 prefill token。因此 C8 的高收益包含重复输入状态复用，不能只归因于并发增加。

一个可交付候选必须同时处理未命中请求和已命中请求，不能临时按 C4/C8 切版本，更不能根据 benchmark 的请求 ID、答案或未来请求选择策略。若以后采用自适应路径，只能依据实际可见的状态命中、容量与队列信息，并作为同一固定实现接受完整测试。

### 2.4 阶段预算结束后又不断开启相似阶段

每个小阶段都有停止条件，不代表整个项目已有停止条件。128 的 1 次候选已结束，未触发控制不转为其他实验。新方案必须有明确的因果依据和准入记录；不能把“Goal 仍 active”当作无限追加测试的理由。

## 3. 突破口在哪一层

```text
请求进入 DeepInfer → 原生 scheduler 分配请求/状态 → Worker
  │
  ├─ 未命中：按既有模型路径完成 prefill → 正常生成
  │                                      └─ 保存可复用混合状态
  └─ 有合法命中：恢复当前请求的私有状态 → 跳过对应目标 prefill
                                            ↓
                                    正常 logits / MTP / decode

框架层要解决：何时复用、状态归属、调度依赖、容量与未命中代价
模型层要说明：KDA/DSA/hidden 等哪些状态共同构成合法续算位置
算子层继续复用：CANN / torch-npu / 固定 SDK，不另造数学实现
```

这里复用的是计算状态，不是答案。128 的批量复制本身来自固定 SDK，并非 DeepInfer 独有算子。当前可研究的区别是 DeepInfer 新增的完整混合状态生命周期和恢复路径，相对于**固定受测参考版本**是否减少了实际工作；不能宣称其他框架永远无法实现。

方向排序：

1. **优先：保留混合状态复用，找到冷侧原模型执行/等待的实际损失。** 已有正式时间记录支持继续做一次有界判定。
2. **只有证据支持才考虑：原生调度依赖、混合状态占用对正常批处理的影响。** 例如容量切分影响批形状、首次使用或同步等待；这些目前不是已确认根因。
3. **停止：继续压缩复制 kernel 的毫秒成本、重写 KDA/DSA/FFN、扩展图形状或参数网格、重跑 CPU/NPU 精度比对。** 现有证据不支持这些作为当前关键路径。

## 4. 最新计时为什么改变了选择

128 正式 C4 每 rank 的复制 stream 区间总和约 2.45–4.57 毫秒；整个状态包装层的主机区间总和约 206–226 毫秒。不同时间域和 rank 不能相加；池容量、调度和正常模型执行的间接影响未包括在内。

正式 C4 中一次 `[0,640)` 未命中调用，在 rank0 的原模型调用及前序等待内耗时 **1.690 秒**，而这一调用**没有任何状态复制**。这比继续研究几毫秒复制更有决策价值。

但不能直接说“删掉这 1.690 秒就过线”：其中有正常计算，主机等待可能与设备工作重叠，而且改变它可能改变后续调度。下一轮必须核对它在整批关键路径上的位置，并比较 114/127/128 的相同类型工作。

8 rank 原有 kernel-preparation 的受监测范围没有 late compile 事件。这只排除了已监测的 slot mapping / lightning indexer 范围，不能泛化成“没有任何延迟编译”。

**Q1 已完成：**只读取已结束作业的缓存、源码与原始时间戳，发现 C4 慢调用中各 rank 均产生了 `REQUESTS=1` 的卷积状态读/写编译缓存；C8 慢调用中均产生了 `REQUESTS=5` 的对应缓存。该 kernel 把请求数作为编译期常量，原准备范围遗漏了它。两个区间均无流式输出事件；C8 后续相同分段调用约 0.285 秒，首次约 1.740 秒，差约 1.455 秒。

这使“服务期间首次编译阻塞”成为唯一优先干预。缓存写入时间不是编译起止计时，C4 又没有后续完全同形状调用，因此仍不能把 1.69 秒全部认作可删除成本。129 的真实任务将回答它是否能带来所需净收益。

**Q2 已完成：**源码 `5c4290726beb475ee7ea200580f07a36a71e515f` 仅相对 128 修改共有准备文件。用既有启动过程中观察到的真实 layout/stride/dtype，为声明的 1–8 请求容量编译读/写模板；不执行新增 kernel、不增加模型 forward 或预热请求。4 项主机契约检查通过，仍待真实 SDK/NPU 验证。该共同修复必须同时给新的 vLLM 参考和同源码关闭状态复用的控制，不能将它归为 DeepInfer 独有优势。

## 6. 验证保留什么，删掉什么

保留：真实 8 rank 执行、原请求与输出长度、无请求失败、状态属于正确请求/位置、4 GiB 总预算、实际公共开关、模型与扩展身份、原始时间戳、退出和资源释放。新缓存的必要状态检查优先放入既有工程请求，不另加一套模型回归矩阵。

删除：CPU 高精度逐位对齐作为性能门禁；全词表 RMSE 单独决定路线；所有旧算子重复回归；与本改动无关的灾备/通用运行器开发；只因为增加了一个参数就穷举组合。

128 与参考完整文本 C4/C8 均为 30/32；这可以帮助判断变化范围，不能冒充正式质量得分。后续出现差异，先判断是否由本次状态恢复错误导致；不把“所有自由生成必须逐 token 一致”扩大成无期限的新目标，也不把未解释差异直接豁免。
