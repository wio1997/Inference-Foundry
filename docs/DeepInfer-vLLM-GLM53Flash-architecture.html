同一个 GLM 模型，两套请求调度
DeepInfer 与 vLLM 在哪里分开、在哪里复用？

当前实现以 DeepInfer 原生引擎、C++ scheduler、Worker 和输出回调驱动请求；模型计算、物理缓存与昇腾算子复用固定版本 SDK。理解“谁调度请求”与“谁执行模型”，就能看清本次适配的边界。

验证范围：910C，7 张物理卡上的 8 个 die，TP8 / DP1 / EP 关闭；完整 45 层 W8A8 权重驻留 NPU。下文描述这条已执行路径，不代表所有 DeepInfer 后端。

两条执行路线逐 token 演示缓存与状态模型与算子调度捕获优化实测范围

01 · 从请求到算子：上层分开，下层复用

DeepInfer 当前接入

自建 HTTP / SSE 入口校验、排队；主线程处理 token IDs 与请求登记
↓
DeepInfer LLMEngine → C++ scheduler选取本步请求、prompt/decode 范围与逻辑块
↓
DeepInfer Worker / 原生回调工作进程生命周期仍由 DeepInfer 管理
↓
薄适配层：SDKBatchSchedule / Adapter原生批次 → SDK 计算描述；请求身份与物理缓存映射
↓
SDK NPUWorker / ModelRunner准备张量、positions、block tables 与模型 metadata
↓ 模型前向与采样后
原生 RequestOutput → HTTP 流式输出更新请求，继续下一步或结束并释放所有权

vLLM + vLLM-Ascend 固定参考

标准 OpenAI API / 输入处理tokenizer、请求参数、流式连接
↓
vLLM EngineCore / V1 Schedulerwaiting/running 请求、token 预算与缓存协调
↓
vLLM Executor / Worker 组织派发模型批次，回收每个请求的计算结果
↓
SDK NPUWorker / ModelRunnerAscend 后端、模型执行、物理缓存视图
↓ 模型前向与采样后
vLLM 输出处理 → 标准 API 流将采样结果归还调度器，更新请求与缓存引用
两边都到达的计算层：GLM-5.3-Flash 模型 → torch-npu / Ascend 扩展 / FLA-NPU → CANN 与 NPU kernel → HCCL 张量并行通信。

DeepInfer 这边创建的是 SDK 的计算 Worker、ModelRunner 与 KVCacheManager，没有创建 vLLM EngineCore、请求 Scheduler、Executor 或 API 服务。SDK 的 SchedulerOutput 在这里是计算描述对象，名称相同不意味着由另一个引擎调度请求。

02 · 从首个输入到输出完成：点一步看状态

教学示例：prompt 有 P0…P3 四个 token，生成 A、B，再预测 EOS。字母只用于解释自回归，不是真实模型预测。

Prefill 处理的是输入历史，最后一个有效位置的 logits 产生首个新 token；之后每轮把刚生成的 token 送回模型。预测出的 EOS 如果没有再输入模型，就不属于缓存已经处理的历史。

03 · “KV 缓存”在 GLM 中包含多种状态

DSA：可寻址的历史

稀疏注意力读取历史表示，涉及模型特定的 latent / 索引 / 压缩及尾部状态。不能把它简化成普通 MHA 的两块完整 K、V 张量。

请求 A → block table → 历史缓存页
position / sequence length → 当前可见历史
稀疏索引 → 选中的历史位置 → attention

KDA：递推摘要 + 短卷积历史

递推状态汇总已处理历史；短卷积状态保留最近窗口。q/k/v 卷积可合并存储。当前 TP8 局部卷积通道 3072、宽度 4、历史长度 3；这些是模型计算布局，不是 scheduler 的 token 配额。

请求 A → state slot A
旧递推状态 + 当前 q/k/v/gate/beta → 新状态
旧卷积历史 + 新投影 → 更新的短窗口
责任DeepInfer 当前路径固定参考 vLLM 路径
请求生命周期DeepInfer 入队、调度、结束判定和回调；适配层维护请求身份。vLLM Scheduler / 输出处理维护请求进度与终止。
逻辑块与物理页C++ scheduler 逻辑信息，经适配层映射到 SDK KVCacheManager 的物理块与状态槽。V1 Scheduler 直接协调 SDK KVCacheManager，再交给 ModelRunner。
实际 NPU 布局本次复用同一套 SDK 混合缓存规划。attention / Mamba 视图可能有 padding 和非连续 stride；不能任意把全池改成连续存储，块复制与页所有权也必须保持。
结束后的回收结束请求提交给 SDK，释放物理缓存引用，再完成原生生命周期收尾。由参考调度 / 缓存管理链释放引用。
前缀缓存 / offload本次两边均关闭前缀缓存与权重 offload。不能据此宣布已验证前缀复用、跨机缓存或 CPU/NPU 池迁移。

权重是跨请求复用的只读参数；请求缓存是随输入更新的历史。mHC 的 hidden/residual 属于当前前向计算，也不应直接当成跨 token KV 状态。

算子在哪一层？

Linear、RMSNorm、量化、Grouped MatMul、卷积、KDA recurrent / chunk、Sparse Flash Attention、mHC 等，是模型执行线路调用的计算单元。

已有 CANN 算子提供计算能力；模型模块负责权重 / scale、激活、归一化、mask、状态与前后处理。框架适配负责把这一整套规则接到当前批次和请求上。

当前主线复用固定 SDK 完整模型语义和现成实现。此次吞吐改进属于图捕获和调用组织，不是重新开发一套数学 kernel。

“库里有算子”解决了计算实现来源，但接口还要接对：shape / stride、dtype / scale、状态原地改写、位置和 slot、prefill/decode 分支、跨 rank 归约与生命周期，都属于调用契约。现成算子不能自动替上层解释这些信息。

05 · 调度差异：谁决定本轮算什么？

视角DeepInfer 当前接入固定参考
入队与准入HTTP 等待队列；原生容量允许时登记请求。标准 API → EngineCore waiting/running 队列。
批次选择C++ scheduler 选择请求与计算范围；适配器提交 SDK 描述。V1 Scheduler 生成模型批次与缓存调度结果。
Prefill本次均启用 chunked prefill，token 预算 1792。切分 prompt 是调度决策；模型内部 chunk/recurrent kernel 的选择是模型 / 算子决策。
连续批处理已验证动态准入、真实批次 8、独立请求完成及状态释放；不能再称当前路径只支持单请求。同样按容量处理连续批次；具体准入和排队时序由参考调度器决定。
多卡同一组 8 die，TP8 / DP1 / EP 关闭，模型权重全驻留 NPU；模型 TP 通信由 HCCL 完成。控制面消息传递不能代替模型实际多卡计算证明。
结束原生 callback / RequestOutput → HTTP SSE；释放适配层与物理缓存所有权。参考输出处理 → API 流；更新参考调度 / 缓存引用。

06 · 本次性能突破在哪：KDA 的图边界

图捕获把固定计算序列录下来，之后直接回放，减少每个 token 重走 Python 和逐个提交的开销。数学计算仍由原有 CANN / FLA-NPU 完成。

PIECEWISE 默认不生成捕获用 attention metadata。只移除 eager 边界会导致 0 层命中；当前通过 SDK 原有 metadata hook，为受限的一步解码预热和捕获补齐元数据。KV transfer 与 speculative 配置明确拒绝。
