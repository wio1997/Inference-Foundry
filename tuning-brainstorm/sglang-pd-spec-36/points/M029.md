# M029｜TP / EP / DP / PP / CP 的切分边界

[任务目录](../README.md) · [执行合同](../CONTRACT.md)

- 审阅状态：待路径核验。
- 类型：config。
- 主线：PD 分离 + 推测解码保留；Ascend 实际配置待运行合同确认。
- 本文是用途、假设与最小实验设计，不是已取得加速的报告。

## 它干什么

TP 切张量，EP 切专家，DP 分请求副本，PP 切层，CP 切上下文；它们决定一张卡做多少工作，以及为了拼回结果要通信多少。PD 是分阶段，不能与 PP 混为一谈。

## 当前怎么做

P 与 D 可有不同并行需求，但 KV 交接需要兼容布局和传输拓扑；D 的推测 target/draft 也必须遵守同一受支持组合。

## 成本在哪里

更多卡降低单卡容量压力，却增加 collective、跨节点链路和流水空隙；少卡也可能装不下权重。

## 这次考察的优化思路

只在容量和后端允许时比较两个等总卡数的 D 并行布局，判断减少通信是否覆盖较小每卡计算量的损失。

## 什么条件下可能适用

先确认硬件连接、内存预算、P/D connector 及目标 MTP 的支持矩阵。

## 新增成本与回退场景

低并发拆成更多副本可能浪费权重；跨机 TP 会放大通信尾巴。

## 不能破坏的语义和生命周期

权重分片与量化一致、rank 协议一致；禁止在运行中不完整改变拓扑。

## 最小实验

**基线**

冻结总卡数、权重、MTP 与 P 配置，记录 D 当前布局。

**唯一改动因素**

选一个满足容量的替代 D 拓扑，独立启动受控实例。

**用例**

- 2/3 并发
- 一个能同时喂满两种布局的固定请求数，需先验容量

**预测**

减少 collective 或慢 rank 等待的布局应缩短有效 token 时间。

**指标**

- 卡秒/有效 token
- collective 时间
- TTFT/ITL
- HBM 与 accepted length

**否定条件**

不满足容量/connector 支持即不适用；快但多用卡不算等资源收益。

**第一个可执行动作**

只做拓扑与内存可行性表，未通过不启动第二布局。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

固定模型、量化与接受规则下的全模型工作，以及各拓扑必需 collective/PD 状态字节。

**资源与依赖边界**

按拓扑的节点/链路容量和计算依赖构造界，含 PP 泡沫、DP 复制容量与 P→D 交接约束。

**怎样校准可达上界**

实测该硬件拓扑上对应消息/矩阵形状的可达计算和 collective；当前 UNKNOWN。

**怎样判断剩余空间**

同总卡数用卡秒/有效输出 token 比较余量，先识别通信瓶颈还是权重容量约束再选择相邻拓扑。

**条件特化与回退**

按负载区间离线选择配置，运行期不可随意换分片；记录重启/重载和权重复制成本。

**何时停止当前方向**

可行拓扑已触达资源/容量界且改进仅来自加卡，停止等资源优化；不能证明未测拓扑全局最优。
