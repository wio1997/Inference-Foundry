# M003｜CPU affinity / NUMA / 线程数

[任务目录](../README.md) · [执行合同](../CONTRACT.md)

- 教学课程：第 4 讲。
- 审阅状态：待路径核验。
- 类型：config。
- 主线：PD 分离 + 推测解码保留；Ascend 实际配置待运行合同确认。
- 本文是用途、假设与最小实验设计，不是已取得加速的报告。

## 它干什么

给调度、通信和分词线程安排合适的 CPU 核，减少线程抢核以及访问远端主机内存。

## 当前怎么做

绑定包含 CPU 亲和与内存放置两部分。固定通用 numa_utils 的自动发现主要检查 CUDA/XPU；不能据此声称 Ascend 自动绑定已生效，要读取实际进程掩码和 NPU/NIC 拓扑。

## 成本在哪里

跨 NUMA 访问、上下文切换和线程排队会延迟提交；绑定过窄也会把多个工作线程挤到一起。

## 这次考察的优化思路

对照已有绑定能力：在 CPU 核数不变时，将调度进程移至设备/通信近端且与高负载线程分开，可能缩短暴露的提交等待。

## 什么条件下可能适用

实际存在可识别拓扑、足够 CPU 配额且测到调度等待；不借用旧机器的 NUMA 数量。

## 新增成本与回退场景

近端核不足；绑核破坏通信线程调度；已有容器 cpuset 使请求绑定无效。

## 不能破坏的语义和生命周期

不改变模型、MTP、P/D 分工和工作线程功能；检查所有 rank 持续进展与进程退出清理。

## 最小实验

**基线**

保存每个实验进程的 affinity、线程数、cpuset、内存节点和 NPU/NIC 对应关系。

**唯一改动因素**

仅改变实验进程 CPU 亲和，先保持线程数及内存策略不变。

**用例**

- 当前绑定
- 等核数的拓扑近端绑定
- 1 与 3 路请求；再加可控前端 CPU 压力

**预测**

确有调度争用时，run-queue 等待和提交空隙同时降低。

**指标**

- CPU migration/context switch
- run-queue 等待
- 设备提交空隙
- ITL 与 core·s

**否定条件**

掩码未生效不能算实验；CPU 指标改善但关键路径不变则不计推理加速。

**第一个可执行动作**

只读确认容器实际权限和 NPU 路径使用的绑定实现，不修改系统级亲和或 IRQ。

**最低执行层级**

拓扑/生效核验 → 单变量配置对照

## 逼近物理极限的分析

**必要工作**

必要的调度、通信和输入线程都要获得 CPU 执行时间；亲和不能减少必要指令。

**资源与依赖边界**

关键线程服务时间受单核执行、内存延迟与 OS 排队约束；总核数或 CPU 标称频率不是可达提交速度。

**怎样校准可达上界**

在同频率/配额下量隔离线程的最好服务时间，再加入实际 IPC 与通信线程；使用实际 NUMA 拓扑和近端内存流量校准。

**怎样判断剩余空间**

若主要差距来自 run-queue 或迁移继续调整核布局/线程量；若差距来自必需串行代码应转到对应机制，不靠继续加核。

**条件特化与回退**

按 rank 数、CPU 配额、NPU/NIC 拓扑、输入长度及并发区间建立方案；小并发和高 MTP 接受率可能改变 CPU 暴露比例。

**何时停止当前方向**

在合法资源配额内邻近配置均无稳定改善，排队与迁移接近可观测底噪，剩余时间可归因于必要服务；不宣称所有机器最优。
