## 它干什么

路由决定把请求交给哪个副本。缓存亲和能少算重复前缀，但选中拥挤副本也会排队；这是 worker 内前缀树之外的一层选择。

## 当前怎么做

现有 gateway 接受独立 P/D 策略配置；固定源码中 HTTP PD 读取两套策略，gRPC PD selection 使用同一个 model/default policy，详见下述追加。已有 cache-aware 和负载阈值。路由器的缓存估计不等于 worker 的即时真实命中。

## 成本在哪里

维护路由树和负载信息有 CPU/通信成本；信息延迟会选错，多个 gateway 的估计也可能不一致。

## 这次考察的优化思路

存在至少两个 P 副本时，仅调整缓存亲和转负载均衡的一个已有阈值，测试节省的 prefill 是否覆盖多出的排队。

## 什么条件下可能适用

必须有可选副本；只有一对 P/D 时无路由选择空间。

## 新增成本与回退场景

热门前缀把单个 P 压满；只看空闲又损失复用。

## 不能破坏的语义和生命周期

模型/adapter/cache key 一致；重试不可重复输出，PD bootstrap 必须落到正确 D。

## 最小实验

**基线**

固定副本数、D 策略和到达序列，记录命中与排队。

**唯一改动因素**

只改一个已存在的 cache/load 阈值。

**用例**

- 2/3 并发共享前缀
- 容量允许时一次热点前缀突发，另保留冷请求

**预测**

热点时减少拥挤 P 的等待，代价是部分命中下降。

**指标**

- 路由耗时
- 真实 prefix hit
- P 排队和 TTFT
- D 排队与 accepted length

**否定条件**

单副本则不适用；排队改善被多算前缀抵消或冷请求饥饿。

**第一个可执行动作**

核对实际副本拓扑和 gateway 策略；无多副本只完成适用性记录。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

每请求至少需要一次正确目标选择；真正未命中部分的 prefill 不能靠路由估计消失。

**资源与依赖边界**

路由→排队→未命中 prefill→交接的实测服务时间模型，受副本容量与缓存事实约束。

**怎样校准可达上界**

同请求长度、真实命中、P/D 负载测各 worker 服务时间与路由开销；当前 UNKNOWN。

**怎样判断剩余空间**

用已知请求流离线比较可行调度的乐观界与现策略，只把可观测信息能实现的差距列为候选。

**条件特化与回退**

只在已测热点与负载区间调阈值，负载信息过期 fallback；计探测、路由树与状态同步成本。

**何时停止当前方向**

单副本不适用；可选副本在实测排队、未命中计算及交接成本上没有可利用差异，且合法选择的改善不足以覆盖维护成本时停止。饱和本身不能证明路由无收益。

## 2026-10-19 实际 gateway 源码核验

[本轮证据](../evidence/2026-10-19-gateway-pd-source/README.md)取得并逐blob校验固定commit的408个gateway文件，附27个相关文件与18条源码观察。HTTP PD 分别读取P/D策略，gRPC factory虽保存两套策略，其实际selection stage却为P/D共用model/default policy；尚未形成Rust运行见证或提交修补，不将此归因为当前服务故障。

缓存估计以pool::model为键，按Unicode字符前缀计匹配，选中即写树；失败回调仅记日志。低匹配分支选择最小请求负载，与顶部“最小树大小”注释不同。淘汰实际比较每tenant字符数；max_tree_size不能当作KV页数、HBM字节数或节点数。HTTP P负载guard可持续到Decode结束/响应body释放，所以P.load不是引擎P队列。

注册/移除workflow、模型/角色/健康/熔断筛选和bootstrap配对已定位。策略依赖候选池同模型/同角色，树键无独立adapter维度；HTTP模型过滤还取决于enable_igw。现有Rust P/D隔离、移除、registry及guard测试只定位未执行。本机无Rust，五次内层下载/环境失败保留，源码子门槛PASS不等于CPU正确性；源码Cargo0.3.2/Rust1.90也不证明部署版本相同。
