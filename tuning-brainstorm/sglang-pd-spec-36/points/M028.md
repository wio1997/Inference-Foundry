# M028｜DeepEP dispatch / combine 的模式选择

[任务目录](../README.md) · [执行合同](../CONTRACT.md)

- 教学课程：第 8 讲。
- 审阅状态：Ascend分派门控/状态模型已核验；DeepEP原生未决。
- 类型：config。
- 主线：PD 分离 + 推测解码保留；Ascend 实际配置待运行合同确认。
- 本文是用途、假设与最小实验设计，不是已取得加速的报告。

## 它干什么

dispatch 把 token 送到专家所在卡，combine 把结果送回来。normal 与 low_latency 是已有通信路径，分别倾向吞吐和低延迟。

## 当前怎么做

固定官方文档给 Ascend PD 的起点是 P normal、D low_latency；Ascend FuseEP 还限制在 PD D 端。具体 CANN、DeepEP、量化与 MTP 支持要查安装版本。

## 成本在哪里

通信存在每次提交成本、链路传输、缓冲和同步；P 长序列分轮还能改变峰值缓冲需求。

## 这次考察的优化思路

如果 P 长输入被通信缓冲限制，可只调整已支持的分轮粒度，在固定总 token 下减少缓冲占用；不强行让 D verify 改成不支持模式。

## 什么条件下可能适用

Ascend DeepEP normal 分轮能力存在，且 P 缓冲/通信确实受限。

## 新增成本与回退场景

轮数更多增加启动和同步；缓冲下降也可能吞吐下降。

## 不能破坏的语义和生命周期

不丢/重发 token，dispatch/combine 数值与路由一致；D MTP 设置冻结。

## 最小实验

**基线**

按已核验的 P normal/D low_latency 建基线。

**唯一改动因素**

只改 P 的一个合法 per-round token 设置并匹配总容量约束。

**用例**

- c2-short、c3-long
- P 输入刚超过单轮容量的边界

**预测**

HBM/通信缓冲下降，且增加的轮次开销不破坏 TTFT 目标。

**指标**

- 通信缓冲峰值
- 轮数与 dispatch/combine 时间
- P 完成与 TTFT
- D accepted length

**否定条件**

没有缓冲瓶颈，或轮次使交接尾巴/TTFT 超限。

**第一个可执行动作**

核对已安装 DeepEP API、分轮参数与 HCCL buffer 计算，不照搬主分支默认值。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

固定路由下必要远端 token 数据与结果回传字节；是否可压缩属另外精度/协议合同。

**资源与依赖边界**

按 dispatch/combine 消息、拓扑 cut 与同步依赖建界；标称链路带宽不能作为可达值。

**怎样校准可达上界**

相同 Ascend 拓扑、消息大小、rank、dtype 和并发模式测有效带宽及每轮启动成本；当前 UNKNOWN。

**怎样判断剩余空间**

必要 bytes/实测可达 bandwidth 之外的空隙来自启动、同步或布局；分轮只改变缓冲与摊销。

**条件特化与回退**

P 长序列合法轮次区间内选粒度，小输入保留原配置；计轮间同步和缓冲常驻，D MTP 固定。

**何时停止当前方向**

每轮开销与内存预算已达稳定取舍，减缓冲导致 TTFT 超限就停；无通信瓶颈不继续扫参数。
