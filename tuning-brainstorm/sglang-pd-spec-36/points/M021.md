## 它干什么

图 replay 把反复提交的一串设备工作预先记录；形状桶是若干预备尺寸，请求数量不匹配时可能补齐到较大桶。

## 当前怎么做

NPU graph runner 选择捕获桶，更新本轮 KV 位置和长度等输入后 replay；推测解码还涉及 target verify、draft 等各自形状。图不是可以复用旧 KV 地址的静态结果。

## 成本在哪里

节省 CPU launch，但 padding 产生额外计算；捕获与静态缓冲占启动时间和 HBM。

## 这次考察的优化思路

若常见 2/3 请求的 verify 形状被补到过大的桶，新增一个实际高频桶可能减少 padding，代价是更多捕获和常驻内存。

## 什么条件下可能适用

目标 NPU 图路径能捕获该形状且 MTP 输入宽度稳定。

## 新增成本与回退场景

低频形状增加桶只占内存；DP 各 rank 形状不统一会失效或回退。

## 不能破坏的语义和生命周期

保护空闲 rank、尾批、accepted length 变化、KV 地址刷新；不能复用捕获时的旧页。

## 最小实验

**基线**

记录 raw shape、选中桶、fallback 和捕获 HBM。

**唯一改动因素**

仅增加一个最常见但缺失的合法桶。

**用例**

- c2-short、c3-long
- 一次 3→2→1 请求退出过程

**预测**

padding token 数下降，并在 D 验证阶段体现为更短 replay。

**指标**

- raw/padded token 比
- replay 与 eager 次数
- 图内存和启动时间
- ITL、accepted length 分布

**否定条件**

原本已精确命中桶，或新增图内存挤掉 KV 使排队更差。

**第一个可执行动作**

从实际日志/trace 导出 target/draft 桶与支持条件，再选唯一新增桶。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

真实 token 的 target/draft 前向与正确输入刷新不可省；padding 是实现开销，需单独计数。

**资源与依赖边界**

去 padding 后的真实计算依赖链与必需输入更新构成下界；图 replay 启动也有测得的最小成本。

**怎样校准可达上界**

相同 NPU 图模式、真实宽度和 dtype 校准空/最小 replay、精确 shape kernel 与内存占用；当前 UNKNOWN。

**怎样判断剩余空间**

用真实/padded 工作量和 replay→首 kernel 空隙估计空间，确认减少桶浪费不会让 KV 容量倒退。

**条件特化与回退**

只增加高频合法 shape 的桶，稀有形状 fallback；统计查桶、切换、capture 摊销与常驻 HBM。

**何时停止当前方向**

高频形状已精确覆盖且启动与输入更新逼近可达界，再加桶无摊销收益；保留其它 shape 的证据缺口。
