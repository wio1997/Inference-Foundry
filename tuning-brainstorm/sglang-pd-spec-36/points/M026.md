## 它干什么

MoE 为每个 token 选少数专家，把属于同一专家的 token 聚起来计算，再按原顺序加权合回。小矩阵与专家分布决定效率。

## 当前怎么做

通用流程是路由→dispatch→重排→grouped GEMM→反重排→combine；Ascend 已有 FuseEP 把其中多步合并，属于现有后端能力。

## 成本在哪里

专家矩阵计算之外，还付出索引、搬运、通信和 padding；2 个请求经过 MTP 验证可能对应很多候选 token。

## 这次考察的优化思路

先检查真实路径是否在 dispatch 输出后又转换一次相同布局；若 producer 与 consumer 接口一致，可研究省一次重复重排。已有 FuseEP 不算新发明。

## 什么条件下可能适用

确认当前 Ascend MoE 实现和量化格式，找到真实重复布局转换。

## 新增成本与回退场景

碎片专家分布可能需要重排；直接消费导致 GEMM 变慢会抵消收益。

## 不能破坏的语义和生命周期

专家编号、路由权重和 token 反向映射不变；冻结 MTP 参数并记录 accept 长度。

## 最小实验

**基线**

保存一个真实层的 hidden、top-k 与专家 token 分布。

**唯一改动因素**

只消除一处证明冗余的重排；无冗余则不改。

**用例**

- c2-short、c3-long
- 同样总 token 数的自然偏斜与较均衡路由回放

**预测**

重排字节减少，dispatch 到 combine 的完整段缩短。

**指标**

- 重排字节/时间
- 每专家 GEMM 形状
- 整层时延
- accepted length 与质量

**否定条件**

接口布局不同、GEMM 退化或端到端无收益即否定。

**第一个可执行动作**

读取实际分派路径与一层 trace，区分通信、重排和 GEMM。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

原 top-k 专家与路由权重确定的 GEMM 和加权合并不可省；必须按每专家 token 分布核算 FLOPs。

**资源与依赖边界**

dispatch→重排→专家计算→combine 的 rank 依赖图，含共享链路与 HBM；单层 wall 由实际慢路径决定。

**怎样校准可达上界**

同硬件、量化、专家大小和直方图校准 grouped GEMM/重排/通信；当前 UNKNOWN。

**怎样判断剩余空间**

区分必要专家工作、padding、重复布局搬运与负载不均；局部 bytes 减少须反映整层关键路径。

**条件特化与回退**

只对匹配布局与已测专家 token 分布启用直接消费；稀疏/溢出形状 fallback，计选择和额外缓冲。

**何时停止当前方向**

重排已融合或必要，剩余时间由近界 GEMM/通信占满；新路由分布需重新检查，不泛化为全局极限。
