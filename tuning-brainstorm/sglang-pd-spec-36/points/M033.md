## 它干什么

设备产生 token 后，还需增量转成文字，经 SSE 发送给用户。推测一次可能接受多个 token，生成时间与用户看到文字的时间并不相同。

## 当前怎么做

detokenizer 已有分组批解码、空输入过滤和文字片段暂存；发送频率由具体接口路径决定，不能把这些已有措施重新叫作候选。

## 成本在哪里

细碎事件增加 CPU、序列化、网络与客户端处理；合并事件会延迟可见输出。

## 这次考察的优化思路

若设备连续工作但 SSE 消息过碎，只对同一次 MTP 已接受结果做一次发送，或调整已有发送间隔；增加缓冲窗口属于体验取舍。

## 什么条件下可能适用

目标 API 支持相应发送粒度，且输出端 CPU/事件频率已是瓶颈。

## 新增成本与回退场景

短回复或交互业务不能接受延迟；慢客户端会触发背压。

## 不能破坏的语义和生命周期

保留 token 顺序、Unicode、stop、usage、finish 事件和取消回收；不漏接受 token。

## 最小实验

**基线**

固定 PD/MTP 和 tokenizer，记录设备产出与客户端到达。

**唯一改动因素**

只改变已有 SSE 合并粒度，预先冻结最大新增可见延迟。

**用例**

- 2/3 并发中文/英文输出
- 一个长回复加慢客户端的受控对照

**预测**

事件数下降，CPU 降低；可见延迟必须仍在约定内。

**指标**

- 事件数/有效 token
- CPU 与队列长度
- 首文本/最终答案时间
- 客户端间隔与取消回收

**否定条件**

CPU 不受影响或可见延迟超限；不能用更晚发送伪装模型加速。

**第一个可执行动作**

先读取实际 stream_interval 和 accepted block 到 SSE 的路径。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

所有已接受 token 的文本语义、协议必要元数据和最终通知都须交付，必要网络字节以实际编码计算。

**资源与依赖边界**

token ready→解码→序列化→发送→客户端接收链路；受 CPU 和链路约束，还受最大可见延迟合同限制。

**怎样校准可达上界**

同 tokenizer、语言文本、事件大小、协议与网络测可达解码/序列化/传输；当前 UNKNOWN。

**怎样判断剩余空间**

分出每事件固定开销和每字节必要开销，合并只消掉前者；不能把缓冲延迟隐去。

**条件特化与回退**

只在允许延迟预算内合并已接受块，短回复/finish 立即 flush；记录 timer/队列管理成本。

**何时停止当前方向**

事件开销已小于必要字节处理或更大合并触碰可见延迟上限，则停止；模型吞吐与用户体验分别记。
