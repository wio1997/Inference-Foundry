## 它干什么

grammar 限制下一 token 必须符合 JSON 等格式。规则编译是一次性准备，按当前生成位置更新 mask 则是每轮工作，两者要分开分析。

## 当前怎么做

已有 grammar backend 缓存编译对象，命中后复制请求状态；推测树还涉及候选的接受与回滚，不能让两个请求共享可变解析状态。

## 成本在哪里

首次编译、每轮 mask 构造/搬运和 CPU 等待；复杂规则可能使设备等 CPU。

## 这次考察的优化思路

重复 schema 的业务先对照预编译缓存命中与冷编译；若缓存已有命中，转查每轮静态 mask 是否真可复用，不能无条件复用状态相关 mask。

## 什么条件下可能适用

业务确实要求结构化输出，目标 grammar+PD+MTP 后端组合受支持。

## 新增成本与回退场景

独特 schema 太多使缓存占内存；schema 简单时编译不是主要成本。

## 不能破坏的语义和生命周期

逐条 schema 校验，保护 EOS、拒绝候选回滚与请求状态隔离；保持约束强度。

## 最小实验

**基线**

固定一个实际 JSON schema、MTP 与请求文本。

**唯一改动因素**

只预编译该 schema；保持每轮 grammar 逻辑不变。

**用例**

- 2/3 并发同 schema 冷/热分开
- 复杂嵌套 schema 与候选被拒绝用例

**预测**

仅首请求编译等待下降；稳态不应被误报为融合收益。

**指标**

- compile/hit 时间
- mask CPU/搬运等待
- 格式通过率
- TTFT 与 accepted length

**否定条件**

业务不用 grammar 则标不适用；已有预编译命中或时延不受其影响则关闭。

**第一个可执行动作**

先检查实际版本对 overlap＋spec＋grammar 的组合支持，再核对 grammar 状态与 MTP rollback；不支持则标为该合同下不适用。另测受支持模式须另立合同并保持 MTP，不能隐性关掉主线功能。

**最低执行层级**

先核验路径与兼容性；通过后做局部实验；最后验证 PD 端到端

## 逼近物理极限的分析

**必要工作**

给定 schema 的有效状态转换、候选合法性检查及允许 token mask 必须保留。

**资源与依赖边界**

编译/状态更新→mask→验证/采样的依赖链，按实际 CPU 可达吞吐与设备搬运约束建界。

**怎样校准可达上界**

同 CPU、tokenizer、schema 复杂度、MTP 树宽与 batch 测编译/更新/mask；当前 UNKNOWN。

**怎样判断剩余空间**

从冷编译和逐轮更新分别减去已有缓存收益，寻找重复编译/复制；状态相关工作不可假定静态。

**条件特化与回退**

只缓存 schema/tokenizer/version 相同的不可变编译产物，状态不同回独立实例；计查表和 clone。

**何时停止当前方向**

编译已全命中且更新是必要依赖，或候选违背 schema/回滚语义则停；不降低约束换速度。
