# M017｜持久状态、增量更新与 GPU metadata

[任务目录](../README.md) · [执行合同](../CONTRACT.md)

- 教学课程：第 4 讲。
- 审阅状态：目标镜像 CPU 元数据与页计数合同已核验；同步收益未测。
- 类型：conditional_candidate。
- 主线：PD 分离 + 推测解码保留；Ascend 实际配置待运行合同确认。
- 本文是用途、假设与最小实验设计，不是已取得加速的报告。

## 它干什么

元数据告诉算子每个请求有多长、在批里哪里、使用哪些 KV。持久状态或增量更新能减少每轮重新整理。

## 当前怎么做

固定 FutureMap 已根据后端 needs_cpu_seq_lens 决定是否回传 CPU 长度；设备上的真实新长度仍更新。TBO/ngram 等消费者会强制需要 CPU 信息。

## 成本在哪里

全量长度镜像的 D2H、同步和 CPU 求和可能暴露等待；让状态常驻设备则要求所有消费者兼容。

## 这次考察的优化思路

核验现有门控在 Ascend MTP 是否有可安全使用的 GPU/NPU-only 路径；这是已有能力的适配审计，不是删接受长度。

## 什么条件下可能适用

必须穷查 target、draft、attention、图准备及其他调度消费者；未声明能力时保持保守默认。

## 新增成本与回退场景

后端偷读 CPU 长度、TBO 分批或 mask 准备可能出错；移到设备计算也会新增任务。

## 不能破坏的语义和生命周期

真实接受长度、设备 seq_lens 与 KV 分配不变；任何 CPU 消费者存在就不能直接关闭镜像。

## 最小实验

**基线**

统计目标 MTP 路径每轮 CPU 长度消费者、D2H 字节和等待。

**唯一改动因素**

只有消费者审计通过才让一个后端声明无需 CPU 镜像；先运行断言差分。

**用例**

- 普通 MTP verify/extend
- 短长混合与变接受长度
- 启用实际需要 CPU 长度的模式作回退保护

**预测**

允许的路径减少 D2H/同步；保护路径仍保留原行为。

**指标**

- 长度镜像字节
- D2H 暴露时间
- 设备长度与分配一致性
- ITL

**否定条件**

任何依赖未证明消失则不执行关闭；复制已经被隐藏或开销很小则降低优先级。

**第一个可执行动作**

审计 decide_needs_cpu_seq_lens 的每个后端声明与实际读点，不凭默认参数推测。

**最低执行层级**

消费者审计 → 断言差分 → 单后端实验

## 逼近物理极限的分析

**必要工作**

每轮算子必须得到真实长度/位置/KV 映射；仅变化部分可增量，依赖上轮接受结果的状态不能提前臆造。

**资源与依赖边界**

若无 CPU 消费者，长度 CPU 镜像理论可为零；有消费者则至少传回它需要的信息并等待真实产出。设备更新成本仍存在。

**怎样校准可达上界**

列出读写表，量必要变化字节、实际搬运字节及等待；分别校准设备驻留计算和回传的实测成本。

**怎样判断剩余空间**

镜像门控后继续检查全量批重建、重复 dtype 转换、可增量的稳定字段；同样审计跨轮生命周期，不以一个 flag 当终点。

**条件特化与回退**

按 attention/草稿后端、TBO/ngram、batch churn、接受长度分布与 context 特化；未经声明的消费者必须保守保留。

**何时停止当前方向**

数据搬运接近真实消费者需要的字节量，新增设备任务不抵消收益，剩余元数据由必要变更解释；资源瓶颈转移后重新评估。
