# Run347 — saved Run239 acceptance and scheduling calibration

This is a **read-only reanalysis** of Run239's measured 48-request diagnostic pass, not a new service benchmark. All eight ranks have identical accepted-count matrices for each of the four measured cohorts. Replaying the 12-slot counts and trimming at exactly 1024 outputs verifies 48/48 outputs and **49,152 useful tokens**. The cohorts ran 298/310/285/302 Target cycles, **1195 total**, yielding 41.131 useful output tokens per cycle (out of a raw 96-slot-token cardinality limit). This observed algorithmic efficiency is a calibration point, not a ceiling on acceptance under another algorithm or schedule.

The 48 observed per-request completion durations total **12,534 slot-cycles**. Holding those durations fixed gives `sum_cohort ceil(sum_slot duration / 12) = 1046` cycles if the four current cohorts remain fixed, or `ceil(12534 / 12) = 1045` under arbitrary packing. These are capacity relaxations, not feasible schedules: legal arrival, prefill/seed, KV/state, shared eight-card resources and changed acceptance remain absent. They are specific to Run239; Run287's 1011/1015 and FIFO1118/1122 use a different diagnostic trajectory and cannot be mixed into a single bound. The independent 512 cardinality floor still assumes all eight candidate tokens can be useful and the current four zero-output handoffs; it cannot be combined with Run239's observed per-request durations as though both were simultaneously achievable.

The last useful token was staged **one Target cycle before** the serving loop stopped in each of four cohorts. This matches the known one-cycle Host progress mirror lag. Four trailing cycles are a Current control observation, not an automatically removable Product gain; changing the completion trigger requires state/parking/all-rank and formal E2E validation. Raw staged tokens exceeded externally useful tokens by 67/72/78/87 per cohort, including overshoot and trailing work, with no attribution of their resource criticality.

Run239's maximum rank serving wall per cohort was 16.810/17.514/16.251/17.279 s. These instrumented host boundaries do not supply per-cycle device costs or a formal Run99 latency. The V3.1 model now carries the same-trace acceptance calibration while leaving finite Hardware/Resource, Scheduling and Product bounds unknown. Next close compulsory Target+DSpark/prefill work and same-path resource capacity, plus actual arrival→seed-ready if refill is revisited; do not convert 1045/1046 or 512 into a TPS upper endpoint.
