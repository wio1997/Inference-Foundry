## Corrected execution dependency

The frozen client holds a concurrency-12 semaphore across each streamed HTTP response (`scripts/bench.py:27–46`). The next request is submitted only when one prior stream ends. `FixedCohortServing.run` parks a completed slot but continues to step the same twelve-slot Runtime until all slots finish, then copies/returns all twelve token histories (`runtime/fixed_serving.py:120–207`). The borrowed ModelRunner calls that method synchronously inside `execute_model` and constructs one `extreme_bulk_output` for all twelve (`model_runner_v1.py:3388–3470`). EngineCore calls `scheduler.update_from_output` only after the executor returns (`core.py:576–608`). The scheduler normally frees a finished request's KV blocks in `_free_request` (`scheduler.py:1818–1838,2220–2266`).

Consequently the next three **real** prompts cannot arrive while nine old slots run in Current. Run331's b2/b3/b4 saved-cycle results (65/62/54) and Run340's replacement budgets assume an execution architecture that does not yet exist. A private seed test with future benchmark prompts would violate the real-arrival dependency and could not establish Product gain. Run341's natural 1–3-request prefill timings belong to the *next* original cohort, after the bulk barrier; they do not measure live refill preparation.

From Run330's original Run287 one-cycle Host-mirror release trajectory, the third free slot occurred at cycle 175/248/256/244 while its cohort ended at 294/297/297/315: conditional windows of 119/49/41/71 cycles. This measures how early a three-completion publication *could* start on that diagnostic trajectory. It is neither a measured arrival time nor available wall-time saving; client/network response delay and continuation overhead are absent, and Run287 is not formal Run99.

## Minimal architecture gate before seed or replacement

1. At a complete all-eight Runtime cycle boundary, retain the same Runtime/Graph storage and all twelve physical KV allocations. Drain side-stream consumers before exposing an output segment. Stage exactly the completed requests' 1024 accepted tokens once; make output publication idempotent across resumes.
2. Return a segment through ModelRunner/EngineCore so Scheduler and HTTP clients can finish those requests and submit new real prompts. Keep Scheduler accounting for the remaining nine consistent with its single scheduled step, or introduce an explicit continuation output path that does not schedule the old nine through the ordinary runner. New prompts remain queued and cannot prefill, seed, overwrite borrowed tensors or reuse pinned old KV pages in this first gate.
3. Resume the *same* Runtime on all eight ranks, preserving collective order, request-to-slot identity, progress baseline, token history, metadata and Host mirror. Continue old nine to completion; release retained KV only when the parked physical readers/writers end. Do not claim Run316's unclosed full snapshot has become safe: this gate retains original objects instead of restoring a copy.
4. Verify all 48 client outputs exactly once at 1024 tokens, all-eight continuation boundaries and FULL Graph gates; prove three subsequent real client requests arrived before the old nine finished, with no early prefill/seed/KV reuse. Capture publication and resume overhead, old-nine pause, and KV retention/release. Only after this gate may a b3 live seed/state-install transaction be tested with actual queued requests.

The apparent simple `return` from `FixedCohortServing.run` is insufficient: it destroys local histories and control position, and the next normal Scheduler step can reshape/reorder the batch and run new requests while the old Runtime borrows fixed tensors. Similarly, sending early HTTP completion without Scheduler/KV lifetime coordination risks releasing pages the parked Graph still addresses. The first implementation cut therefore spans serving continuation, ModelRunner output transport, EngineCore/Scheduler accounting, and KV pinning. Astra High independently confirmed the arrival constraint and this gate order; the exact transport design is an implementation choice, not yet validated.
