# Loop075 Run348–352 — concurrent real-shape GMM resource calibration

Goal: reduce one Resource/Hardware input uncertainty on the actual 8×910B3 without treating an isolated operator as the Product critical path. The frozen service was stopped; this ran in the existing CANN9.1/driver26.0.rc1 container, using independently selected Run121 per-rank route-count vectors from **different** ordinal layers `84/82/66/62/60/72/50/74`, packed format29 W4A8 GMM1 `[32,4096,512]` and GMM2 `[32,2048,512]`, and synthetic zero input/weights. Only pre-capture output shape/finite checks were done; replay output and native op count were not checked. All eight processes selected 15 active experts each and 60–75 routed input tokens. This is not a coherent real Target layer's all-rank route. No borrowed framework source changed.

Run348's direct event wrapper produced GMM1 328–403 µs and GMM2 151–178 µs per rank, because each interval includes a separate Host enqueue. It **does not** calibrate kernel or HBM capacity. Runs349/350/351 reduced submission contribution: each NPU Graph capture requested 16 same-shape operators, measured over 30 replays after warmup; the event span is divided by 16. Run349 and Run351 launched all eight ranks concurrently, with common **Host** windows overlapping at least31.6 ms and start spreads below0.53 ms; this does not prove every replay's device interval overlapped all ranks. Run350 ran the same rank0 route and Graph with only one card, giving an A/B/A timing check.
