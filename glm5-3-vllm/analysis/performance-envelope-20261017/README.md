# GLM5.3 双机性能边界：第一版数值预研

2026-10-17。**已完成离线计算，没有新启动设备实验。下面是明确假设下的乐观资源模型，不是已经证明可达的性能，也不是覆盖所有算法的物理极限。** 模型的用途是给研究一个数量级参照，找出需要补证据的差距。

## 当前能回答什么

- 两台 910C，各 8 卡/16 die；当前对照布局为一台 P、一台 D，各 TP16。每个阶段只能使用自己一台的资源。
- 完整 GLM5.3 W8A8C8，现有算子、全 SDMA、MemCache 路径；不使用投机解码，不缩小层数/专家数。
- 先固定 256/64、1024/64 输入/输出作为已有正确性和性能证据的锚点；4096/128 和更大 batch 仅作分析情景。
- 未收到生产 TTFT/TPOT SLO 或请求分布。因此先给条件曲线，不宣称找到了最大合格业务吞吐。

### 第一组数值：单请求，固定长度

以下取**独立均匀专家路由**情景：每层每 token 从 256 个专家选 8 个；同批 token 可复用专家权重。流量模型假设每个触及矩阵按一字节权重读取一次、各 rank 完全均衡，额外代价见下文。输入长度不包含输出长度。

| 输入/输出 token | P 一次前向资源屋顶时间 | 当前 PD 协议首 token 资源屋顶时间 | Decode 平均每步资源屋顶时间 | 完整请求输出 token/s | 同窗口输入 token/s |
|---|---:|---:|---:|---:|---:|
| 256 / 64 | 29.0 ms | 57.5 ms | 1.58 ms | 407 | 1,627 |
| 1024 / 64 | 29.0 ms | 57.6 ms | 1.61 ms | 403 | 6,440 |
| 4096 / 128 | 32.3–43.3 ms | 60.8–71.8 ms | 1.65 ms | 455–474 | 14,567–15,164 |

**这些数字只能称“资源屋顶情景”。** 未计入实际量化/反量化、向量/标量运算、CPU/算子启动、TP 集合通信、完整 KV 交接、排队及各种竞争；D 尾部前向若需展开缓存前缀的 K/V，该展开/物化也尚未计入。不能作为服务承诺或把与实测的比值直接叫作优化潜力。小 batch 时，两种参考算力档位给出相同时间，是因为这份模型的 HBM 项更大，并不说明现场已证实受 HBM 限制。

“PD 首 token”这一列还特意保留了当前协议的额外工作：P 先生成一个 token 但没有直接返回给客户；D 取回完整缓存块后，重算 128-token 尾部并生成首个可见 token。因此模型计为 P 前向 + D 尾部前向，省略了两者之间的传输耗时。直接返回 P 首 token 是另一种执行方式；此前原型未过正确性关，不能当作已经成立的更快方案。

路由会改变上述估算。以 1024/64 为例，若所有 token 恰好选择相同 8 个专家，PD 时间模型为 8.7–11.2 ms；均匀独立路由约 57.6 ms。这是**不同输入/路由情景，不是可随意调节的参数，也不是统计置信区间**。在未取得真实路由并集前，57.6 ms 不能作为该输入的严格下界。

### 当前实测对照

来自 `accepted-short-medium-baseline.json`：每档 12 个计时请求，另有预热；固定 64 输出、C1、greedy、ignore_eos。表中延迟为 p50，吞吐来自完整计时窗口，未用分位数拼出吞吐。

| 输入/输出 token | 实测 TTFT p50 | 实测 TPOT p50 | 实测输出 token/s | 对应输入 token/s |
|---|---:|---:|---:|---:|
| 256 / 64 | 404.3 ms | 190.9 ms | 5.161 | 20.64 |
| 1024 / 64 | 521.7 ms | 188.4 ms | 5.161 | 82.57 |

这是指定短/中输入、C1 的有限验收；C4 严格输出检查失败，长输入仍有正确性问题，不能把这些结果推广到生产或高并发，也不能据此比较 vLLM 与 SGLang 的最优性能。它是历史已完成的测量，不表示服务当前保持运行。

约 188 ms 实测 TPOT 与约 1.6 ms 流量模型之间的差距，目前混合了未建模成本、过于乐观的假设和实现额外开销。**尚未完成归因，更没有证明可以加速一百倍。** 下一步应先把已正确路径的一次 decode 分解，识别差距，而不是再遍历启动参数。

## “最大输入和输出”的计量方式

固定每请求 I 个输入、O 个输出，若完整服务每秒成功完成 λ 个请求：

```text
输入吞吐 = I × λ
输出吞吐 = O × λ
```

两者在固定输入输出比下联动，不能分别取峰值然后相加。对单个请求，`完成时间 = TTFT + (O−1)×TPOT`；这个恒等式逐请求成立，不能直接把 TTFT p50 和 TPOT p50 相加后当成实测吞吐。

下面展示 1024/64、均匀路由的**同步批次模型**。假设两个 PD 阶段可流水处理多个批次，周期是 `max(P批时间, D尾部前向+63步解码)`。它只描述该组织方式，不是所有连续组批方式的上界；实际排队和传输尚未计入。

| 每批请求数 | Decode 每步资源时间 | 稳态模型输出 token/s | 稳态模型输入 token/s | 适用范围 |
|---|---:|---:|---:|---|
| 1 | 1.61 ms | 492 | 7,879 | 流水需要多批在途；不是全服务只有 1 个并发请求 |
| 4 | 4.21 ms | 870 | 13,920 | 当前 C4 未通过正确性验证 |
| 16 | 12.54 ms | 1,250 | 20,000 | 超出当前 max_num_seqs=4，未验证 workspace/调度 |
| 64 | 27.60 ms | 约 2,250–2,277 | 约 36,000–36,431 | 同上，且长时间排队会改变 TTFT |

批次变大可增加总吞吐，同时也会增加每请求间隔；一个没有延迟约束的吞吐最大值，不能直接作为交互服务的目标。正式目标应是：**在确定的模型、硬件、精度、输入输出分布、成功率和 TTFT/TPOT 要求下，最大化持续完成的输入/输出 token 量。** 当前不擅自替用户设置 SLO。

## 容量：输入最长多少，输出最多多少

现场捕获的 KV 表示，每个 token、每个 rank：

```text
78 层 packed MLA：78 × 656                    = 51,168 bytes
5 层 BF16 Indexer key：5 × 128 × 2             =  1,280 bytes
16 层 INT8 Indexer key + 单个 FP16 scale：16 × (128+2) = 2,080 bytes
总计                                            54,528 bytes
128-token block                              6,979,584 bytes
```

KV 在 TP ranks 上存在复制，不能把 16 个 rank 的 token 槽相加当成单个请求容量。

| 项目 | 已捕获配置的数值 | 解释 |
|---|---:|---|
| P KV block 数/rank | 1,108 | 141,824 个 token 槽/rank |
| D KV block 数/rank | 1,289 | 164,992 个 token 槽/rank |
| 当前 max_model_len | 8,192 | 当前输入与输出总长度边界 |
| 当前 max_num_seqs | 4 | 当前接纳上限，不等于物理容量上限 |
| 模型配置 max_position_embeddings | 1,048,576 | 模型配置值，不证明部署能运行该长度 |

当前配置下，预留 O 个输出时需满足 `I + O ≤ 8192`；例如预留 64 输出，可用输入上限为 8128（输入已包含模板/特殊 token）。这只是参数和容量关系，尚不是该长度的正确性验收。

KV token 槽还需为所有活跃请求和缓存驻留共同分配，并按 128 对齐。单请求是否能扩大到 14万/16万，取决于 workspace、其他驻留内存、算子及服务路径，不由 KV 槽数单独决定。DRAM 缓存池容量也不能直接加到 NPU 的活跃 KV 容量。按当前复制表示，1,048,576 token 单 KV 就需53.25GiB/rank，加上约46–47GiB/rank权重后无法驻留；模型配置的百万长度并非该部署的容量。

## 计算依据与可复现入口

实际 config：78 层，3 dense +75 MoE，hidden 6144，256 routed experts/top8/shared1，64 attention heads，q rank2048，KV rank512，nope192/rope64/v256，21 full Indexer +57 shared，indexer32×128/top2048。MTP 层存在，但本模型未启用投机解码，因此不计其执行收益或开销。

按常规逻辑矩阵账本，prefill 主体约 **78.692G ops/input token**，每次最终 logits 另加1.903G ops；一轮 decode 的线性矩阵合计约 **80.596G ops/output token**，1 MAC算2ops。Attention pair、Indexer点积另计，norm/softmax/top-k等未计。展开式prefill与吸收式decode作为明确情景，尚未证明现场所有shape都使用此路径。

MoE 权重流量按专家并集，计算量按 token×top-k。独立均匀路由时，N个token触及专家数的期望是 `256×[1−(1−8/256)^N]`；模型同时输出全相同路由、均匀路由、最大专家并集三种情况。所有线性矩阵暂按一字节/INT8作乐观松弛，**实际存在 FLOAT Indexer投影和FP32 router**，不代表修改了精度。量化元数据、复制矩阵与中间缓冲需要下一版补齐。

每个PD阶段采用16die×1.6TB/s的HBM参考屋顶；矩阵计算采用两档参考额定能力。华为800I A3官方规格为整机4.48 PFLOPS FP16 /8.96 POPS INT8；800T A3为约6.0/12.0。论文v1给出376TFLOPS BF16与752TOPS INT8/die，v2已去掉绝对计算峰值。现场 `Ascend910_9392` 尚未映射到确切算力档位；800I的BF16与FP16等速是情景假设。以上并非实测有效速率，也不把超节点全系统资源算给这两台。[800I规格](https://e.huawei.com/cn/products/computing/ascend/atlas-800i-a3)、[800T规格](https://e.huawei.com/cn/products/computing/ascend/atlas-800t-a3)、[论文v1](https://arxiv.org/html/2506.12708v1)、[论文v2](https://arxiv.org/html/2506.12708v2)

同一Cube上的不同精度矩阵需求按额定能力归一化后相加；HBM字节累加。最乐观资源时间取 `max(Cube需求时间, HBM需求时间)`。跨层依赖、调用时延与资源争用只会使这个简化模型更需要校准；不同算法/驻留方式也可能改变资源需求，因此这些数值不构成全域不可能性证明。


- 自检覆盖矩阵账本、KV字节守恒、专家并集范围、稀疏/因果pair计数和资源需求单调性。

## 下一次只补会改变决策的证据

1. 延续执行线的正确性修复，不将不正确的高并发结果用于优化验收。
2. 从已经正确的短输入decode取一个短执行片段：实际dtype、rank复制、专家并集、主要算子与通信/CPU等待。先解释188ms由哪些部分组成；不需要重做全模型参数搜索。
3. 用真实shape的现有算子片段和通信校准，把“资源屋顶”收紧成可检验目标。若等待占主要差距，研究组织和同步；若有效吞吐受shape限制，研究批次/布局；若成本不可消除，修正目标与资源分配。
4. 收到业务延迟要求后，过滤违反TTFT/TPOT或内存/正确性的情景，再比较最大持续输入/输出吞吐。增加设备数量时重新计入拓扑与分片变化，不按卡数线性外推。

已有经验、当前实现和理论松弛各保留自己的结论范围。第一版先提供可计算的研究坐标；不预先宣布接近最优，也不为完善理论而停止实现探索。
