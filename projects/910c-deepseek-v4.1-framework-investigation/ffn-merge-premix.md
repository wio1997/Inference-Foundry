# FFN 输出合并到下一层 premix，固定路由、权重与并行配置

在 171 冻结 C8 的 16 个 rank、4 波 eager、40 层中，共有 2,560 处共享 Down 的 BF16 输出与路由结果相加后交给 HcPost。相加的两端都是本地 `[q,5120]`，其中 960 处 q=3，其余 1,600 处分布在 416、419、816、817、818 行，每个行数各 320 处。使用合并的真实行数。路由算子的填充行数可能更大。[逐形状计数与估算](baselines/ffn-merge-premix.json)

## 能省的是哪份数据

| 算子边界 | 每个本地有效行能少读写什么 | 必须保留什么 |
|---|---|---|
| ForeachAddList → HcPost | 合并结果 X 少写再少读，共 20,480 B | 读取两份专家输出，先把和舍入到 BF16，再按原顺序做 HcPost 四路组合 |
| 共享 Down → 上述两算子 | 共享 Down 的 5,120 个 BF16 也能就地交付时，另省 20,480 B | 原整数点积、scale、BF16 分支舍入，以及已到达的路由结果。若 Down 有额外读者，或 Cube 到 Vector 必须落地，这部分要扣回 |
| HcPost → 下一层直接 premix | 原输出每行含 4×5,120 个 BF16。若就地生成 Y，少读一次 40,960 B | 原残差仍写回供稍后读者使用。只有 34 个直接入口计入；另 2 个 Engram、3 个辅助读者和末层各保留原交付。该读取已在 Post→Pre 候选中计过 |

## 冻结 C8 和普通请求的收益估算

每个方案使用同一批 rank、同一后续会合点和相同专家分布。三行形状保留原图。表内是两种搬运速率口径与归档时钟范围的包络。起点为首 token P90 1,491.85 ms、整批 18,590.77 ms。

| 方案 | 首 token P90 预计缩短 | 整批预计缩短 |
|---|---:|---:|
| 仅合并 X 的写读 | 0.16–1.97 ms | 0.16–1.97 ms |
| 再由共享 Down 直接交付 | 0.33–3.95 ms | 0.33–3.95 ms |
| 单独对 34 个直接入口省一次残差读 | 0.27–3.35 ms | 0.27–3.35 ms |
| 三项联合，重算关键 rank 和请求 | 0.60–7.30 ms（至多约 0.49%） | 0.60–7.30 ms（至多约 0.039%） |
| 已有直接 premix 后，再加入 Down 和合并 X 的增量 | 0.33–3.95 ms | 0.33–3.95 ms |

这些是读写充分暴露的情景估算。每个原任务的节省不超过其记录时长，三项联合不另加此前 Post→Pre→Norm 的估算。按每层下一次 EP16 入口、末层 Post 结束作为会合点，保留逐卡相对时钟范围；假设余下计算可随之提前。两个端点在本次得到同样的绝对数值，因为最慢首 token 已经过全部四波 eager，后续 graph 又全部走原路径。改变调度、缓存命中或融合后核效率会改变结果。[逐请求、时钟范围与原始指纹](baselines/ffn-merge-premix.json)

额外给足独立加法的提交收益，将整项旧 merge 和到 HcPost 的间隔都按免费、并让 Post 少读一次 X，首 token 最有利估算仍只省 6.47 ms。这个估算与“仅合并 X”是同一改写的两种定价。对六个普通请求，按各自首段行数折算，三项联合最高约省整段响应的 0.099%，其中仅合并 X 最高约 0.027%。普通形状采用归档带宽插算，未对这几个形状重测。[普通请求分项](baselines/ffn-merge-premix.json)

## 与既有实测的关系

归档原生小样本中，M3、M211、M1023 的融合核相对原生两算子中位分别快 17.63 µs、快 5.56 µs、慢 11.94 µs。M3 改版的冻结 C8 输出通过既有检查，整批中位比前后参照分别慢 0.31% 和 0.19%。省了一份写读仍可能因核效率或调度损失而变慢。固定当前分布与常见负载，这组从优先候选移出。重新评估的依据是新增可消除且落在请求关键路径上的工作，或有代表性的新形状分布。[归档对照与条件](baselines/ffn-merge-premix.json)

## 路由专家的激活量化能给第二次矩阵乘省多少读取

固定目标模型的 W8A8、专家选择、权重及列块分工。SwiGLU 和逐行量化已合在一起，每条分派产生 2,304 B 的 INT8 激活。后面的 GMM2 计算 5,120 个输出，每块 256 列，共 20 个列块。同一行在每个列块中按 512、512、512、512、256 个元素读入 L1。这是 20 次逻辑整行读取。现有 profile 没有给出对应的 20 次 HBM 缺失，行 scale 在输出端仍有读者。[171 源码指纹及请求估算](baselines/routed-activation-readers.json)

24 个 Cube 核轮转领取任务，列块分成 9、9、2 三组。对于同一行块，每组内列块编号连续，落到不同的核。反转行块次序和轮换起始核都保留这一性质。因此至少有 9 个核要读，同一核最多读 3 次。单个专家本次最多 128 行时，20 个列块全部分给不同核，单核最多读 1 次。即使能将量化结果免费直接交给一个核并一直保留，其他核还需要原来的全局写入。本轮到此即可判定单核方案，无需统计每个专家在每层落到哪张卡。

| 情景（均假设节省全部传到请求） | 冻结 C8 首 token P90 | 冻结 C8 整批 | 六个普通请求中整段最高 |
|---|---:|---:|---:|
| 单独将激活直接交给一个核，最多省 3 次读 | 3.04 ms（0.20%） | 4.25 ms（0.023%） | 0.040% |
| 上一项加上 GMM1 的 FP16 gate/up 写读全省 | 11.13 ms（0.75%） | 15.59 ms（0.084%） | 0.148% |
| 敏感性参照，FP16 写读、INT8 写入和全部 20 次读取都免费 | 29.35 ms（1.97%） | 41.10 ms（0.221%） | 0.390% |

带宽沿用同机归档的连续拷贝参考，单份有效载荷约 1.203 TB/s。分开计算单向读取时用双向总字节速率。沿用原 40 层、八请求的逐层最大接收行数与客户端截止时点。普通请求按自身提示长度、已观测图次数、归档行数及两轮实际服务时间估算。前两种情景在六个普通请求中的首 token 降幅最高分别约 0.096% 和 0.352%。这些数字是给定速率和暴露假设下的估算，不能当作实测速比或硬件绝对上限。[原有计价口径](baselines/routed-expert-handoffs.json) · [各情景逐请求数值](baselines/routed-activation-readers.json)

单核直接交付从深查队列移出。跨核交付仅在长提示首 token 仍留一项条件。即使充分省掉上一处 FP16 写读，按同一速率，每条分派还须净省约 6.74 次 INT8 单向整行传输才能达到 1%。新增分发和同步要扣除。专家换卡、冷热复制或权重重分配不会改变上述融合归因。未观测到可兑现该门槛的免费跨核通路。
