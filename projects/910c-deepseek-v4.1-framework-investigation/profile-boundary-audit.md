# 从 profile 热点定位到可省的算子工作

固定输入、路由、并行配置、专家和权重放置。对每个候选记下哪份数据由谁生成、谁还会读、融合后具体少做什么。先把同一份工作跨层、跨迭代汇总到实际请求，再决定是否需要读实现。一次很小的转换如果能让上游直接交付、多个读者共用或下游提前，按整个受影响区域估价。单靠调整冷热专家、副本或权重分片带来的收益在入口归档。[逐项记录](fusion-attribution.md)

## 两批 profile 的热点复核

| 已有采样 | 形状与阶段签名 | 至少一个本地窗口达到 1% 的签名 | 汇总后达到 1% 的算子类型 | 只看单个签名会漏掉的类型 |
|---|---:|---:|---:|---|
| CP + slot + CPU plan 的 112 个逐卡解码周期 | 405 | 24 | 19 | 局部旋转、SMLA 元数据、Transpose、ReduceScatter |
| 冻结 C8 的 64 个逐卡 eager 目标主体 | 663 | 72 | 15 | 局部旋转、PadV3、RMSNorm、Transpose |

两组有 20 种不同的热点类型。矩阵乘按权重形状找对应投影，共用同一读写的 shape 变体查同一份估值。通信的 N/A 签名只作导航，实际计价要绑定通信组、载荷及消费方。两个队列的分母分别是解码周期和 eager 主体。这里的 1% 仅用于找到需要对照的类型；小算子组成的链和未执行分支继续按数据流登记。[类型、分项签名和融合边界](baselines/profile-boundary-audit.json) · [执行顺序与分支台账](branch-coverage.md)

## MoE 的例子

在解码样本里，DispatchFFNCombine 占单卡本地周期的中位数为 25.10%。保持路由和权重放置后，能单独归因的机会之一是把 GMM1 的输出交给激活和量化，再交给 GMM2。两份中间结果的搬运都暴露时，按已有搬运速率估算，冻结 C8 整批约省 14.17 ms（0.076%）。同波同卡的同一专家在每次 GMM 内已经按来源归组。[固定专家的两处数据交付](baselines/routed-expert-handoffs.json) · [原生归组证据](four-mixed-fusion-edges.md)

目标图每层一次的 BF16 加法与 HcPost 确实有融合边。三行输入的独立原生对照中位省 17.625 µs，但目标 M3 改版的冻结 C8 整批中位耗时比前、后参照分别增加 0.31% 和 0.19%。这条已有更贴近用户请求的对照，停止按目标图调用次数推算新增收益。更大行数及草稿走各自的分支。[已有对照与适用范围](ffn-merge-premix.md)

## Attention 元数据合并的请求预算

这项水平融合把本轮目标的 SMLA 与 QLI tiling 合并为一次多输出提交，直接写各自原有的持久输出，并保留各组的就绪信号。相同生成代与键的跨层复用已经存在。合并不同键时，每个输出仍需使用自己的序列长度、掩码、比例及布局。图内读者和本轮 eager Attention 均按原有事件读取。若晚发布影响任何早读者，需要单独保留其就绪时点。

从同一批八个请求的 16 份归档中，用上波该 rank 的草稿结束和本波目标开始绑定了 **17,892 次**生产。每次都在同一生产流上找到 AICPU kernel、随后的持久缓冲区拷贝及就绪信号，也找到了三个对应的主机 API。根据真实请求数与本卡工作，本轮的有效路径有两种：3 个 SMLA 加 2 个 QLI，或仅 2 个 QLI。冻结图遇到 B1 时仍使用四请求的物理输入形状。草稿自身的元数据单列。

| 观察项 | 冻结 C8 结果 |
|---|---|
| 3,568 个活跃逐卡目标图窗口 | 最后一个就绪信号早于图开始至少 0.540 ms，中位提前 3.559 ms。同组 AICPU 执行时间中位为 0.836 ms |
| 56 个活跃逐卡 eager 目标窗口 | 最后一个就绪信号早于首个目标 HcPre 至少 3.745 ms，中位提前 7.310 ms |
| 保持原提交和其余流时序，仅提前设备端发布 | 在上述图内或 eager Attention 等待读者处，原结果均已就绪，可缩短的直接等待为 0 |
| 直接写原缓冲，假设已绑定的 launch 与拷贝 API 都免费，保留所有就绪信号 | 首 token P90 省 0.461 ms，整批省 26.16 ms（0.141%） |
| 为替代调用保留一次同卡同波中位 launch 成本，每波取最有利卡 | 全部传递到客户端时，首 token 省 0.416 ms，整批省 23.60 ms（0.127%）。只传递一半时，整批省 11.80 ms |

六个普通请求按各自两轮原服务的时长、验证次数估算，B1 借用冻结中的三个 B1 图组及两个 B1 eager 组。即使已有 launch 和拷贝 API 完全免费且全部传到客户端，整段响应最高约省 **0.161%**；保留一次替代 launch 后为 **0.139%**。这些是对已绑定开销的情景估算。Python 侧额外准备及资源竞争没有分项归因。[各请求、分支计数及源数据哈希](baselines/profile-boundary-audit.json)

对这条边停止设备端深查。冻结整批若要达到 1%，除了让已绑定的 26.16 ms 主机工作全部消失，仍要找到约 159.75 ms 能传到客户端的额外节省。只有出现具体且足量的共同准备工作或新的受阻读者，才重新估价。整张模型的未观测场景和跨模块共用仍在原台账中。[分支范围](scope-reconciliation.md)
