# 草稿验证后的状态怎样交给下一轮

本轮在原 171 冻结 profile 中按任务号定位了两处算子交付。第一处把上一轮的 seed 与 draft ID 按本轮请求映射写入 token bank。第二处根据接受计数与旧行映射，生成已计算长度、已接受长度、普通位置和 seq_lens。两处可以分别合并提交。原始 draft ID 的提前校验、有效计数回传、slot 批写及 CPU 所填的混合请求行仍有各自的读者。[机器可读估算、原始记录指纹与适用条件](baselines/draft-state-handoffs.json)

| 冻结 C8 情景 | 首 token P90 预计缩短 | 整批预计缩短 |
|---|---:|---:|
| 两处匹配的设备任务全部免费 | 0.40 ms | 25.03 ms（0.135%） |
| 主线程净省时有一半落在关键路径 | 0.29 ms | 63.30 ms（0.340%） |
| 主线程净省时全部落在关键路径 | 0.59 ms | 126.59 ms（0.681%） |
| 首次草稿输入的已定位复制、长度算术与填充全部免费 | 0.19 ms | 2.64 ms（0.014%） |

冻结调度有 227 波、453 次 TP8 调用，覆盖 16 个 rank。3,608 次状态重映射匹配 17 个设备任务的签名，3,584 次匹配独立的 ID 写入链。每波允许取最有利的 rank，按请求首段和结束时点累计。未匹配的任务留空。已有六输出 copy/expand、26 项 slot 批写、CPU 计划复用和其它 H2D 未计入。[分支与同一份工作的归属](scope-reconciliation.md)

主线程模型另用 48 个有调用栈的 B4 样本。每个样本的 32 个设备任务归到 21 个主线程调用，重叠区间取并集。扣除两次替代提交的估计成本后，样本净省时中位为 535 µs；要让整批快 1%，215 个匹配波次平均须有约 865 µs 实际落在关键路径上。表中两种暴露比例是敏感性估计。两份 profile 没有同次请求的完整主线程关键路径；设备、运行时 launch API 和主线程数字各自估价，彼此可能重叠。

六个普通请求覆盖聊天与代码、单请求与混合到达。按各自实际验证次数，给每次验证套用已见单请求形状中最大的设备成本，整段响应降幅估算为 0.065%–0.157%。这六例达到 1% 所需的主线程净节省随请求变化，约为每次验证 641–1,555 µs。普通请求没有同形状的主线程调用栈计价，本轮不外推 B4 的主线程收益。

## 早期可排除的几笔工作

- 现有草稿输入核已经一次生成六份输出。70 次有配置佐证的 EP0 调用都只有一个 attention group，跨组重复的公共写入在这些调用中为零。其它合法多组配置保留条件。[逐项处置](baselines/fusion-scope.json)
- 另有一段位置 gather 可能完全没有消费者。在能够删除它的条件下，连同上表首次输入的复制、算术与填充都免费，整批共省 6.29 ms。这里的死工作删除单列。三任务 ID 清理链即使全部免费，也只省整批 1.32 ms。
- 裁掉旧滑窗行属于减少需求行的情景。453 次 TP8 调用中只有 5 次有长提示段，其余验证行全部保留。若所有后续读者、回退和缓存生命周期都允许每个请求只保留末尾 128 行，按实际形状及插值估计整批省 7.69 ms；在已经计过直接写 KV 的基线上，增量约 4.69 ms。上述数字均不计入融合收益。改变行域的数值等价和读者退役仍待证实。[设备阶段、保留行和所用基线](baselines/draft-state-handoffs.json)

本轮按组降级这两处状态写入。该结论适用于已覆盖的设备工作和上述主线程模型；如果普通负载中同一批提交呈现更大的已暴露时间，可直接用每请求门槛重算。

## 验证、五步草稿 ID 与下一轮状态的共同预算

把目标验证交付的 seed 和有效计数、五步草稿 ID、下一轮输入和位置映射对到同一个请求后，冻结 C8 的已计价融合降级。把所有列出的设备任务都当作免费，并允许主线程和设备节省串行传递，在下述等待与提交线程假设下，首 token P90 估算省 **0.71 ms（0.047%）**，整批省 **63.86 ms（0.344%）**。这里保留每步 W1、W2、分数修正、ArgMax 和全部 slot 写入。已验收的 slot 批写有自己的基线。[逐请求与逐分支结果](baselines/cross-iteration-ids.json)

| 实际交付 | 同一份工作怎样定价 | 冻结整批按最有利的实际 rank 估算 |
|---|---|---:|
| 本轮验证 → seed 和有效计数 | 将目标选词末尾至侧流计数事件就绪的整段时间免除，保留公开输出、丢弃与备选 token 的语义 | 10.10 ms |
| 草稿当前选词 → 下一个 W1 与最终草稿 ID | 每步可直接输出需要的 ID 类型。每个多请求调用再免 6 次窄 ID 缓冲区写入及 5 次前驱取列。单请求的 40 条逐卡记录各只有 5 次类型转换 | 15.89 ms |
| 上轮 seed、draft 与计数 → 下轮输入 ID、位置和长度 | 只计已绑定的 ID 写入、接受状态重映射、位置和 seq_lens 任务。保持旧行映射、缓冲区容量和有效期 | 25.03 ms |
| 上述三项联合 | 每个接收波次在同一张卡上合算，再重算请求的最后一波 | 49.99 ms |
| 再由生产者分别交付原始 draft ID 与清理过的输入 | 免除已匹配的后段清理任务，再以另一批 72 个调用给原始 ID 读取的五个任务定价。96 个逐卡样本没有相同 B/D 的参照，给它们最大的已有单次值 | 全部设备项合计 60.08 ms |

五步之间仍有真依赖，上一步的获胜 token 决定下一次 W1 查表。直接交付可以少做缩窄/扩宽、取列和回写，外部仍需可读的最终草稿。当前实现返回去掉 seed 列的视图，仍须保留行距、有效行和读者生命周期。原始草稿要在清理之前交给验证器。例如，原始 −1 遇到目标 0 是拒绝，若提前把 −1 覆盖成 0，就可能错误接受。双输出情景因此保留原始值和清理值，不提前覆盖公开缓冲。五步中的宽分数面拷贝已在[词表选词估算](baselines/vocab-selection-fusion.json)定价，这里只计窄 ID。[源码位置、任务形状与预算](baselines/cross-iteration-ids.json)

### 主线程能把多少节省传给请求

171 固定版本先提交输入 ID 和位置重映射，随后在同一工作进程中读取上一轮有效计数以纠正 CPU 长度，再提交原始 slot 映射。对稳定满批的 3,408 条逐卡跨轮记录，分别用该波的主机与设备因果时钟界，保留所有与源码位置和流次序相容的等待。即使先让计数提前整个原选词至事件的时长，其中 **3,402 条**的所有相容等待仍在计数就绪前进入。这时主线程少花的时间会在等待处补回来。另有 3,406 条的状态任务最后一笔 launch 已早于计入加速后的草稿 ID 结束时点，按时钟界计算，中位领先 23.80 ms。[同波等待及 launch 证据](baselines/cross-iteration-ids.json)

| 对早提交的假设 | 主线程额外可传出的整批时间 | 与表内全部设备项联合 |
|---|---:|---:|
| 按当前计数等待约束工作主线程 | 2.25 ms | — |
| 再为独立提交线程保留余量，有充分的 CANN 空档才吸收提前量 | 3.84 ms | 63.86 ms（0.344%） |
| 假设 48 个旧样本中的主线程净节省都能完全传递 | 126.00 ms | 184.44 ms（0.992%） |

profile 没有导出事件句柄和提交队列深度。第二行的 CANN 空档能吸收前移工作的条件仍需成立，第三行给出了放开这个条件的敏感性。八个请求分别截止于自身产生输出的波次；即使再把最后一个波次产生但缺少后继消费者的 seed 和 ID 也算进去，第二行的整批估算只是从 63.86 变到 63.91 ms。

还有 14 个含请求换入、换出或非满批状态重映射的波次没有可直接套用的主线程净时间。按第二行模型，仅靠这些波次把整批收益推到 1%，还需每波再净省约 **8.72 ms** 并传到最慢请求；按第三行的完全传递假设，则只差 **0.105 ms/波**。这个分支保留条件，不能把缺少的主机时间填成零后宣称硬件上限。[八请求所需差额](baselines/cross-iteration-ids.json)

### 普通单请求

冻结记录中各有一个 B1 提示转验证、一个 B1 验证转验证的 TP8 组。第一步取前一组八个 rank 的最大值，其余验证用后一组最大值，再加上双输出情景。按六个普通对话与代码请求的实际验证次数，设备项估算省整段 **0.10%–0.25%**。例如代码单请求只有 3 次验证，约省 0.48 ms；后续对话有 47 次，约省 7.48 ms。后者达到整段 1% 还需每步另有 **0.48–0.54 ms** 暴露的主机收益。B1 验证转验证的八条记录没有匹配到这次定价所需的计数等待，两个 TP8 组不足以估计普通流量分布，所以没有套用满批的等待比例。[六请求、样本数与两个原服务参照](baselines/cross-iteration-ids.json)
