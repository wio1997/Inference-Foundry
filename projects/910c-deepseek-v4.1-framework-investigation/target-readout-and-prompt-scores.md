# 末层读出、词表投影与分数读者

**冻结 C8 的 greedy 生成可以结束这一组配对。** 保留目标词表投影及其计算，把末层 HcPost 到投影开始、投影结束到 greedy 选词或验证完成两段时间全部免除，首 token P90 估算能省 14.933 ms。要达到 1% 须省 14.919 ms，相差约 14 µs。整批即使享有这份全部提前量也只省 0.83%。请求未开启提示词评分，这个可选分支的收益另算。

## 已有 profile 可以一次筛掉的组合

| 同一请求上免除的范围 | 冻结 C8 首 token P90 | 冻结 C8 整批 |
|---|---:|---:|
| 从末层 HcPost 开始直到词表投影开始 | 14.106 ms | 78.687 ms |
| 从词表投影结束直到 greedy 结果就绪 | 0.826 ms | 75.635 ms |
| 联合免除两段的所有工作、通信和间隔 | 14.933 ms（1.001%） | 154.322 ms（0.830%） |
| 仅免除已具名的末层加权归约与 RMS、head 输入检查及选行、宽分数拷贝与转置 | 8.166 ms（0.547%） | 60.402 ms（0.325%） |

4 个有请求的 eager 波次和 223 个图波次，合计 453 次 TP8 调用、3,624 条逐卡记录。每一波分别取投影前后对方案最有利的卡，假定节省全部串行传递。每个请求只累计到实际产生其首 token 或最后一次验证的波次，再重算八请求的最大值。第 4 号请求经过前四波，每波平均仅能留下 3.50 µs 的额外暴露时间，才能让首 token 跨过 1%。这说明联合方案也很难靠这些已有交付达到参考线。表中第四行仍把必须完成的归约当作免费，实际可节省的部分还要扣除替代工作。目标矩阵乘本身、草稿生成和之后的 CPU 发布均在表外。[逐请求预算与源码指纹](baselines/target-readout-and-prompt-scores.json)

## 启用提示词评分后，哪些算子可以融合

启用有限的 `prompt_logprobs` 时，每个有需求的请求单独把该段隐藏状态送入词表头。第 i 行给提示中的第 i+1 个 token 打分。一段从头完整评分的 N 个 token 共需 N−1 行，分块时按工作进程的实际起始位置、剩余行数计。冻结 C8 和六个普通对话、代码请求的原始请求体均未启用此功能。下面是沿用普通输入长度的开启情景。

| 请求条件 | 必须保留的结果 | 可以合并的工作 |
|---|---|---|
| 未请求，当前请求未调度，只有 prompt embedding 或本段剩余零行 | 原有分支的输出与状态 | 跳过本项。沿用缓存时按本次实际评分行数估算 |
| K=0 | 指定 token 的分数与含并列的排名 | 归一化和排名可以直连，仍须看完整词表才能计数 |
| 0<K<V，返回有限个分数 | 指定 token、排名及原 Top-K 的 ID、分数与顺序 | 全词表归一化、Top-K、指定 token 读取和排名可共用一次分数扫描。指定 ID 进入 Top-K 时仍保留两处结果 |
| 原始或处理后 logits 分值模式 | 规定的 FP32 logits、排名和 Top-K | 提示评分跳过生成侧处理器，直接按原 logits 比较，省去归一化阶段。171 归档配置使用 raw_logprobs |
| 全词表，或仍有外部稠密分数读者 | 完整分数和所需顺序 | 保留稠密交付。－1 在工作进程中表示 V，具体请求仍须满足服务入口限制 |

**先保留现有 TP8 通信。** 让一个读者直接消费归集后的 BF16 词表。对归一化分数，第一遍求原有归一化参数，第二遍计算 FP32 分数并同时做 Top-K 和排名。这样可省完整 FP32 分数面的写入与后续重读。估算已扣第二遍 BF16 读取，只有能直接消费 TP-major 布局时才加上省去转置的收益。必须保留原生舍入、Top-K 并列选择及异常行行为。已有反例中，约 1e−8 和 0 经 FP32 log-softmax 后同为 −0.69314718，第一列的含并列排名由 1 变为 2。[反例、分支和计价口径](baselines/target-readout-and-prompt-scores.json)

**可选的跨卡融合。** 各词表分片在原卡保留权重和完整点积，只交换归一化与选词所需的摘要。归一化模式按三次通信估价，分别交付行最大值与指定 token 的值、移位指数和、最后的局部 Top-K 与含并列计数。原始 logits 模式只需交付指定值，随后合并局部 Top-K 与计数。Top-K 及排名须在与原版一致的 FP32 分数上完成，最终 CPU 写回和同步保留。启用前须证明分片归约复现原分数，并且能复现原并列选择；不满足数值合同的分支仍走原路径。下表假设所计行都能进入融合分支。

| 冷提示长度、有限 K=5 | 保持稠密通信，只做本地融合 | 再用分片摘要，两个改动合计 |
|---|---:|---:|
| 1,018–1,019，对话 | 0.55–1.53 ms | 1.61–3.33 ms |
| 1,464，代码 | 0.79–2.20 ms | 2.42–4.82 ms |
| 2,187，混合批中的代码 | 1.17–3.29 ms | 3.74–7.23 ms |

保持普通记录里每请求一次有效 prefill 的形态，按现有带宽、通信启动成本和充分暴露估算。六个原请求没有提示评分，**开启后的端到端分母未知**。以 1,464 个 token 为例，若开启评分后的原服务首 token 为 300 ms，需要实际省 3.00 ms 才有 1%；若为 600 ms，需要 6.00 ms，已超过表内情景。上述毫秒数没有除以关闭评分时的首 token 来宣称实际百分比。[六请求及 K=0/K=5 分项](baselines/target-readout-and-prompt-scores.json)

块大小可能改变取舍。每块单独付三次通信启动成本，按当前两套通信校准，跨卡部分抵消自身开销需要平均每块约 44–192 个有效评分行。将 1,464 个 token 映射到每块 128 行、按默认启动成本，跨卡部分相对已融合的本地读者约慢 1.02–1.07 ms；每块 256 行、按调优启动成本，则约省 2.18–2.21 ms。单次大块的稠密通信有效速率借自同机 34–67 MB 的 BF16 TP8 归集，外推到 263–565 MB；小摘要使用同机 FP32 启动成本并另计有效载荷。收益还取决于实际分块、缓存、归约、Top-K 合并和通信的可见时长。把这项保留给确有提示评分需求的负载。[分块与通信敏感性](baselines/target-readout-and-prompt-scores.json)
