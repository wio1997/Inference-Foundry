# M06 Router、路由/共享专家、EP 收发

执行位置：FFN主体。当前记录状态：`SCOPED_PRIORITY_DISPOSITIONS_RECORDED_OPEN_F21_FRONTIERS`。完整模块优化穷尽：**未证实**。

## 实际分支与排查范围

动态 router/固定表/图像行；路由和共享专家；W8A8/其它合法量化；EP；mask、LoRA、EPLB 和权重更新。

## 已有价值判断

4480 次当前目标调用无固定路由表；selected-dot 不适用。共享四任务约 3.98% 周期，值得一次固定对照。显式 fork 的两种合成路由输出全等，但仅省 4.076/5.924 μs，低于 13.893 μs 门槛。

## 必须保留的语义与读者

保留两支输出、专家计数、BF16/INT32/FP32 边界、每层激活和量化尺度。跨调用复用必须同层、同专家、同权重版本和合法状态。

## 融合之外的完整改写空间

动态路由 producer/packet；共享/路由重排；F21 内部计算通信拆分；部分结果交付；合并到 HC Post；跨层/迭代资源与权重驻留。

## 尚缺的关键证据和继续条件

F21 task 包含等待。新 trace 中区间相交伴随共享投影变长，不能按重叠长度计收益。分阶段可用资源/peer readiness 与更广设计仍未定案。

目标第1–39层 F21 合计占本地周期的中位数为22.61%。历史同角色计数中，76.70%的接收专家槽为空，当前核对到的源码仍按专家同步并发布就绪信号。保留两个分段边界后，空专家信号变体已完成16rank原生对照。输出一致，两种稀疏路由均未过净省14.25微秒的门槛，暂缓该实现。小 M 正行输入的原生反事实已完成。5 组路由的输入预置中位仅省 1.54–6.92 µs/次，暂缓单独实现。大 M 的不同量化分支保留。[接收方预置对照](../baselines/f21-peer-input-value.json) [原生对照](../baselines/f21-sparse-publication.json) [F21 证据](../baselines/f21-readiness.json)

已绑定首 token 的 2,560 次 F21 原生调用及真实专家计数。M816–818 的 11000 分支每卡只有 20 次额外的整行量化，40 个核心的最大行数已为均衡下限 21。M816/M817 的 400 次零发送调用均需为其他卡执行专家计算。保留跨卡返回与同步。[各组到达及收发证据](../baselines/prefill-f21-attention.json)

同一轮 C8 的两个引擎各完成 4 个请求，排队时间合计分别为 0.159 和 0.155 ms。若请求 0、6 在前一步决策时都已入队，原来两次调度决策必须相距至多 79.45 µs。启动参数启用了异步调度，worker 入口不能代替这个时点。后续一次冻结 C8 已补齐请求交付时间线。[请求时点与负载](../baselines/prefill-admission.json)

新 C8 的 8 个请求输出均与归档一致。6 个较晚首次调度的请求在本 DP 前一次非空决策时都未完成分词。第 8 个输入在 CPU 对照上的就绪中位时间为 612.09 ms（默认）、169.68 ms（四线程）、73.70 ms（复用种子前缀）及 21.36 ms（两者合用）。四线程配置的冻结对照结果见本轮记录。[调用时点与四组对照](../baselines/prefill-request-delivery.json)

在固定 DP 和请求内 token 依赖下，将两个独立的首 token 请求提前到相邻步骤，可形成一个待证的跨 DP 组合。若 CP 行分配保持当前几何，两步每层合计 padding 可从 13,048 行降至 40 行。在路由成员不变时，40 层可少出现 5,030–9,350 次有任务的专家实例。两种排法每层仍须处理 78,480 项专家分配；两步 EP 收发、临界耗时与输出正确性仍需核对。[配对条件](../baselines/prefill-selected-kv.json)

线程池实际宽度依次为 1 / 4 / 1。三组各有一次准入和三次计时，12 轮共 96 份输出文本逐个与归档一致。按前参照 / 四线程 / 后参照顺序，慢请求的首 token 延迟中位为 1.2496 / 0.9855 / 1.2177 秒，四线程分别缩短 21.130% / 19.064%，通过冻结门槛。整轮耗时中位为 15.6522 / 15.5043 / 15.8759 秒，分别缩短 0.945% / 2.340%，对前参照未达到 1%。 [冻结 C8](../baselines/renderer-c8.json)

64 个历史首 token 区间共 135,592 条 native 记录。由 22,248 次矩阵与专家调用核算直接算法工作量。在 1.8 GHz 参考条件下，M416、816、817、818 的部分计算时间下限为 10.49、20.57、20.59、25.47 ms。各层本地活跃专家权重按未压缩直读、每卡起始最多驻留 192 MiB 估算。若要在各自的部分计算下限时间内搬完这些权重，需达到 2.17、1.11、1.09、0.94 TB/s。实际可达带宽、驻留与物理时钟上界仍待约束。 [条件下限](../baselines/eager-resources-and-copies.json)

四个 prefill 批次的 2,560 个层/rank 入口都已绑定。在 M416 的 DP1，320 个 Attention 前半层走填零与 ReduceScatter 路径。用前后两个目标图的 80 组短 F21 通信和 160 组 eager F21 约束各卡相对时钟偏差，并假设该时段偏差稳定。四批共 160 层有 159 层由行数较多的卡组最后进入 MoE。M818 的另一层由 419 行一侧最后进入。单靠每段 eager 内的调用约束只能确定 36 层，事件记录的缺失或时间重叠均不能证明独立。第 0 层真实权重、合成 BF16 输入、两组 TP8 同时执行。只前移 OA 时，按 Q816、817、419、818 排列，无显式预触的单层配对中位节省分别为 278.00、386.26、285.92、312.30 µs；预触 224 MiB 后分别为 162.90、329.42、129.94、159.64 µs。四组都通过逐位验收与既定门槛。把实测变化按各层最后进入 MoE 的卡组计入，历史最慢请求的条件预算为 35.36–45.63 ms，占首 token 的 2.37%–3.06%。该预算假定每层都取得第 0 层的局部改善并传播到后续环节。真实模型的输入、常驻显存、命中和回退另见本轮服务记录。 [双组原生样本和跨卡计价](../baselines/projection-joint-arrival.json)

用同一批 profile 对一整类方案做了筛查。假定对端进入 MoE 的时刻固定，只让本层行数较少的一组提前，160 个层入口中有 159 个的最晚到达时刻保持原值。仅 M818 第 0 层有空间，即使把该侧全部前置耗时清零，最晚到达最多提前 5.944 ms，约占历史最慢请求首 token 的 0.398%。加速较晚的一组、提早发布专家输入、减少共享资源争用或移除同步，均需按各自的机制核算。 [逐层筛查](../baselines/oa-service.json)

171 的两个 TP8 组、每组 40 层已装入真实 OA 权重，每逻辑设备新增权重 2.5 GiB。两轮冻结 C8 实际送入 OB 的 16,179,527,680 个 BF16 字逐位一致。第三轮的行数改变，按每组每层计的 200 次大行数调用全部回退，三轮共 24 个完整输出及负载计数均与归档一致。候选执行 0 次，按预设规则跳过 9 轮计时，真实服务提速仍未知。合并前两轮两个 DP 的行数也只能命中 0 次。即使加入两份历史尺寸资料，按 DP 也仅能匹配 80/200 次，历史尺寸只用于准备。三个服务启动尝试均已恢复原启动脚本并通过 HTTP 200 和 2 token 生成检查。第一次自动分配的总量与历史记录相差 16 块。第二次把前端合计用于单引擎，导致 KV 分配显存不足。第三次在同一服务进程对所有组别固定 DP0 的 17,302 块和 DP1 的 17,303 块，block size 为 128。历史数据只保存总量 34,605。离线把新 OA 的行数向上对齐到 32、64 或 128，三种情形都覆盖留出轮次中的 3/5 组尺寸，但额外逻辑行数分别为 3.26%、5.21% 和 13.00%。先查原算子舍入和 kernel 选择能否覆盖 16/32 行分组，再决定是否值得原生计时。 [服务验证和容量](../baselines/oa-service.json)

4 个首 token 批次共 2,560 条 Attention Post 至 MoE 入口的逐卡路径。轻载卡组走 1,280 条填充路径，重载卡组的 1,280 条对应路径直接路由。按固定对端与原调度计价，对历史最慢请求，消除全部路由 PadV3 和 MemSet 的条件上限是 0.211 ms，独立 RMSNormCast 是 5.389 ms。Attention HcPost、FFN HcPre 与 RMSNormCast 三者的联合上限为 48.480 ms。达到该请求首 token 的 1% 需要兑现这个乐观预算的 30.8%。若联合变换只少读一次 BF16 残差，全部暴露时所需的盈亏平衡速率为 313.8 GB/s。按同字节 TensorMove 的实测中位耗时估算，四段累计仅 3.933 ms。实际 HcPre 的读取、缓存与计算重叠仍需独立判断，后续 FFNPost 还需要这份残差。 [逐分支与逐请求预算](../baselines/ffn-entry.json)
