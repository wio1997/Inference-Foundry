# M04 SP 输出交付与 mHC Attention 后置

执行位置：Attention输出到 FFN 前置之间。当前记录状态：`SCOPED_PRIORITY_SCREENED_CONDITIONAL_FRONTIERS_RETAINED`。完整模块优化穷尽：**未证实**。

OA 和 OB 是同一分片上的两次输出投影。2,240 个非空逐卡层中有 1,600 次 OB 输出拷贝；另有 320 个空侧直接填零后归约。24 行图上 2,560 条链的 OA→OB 间隙中位为 0.02 µs。保留两次矩阵乘、BF16 中间舍入和 ReduceScatter，按同机连续搬运速率折算，省中间写读及间隙只值约 0.99 ms 首 token P90；若能直接写通信输入，则为 5.70–6.51 ms（0.38%–0.44%），整批 6.13–6.95 ms，六个普通请求响应最高约 0.13%。单独搬运融合降级。 分块流水只有在已舍入的 OA 结果可按块交给 OB、维持各自归约顺序，并且硬件有未占用资源时才可能另有收益。按相同搬运估价，若能隐藏两次投影剩余时间中较短者的 25%，冻结首 token P90 估算省 13.88–14.63 ms；隐藏 50% 时省 21.56–22.61 ms（1.45%–1.52%），整批省 0.48%，六个普通请求响应最高 0.65%。这只是敏感性估算。按另一个更有利的独立拷贝代理且完全重叠，整批才约省 194–197 ms。是否能做到这些重叠仍缺证据。 [固定分片投影与请求](../baselines/oa-ob-fusion.json)

归档中有 2,560 处 AttentionPost→FFNPre 以及 2,176 处直接相邻的 FFNPost→下一层 AttentionPre。两处均可考虑由 Post 同时交付原 BF16 残差、供 Cube 使用的扩宽值和按外部系数归约的 Y，并保留 Y 的 BF16 舍入及后续归一化读者。每次完整目标模型前向按 40 处 FFN 和 34 处 Attention 计价。若仅省一次残差读取及 Y 的写读，C8 首 token P90 估算省 5.47–10.94 ms。若两次残差读取均省、扩宽写入等成本，估算省 9.12–18.23 ms。按有利搬运速率给扩宽写增加 25% 成本后只省 14.59 ms，已低于 14.92 ms 门槛。六个普通请求在等成本的有利估算下，首 token 最高 0.635%，响应完成最高 0.260%。 [同一批请求的两处 mHC 交付](../baselines/hc-paired-boundaries.json)

4 批共 2,240 条真实 Attention 发送链。保留逆旋转、按旧转置时间的 25% 计入直接布局写入，首 token P90 估算省 5.62–9.55 ms，整批省 91.61–95.54 ms。六个普通请求各省 1.66–26.68 ms。只给 400 条空发送预置零缓冲区，原 EP16 到达模型给首 token P90 的收益为零。 [发送端与请求](../baselines/attention-send.json)

Attention Post 额外交付扩宽的 FP32 残差时，每行少读一份 BF16，Cube 仍需读 FP32。历史 eager 首 token P90 在两种同速计价下省 0.36–3.93 ms。只存 FP32 则另有两个读者需要读取宽残差，净省字节为零。只读核对固定 checkpoint 中 40 个 Attention 和 40 个 FFN 投影矩阵，每个矩阵都有单 BF16 权重无法保留原投影操作数精度的系数。 [残差布局与系数](../baselines/hc-workspace-delivery.json)

2,560 条归档逐卡链上，若片上同时接住 HcPre 对四路残差的两次读取以及 Y 的写读，按同尺寸 TensorMove 的两种字节计价，C8 首 token P90 约省 4.92–9.83 ms。即使路由直接接住宽输出，也约为 6.88–13.76 ms。内部 FP32 工作区写读每行另有 163,840 B，若也能消除，联合情景为 12.78–25.56 ms。171 安装的 CANN 9.2 标准 UB→L1 接口仍经 GM。上述工作区全省的假设不适用于该路径。 [按读写与请求估算](../baselines/hc-tensor-traffic.json)

## 实际分支与排查范围

Attention 输出 ReduceScatter、HcPost、后续 FFN 输入与延迟残差。

## 已有价值判断

当前 4480 个边界；Post 加两侧间隔按零成本处理的占比最高 0.746%。不为孤立后置融合开新探针。

## 必须保留的语义与读者

Post 的舍入输出同时是 FFN Pre 输入和稍后 FFN Post 的残差；前向驻留不能删除延迟读者。通信不重复归入新收益。

## 融合之外的完整改写空间

Post/Pre 共驻留；producer 到残差双输出；通信 tile 与消费者联合。

## 尚缺的关键证据和继续条件

是否有大于单边界的数据复用/调度改变。旧记录编号错误已修复，全部原数值保持不变。

在 2,240 条同层 OA → OB → ReduceScatter → HcPost 链中，1,600 条包含 OB 输出拷贝。把接口间隙和后续拷贝全部消掉，对八个历史请求的乐观预算分别仅占各自 TTFT 的 0.232%–0.389%，暂缓该单项。先前的 1.003%–1.809% 包含两次矩阵实现内部的全部可变时间。固定分片的独立搬运融合已降级，矩阵工作仅按可重叠部分另行计价。直接预乘权重使每行 MAC 从 9,437,184 增至 20,971,520，且中间 BF16 舍入可产生不同结果。M416 的 DP1 有 320 个逐卡层走填零与归约路径，投影融合在该侧收益计零。 [按请求及实际签名计价](../baselines/eager-resources-and-copies.json)

在 2,240 条逐卡链中同时绑定了 280 组八卡 AllToAll、输出投影、ReduceScatter 和 HcPost。按 BF16 和环形 ReduceScatter 的逻辑字节，若在行所属的卡上完成 OA 与八个 OB 部分结果的归约，可省 129,024 B/本地填充行。首次取得七个对端权重分片需 126 MiB/卡/层，累计 1,024 行时收支相抵。当前每次只有 3–818 行，逐次收集两段权重会增加传输。若只获取一次并跨历史批次保留，DP0 / DP1 可覆盖 1,655 / 1,637 行，仍须支付 HBM 读取、计算和本地归约。前者覆盖四个载体，后者覆盖三个，M416 的 DP1 未绑定。原服务恢复后的显存快照，各逻辑芯片报告剩余 5,101–5,518 MB。若原分片保留且完整权重另开缓冲，40 层每卡需额外 5,760 MiB。共享或回收本地分片时，理论额外载荷为 5,040 MiB，还需核算临时工作区和分配器。保留部分层常驻，以及只复制 OB 的方案。 [逐组通信和容量](../baselines/projection-owners.json)

单次八卡实验复用同一批输入和第 0 层真实权重，同时比较只前移 OA、只前移 OB 和两段都前移。416、818 行只前移 OA 都逐位一致。按每轮最慢 rank 配对，无显式缓冲预触时每层中位省 164.92、222.28 µs，预触 224 MiB 后为 232.82、161.72 µs。416 行只前移 OB 或两段都前移均变慢；818 行的 OB 有 15,019 个部分结果改变，合并输出有 1,236 处不同。3 行原生 AIV 归约在相同诊断输入上重复运行会出现位差，不能用大尺寸归约的舍入次序推断。历史最慢请求在 DP1，首 token 为 1,491.85 ms。在同 DP 已观测且通过原生验证的行数上，把第 0 层配对中位应用到 40 层并假定全额暴露，可省 6.47–8.89 ms，占 0.43%–0.60%。这是一种情景估算。实际服务各层、跨 DP 等待和其它尺寸的收益仍待核对。先合并估价，再决定是否接入服务。 [逐项证据](../baselines/projection-owner-native.json)

四个 prefill 批次的 2,560 个层/rank 入口都已绑定。在 M416 的 DP1，320 个 Attention 前半层走填零与 ReduceScatter 路径。用前后两个目标图的 80 组短 F21 通信和 160 组 eager F21 约束各卡相对时钟偏差，并假设该时段偏差稳定。四批共 160 层有 159 层由行数较多的卡组最后进入 MoE。M818 的另一层由 419 行一侧最后进入。单靠每段 eager 内的调用约束只能确定 36 层，事件记录的缺失或时间重叠均不能证明独立。第 0 层真实权重、合成 BF16 输入、两组 TP8 同时执行。只前移 OA 时，按 Q816、817、419、818 排列，无显式预触的单层配对中位节省分别为 278.00、386.26、285.92、312.30 µs；预触 224 MiB 后分别为 162.90、329.42、129.94、159.64 µs。四组都通过逐位验收与既定门槛。把实测变化按各层最后进入 MoE 的卡组计入，历史最慢请求的条件预算为 35.36–45.63 ms，占首 token 的 2.37%–3.06%。该预算假定每层都取得第 0 层的局部改善并传播到后续环节。真实模型的输入、常驻显存、命中和回退另见本轮服务记录。 [双组原生样本和跨卡计价](../baselines/projection-joint-arrival.json)

用同一批 profile 对一整类方案做了筛查。假定对端进入 MoE 的时刻固定，只让本层行数较少的一组提前，160 个层入口中有 159 个的最晚到达时刻保持原值。仅 M818 第 0 层有空间，即使把该侧全部前置耗时清零，最晚到达最多提前 5.944 ms，约占历史最慢请求首 token 的 0.398%。加速较晚的一组、提早发布专家输入、减少共享资源争用或移除同步，均需按各自的机制核算。 [逐层筛查](../baselines/oa-service.json)

171 的两个 TP8 组、每组 40 层已装入真实 OA 权重，每逻辑设备新增权重 2.5 GiB。两轮冻结 C8 实际送入 OB 的 16,179,527,680 个 BF16 字逐位一致。第三轮的行数改变，按每组每层计的 200 次大行数调用全部回退，三轮共 24 个完整输出及负载计数均与归档一致。候选执行 0 次，按预设规则跳过 9 轮计时，真实服务提速仍未知。合并前两轮两个 DP 的行数也只能命中 0 次。即使加入两份历史尺寸资料，按 DP 也仅能匹配 80/200 次，历史尺寸只用于准备。三个服务启动尝试均已恢复原启动脚本并通过 HTTP 200 和 2 token 生成检查。第一次自动分配的总量与历史记录相差 16 块。第二次把前端合计用于单引擎，导致 KV 分配显存不足。第三次在同一服务进程对所有组别固定 DP0 的 17,302 块和 DP1 的 17,303 块，block size 为 128。历史数据只保存总量 34,605。离线把新 OA 的行数向上对齐到 32、64 或 128，三种情形都覆盖留出轮次中的 3/5 组尺寸，但额外逻辑行数分别为 3.26%、5.21% 和 13.00%。先查原算子舍入和 kernel 选择能否覆盖 16/32 行分组，再决定是否值得原生计时。 [服务验证和容量](../baselines/oa-service.json)
