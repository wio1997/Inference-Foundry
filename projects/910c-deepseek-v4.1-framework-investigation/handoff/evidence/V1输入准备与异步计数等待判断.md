# V1 输入准备与异步计数等待

## 介绍

从 V1 worker 的 `_prepare_inputs` 走到 target attention、Engram 和 DSpark 的实际输入。冻结路径为 910C、CANN 9.2.0、V1、TP8 DP2 EP16 PP1、DCP1、DSACP、K5 异步调度。旧归档用于判断这一轮的 host staging、设备索引和跨轮等待各有多大改写空间。

## 到了哪里

1. **当前请求行。** Worker 更新请求状态、compact 与 reorder 后生成 `current → previous` 映射。先提交 block table，再根据 scheduled counts 生成当前 request-index、行内 query offset 和实际 QSL。上一轮不存在的请求用 -1。prefill/no-cache、单 token、带草稿的 verify、chunked prefill 分别保留。带草稿时 `_build_attn_state` 的返回值和写给 backend 的 `self.attn_state` 可以不同，DSpark 的 SpecDecoding 会在后者标成 ChunkedPrefill。
2. **输入 ID。** 当前 CPU token 表先按乐观位置 gather。继承的 `_prepare_input_ids` 在无前轮时上传整个前缀，混合新行时先上传再补已有请求。全覆盖时无需上传 CPU IDs。普通无草稿且行稳定可用连续 copy，带草稿则先 scatter 上一轮 sampled IDs，再按 previous stride scatter 草稿，原 int32 转换和 PAD 含义保留。176 轮都看到 CPU `index_select`、首次设备 index 前一个顶层 copy 和两次 scatter，符合 QSL copy 加全 GPU carry 的源码顺序。归档没有输入值或直接分支标签，混合 prefill、新入/恢复、CPU fallback 与 prompt embeds 保留原分支。
3. **设备长度和位置。** 上一轮的有效 sampled count 是一张上一代 GPU 表，另走 side stream D2H。设备纠偏在前轮有草稿的请求上读旧 computed row，加 valid count。新请求、无草稿、重算 rewind 用本轮 CPU fallback。读旧 bank 的 gather 在写本轮前完成。若用同一 bank 边读边写，重排 `[1,0]` 能把预期 `[203,102]` 改成 `[203,205]`。设备 position 是纠偏后 computed 加 query offset，seq lens 是纠偏后 computed 加当前 scheduled count。它们交给 raw slot mapping、SMLA/QLI 等实际读者。DCP1 走通常设备 position 分支。另读了 DCP manager 的不重建、纯设备重建和 CPU 重 gather/H2D 分支，DCP>1 未套用本轮价格。
4. **CPU 镜像和两次等待。** `_prepare_inputs` 先按乐观长度决定 discard 行，随后才修正 `optimistic_seq_lens_cpu`。实际拒绝数为 `prev_drafts + 1 - valid_count`。较早的 `num_accepted_tokens_event` 用于按当前请求重排 accepted buffer，合法 hybrid 路径仍需它。较晚的 `valid_sampled_token_count_event` 保护 CPU 镜像。随后 `use_compress` 的 deferred callback 还会读取同代 count，更新请求和 batch 的 CPU computed，形成第二套 DSA CPU positions。当前 V4.1 builder 用 device positions，DSpark padded 分支只转交 `positions_cpu`，nonpadded helper 确实会索引它。可核查是否在冻结路径按需生成，仍须保留 callback 自身和其他 backend/capture 读者。后一段重复生成 request-index 时可共享本轮行映射，乐观位置和修正位置各自保存。
5. **最后读者。** 初次实际 QSL 在 FIA padding 前已被 slot mapping 与 logits 使用。FIA 扩展请求行后，Engram 只取 actual QSL 前缀及源层物理 table/slot，prompt lookback 在 deferred 修正后从 CPU prompt 表取，生成历史回落到设备 slot cache。Target attention 另读 CP 局部 QSL/设备 lengths 与修正 CPU 镜像；DSpark 从 unpadded common、实际选行和每组物理 view 建下一份非因果交付。Target logits/draft IDs 的 gather 在 sanitize/clamp 前读取原输入，模型/embedding 用之后的 GPU IDs。GPU buffer lease、pinned source event 和 metadata producer/consumer 退役继续分别保存。

## 两个可检验的改写

- **跨轮等待与本轮准备交错。** 第二次 count wait 前，设备 computed、positions、seq lengths 和当前实际 QSL 均已排队。后续 slot mapping、spec 索引的 H2D 与 draft ID gather 不读 CPU 长度镜像。可先提交这些工作，在 CPU 镜像首读前等待同一代 count，再修正镜像和完成原 deferred callback。现有 graph/DP 选择读的是 `input_batch.num_computed_tokens_cpu` 的原阶段值，移动镜像计算时保持该输入与 callback 原顺序。 正常 `_build_attention_metadata` 首个直接镜像读点是第 3534 行的 max length，capture 的早分支使用配置上限，后面仍绑定镜像视图。两次同代 CPU count 读取可考虑共用已就绪快照。DMA 源不能提前覆写，异常、空批、capture 与 collective 顺序仍需核实。
- **共享整数行计划。** 对每个请求，当前 QSL 累计末端为 `E`，草稿宽为 `d`。原 logits 选 `E-d-1+j`，其后 `target_logits_indices+1` 对应的 draft ID 直接来自 `E-d+j`，其中 `0 ≤ j < d`。样本累计末端减去经过的请求数即 draft 累计末端。对 111,150 个合法小 batch 做整数对照。单独改 gather 仍要支付新索引的生成和交付，保留五个 metadata 输出的 dtype、偏移、地址、事件与 pre-sanitize 哨兵。较大方案可把行计划与 sampled/draft scatter、位置/slot staging 一并考虑。

## 结果

配平 C8 32K/1K 旧诊断，16 卡、176 轮，平均每卡 11 轮，窗口 1025.502734 ms。该窗口 `_prepare_inputs` 应用墙钟 75.554844 ms/卡，有时钟余量的设备 Free 重合 2.810875 ms/卡。每轮先后看到两个 event wrapper，第二个都包含 slot 提交前的 `aclrtSynchronizeEvent`，与 source 中 valid-count D2H 等待位置对应。ACL 合计 39.370562 ms/卡，单次中位 3.044875 ms，两段同步 wrapper 的 Free 重合共 1.904969 ms/卡。墙钟中包含正在运行的前轮工作。

| 状态 | 范围 | 定价与决定 |
| --- | --- | --- |
| 待确认 | 延后 CPU 长度镜像等待，并先提交独立设备准备 | 每轮按原 ACL wait 与 slot/spec 应用墙钟较小值给出 9.052891 ms/卡（0.883%）的乐观重叠。放宽到 slot 起点至 prepare 返回为 11.361703 ms/卡。只在兑现 50%、新增 0.1 ms/轮时，局部净约 3.426 ms/卡。再假设对配平轻量参照转移 50%，229/231 轮的条件请求代理为 24.322 ms/批（0.152%）。实际时序、首读前剩余等待与代次成本决定去留。 |
| 已停止 | 单独剪 CPU ID gather 或替换第二次 draft gather | CPU gather 0.059484 ms/卡。第二 gather host 0.199000 ms/卡，176 个 IndexCheck 和 176 个 IndexAiCore 合计设备 0.177406 ms/卡。放宽把三项直加也只占窗 0.0425%，整段行计划仍待确认。 |
| 已停止 | 取消计数就绪条件、同 bank 无快照重排、直接删首实际 QSL 发布 | 分别破坏 D2H 就绪、跨行 snapshot 和 padding 前读者。 |
| 已确认可实现 | 新替换原语 | 本段无新增逐位准入。 |

较大共同 frame、target gid12、Engram owner/input 与 DSpark context 候选继续各自分账。原 C8 和六普通的实际请求净收益未归因。接着从 target 的 _build_attention_metadata 走完组装、首个 packet owner、空 query 和 FULL 图实际读者，定位 CPU 计数最早读点，保留目标与草稿各自的地址和退役合同。
