# 启动预热与容量交付判断

## 介绍

从 worker 的完整启动交付开始，追模型加载期间的早预热、四个 Triton helper、MM encoder profile、workspace 分配、图捕获及退役。先判断能否少算、少搬、重叠等待，以及常驻容量能否支持更大的热路径融合。固定目标仍是 C8 32768/1024/90%prefix 和六个 ordinary 的暖服务；每个替换原语逐位一致。

## 到了哪里

32 个运行树文件的身份与本地原件一致；实际审阅范围单列在 `startup-delivery-source-review.json`，未读的 native/helper 内部不因 hash、入口或文件数被记为完成。本轮只读原容器源码、配置、已完成诊断的日志和 safetensors 头部，模型/NPU/请求/新 profile/远端写入/服务变更均为 0。

实际调用顺序是加载与可选早预热 → profile_run → worker.compile_or_warm_up_model 的 kernel_warmup → graph capture → 锁定 workspace → 请求。early_kernel 和 early_NZ 在冻结配置默认 False，saved additional-config 无覆盖；不能把源码中的可选 daemon 当已生效重叠。join 有超时及异常回退，不能据 start 推断成功。

四个 helper 已读到调用与合法 guard：

| helper | 实际交付及区别 |
|---|---|
| rejection | K=5、maxreq=4、PP1 只需 NO_DRAFT_PROBS=True。按 BLOCK_SIZE 去重；V≥4 时只有 representative4，不是 1/2/4。prepare 一次、recovered/expand/greedy/random-or-block/entropy 按各自 constexpr；dummy rand 会消耗 RNG。K5 helper 本身不证明 K1 和所有真实 JIT key 已覆盖。 |
| penalties | 4×16160 TP-local logits、257 prompt；中性惩罚也执行以预热。真实 AscendSampler 与 AscendRejectionSampler 的 no_penalties guard 返回原 logits，不能把这份冷开销算成现有热路径惩罚可删。 |
| rms | 严格检查 AscendDSABackend 身份；V4.1 cache layer 返回 DeepseekV41CacheBackend。早预热 assume_used 可绕过 guard，但当前默认关闭；16 rank 的 .000s 只作旁证。live RMS 的自适应 UB block 也不等于 helper 注释的普遍 JIT 完备证明。 |
| indexer | 量化 1×32×128 query、ratio1/2、sort row-block1/2/4/8。预热不传 lengths_output，真实调用传 topk_lengths；topk512 时 rows≤1024 才合并长度，大行数另做比较/求和。两者不能混为已扫完的热算子。 |

既有 `framework-profile-20261109T192807Z/service.log`（SHA `16cf3814…`）的全部 16 rank：rejection .262–.298s、penalties .019–.023s、rms .000s、indexer .045–.057s、总 wrapper .329–.378s。并行 rank 不相加；.378s 是旧诊断启动 envelope，非可消冷延迟、非请求收益。encoder 日志与 warmup 之间约 8 秒还包含 dummy 模型、sampler 和同步，不能当纯视觉塔耗时。

workspace 追至 per-(ubatch,lane) 的 256B 对齐视图、只扩大当前 slot、旧引用清除、empty_cache、新分配、继承 GPU capture 的 lock，以及 shutdown/reset。锁定后超量申请抛错，不是在热请求中合法重新分配。当前两源码树 33 文件的 literal 引用清单是定位工具：Ascend 侧是初始化入口，没有证明该模型在用通用 get_simultaneous，更不能证明 native/ACL/DFC workspace 为零。lane ContextVar 退出不等于设备完成；跨流/迭代复用还需真实最后读者和 lease。

MM 分支不能由“请求纯文本”推成启动不执行。nested vision_config 经原 DeepseekV41Config 映射为 32 层、dim1024、inter2816、patch14、downsample3、maximage1024。完成日志两个 DP leader 明确 profile 8192 encoder tokens/8 images。原 profile_run 调 model.embed_multimodal、暂存 encoder_cache，最大 dummy model/sampler 后同步并 clear/gc。determine_available_memory 使用非 KV 峰值计算 KV 预算；即便显式 KV bytes 或 startup plan 命中，仍调用 profile_run。

为了判断容量是否会改变大方案去留，定点只读 142 个直接 safetensors 文件的头部，张量 payload 读取 0。原 `_vision_parameter_name` 的命名规则匹配 266 个 tensor，总 485268480 元素，全部 checkpoint BF16：970536960 B＝925.576171875 MiB。源构造 vision/aligner 转 model dtype，三个 delimiter 显式 FP32，合计约 925.60546875 MiB；未声称 live storage dtype/allocator 已观测。

## 结果

**已停止：以删除冷 helper/MM 计算提高既定暖请求速度的独立方案。** 这些调用在计时请求前结束，直接暖请求信用为 0；同预算的小融合也停止。冷启动可能有价值，但不是当前请求指标的新增收益，不追加冷启动测量。

**已停止：删除 captured 热路径的通用 workspace 增长。** 锁定后该增长不合法，删除其“重复分配”的信用为 0。这不剪掉真实 native workspace、更大 producer/consumer 融合或新多 lane/lease 设计。

**待确认：文本专用容量与有价值热融合的联合方案。** 视觉参数 payload 单独不足此前 full-owner OA 所需 2240 MiB/卡；即使参数全 FP32 也仅 1851.152 MiB。这个比较仅排除“只靠这笔声明参数足额供给”的容量假设，不能当物理 VRAM 上界；allocator、非参数 buffer、原有 headroom、profile 峰值和 capture 内存另算。当前没有证据表明 OA 必须依赖它。改变 MM 开关还会影响 MM-prefix config、权重加载和 KV 预算；需保留原行为/容量及逐位验收，不能直接认领请求速度。不为不改变当前去留的实际 allocator 参数继续补证。

**待确认，下一段深入：真实 indexer 的 query 量化 → QLI membership/candidates → chronological indices/lengths → 多层 SMLA。** quantizer 包含 FP16 scale 舍入、div_rn、nearbyint 和 clamp，不能以实数约掉归一化。sort 使用可逆 FP32 bit key；集合等价不等于后续 BF16/FP 累加逐位。group 已共享一次 selected bank，融入每个消费者可能重复排序。先从真实 caller/CP 取行量与共享范围，用匹配的旧 profile 给整段上界和有成本价格，再决定值得深入的 native 边界；冷预热 45–57ms 不作热算子价格。

本轮没有新替换原语准入、性能基线提升或服务改动。早先 header index 假设失败的 ERROR/INVALID Run 保留；修订后才用直接 header catalog。analyzer 初稿误用扁平字段名导致 KeyError:dim，已改成 nested 原字段并复算，错误记录在 exploration-notes。全链路仍未扫完，已读范围与具体未决项不是完成证明。
