# S01 请求与缓存状态：从实际消费者筛工作

本段完成首轮判断；只覆盖状态更新到 `_prepare_inputs` 入口，未覆盖后续metadata builder、Engram或模型层。源码先确定工作，随后才使用保存的metadata观测核对几何/发生分支；未从旧候选目录选题。

## 下游必须得到什么

`_prepare_inputs` 需要本轮稳定的请求行号、block表、CPU token bank、乐观计算位置和上一轮映射；压缩注意力builder还需要修正后的CPU长度/位置。下一轮仍会读 `requests` 和persistent batch，因此仅给当前模型交付device tensor不能删除host状态。

实际顺序是：结束请求退役 → 移除未调度/重启请求 → 新请求建立 → 旧请求/blocks/draft更新 → add/condense/reorder → refresh metadata → `_prepare_inputs`。同一个ID完成后立即重提时，先退役旧代次再建立新代次；不能只凭ID相同复用旧状态。

## 共同公式与实际同步

令上一轮draft长度为 `d_old`，采样有效计数为 `v_old`（包括保留下来的seed/bonus位置），同一请求的拒绝修正量是：

`δ = d_old - (v_old - 1) = d_old + 1 - v_old`。

host的deferred correction将乐观 `num_computed_tokens` 减δ；`_correct_optimistic_seq_lens_cpu` 对CPU长度使用同一修正。GPU的对应活动行由上一轮device计算位置加 `v_old` 得到；新请求、无旧draft或无映射的行用CPU fallback。

**当前压缩路径并非等到模型后才执行host deferred correction。** `execute_model:2457–2473` 在 `use_compress` 下先调用它，再生成 `_dsa_positions_np_buf`；`_prepare_inputs:1619` 也会校正CPU长度。父方法注释中“model后纠正”的一般说明不能覆盖这个实际caller顺序。两处对接受数的host读取只有在原event已完成后才合法；同步调用出现两次不代表存在两段可删除等待。

可把同一host侧δ计算和两个结果更新共同完成，或避免已被device overlay全覆盖的CPU ID准备。但它们只属于输入共同计划的host增量，不能把host镜像、block更新及实际读者一并删除。C02的价值门槛决定是否深入这些小工作。
