# 请求代次与终止轮交付判断

Goal ACTIVE；全链路未扫全，每个替换原语逐位一致。本轮是源码、原方法控制fixture与既有同负载记录分析，没有新NPU/模型/服务请求/profile、远端写入或原语准入。

## 介绍

从入口实际 request ID 与归一化 SamplingParams，沿 abort双队列、异步future、worker tombstone、stop裁剪、前端detokenizer与异常传播追到消费者。由消费者反推更大边界：当前请求已经没有下一轮需求时，能否省去完整DSpark尾部、提前交付结果，或取消确实多余的后续工作；不先优化孤立stop判断。

## 到了哪里

- 重新核对171主机与原容器；18运行树源14旧SHA匹配/4新取。具体范围见 [source review](request-lifecycle-source-review.json)，身份不等于所有callee、loaded bytecode或binary已验证。
- `InputProcessor.assign_request_id` 保留external ID，默认追加8随机字符作为internal ID；支持环境opt-out。这里只证明源规则，不声称live opt-out值或无碰撞保证；联合设计本就需要显式代次，因此未为此补一个不改变去留的运行探针。n>1会分child；streaming-input会沿同一internal ID继续不同chunk。固定C8/六普通为n1、普通token-list输入，不能把输出stream=True误认成streaming-input。
- 外部ID abort可能命中多个internal ID；内部abort只作用对应代。输入线程同时发eager abort队列和ordered input队列，scheduler按幂等abort处理；旧future更新前先处理abort，frontend也丢弃已移除ID的迟到结果。worker移除tombstone再安装新状态；这些控制顺序不证明原device读者或storage lease已经退役。
- 固定API的新建SamplingParams在`ignore_eos=True`归一化后主EOS不成为stop；extra EOS与显式stop IDs仍留在`all_stop_token_ids`供min-token处理，用户显式stop IDs也仍有效。一般替换须读取实际归一化字段，不能只看原始ignore标志；更新函数不会主动清空调用者已有的private EOS字段。`check_stop`区分EOS/stop token、长度、min-token与重复检测；前端detokenizer另做跨token的stop-string检查并向engine发送abort。不能用一个EOS并集或一个CPU“空valid列表”替代这些消费者。
- 当前async＋PP1队列大小2。worker `_bookkeeping_sync` 的valid CPU列表此时为空，实际采样在device上，并写入`-1`占位。GPU有效采样数、可见裁剪后token数、CPU乐观长度不同；原方法fixture中3个有效候选因max_tokens只交付1个。
- executor失败/执行异常会重新抛出，fatal EngineCore发送ENGINE_CORE_DEAD并shutdown，client/output handler向请求传播。预处理失败/MM重试是不同的请求级分支。ZMQ零拷贝frame持有owner，但不自动允许修改字节；输出可变bytearray等首frame tracker完成才复用。它们都属于提前交付/BatchFrame的真实所有权边界。

### 先复用已有数学界，再扩大合法范围

现有保守长度界剔除了placeholder代表的未决草稿，保证即使全拒绝也至少有一步真实进展。可以把同一post-schedule谓词保存到不可变`SchedulerOutput/BatchFrame`的逐请求、逐step代次中，再随既有DP交付发布no-next-demand标志；这部分不需要为拿到完整accepted count新增D2H等待。fixture的P1000/max13案例：确认输出12后调度6输入/6占位，界为True；确认输出8时为False，尽管实际多接受仍可能在本轮终止。因此它是保守子集，不能把所有最终轮都计为命中。

`_skip_drafting`目前仍会跑完整DSpark dummy query group来保持DP/EP服务，单独调用它不消掉三body。只有全部相关DP/TP决定一致、没有仍活peer或已入队消费者依赖旧draft IDs，才可考虑真正跳过未来query body/head/Markov；仍须按原方式保存valid count及全宽zero placeholders、保持collective序列和前轮最后读者。局部terminal不能单方跳过远端专家服务，也不能改变仍活行的M、行序、量化/归约位模式。

终止不等于cache生产者全死。真实继承路径`AscendDflashProposer.build_model_inputs_first_pass`会先做context KV预计算，DSpark模型逐层写各自SWA cache；这不是从dummy/profile分支推断的真实请求行为。后续prefix replay、物理页alias与发布边界仍可能读取这些写入。先保留context/cache生产者，仅删除确证未来专用的输出；若扩大到整段，则须重证所有prefix/cross-layer读者及cache代次。不能把“客户端不会再要token”当作删除cache写者的充分条件。

实际accepted-count扩展及后续target取消是更大的另一层判断：已有界已经阻止的轮不计收益；其它轮必须辨明是否已入队、是否已读取draft IDs、是否为新请求/真实peer服务以及取消会否改变原算术几何。当前档案只记scheduled tokens，缺逐step保守资格、accepted count与真实future依赖。保留这些具体缺口，继续剩余路径。

### 匹配负载的已有价格及限制

原C8的GPU-facing父区间是“target head/verification最后native任务结束→draft最后score结束”，覆盖整尾部，有意免费删除比合法候选更多的工作。7终止波为219/221/222/224/227/228/229，每波取local时长最大值后求和，不把16rank相加。其后CPU/D2H/socket EOF、此前host规划与更广排队变化在此边界外；不能把32ms当它们的总上界。

六普通使用精确历史client源 `eba6f84d…`，从其9144f2d提交提取并与原contract hash核对；当前工作副本SHA不同，未混用。确认其max_tokens为126/13/300/20/126/13、temperature0、ignore_eosTrue。18条stock/observed/recovered-stock记录分别保留，不相减、不平均迁移；四个名称的输出hash跨arm不同，旧守卫也已明确此限制，不能当逐位参考对或替换成功。

例如code-single原stock总483.325981ms，固定此前可见prefix时末尾有序交付间隔60.223906ms，约12.46%；其1%收益门槛为4.833260ms。recovered-stock总466.607068ms，对应间隔65.749658ms。它们只给端点松弛敏感度，不是本地native尾部时长或预计净省；不能借C8的body时间代填。决定下一步的缺口是普通负载逐轮资格、完整native/CPU尾部父区间，以及新增flag/fence/collective/lease成本。保留联合范围，尚无开发准入。
