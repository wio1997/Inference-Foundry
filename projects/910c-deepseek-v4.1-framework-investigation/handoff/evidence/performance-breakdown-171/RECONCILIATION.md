# 算子为何没有直接加到54%：已经逐区间核准

统一使用同一次16卡、每卡11个闭合循环的设备窗口。之前展示的头部11项仅占45.31%；其余68类占11.99%。两者相加是所有79类各自任务区间的累计，不是互斥时间账。

| 从排行榜回到设备总账 | 平均ms/卡 | 占设备窗口 |
|---|---:|---:|
| 79类各自的区间时长相加 | 480.93792 | 57.30109% |
| 减：不同类型并行造成的重复计时 | -26.07197 | -3.10637% |
| 全部79类任务的时间并集 | 454.86595 | 54.19473% |
| 减：并集在CANN Computing之外的边界部分 | -0.04050 | -0.00483% |
| 加：Computing中未被CSV任务覆盖的边界部分 | 0.04031 | 0.00480% |
| CANN Computing | **454.86577** | **54.19471%** |

前后边界抵消后的差额仅0.0001875ms，不是新的性能瓶颈。主要区别是重复计算并行。

## 可加总的计算活动树

```text
Computing 454.86577ms
├─ 只有一个算子类型活跃的区间 428.78914ms
├─ 多个算子类型并行的共享区间 26.03631ms
└─ CSV未匹配边界区间 0.04031ms
```

子项互斥、可直接相加。全部单算子项和并行组合见[computing-time-tree.csv](computing-time-tree.csv)。并行组合保留所有算子名，不随意把共享时长分给其中一个。三项及以上同时活跃时，重复计时可以大于该并行区域自身的时长。

这棵树用于时间对账，不能把独占时长直接当作优化收益，也不能说并行项没有优化价值；净收益仍要沿依赖与资源重排判断。Host各阶段另建同线程父子树，CPU与设备按同一时间轴对齐，不把跨线程/跨卡时间直接相加。
