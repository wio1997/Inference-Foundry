# 如何把每段时间打印清楚，再决定框架优化

当前结果已区分“范围已测”和“具体函数已知”。输入准备阶段的空档309.77ms里，155.35ms仍无cpu_op范围覆盖，可能是Python代码、运行时调用或线程停顿；不能将其直接命名为调度耗时。

## 一份可对账的时间树

每个节点都保留：线程/rank、迭代与batch代次、源码入口、开始/结束、包含子调用的墙钟、子调用并集、自身未归属时间、与设备空档交集、证据等级。单线程中：

```text
父节点墙钟 = 子节点覆盖区间的并集 + 父节点自身未归属区间
```

CPU主线程、后台提交线程和设备流分别记树，沿同一时钟与提交/事件关联对齐。不同线程、设备流、rank或卡的时间不相加当成请求耗时。设备并行区域作为共享节点出现；完整可加总Computing树已由现有数据生成，不需新采集。

## 全程轻量，热点细分

全程只记录请求边界和每轮大阶段的轻量区间，覆盖所有迭代，得到完整请求预算；细粒度CPU/NPU事件只采热点短窗口。两者使用相同迭代ID、rank、batch代次和时钟标定点关联。当前839ms短窗口不能直接放大成完整16秒分解。

现有VLLM_CUSTOM_SCOPES_FOR_PROFILING只提供prepare input等父标签。下一轮若要补155ms的函数归属，需要在自有诊断实例增加以下子范围，而不是再次只打开同一父开关。

| 待补子范围 | 已核对的冻结入口 | 要区分什么 |
|---|---|---|
| 请求状态更新 | model_runner_v1._update_states:961–997 | 请求映射、状态修正与代次处理 |
| 下一轮输入构造 | _prepare_inputs:1281–1694 | 位置/长度、索引、block table与slot、接受计数等待 |
| 批次与DP协调 | _determine_batch_execution_and_padding:3325–3432 | 组间协调、padding与图bucket选择 |
| 注意力参数总构造 | _build_attention_metadata:3449–3907 | 遍历缓存/Attention组、共用与组专属数据 |
| CP子构造 | CPMetadataBuilder.build → _build_global_metadata / _build_local_token_metadata | 区间、长度、suffix、掩码是否重复计算 |
| 入图前输入处理 | execute_model中_preprocess调用:2523 | embedding等输入处理与实际数据交付 |
| 原生参数提交 | SMLA/QLI metadata wrapper与producer任务交付 | CPU构造、后台入队、设备执行和完成栅栏 |

这些是待加的诊断标记，不是已测到的子函数耗时。继续按父→子展开，只有会改变开发排序的大额未知才下钻；不默认全模型逐行追踪。首轮先补上表少数函数，读结果后再决定是否细到CPU对象构造、字典、NumPy或特定库调用。

记录Host入口/出口不能直接当作设备执行耗时。沿用CANN HostToDevice、connection_id、Model/Task/Stream与事件依赖，核对何时提交、何时执行、何时被下游消费。避免在每段后强制设备同步，以免破坏原有并行；采集本身开销也需与无采集参考比较。

## 框架优化的推进顺序

1. 固定版本、负载、并行、缓存命中、输出与数值合同。无profile整批吞吐是最终指标，保留TTFT/输出间隔、每轮有效token和负载平衡。
2. 用互斥时间树核对总账；用算子排行查局部热点。未知时间明确保留，不用“调度”替代未知。
3. 本项目先收敛输入/metadata共同构造的大段：先为155ms补函数证据，再判断兼容同代区间/长度/掩码能否只算一次、固定缓冲与批量发布。旧CPU-plan、slot mapping和H2D收益不重复计。
4. 目标DFC是设备最大单项，按内部权重读取、GMM、同步和消费者拆预算。量化矩阵乘、mHC和Attention按实际shape和交付链绑定，不能把多调用点的一个Type直接当一个开发项目。
5. 每个方案先写“减少什么工作、允许怎样重叠、会增加什么成本、预期哪些时间区间缩短”。以相同输入/输出就绪界估计净省，预算不足的小方案结束；扩大后能额外消除工作的大parent另算。
6. 一次只做一个可验证的大范围机制，先验证正确性与数值合同，再跑无profile同负载。若CPU函数变快而设备空档/请求耗时不降，就说明收益未传到关键交付，不能宣称吞吐提升。
7. 接受一个方案后重做剩余预算，跟踪瓶颈转移；所有方案通过同基线组合实验兑现，不能直接相加各自的百分比。

本轮交付时间核准和下一次标记清单，不新增模型/NPU测试，不修改运行时实现。现有profile的逐函数未知尚未自动补齐，具体融合方案和两倍收益均不作已完成处理。
