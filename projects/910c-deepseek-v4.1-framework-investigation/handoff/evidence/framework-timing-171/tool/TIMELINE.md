# 完整timeline的组织与验收逻辑

完整性的对象是**固定版本、配置、负载与起终点内的实际执行**。新请求长度、并发、prefill/decode、cache命中、投机接受率或并行策略产生不同路径时，增加对应case，不把一次trace当作框架所有路径。

## 一、先建交付图，再贴时间

每个节点回答：输入何时就绪，执行什么，结果交给谁。每条边回答：直接调用、入队/出队、IPC、异步任务、collective或设备事件，靠什么ID证明前后属于同一次交付。

```text
请求进入
 → 解析/tokenize/cache → 排队 → 调度组批
 → IPC发布/worker接收
 → 输入与状态/位置/slot/metadata准备
 → 目标模型〔Engram → mHC → Attention → MoE等实际层序〕
 → logits/采样/投机校验/草稿〔有回路则逐迭代展开〕
 → 状态更新/worker回包 → EngineCore回收 → 输出发送 → 最终交付
```

多卡、多个stream、跨层、草稿回路都是这张交付图的分叉与合流，必须保留实际同步。模块边界用于组织，不阻止融合或跨模块调度分析。

## 二、把一条请求展开成多条时间轨道

|轨道|至少保留什么|关键关联|
|---|---|---|
|客户端/API|提交、服务接收、token就绪、输出首包/末包|request_id与客户端/服务器时钟|
|请求队列/调度器|入队/出队、schedule、batch生成/更新|request_id→batch_id/代次，队列长度|
|IPC/执行队列|发送、可消费、接收、结果发布/回收|batch_id、RPC/消息ID、worker rank|
|worker Host主/辅线程|状态更新、输入、metadata、目标/草稿调用、采样|PID/TID、迭代/代次、父span|
|runtime提交线程|Host API、提交排队、事件等待|correlation_id/flow、stream、task|
|每卡每stream|kernel开始/结束、collective、copy、event|rank/device/stream/task与实际依赖|

同一时刻可以有很多轨道在工作。分别记录，再按依赖看结果什么时候能交付；不把多线程、多卡或CPU/设备时间纵向相加。

## 三、有限窗口内，每一段都要有去处

对每条轨道，先定义观测区间W=[开始,结束]。将所有事件边界排序，切成最小时间段。每个小段填写：**已记录执行、已知等待/排队/传输、未观测**。未观测不填0，也不自动改叫调度或设备空闲。

```text
W = 已归属区间的并集 ⊎ 未观测区间
父函数区间 = 子区间并集 ⊎ 父函数自身区间
```

`⊎`表示互不重叠地计一次。父子表是展开关系。设备计算与通信并行时，另列共享区间；同类/跨类kernel累计时长与设备墙钟分别保留。

**沿交付边逐条查缺口**：

- 有发送无接收：缺接收标记或消息关联。
- 有提交无设备开始：查队列、依赖和runtime/device flow。
- 设备空档但上游Host正在工作：下钻这个Host阶段。
- Host正在等待：追被等待的结果及生产者，不能把所有等待都记成调度计算。
- 事件无法连到request/batch：标“时间已测、归属待确认”，不靠时间接近强行连接。
- 父区间比子区间并集大：自身区间仍有实际代码、库调用或等待，按价值决定继续下钻。

## 四、完整性用表验收

每个case都有一张覆盖表：

|交付区域|起/终边界|轨道与版本|时间范围覆盖|函数/任务归属|上下游ID关联|未知ms/原因|下一条补证|
|---|---|---|---|---|---|---|---|
|示例：输入准备|worker收到批次→forward输入就绪|worker主线程/冻结SHA|全请求或指定短窗|已标函数/待补函数|batch代次已连/缺失|实填|只补会改变排序的缺口|

“时间窗口采全”“事件归属清楚”“上下游因果连通”分别检查。报告必须显示各自缺口；覆盖表不能由报告成稿自动变成完成。

## 五、从最大时间块向下，不遍历所有小函数

1. 先画整个请求的墙钟，以及CPU/设备/通信和排队的并行关系。
2. 找使最终结果迟交付的最大区域，估计在当前依赖下能影响多少请求时间。
3. 对该区域展开阶段/函数/算子；每次只下钻尚未解释、且能改变开发取舍的最大时间块。
4. 以数据交付为大小边界，先考虑整段数学消除/共享、融合、megakernel和重叠，再沿必要精度、状态、同步或资源边界缩小。
5. 用已有单位成本计算候选净价。预算不足则停止同范围小方案；能额外消除工作的更大区域另算。

一张完整的交付图可以容纳未知；要把未知全部解释到某个粒度，需要相应标记和采样。完整性与无限细分是两个独立维度。

## 六、统一时钟与探针开销也是数据

同机单调时钟、墙钟和profiler时钟仍可能有偏移或漂移。用相同事件锚点校准，并保留残差和可行误差范围；跨机记录clock校准，不仅比较绝对时间。误差范围内的先后关系不得当作严格依赖。

先采完整请求的轻量标记，再对热点短窗采详细CPU/NPU事件。记录轻量、详细与真正无探针参考的差异。能识别的新增标记边界单列；扣除边界不能恢复未发生的无探针执行，不可把扣除后结果当已验证性能。

本次171：完整请求轻量记录覆盖18个进程；设备与细函数是16卡稳态短窗。本次API逐函数、跨进程自动batch关联、DFC内部与off-CPU具体原因仍有缺口，须在总图保持明确。SGLang/DeepInfer沿以上同一逻辑绑定实际代码，当前未在这些框架实跑。

## 七、用交付图计算关键路径

对已知依赖的任务v，记录执行开始s、结束f及任务时长d。将队列、资源或同步等待单列为w：

```text
s(v) = max{ f(u) : u是v的已知前驱 } + w(v)
f(v) = s(v) + d(v)
T请求 = f(最终交付) - s(请求进入)
```

当所有前驱/资源关系尚未找到时，w只能写“未解释间隔”，不能命名具体原因。相邻事件有时间间隔，只说明存在间隔；证明是哪项调度、哪条锁或哪次数据交付，需要对应事件/ID。

沿最终交付向前追依赖，再向下展开最大的执行或等待节点，即得到“全链路→热点→源码/算子”的同一套逻辑。优化候选改变子图：保留相同外部结果、精度与状态后重算交付时间，不能只用删除的kernel累计时长预测整体吞吐。
