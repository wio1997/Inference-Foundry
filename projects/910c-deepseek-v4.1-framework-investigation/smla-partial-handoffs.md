# 压缩 Attention 的首段 FP32 交付

**只保留长提示首 token 的联合候选。** 38 个压缩 Attention 层中，若一次查询既读滑窗又读压缩 KV，首段矩阵乘的 FP32 结果会由 Vector 原样复制一次。让 Cube 直接写入后段要读的位置，每个命中查询、每层可少读和少写各 128 KiB。这是逻辑 GM 流量，实际耗时取决于缓存、流水和同步。单项在参考带宽下全部兑现，冻结 C8 首 token P90 也只省约 11.85–11.87 ms，低于本轮 1% 参考线 14.92 ms。[逐分支合同及实际估算](baselines/smla-inner-handoffs.json)

| 在同一 SMLA 中可消除的工作 | C8 首 token P90 预计节省 | C8 整批预计节省 | 六个普通请求整段的最高估值 |
|---|---:|---:|---:|
| 首段 FP32 原样复制 | 5.93–5.94 ms | 7.25–7.32 ms | 0.085% |
| 单独省去压缩 KV 临时面板的净写读 | 11.85–11.87 ms | 14.50–14.64 ms | 0.170% |
| 两处共同消除 | **17.77–17.81 ms（1.19%）** | **21.74–21.97 ms（约 0.12%）** | **0.256%** |

上表按每个命中查询有 256 个有效压缩位置、稀疏新读与原面板访问等速、有效双向速率 2.405 TB/s、搬运差额的 50% 暴露，并假设没有新增暴露的同步耗时。8 个冻结请求分别对齐自己的首 token 及最后一次校验，依次经过 TP8 与 EP16 的最晚到达。图内使用 128 个已有逐卡窗口作为同形状参照。普通请求使用六个真实请求各自的长度和两次对照耗时，包含混合 prefill 的情景。数值是已有 profile 上的条件估算。前一轮三项联合估算已包含 KV 面板这一行，两份结果不能相加。[原联合估算](joint-attention-frontiers.md) · [波次、形状和假设](baselines/smla-inner-handoffs.json)

## 哪些分支有这次复制

固定模型每个 KV 头对应 64 个查询头，头宽 512，滑窗 128。910C 选中的 CSA 路径一次可处理 512 个 KV 位置。一个滑窗块加一个非空压缩块时，首块的 PV 先写 FP32 工作区。Vector 读入这份结果，在首块跳过历史缩放与相加，在非末块跳过除法，随后将原值写到另一处工作区。压缩块的 Vector 读取该处结果，再做在线 softmax 缩放、相加、归一化和最终输出。两份工作区使用相同的逐行列偏移。候选改变首块 Cube 的写入目的地，保留末块的计算与读者。两槽轮换时要保证旧查询读完才允许新查询覆盖，并保留行地址、精度和事件先后。[固定源码版本与分支行号](baselines/smla-inner-handoffs.json)

压缩为空、滑窗单块即结束时，首段复制收益为零。两个仅滑窗层、草稿、其它头比例和跨核切分路径均未计入。若想另外在 Vector 片上保留这一整块，原分块每个 Vector 至少需 64 KiB；当前缓冲分配在计入可选 LSE 之前最多余 3,328 B。只把概率张量的搬运改成 171 的 CANN 9.2 UB→L1 接口也省不掉写读，目标 SDK 的实现先写 GM，再由矩阵服务填 L1。已有 PV 会在四个输出列块之间复用概率。两条推论均未给联合候选增加收益。[缓冲预算及两个目标 SDK 文件的版本证据](baselines/smla-inner-handoffs.json)

## 哪个条件会改变取舍

同一模型将每查询的有效压缩位置统一设为 128 / 256 / 512，首 token P90 分别约省 11.85 / 17.78 / 29.63 ms。跨过 1% 的统一长度约为 **194–195**。在 256 个位置的情景，每个命中查询、每层、每卡只要摊入约 **26–27 ns** 的额外关键路径开销，联合收益就会跌回 1% 以下。原 profile 记录了容量和执行形状，真实逐行有效长度、改写后的稀疏读速率与同步开销尚未得到验证。对普通交互及 C8 整批，这一项降级；对长提示首 token 保留上述进入条件。[位置证据的适用范围](baselines/smla-panel-occupancy.json) · [两项敏感性计算](baselines/smla-inner-handoffs.json)

## 两次稀疏读取和跨层共享，哪项值得保留

**长提示首 token 保留有条件的 KV 直读；跨层保留整块 KV 面板的优先级更低。** 每查询 256 个有效压缩位置、搬运差额有一半暴露时，若 QK 和 PV 两次直接读取的有效速率相同，两者均需达到原搬运参考的 **80.4%–80.6%**，与首段 PV 直写合起来才可能将冻结首 token P90 缩短 1%。若两者仅达 75%，预计省 13.82–13.85 ms，低于 14.92 ms 的参考线。六个普通请求按原速率模型，即使两处直读同速且首段直写成立，整段最高估值为 0.256%；将有效位置上限提高到 512 时约为 0.426%。[逐波估算、原始数据及条件](baselines/smla-kv-readers.json)

### 先扣掉必须保留的读取

每个有效位置有一行 1,024 B 的 BF16 KV。原 Vector 从分页缓存读一次，整理后写一次；QK、PV 从这一新写的面板各读一次。取消面板后，QK、PV 均需从稀疏地址获得对应值。以同一归档双向拷贝率为计价单位，原路径的行搬运成本系数为 `1/v + 3`，两次直读为 `1/q + 1/p`。其中 v、q、p 分别为原稀疏读、QK 新读、PV 新读的相对有效速率。原面板读写取 1。保留滑窗、两个矩阵计算、原顺序、一次 FP32 首段直写的独立收益，再按 16 卡实际汇合和各请求的终止波次重算。参考的 2.405 TB/s 对读写合计字节计价，两次新读的速率仍是变量。[固定模型与计算式](baselines/smla-kv-readers.json)

| 每个命中查询的有效位置数 | QK、PV 同速时，首 token 达 1% 所需相对速率 | QK 达参考速率时，PV 所需相对速率 | 两次均与参考等速时，每次调用至少多少比例的选中行走直读 |
|---:|---:|---:|---:|
| 128 | 205.3%–207.5% | 即使 PV 读取近乎免费，模型仍未过线 | 全部选中行均直读仍未过线 |
| 256 | 80.4%–80.6% | 67.2%–67.5% | 75.6%–75.9% |
| 512 | 61.7%–61.8% | 44.6%–44.7% | 37.8%–38.0% |

表内将原 Vector 稀疏读速率取为参考速率。若它原本只有参考的一半，即使两个新读者都只有参考的 75%，256 行联合估算也回升到 19.75–19.79 ms。行占比一列假设每个调用都有同样的命中比例，未命中行沿用原搬运，所有非空压缩查询仍有首段直写。分开按实际层代价算，只在 20 个 C1 层或只在 18 个 C2 层启用直读，256 行时首 token 分别约省 12.16–12.19 或 11.54–11.56 ms；512 行时分别约为 18.40–18.44 或 17.15–17.19 ms。因此某一压缩比分支能够单独过线，取决于它真正交付的有效行数。[按分支、覆盖和速率计算](baselines/smla-kv-readers.json)

### 已保存的索引揭示了哪些搬运约束

910C 固定源码将稀疏块大小设为一行。Vector 可把两个地址有正间距的物理行放在同一条带步幅的搬运指令中。地址不同时，快路径从较小物理地址开始写面板；重复地址、超界和步幅过大等分支另行处理。例如逆序页表将有效逻辑行 127、128 映射为物理行 383、128。在上限为 130 时，这一对以 128、383 的顺序交付。QK 和 PV 必须取同一套行顺序，逐位对齐原结果还须保留归约顺序。如果新路径只把逻辑索引排序后交给 Cube，跨页时可能得到另一顺序。[源码锚点和可复算的两行例子](baselines/smla-kv-readers.json)

当前 Cube 的 QK 按 128 行、两段 256 列搬运，PV 按 128 行、四段 128 列搬运。因此 512 个位置在连续面板上共需 24 次对应的 Cube 输入搬运；直接从分页缓存读取时，行地址可能切开这些块。两次原生 QLI 归档中的三种输入，去重后只有两份不同的完整输出，各有三个查询。由原始 ID 重建的六行排序及填充结果均通过原 SHA-256 校验。将它们投到正序和逆序的 128 行 KV 页表，保持原成对交付顺序，按连续地址切分需 **24–78 次** Cube 输入搬运；放宽为可表达的正固定步幅、暂忽略硬件步幅上限时为 **24–60 次**。这六行来自数值夹具；该页表映射是给 BF16 KV 的情景，实际 C8 的逐行分布仍未知。QK/PV 共用的三个 KV L1 缓冲合计 192 KiB，最多装下 192 行完整 KV。256 或 512 行全程只读一次还需要改变分块及缓冲生命周期。[夹具哈希、读取宽度和顺序](baselines/smla-kv-readers.json)

另一个已测 Q416 夹具选择 512 行。按其实际的均匀无放回采样规则，在 1,024 行字典的原布局上，每个查询有 512 段页内连续地址；预打包后，平均仍约有 258–260 段。8,192 行字典预打包后约有 480–481 段。已有对照的四组条件只改变 KV 位置，仍走原生 Vector 整理，30 次后续调用的中位差额外推为 0.009–0.069 ms。它能降低对独立字典打包的预期，无法给融合后 Cube 的稀疏读速率赋值。[采样规则、连续段期望和原生对照](baselines/smla-kv-readers.json)

### 让相同索引的后续层共用已整理的面板

八个索引生产层中，三组各供六层使用，五组各供四层使用。若同组查询、有效长度、物理 KV 映射、数值代次和行序全部相符，首层 Vector 可在原整理的位置直接发布一份保留到最后读者的面板。其余 30 层各省一次分页读取及面板写入，QK、PV 继续各读一次面板。现有环形工作区按每核三槽轮换，跨层交付要另有按查询/代次寻址的地址和退役条件。[层归属、首读者与后续读者](baselines/smla-kv-readers.json)

| 256 行时，沿冻结请求重算 | 首 token P90 预计节省 |
|---|---:|
| 30 个后续读者复用，保留原首段 PV 搬运 | 9.35–9.37 ms |
| 另加首段直写，且后续两次面板读均与原新写面板同速 | 15.28–15.31 ms |
| 后续面板读速率降到原参考的 90%，仍加首段直写 | 14.24–14.27 ms |
| 后续读同速，但首层必须把原面板再完整拷贝一份才发布 | 12.78–12.81 ms |

要跨过 1%，256 行时后续读速率约需维持原参考的 **96.0%–96.3%**。Q416 若按 512 行槽位存储，一代面板每卡需 208 MiB；Q818 为 409 MiB。已有 368 个非空逐卡索引代次的首末读者间隔中位为 22.47 ms。根据 1,380 次后续读取之间的专家权重访问估算，有 1,378 次的权重覆盖量超过整卡 192 MiB L2。能否保持足够的实际读取速率仍未知。两条 KV 提案都涉及同一份原面板：对同一行选择其中一种，首段 FP32 直写只计一次。[容量、存活时间及请求侧预算](baselines/smla-kv-readers.json)
