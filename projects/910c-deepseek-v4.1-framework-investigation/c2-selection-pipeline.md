# Attention 的 C2 池化、索引选择与首个读者

在相同的查询、键、专家和权重分布下，C2 的两次投影、pool、ring 更新、RMS，以及索引选择到首个 Attention 的交付，可以按实际少掉的内存读写一起估值。在冻结 C8 的有利时钟情景中，这些直接交付合计预计省 **0.353 ms 首 token P90（0.024%）和 0.461 ms 整批（0.0025%）**。六个普通请求按各自的 prefill 和验证次数外推，整段响应的估算最高 0.005%。这一组在当前负载下结束独立深查。[逐请求结果、形状与证据指纹](baselines/c2-selection-pipeline.json)

| 在原分片和工作行上可消掉的交付 | C8 首 token P90 | C8 整批 |
|---|---:|---:|
| 两个 512 通道 FP32 投影直接供 pool 和 ring 更新读取 | 0.235 ms | 0.288 ms |
| pool 与 ring 共读尾部投影，pool 以原 BF16 舍入交给 RMS | 0.060 ms | 0.100 ms |
| QLI 原始索引由整理算子直接接手，首个 Attention 直接读取结果 | 0.059 ms | 0.073 ms |

上述均为已有 profile 支持的情景估算。采用同机连续拷贝的读加写速率 2.405 TB/s，并把有利情景的局部节省向后传递到原转置完成时点。下一步在 TP8 取最迟就绪的 rank，在每个调度波次取较有利的活跃 DP，再按各请求的实际终点重算。局部排队、非连续访存及片上资源竞争都会影响可兑现的比例。以原首 token P90 1,491.85 ms 和整批 18,590.77 ms 为分母。[口径与逐卡记录入口](baselines/c2-selection-pipeline.json)

## 分支如何影响判断

- 对 C2 的 10,872 处逐卡层调用，投影输出还要供 ring 更新保留每个请求最后至多 32 个有效行。存在有效状态页且长度不超过 32 时，ring 已要求所有行。所有完成端点都发布时，pool 和 ring 也合计要求全部有效行。可以省中间面的交付，不能按整段投影耗时给融合记收益。
- 有发布目的但没有 pool 完成值的行，要交付经过原 RMS、旋转和量化的默认值。奇数起点的首个有效配对可能依赖旧 ring 前驱。应先读旧值或沿用原有两阶段顺序。缩到三或四个槽位改变容量，受回退长度和物理别名约束。
- 索引源位于第 2、8、14、20、24、28、32、36 层，按零起始编号。后续各层仍可能复用已排序的索引。每查询 512 个 INT32 位置，首个 Attention 消费之后仍须发布后续层需要的结果。正 DP 的 eager 调用里有 80 处本地 Q 为空，这些位置可同时承担 KV 或跨卡职责。非空 Q 且空 key 时的初始化频次仍未定。[C2 消费者、默认值与 hazard](baselines/fusion-scope.json)

## 分块提前消费值多少

同一个查询按键块打分时，后续键可以改写当前 Top-K。沿原生拆分归并路径，需要完成最终归并和索引整理，才能交给 Attention。不同查询各自完成最终选择后，可以按查询分组交付，保持并列顺序、填充项和后续层复用。这种重排对请求的作用单列，避免把重叠时间计入消除索引写读的收益。

复用 446 次图内及 7 次 eager TP8 调用。八个源层在图中共 28,544 处运行选择和 Attention，在 eager 有 368 处。在原生每序列四查询分块、原 SP 分片下，图内有两组有效查询可流水的位置为 0，eager 中有 320 处。在这些位置按最多四批交付，以每组有效行数分配两段的已测时长。假设每次额外交付花 2 µs，冻结结果如下。[分组算法、时钟约束与实测算子时长](baselines/c2-selection-pipeline.json)

| 分组情景 | 首 token P90 缩短 | 整批缩短 |
|---|---:|---:|
| 可兑现理想重叠的 25%，计额外交付 | 3.71 ms（0.25%） | 3.71 ms（0.020%） |
| 可兑现 50%，计额外交付 | 7.61 ms（0.51%） | 7.61 ms（0.041%） |
| 理想重叠全部兑现，交付免费 | 15.60 ms（1.05%） | 15.60 ms（0.084%） |

按每次 2 µs，达到首 token 1% 所需的重叠兑现比例在有利时钟情景为 96.9%，按导出时钟对齐为 98.0%。六个普通请求在 50% 情景下预计首 token 最多缩短 0.276%，响应最多缩短 0.108%。这些比例只适用于这里的分组策略、原版 QLI 基线和计价模型。每行有效键数、各组耗时和新资源竞争缺少直接测量。普通请求使用已有 prefill 插值及单请求验证形状，尚无该流水方案的端到端对照。

SMLA 内部的压缩 KV gather → QK/PV 还可能去掉另一份更宽的 BF16 中间面。按它自己的字节数和有效索引行数评估，不能用本页对 INT32 索引交付的估值淘汰它。[有效行数对请求收益的影响](baselines/smla-panel-occupancy.json)
