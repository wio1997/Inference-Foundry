## 单次调用的实际成本

385,100 条既有设备记录已按阶段、kernel、全部输入输出 shape/dtype、DP 与 eager 批次行数分组，得到 1,698 组条件。每组保存样本数、覆盖的 rank、最短、中位、P95、最长时间。直接矩阵乘按一次乘加计一个 MAC。TensorMove 按逻辑输出字节计价。实际格式、缓存冷热和同时执行的工作仍需匹配。[逐条件样本统计](profile-units.json)

查询 `python3 tools/query_global_cost.py --unit MatMulV2 --phase eager_first_token --dp 0 --carrier 416 --inputs '416,5120;1280,5120'`，可取到该 BF16 投影在八个 rank 的 320 次记录。单次中位 34.78 µs、P95 37.42 µs。查询 `--comm allGather --phase eager_first_token --dp 0` 可用相同阶段的消息口径查看通信。收藏的签名若在新条件中没有命中，先判断整个区域能否改变请求排序，再决定是否集中补测。

将所有真实本地 Q 投影的时间都与 TP8 AllGather 重叠，保持其它阶段、等待和发射空隙固定。即便每层都取最慢实测样本、所有重叠均兑现，历史八请求的首 token P90 至多缩短 9.011 ms，本轮准入需要 14.919 ms。仅改变本地 Q 与通信顺序的版本跳过独立 C8。实际改写 FFNPost、同时生成残差与 Y 的两个版本已完成冻结 C8，两项服务指标均未通过。[跨层模型对照](attention-handoff-c8.json)[逐批次和逐请求上界](attention-service-budget.json)

## 最终 FFN 的替代成本

老排程中独立最终 FFN 的模型内工作和末端读出的收集、复制与归一化分别最多缩短历史首 token P90 9.429 和 13.563 ms。二者联合的分阶段预算为 22.992 ms。对四批假设相同的替代用时，按八个请求分别重算，达到 1% 门槛时每批能用 2.018 ms。实际规划还要计入选行、重排、投递、协调和按新形状计算。171 的功能对照和容器内 CPU 准备对照给出了原归属、重分布与有效位的实际输入。[请求预算与行布局](terminal-sparsity.json)

## 从请求收益反推要测什么

`python3 tools/query_global_cost.py --screen TensorMove` 返回同名算子在两个阶段各自的预算。加 `--details --screen-cohort decode` 可按输入输出 shape、dtype 和 kernel 查询。当前 decode 的 405 组签名中，381 组在全部 112 个本地周期均低于 1%。历史 prefill 的 663 组中，591 组在全部 64 个 rank 模型体均低于 1%。全程复用已有缓存，无新增 profile 导出。[逐项筛查](operator-value-screen.json)

- 只省布局操作本身时，decode 每周期至多两次 TensorMove，最高占 0.0515%。将 Cast 整类都计入也最高占 0.565%。这两类单独的小改动可以先跳过。
- 同名 Transpose 在 decode 和历史 prefill 的最高占比分别达 1.2811% 与 1.4007%。沿热层找产生该布局的写者，核对下游读者。分支和多个算子共享一次物化时，按联合区间取并集。
- 准备服务实验前，将实际分支命中次数和每次完整区域节省的毫秒数，放回对应请求的首 token 或整批耗时。记录还差多少毫秒才值得验证。通信或服务取得新样本时更新单位成本，拓扑、消息大小、布局或并发条件变化才重开受影响的测量。[专家回写原生与 C8](expert-return-native.json)

## 同一容量指标的计数口径

vLLM 前端将每个 DP 引擎报告的 KV 块相加，两个 engine 标签显示同一个合计。启动配置中的块数控制单个引擎的实际分配。一次原服务启动的两个标签都显示 34,615 块，结合每个引擎的 token 容量可独立还原为 DP0 的 17,309 块和 DP1 的 17,306 块。冻结服务对照时同时保存每个引擎的分配、总量和 block size。未来需要长期驻留权重的模块可以直接复用这个计数口径。[源码哈希、两次启动和计算过程](oa-service.json)

## 已经省掉的实验

- 终端 mHC 两次 AllGather 在 112 个模型窗口最多占本地周期 0.074%。单独缩窄它们暂缓，联合重排可复用同一组记录。[模型与回放](collective-calibration.json)
- F21 的 5 组 M3 真实路由中，即使接收布局已就位，诊断内配对中位每次仅省 1.54–6.92 µs，低于预设 14.25 µs。暂缓这组路由的单独打包和共享输入实现。更大 M 的量化分支已另外登记。[对照和分支](f21-peer-input-value.json)

- 三个大 M 的专家算子在原有 40 个核心上，跨核重复整行量化均只有 20 次。400 次零发送调用仍需参与接收专家计算。已逐 rank 验证四段 eager 模型体与 225 次图调用互不重叠，可复用共同时间分母。首 token 同层 QLI 与 SMLA 之间的交接区间最多占这个并集的 0.039%。以上两项可直接复用于融合价值筛查。[大 M 与 Attention 交付成本](prefill-f21-attention.json)

- 171 单卡上 Q416 的已选 KV 提前排紧，1,024/8,192 个不同 KV 行和两种缓存压力条件均未通过预设价值门槛。按同一请求的 30 次后续读者折算，未计打包代价时最多省约 0.069 ms，门槛为 4.488 ms。[原生配对、工作集和请求](prefill-selected-kv.json)

- C8 首 token 的两个 DP 各完成 4 个请求，引擎排队合计分别为 0.159 和 0.155 ms。对原排程，两个候选请求都已在前一步排队的必要条件是两次调度决策相距至多 79.45 µs。跨步合批另查 40 层接收负载和 39 段前置时间。[请求时间和专家工作](prefill-admission.json)

- 新一轮 C8 的 6 个较晚首调度请求在前一次非空调度时均未完成分词。8 份输入共用一个由 seed 得出的 28,789 token 前缀。四种 CPU 对照都保留每个请求的全部 32,768 个 ID。第八个输入就绪中位耗时分别为 612.09 ms（单线程）、169.68 ms（四线程）、73.70 ms（单线程复用前缀）及 21.36 ms（四线程复用前缀）。四线程配置的服务结果已按两项指标分别裁决。[冻结 C8](renderer-c8.json)[分阶段证据、适用条件及对照协议](prefill-request-delivery.json)

- 64 个历史首 token rank 区间共 135,592 条原生记录。其中 22,248 次直接矩阵或专家调用已折算成 MAC 和有用专家权重字节。在 1.8 GHz 参考条件下，四种载体的部分计算时间下限分别为 10.49、20.57、20.59、25.47 ms。实际时钟上界、HBM 流量和可达带宽仍需独立约束。[按载体查询](eager-resources-and-copies.json)
- 1,920 次 TensorMove 已整理为 26 种签名。按实际张量字节查同一批 profile 的耗时、次数及关联的输出链，例如 `python3 tools/query_global_cost.py --copy-bytes 34078720`。在 2,240 条注意力输出链中，单独去掉接口间隙与输出拷贝最多占八个历史请求各自首 token 延迟的 0.232%–0.389%。共同生产者改写若改变矩阵内读写或集合通信，须按扩大后的范围计价。[签名与逐请求预算](eager-resources-and-copies.json)

- 已定位 280 组完整 TP8 的输入 AllToAll 和输出 ReduceScatter。每层按保留原始 BF16 分片和环形 ReduceScatter 的逻辑字节估算，两段权重驻留的联合方案可省 129,024 B/本地填充行。每卡每层新获取七个对端分片需 126 MiB，累计 1,024 行时两项相等。此处按同一代权重的复用时长判断。[真实尺寸、显存与字节条件](projection-owners.json)

## MoE 跨卡输入与复用

查 `--region prefill_expert_traffic_and_exits` 可复用 160 组 EP16 调用的跨 rank、物理卡和 DP 分派量边界，以及最晚退出和下一层就绪的时间差。416、816、817 行的跨 DP 输入分派总量区间宽度分别为下界的 2.87%、0.37%、0.73%。818 行的范围是 373,329–1,979,409 次；需要精确流量时优先补这一档。已用另外 454 组实际路由 ID 检查计算公式。真实带宽与应用层分派计数采用不同分母。[逐载体数据和推导](expert-traffic.json)

同负载的新诊断给出了 416、816、817、834 行的实际物理路由。用 `--region prefill_expert_natural_delivery` 查每种行数按 rank、卡和 DP 发布一次的输入量、五种跨专家驻留窗口和原负载上限下的有序返回字节。原始路由可在服务器重放。历史 818 行仍保留原区间。[实测输入与返回](expert-natural-delivery.json)

三张原生表共用相同的五组大尺寸专家路由。用 `--region expert_cross_card_input` 查输入已就位时可省的整算子时间，用 `--region expert_repeat_row_cache` 查计入首次写入和后续解包的真实重复行缓存，用 `--region expert_weight_placement` 查同卡双芯片或跨卡重排在 prefill 与 decode 上的配对耗时。两种重排均加速了五组 prefill，五组 decode 的延迟比中位数分别上升 4.09% 和 11.73%。用 `--region expert_dual_layout_capacity` 查原服务可用显存及按层容量筛查。[完整算子与显存对照](expert-native-and-placement.json)

同样的 cast 请求在原探针环境返回 ND（格式 2），而模型执行器开启内部格式。比较共享权重时须记录参与运算的实体格式、步长、槽位指针、权重及 scale 的所属专家。修正对照已逐 rank 核验 FRACTAL_NZ（格式 29）和 96 个地址偏移。用 `--region expert_NZ_conditional_latency` 查不同输入的实际整算子耗时，用 `--region expert_partial_weight_placement` 查每芯片每层移动 1、2、3 个专家的容量和负载，用 `--region expert_placement_model_service` 查询冻结服务结果。用 `--region expert_shape_guard_coverage` 查每轮所有真实行数和零命中轮，先决定精确形状守卫能覆盖多少次调用。用 `--region expert_sparse_joint_traffic` 可在同一组真实输入上同时查布局变化后的去重空间、有序返回字节和跨卡分派量，避免重复采集及重复计算收益。[专家权重共享和分支对照](expert-sparse-placement.json)

## 六路专家返回的成本

查 `--region expert_ordered_return_placement` 比较同一输入按源端、空闲对端和容量受限位置归约的跨卡字节与最忙卡收发量。查 `--region expert_ordered_return_depth` 判断保留原累加顺序且只允许一次跨卡时的流量上限。查 `--region expert_return_to_merge` 对齐三种输入行数的源端合并期限。更改布局、允许额外传输或移动后续读者均会改变适用条件。[参数、约束和源文件哈希](expert-ordered-return.json)

## 如何决定下一批补测

把缺口按物理组、后端和 kernel、阶段、shape/dtype/布局、字节口径、并发和冷热条件合并，记录它服务的候选与决定。若需付出的时间在所有可信情形下都超出可省预算，直接暂缓。若必须交付 B 字节、暴露时间最多 T 微秒，在这项传输必须串行完成的前提下，所需速率至少为 B / (1000 × T) GB/s。已有相同条件的时间样本优先使用。存在重叠时只对实际暴露段使用这个判断，并保留 rank 就绪与最早读者。

集中测量按需要决定的条件组合执行。保存输入、输出、原始样本、统计口径、环境与 Git 哈希；变更只使相关行失效。目前没有可量化的分析用时对照。
