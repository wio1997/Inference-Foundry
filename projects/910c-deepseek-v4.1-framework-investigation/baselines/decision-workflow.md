# 用共享证据加快算子优化判断

先按模型执行顺序判断模块价值，再查询同版本、同负载的公共成本。一次整理的结果应能回答多个候选，不能只留下必须重新阅读的大文件。

## 已经落实的复用

- 112个本地周期、83类算子导航、41组区域成本或频次表，统一进入 `atlas.json`。
- 16016条通信记录按组、消息大小、dtype、阶段划成28类；15792条已绑定native，224条保留未绑定状态。
- 成功环境、精确源码与缓存哈希、原生对照和失败变体保留引用。发生变化只失效对应条目，不全套重测。
- 本次接入问题直接复用16worker、128代际、3328次已保存的CP构建调用；没有新增profile或NPU诊断。

通信表是当前条件下的实际耗时表，包含等待与竞争。纯传输带宽、HBM/L2/UVA可达速率及通用调度曲线仍有缺口，不能标记为全部校准完成。

## 决策顺序

| 步骤 | 要回答的问题 | 可以停止的条件 |
|---|---|---|
| 真实命中 | 哪个分支、shape、阶段、rank实际执行，发生多少次？ | 未命中分支保留条件，不为它伪造当前收益 |
| 完整价值 | 整个可改写区域免费、其它工作不变时，最多能省多少？ | 连乐观预算也很小，则暂缓独立实现；共同producer或布局变换单独按联合范围计价 |
| 共用成本 | 必要计算、字节搬运、通信、同步和竞争已有何种同范围证据？ | 命中有效证据就直接引用，不重采、不反复读源码 |
| 决策敏感性 | 未知成本变好或变坏，是否会改变做/不做？ | 两端结论相同就不专门测；没有可信区间则保持未知 |
| 集中补证 | 哪一项测量能同时解决哪些候选的关键缺口？ | 按实际用例和资源族合并；不扫全shape、全算法组合 |
| 真实接入 | 全部调用中候选是否启用，为什么回退，输出是否一致？ | 启用或数值验收失败即停止，先保存明确原因，不进入计时 |
| 冻结对照 | 正确方案在同负载及前后参照下实际快多少？ | 完成冻结样本即裁决；不重抽样、不降低门槛追求正收益 |

本地周期、原生caller与完整C8服务是不同计价范围。跨卡/跨迭代或重叠区间不可相加为端到端收益；每个组合保留任务集合，去重后再计价。

## 这次需要承认并修正的低效

批量slot写入的第一次服务对照，先完成3条基线计时，随后candidate-0发现0条批量使用记录。原生26任务和理想调用序列的CPU检查，没有证明完整生产helper调用都符合选择条件；接入代码又没有保存拒绝序列。这让一次服务启动没有给出足够明确的诊断。

现有证据只证明模式已送达16worker、客户端输出相同且服务已恢复。不能称为批量数值通过，也不能称为性能无收益。已把后续接入验收放到任何计时之前：记录enable条件、全部标量调用签名、首次拒绝、待发布数量及flush结果。诊断有上限，超限明确记为证据不足；计时窗口不保留观察器。

后续完整记录已经定位原因：48个B4代际均为26次helper调用，第3/4次的ratio为1、compressed为True；没有出现此前怀疑的额外回退调用。原始数值代码在ratio1下不读取这个标志对应的分支，现已证明等价并修正守卫，原始参数仍保留作参照。

修正后的准入又发现缓存问题，在任何计时前停止并恢复服务。当前安装的Triton将函数起始行号纳入缓存键；在kernel前插入辅助函数使行号从34变成48。把辅助函数移到kernel后面恢复了旧键。11.15秒私有验证中，批量kernel从第一次调用起只允许缓存命中；两次重新绑定命中、零缺失，四种地址对齐的完整输出一致，7个旧缓存文件哈希不变。只改变行号可精确复现服务失败键。这是可复用的环境证据，不能仅凭kernel文本相同就宣布缓存可复用。参照helper走普通路径，未做整个进程的编译审计。

修正后的冻结C8现已完成：12case文本一致、16worker/2496完整银行比较通过；候选中位12.639457秒，比前后基线少3.392000%/2.215879%，全部候选快于全部参照。原服务恢复。旧部分样本没有混入，完成后不追加样本。

## 效率如何验收

记录复用命中数、实现前筛掉的低价值项、每次补测解决的决策数、重复取证和接入失败数。文档数量和代码阅读量不算优化进展。当前没有可支撑“分析速度提升若干倍”的测量，因此不报倍数。

完整优化覆盖与数值理论上限仍未完成。这里的共享成本和流程修正用于减少重复工作，不替代未分析分支与关键证据。

公共拓扑与取证优先级已整理为[topology.json](topology.json)和[material-gaps.json](material-gaps.json)。当前只读查询不停止服务、不加载模型；先验收通信参数口径，再决定统一计价，不按模块重复测同一物理连接。

通信校准现已完成。默认后端曾因缺少服务的AIV和缓冲配置而出现显著时差。后续匹配涉及通信的候选时，需同时查参数、运行模式和实际kernel。终端mHC两次AllGather的实际局部占比最高0.074%，已暂缓独立实现。[校准数据](collective-calibration.json)

本地分析仓库可用 `python3 tools/query_global_cost.py --module M06` 查模块需要的成本族、尚缺的证据和已保存的结果。用 `--comm allGather --count 387840 --dp 1` 可同时查模型记录、同条件回放、耗时及有效 GB/s。

按模块先查[共享单位成本速查](unit-costs.md)。其中的 F21 小 M 路径已完成输入预置对照，大 M 的两种分支使用各自的成本分母。

同一批首 token 原生记录现可同时回答矩阵工作量、专家权重与拷贝成本。按字节、shape 和 kernel 复用 26 种 TensorMove 签名。已按 8 个历史请求给注意力输出交接定价，单独消除间隙和后续拷贝的乐观预算低于各自 TTFT 的 0.39%，暂缓单独实现。需要新数据的是会改变矩阵吞吐或通信读者布局的联合改写。[分载体与分请求核算](eager-resources-and-copies.json)

## 本轮如何合并三种投影判断

一套 TP8 启动、一组真实权重和三种实际消息大小，同时检验三种权重放置方式。把输入、原始 OA、原始 OB 部分和原生归约分别比对，能直接定位 818 行的差异来自重算的 OB 部分。416 行的两个物化 OB 变体全部配对变慢，818 行在计时前被数值验收筛掉。仅提前 OA 的局部耗时通过，再用已归档的八请求时间线核价。[原生比较和逐请求结果](projection-owner-native.json)

值得修正的顺序是把“慢请求到底会命中几次”提前到服务接入之前。对两种已验证行数，历史最慢请求在同 DP 上的条件预算只有 6.47–8.89 ms。先用已有数据合并核算剩余真实大尺寸及跨 DP 等待，决定是否值得接入。一次小 shape 转换若是纯 view，按零物化字节处理；若有真实拷贝，按命中次数和区间并集计价，有共同 producer 的路径再按联合范围算一次。缺少调用栈、地址或时序字段时保留未知。

同一资源问题用一次全局查询定位。运行 `python3 tools/query_global_cost.py --shared` 可读取四类成本、其原计划受益模块、已核验来源及停止条件。把通信 API、实际内核、大小、dtype、拓扑、并发和 eager/图执行都对上，再复用对应行。对一轮最多能省的暴露时间先扣除必要的新工作；只有仍能改变请求指标或模块排序的未知量进入下一批测量。
