## 一个请求集合可以回答哪些问题

对同样八个请求重新计算每种替代后的 P90。16 项中，7 项在各自全部已列场景低于 14.919 ms，5 项要先分清同步或释放条件，4 项仍有继续核验的空间。例如，两次末端 TP8 收集取 16 rank 的宽松包络也只有 6.047 ms。扩大到最终 FFN 与实际输出投影时，两种跨卡假设分别有 24.429 和 35.169 ms 空间。下一次只需查哪些行仍有读者，就能决定值不值得改最终 FFN。相邻和嵌套范围分别算，跨阶段移动一旦改变到达时间，就重新选择适用范围。[全部分项与假设](request-region-screen.json) · [逐卡与逐请求证据](terminal-draft-request-costs.json)

在本报告目录里，以下命令直接读取已经发布的 JSON。第一条列出各项预算，第二条取 416 行 prefill 中 DP0 的 TP8 AllGather，保留字节、调用数和最慢 rank 的统计量。

```sh
jq -r '.rows[] | [.module, .region, .screen, (.P90_upper_ms_by_scenario | tojson)] | @tsv' baselines/request-region-screen.json
jq '.entries[] | select(.M == 416 and .DP == 0 and .operator == "hcom_allGather_") | {count, calls, per_rank_input_bytes, per_rank_output_bytes, max_rank_us, logical_payload_GB_s_at_median}' baselines/eager-tp8.json
```

## 本次反思

此前把“落盘”当成了“可复用”：许多频次、区间、拓扑与失败结果已经保存，但每个候选还要重新寻找、解释和判断适用范围。另一方面，先做接口/局部正确性再估算完整收益，使一些成本过小的候选进入了实验；M06 的接入失败也暴露出环境准备没有充分复用。这些是流程问题，不应归因于代码量大。

先整理已有摘要，形成 [成本数据表](atlas.json)；随后只读补齐已有数据库的通信字段和缺失相邻区间，不重新采集 profile、不启动 NPU。表内区分当前 CP+slot+CPUplan、历史 clean profile、历史 Engram 和合成原生对照。已有算子频次表只是入口；其汇总包含不同 shape、target/draft 与准备阶段，不能冒充每个 shape 的微基准。

### 一批证据如何减少下一次实验

在 M06，五组真实 prefill 路由现在可重复用于三个问题：跨卡输入已就位时整算子最多暴露多少时间、只缓存真正重复行的净耗时、改变专家位置对最忙 rank 的影响。相同的路由、专家计数和物理拓扑只整理一次。把小 M 的 decode 同时放进布局对照，筛出了“prefill 变快、decode 变慢”的分支，再查既有原服务显存快照，就能排除固定 KV 容量下的全层双布局。三次原生对照复用旧路由，该轮额外模型 C8 次数为零。三次独立还原服务都产生了模型重载；以后可在同一个已授权窗口内批跑兼容对照，保留各自的独立基线、恢复条件和产物哈希。分析工时还没有可比较的计时基准。[五个大 M、五个小 M 与容量](expert-native-and-placement.json)

优先级按真实调用次数、可移出关键路径的时间和共享读者确定。低频 shape 转换一旦在完整相关范围内连乐观预算也很小，就在所属模块登记范围和重新评估条件。对有价值且证据不足的区域，先查通信、内存、计算、调度四类共享记录，把相同拓扑、阶段、消息大小、并发和布局的缺口合并成一次测量。每条记录同时给出适用条件、误差或样本范围、依赖的源码与数据版本；后续只重测发生变化的条件。

本轮的格式纠错补充了一项复用条件。对 910C 的权重布局，要记录设备上返回的 format ID、实际字节、指针偏移与形状。逐卡确认原布局和每个专家视图确实为格式 29 后，按真实输入尺寸的守卫重新计价。仅保存请求的 cast 参数不足以区分 ND 和 FRACTAL_NZ。[格式、容量与服务验证](expert-sparse-placement.json)

另一个可以直接计数的浪费出现在模型对照。第一次在 16 个 rank 准备好权重才发现包装函数漏接框架的关键字参数。从提交到验证原服务恢复用了 11 分 30 秒，取得有效 C8 样本 0 个。已把相同调用方式加入加载前检查。与之对应，160 个已留存的层路由可以直接在 CPU 上同时重算两种布局的输入去重和有序返回字节。原布局和候选布局的返回归约分别能节省 6.491 GB 和 5.648 GB 逻辑跨卡流量，这次定价新增路由采集 0 次。后续更换布局时复用同一输入重新算所有受影响的成本。[实测与失败记录](expert-sparse-placement.json)

对按形状选择的优化，先用每轮请求的全部实际输入行数计算命中和回退，再评估单位成本。相同的 C8 输入在调度后产生过整轮零命中；在一个路由样本上把 40 层和 16 个 rank 测全，只增加了该样本的证据，不能折算成更多独立请求。服务试验若估算自然流量收益，应预先纳入零命中轮次；若估算单独命中分支的收益，要另行记录其出现频次。这两个问题的分母要在启动模型前确定。[逐轮命中记录](expert-sparse-placement.json)

通信的核心问题是“这类工作在这些条件下要多久”，不是一个通用 GB/s。分别保存消息字节口径、组内角色、算法、延迟、有效吞吐、等待和并发状态；无法分离的字段保持未知。用经验曲线预测可达性能，用经过论证的物理容量约束理论界，两者分开。

## 每个候选只经过一次的决策流程

1. **命中与频次**：确定真实分支、shape、读者、阶段与版本；查已有索引，缺失字段不表示独立。
2. **整体价值筛查**：绑定完整改写区域及共同受益项，对任务区间去重。只在外部工作固定的假设下，把全部替代工作免费作为乐观筛查；零成本仍太小的独立变换直接暂缓。低频只计实际发生次数。
3. **共享成本估算**：对仍有价值的方案，查询适用曲线，估算必要计算、搬运、通信、同步、资源竞争与关键路径。不同层/卡/周期的耗时不相加当收益。
4. **看结论是否依赖未知**：在合理参数区间两端，若优先级都不变，无需专门补测；若会从做变成不做，才登记一个共享缺口及其全部受益模块。资料不足以设定区间则标记未知，不能虚构界。
5. **集中补证与验收**：同一环境窗口可完成多种有用途的基础测量，但每个 case 保留独立合同。正确性/机制/原生收益/服务收益分层；旧失败变体不追加样本或调低门槛。

1% 仍只是原有工作排序参考；冻结实验的验收门槛保持原值。相邻多个低价值动作若由同一 producer、布局或所有权改写共同消除，要对联合区域重新定价，不能按单项小就漏掉组合。尚未执行的合法分支继续保留覆盖记录。

## 一次性准备的边界

一次性完成当前版本、实际工作负载需要的公共成本项，不做全设备、全 shape、全算法笛卡尔积扫描。先复用已有 profile 的正向命中和大小范围，将新测量收敛到实际小消息、拐点、大消息或两端代表；不能凭微基准给未观测负载全量背书。

具体缺口、准入条件、输出与停止规则见 [集中补测清单](calibration-plan.json)。通信消息/耗时字段已补齐；一个固定caller批量对照已完成，通用物理资源曲线仍未校准，不能算成已测带宽。M00–M11当前范围的一轮顺序价值筛查已记录，继续联合准备与发布；全局基础项准备不成为暂停全部模块的前置关卡。

## 查询与失效规则

分析库中运行 `python3 tools/query_global_cost.py --op hcom_` 查询通信导航，或 `--region current_ffn_post` 查询区域表。查询校验原文件 SHA256，条目过期则重建受影响视图。重建命令为 `python3 tools/build_global_cost_baseline.py`，不访问服务器。

具体通信成本可运行 `python3 tools/query_global_cost.py --comm allGather --count 15360 --dp 0 --phase target_graph`，加 `--details` 查看逐rank分布。返回实际count、dtype、组、阶段、次数与耗时；`reported_count_bytes`仅表示count乘以元素字节数。校准项另列每rank的逻辑输入和输出字节，等分AllToAll的count按每个对端解释。物理链路流量和纯传输带宽仍未知。dtype按安装头文件的HcclDataType枚举解码，不能查同编号的字符串表。重建该表运行 `python3 tools/build_communication_cost_catalog.py`，复用本地缓存，不访问服务器。

复用键包括硬件/拓扑、软件及内核版本、phase、shape/dtype/布局、通信组、消息字节口径、图/流、缓存与权重代际、并发条件。变更只使相关条目失效；迁移服务器或改变 CANN 后不能直接继承性能数字。

后续记录四项效率指标：重复取证次数、已绑定范围内低价值项在实现前的淘汰情况、每次补测实际改变的决策、实验接入失败次数。尚未做前后统计，当前不能声称分析速度已提升多少倍。
