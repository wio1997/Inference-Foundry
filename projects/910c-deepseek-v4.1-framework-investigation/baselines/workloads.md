# 不同推理负载下，哪些融合值得继续

171 已完成对照的负载是 8 个并发请求，每个请求输入 32,768、输出 1,024 个 token，前缀命中约 90%。抽查方式为扫描冻结版本的 44 个 C8 结果文件，其中 11 个含符合口径的完整客户端记录。113 组共 904 条请求观测的输入、输出和每组命中计数完全相同。反复测同一配置能核对波动和改写效果，不能据此增加场景覆盖。本机已测的收益和已暂缓的候选都保留这一条件。下面用公开服务中的真实请求校正筛选顺序。171 的自然流量占比和跨场景加速仍未知。下文给出按这些长度复现的 171 实际命中记录。[本机对照](ep16-batched-slot-c8.json) · [原始分布与计算口径](representative-workloads.json)

## 171 的普通请求已实测

使用服务器已有的 Python 标准库文档和代码构造提示词，按公开轨迹中的真实配对固定输入和输出长度。独立对话为 1,019 入、126 出，独立代码回复为 1,464 入、13 出。混合阶段在对话第一次产生文本后送入另一条请求。两个原服务世代和中间的观测世代各执行六份相同输入。长度覆盖有直接证据，外部请求的原文、专家路由、真实流量占比和繁忙程度仍未知。[请求与计数](ordinary-guards.json)

### 复用相同前缀时，缓存命中能否传到用户

自然调度下，原服务中的两条后续请求都到了另一组 DP，缓存命中为零。随后在恢复的原服务上做四对对照，每种长度都轮流用 DP0、DP1 建立前缀，并交换先冷后热与先热后冷的顺序。同一对内向两组 DP 发完全相同的输入。单次对话回原组可多命中 **896/1,019** 个 token，代码回复可多命中 **1,408/1,464** 个。四对首 token 有两对更快、两对更慢，四对完整输出有一对相同。当前可复用的是节省的预填充 token 数；延迟改善还需在相同输出、自然排队和实际 KV 压力下验证。[四对逐次结果](prefix-routing.json)

冻结 32K C8 有不同的上限。用 171 当前 tokenizer 核对 8 份完整输入和两份 29,696-token 种子，每条请求同时匹配两个种子和其余七条完整输入。即使两组 DP 共享全部这些前缀，按 128-token 块计也最多命中 **235,904** 个，与已测结果相同。仅靠换 DP 不能再增加这批请求的命中。改变排队、计算与通信排程要另计。[逐请求前缀上限](c8-prefix-ceiling.json)

两份公开轨迹的所有请求在全部输出位置的逻辑上下文都落在 16,384 以内。若以 512 个未压缩逻辑位置为界，符合的输出位置分别占对话的 19.6% 和代码的 20.7%。实际 kernel 的 K 还受缓存压缩、CP 和批处理影响；上述比例只用来选择下一次要复核的区间。[QLI 覆盖与边界](short-indexer.json)

## 怎样改变候选排序

- 如果某个分支只在用户已经收到 32 个输出 token 之后才启动，在上述代码样本中，最多可触及 17.8% 的请求和 41.0% 的输出 token。对话样本中分别为 97.0% 和 85.0%。相同的生成后段融合，对短回复延迟和对话吞吐有很不同的潜在价值。投机解码实际用多少个设备迭代，需要从运行记录绑定。[不同输出位置的覆盖曲线](representative-workloads.json)
- 对 EP16 的 800–834 行布局，所看的是实际 eager prefill 批行数。优化配置的三轮候选计时里，14 个自然批有 4 个命中。用户提示词长度无法推出每次 kernel 的行数。其它负载先统计实际 guard 命中、各批在排队和通信中所占的时间，再计入每 rank 约 2.64 GiB 的附加常驻开销和 KV 影响。该布局当前属于长输入 C8 的实测项。[逐轮计时、容量和输出核对](ep16-batched-slot-c8.json)
- 批量 slot 写入与 QLI 共用转换都要看真实 decode 迭代、选中的图和共同读者。短对话优先计入首 token 前的工作；持续到达的混合请求则按 prefill 和 decode 交错时的排队、流式延迟和吞吐重算。已测 26 项写入和选中层数都要在目标场景实际出现。[slot 与 QLI 的同基线增量](qli-batched-slot-c8.json)
- DSpark 和 mHC 已裁决的单独方案保留对应阶段、shape、依赖与计时口径。换成短输入或缓存未命中时，先按该负载重算整个模块的可省时间。只有影响实质收益才需要细查。集群到达日志也需绑定每个实例的调度结果，才能得出每卡自然并发和算子行数。[DSpark 的整组预算](draft-fixed-expert.json) · [mHC 的条件成本](mhc-iteration-cost.json)

已有的本机调用、缓存与回放计数按请求阶段复用。下一步只给尚有可改工作的短上下文索引生成与消费联合路径定价。用户侧低并发、持续混合负载、缓存冷暖按实际观测标注。覆盖不足先保留“待验证”；只有能改变排序的缺口才安排新采集。正常路径必须计入回退、初始化、KV 占用和资源竞争。单次异常保留为正确性或条件边界，不进入日常加速的平均值。
