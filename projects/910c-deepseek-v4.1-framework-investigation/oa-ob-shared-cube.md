# Attention 输出的 OA→OB 融合能省多少

固定 171 的 W8A8 模型、TP8 与原权重分片。OA、OB 这两次输出投影实际走 BF16。保留 OA 输出的 BF16 舍入、OB 每个输出的 K 维归约和原 ReduceScatter。**同核完成整组行的方案在 24 行 decode 图上降级。较大 prefill 保留首 token 条件机会。** 以下时延是重算已有 profile 的结果。[请求估算及参数](baselines/oa-ob-shared-cube.json)

## 为什么不能直接把两个矩阵乘的时间叠起来

冻结 prefill 的 3,328、3,352、6,528、6,536、6,544 行都能对应到已有 171 主机 tiling 记录。OA 使用 24 个 Cube 核，单块覆盖 128 行、256 个输出通道。OB 的一个输出点要用同一行全部 1,024 个通道。要省下 OA 中间面的写回，需要说明四块怎样交给 OB。现有 CANN 9.2 支持在一个 AIC 内将 L0C 的 FP32 结果舍入成 BF16 后送入其 L1，跨核交付还需要另行计价。[本机 tiling、Fixpipe 源码指纹与约束](baselines/oa-ob-shared-cube.json)

让一个核完成同一行块的两次投影时，两段 MAC 使用同一个 Cube。若各核的行工作量成比例，同一个负载最大的核也决定两段的算术下限；把两段接起来不会减少这些 MAC 周期。能缩短的部分包括全局中间写读、一次提交，以及不同执行单元之间可以重叠的等待或搬运。归档的 4,424 对 OA/OB 有 4,367 对具备两侧 PMU 计数。6,528 行的历史样本中，两核函数耗时之和中位为 462.22 µs，按整卡 24 核及 1.8 GHz 折算，MAC 和 MTE2 的计数分别约为 353.72 和 382.43 µs。两种流水可重叠，因此按各自约束取最大值。[逐形状计数、缺失数量与频率口径](baselines/oa-ob-shared-cube.json)

## 一个可以直接筛掉形状的下限

在一个核每次完成整组行、权重作为右矩阵经 L1→L0B 的方案中，每组行需 8 MiB 的 OA 权重和 10 MiB 的 OB 权重。即使每次已有 64 KiB 权重在 L0B，按每核每周期最多 128 字节、归档参考频率 1.8 GHz，读完一组权重也至少需 **81.64 µs**。24 行图上原生两次投影连同间隙的中位为 **67.00 µs**，全部 2,560 对都早于这个下限。多行块共用一遍权重、另一条操作数通路、跨核传递或复制计算要按自己的成本判断。[Ascend 2201 架构规格](https://asc.gitcode.com/guide/programming_guide/advanced_programming/hardware_implementation/architecture_spec/npu_arch_2201.html) · [本机样本与计算](baselines/oa-ob-shared-cube.json)

对非空的大 prefill，先让每个形状选择自己的行块。以下“乐观上限”还允许逐次选择原实现、免除全部额外开销，并把投影时间压到计算与上述权重搬运下限两者中较大的一项。首 token P90 的 1% 对应 14.92 ms。

| 每块行数 | 冻结 C8 首 token P90 的乐观缩短量 | 处置 |
|---:|---:|---|
| 16 / 32 | 均为 0 ms | 这一交付方式在冻结 C8 退出 |
| 48 | 4.25–6.77 ms | 单独降级 |
| 64 | 13.66–16.27 ms | 对各卡到达时差敏感 |
| 80 / 96 | 15.34–17.95 / 18.54–21.14 ms | 条件保留 |
| 112 / 128 | 9.73–12.15 / 2.54–4.72 ms | 固定高度在整组 C8 降级；较少行块能使最后一批核利用率降低 |

各形状分别取行块时，3,328 和 3,352 行的参考下限最低点是 144 行；6,528–6,544 行有 96 和 144 行两个最低点。这些值只描述理想几何。剩余 L1 工作区、输入加载、实际吞吐和数值合同仍会限制收益。[各形状的 Cube 与 L0B 下限](baselines/oa-ob-shared-cube.json)

## 折算到请求

保留 24 行原图，按原有效行和 DP 到达范围逐层折算，重新取八个请求的 P90。固定各阶段原有计算后，在连续搬运估价下，同核候选要让首 token 达到 1%，即使按参考资源上限估计，也约需隐藏剩余较短投影的 **26.4%–28.8%**。仅凭两个投影相邻，无法确认这项重叠可实现。

| 大 prefill 情景 | 冻结首 token P90 预计缩短 | 冻结整批预计缩短 |
|---|---:|---:|
| 较短阶段可隐藏一半，MAC 和权重搬运都达参考上限的 80% | 8.20–10.80 ms（0.55%–0.72%） | 0.04%–0.06% |
| 同样重叠，两种资源都达 90% | 15.34–17.94 ms（1.03%–1.20%） | 0.08%–0.10% |
| 同样重叠，均按参考上限 | 20.30–21.49 ms（1.36%–1.44%） | 0.11%–0.12% |

在这三个情景中普通六个请求的响应降幅最高约 0.42%。令两种资源的有效速率按相同系数变化，半重叠情景下，冻结首 token 要过 1%，有利和保守到达界分别需要约 85.5% 和 89.3%。另外按旧 MAC 和 MTE2 的历史计数均保留、仍允许隐藏较短阶段的一半，加入本地行块约束后，冻结首 token 估算省 16.77–19.36 ms。历史计数来自另一次同机采集，对缺少相同形状的点按行数插值。以上假设均未经过融合内核服务实测。[逐请求原始数字、归约、速率和分支假设](baselines/oa-ob-shared-cube.json)

## 接收端逆旋转

把 SparseFlashMla 输出后的逆旋转推到 AllToAll 接收端，作为 OA 输入的一部分。保持发送补零、转置、通信和两次投影。每个接收端都必须拿到与原 token/head 配对的 cos/sin，只旋转有效行，在投影前恢复原 BF16 值。即使让原旋转任务免费消失并免去接收端的全部新增成本，冻结首 token P90 估算也只省 **4.84–5.33 ms**，整批省 **39.82–42.27 ms**，普通六请求的响应最高约 **0.28%**。这个改写单独降级，发送端融合也只能计一次相同的旋转。[实际发送者、请求窗口与估算](baselines/receiver-inverse-rope.json)
