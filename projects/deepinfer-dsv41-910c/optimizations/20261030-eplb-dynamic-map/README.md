# 专家映射动态长度候选

静态 16 副本融合映射在完整模型首轮产生明显 TTFT 退化。检查发现该内核按输入元素数编译特化，首轮请求附近出现大量新的编译缓存文件；时间相关性支持编译可能参与退化，但不能证明全部耗时来源。

独立候选只将输入元素数 N 改为禁止特化的运行时参数，保持副本选择公式、权重、路由、布局和调用方式。原静态映射与融合映射均保留。

## 完整模型对照

三个候选均使用静态 16 副本布局及同一 32K 输入、1K 输出、并发 8 的请求，服务依次启动，各测两轮。所有轮次实际 KV 命中 235,904 / 262,144，16 rank 路径检查通过；每轮 8 条完整输出逐 token 一致。

| --- | ---: | ---: | ---: |
| 原始映射 | 630.4 / 587.7 | 12.4 / 12.3 | 607.213 / 604.793 |

与静态长度融合版相比，动态长度消除了本次首轮大幅延迟，但第二轮 TTFT 高 12.4 ms、TPOT 高 0.1 ms、吞吐低 0.61%。与原始映射相比，动态长度两轮 TTFT 分别低 25.6、30.7 ms，吞吐分别高约 0.022%、0.018%；不同服务重启及短样本限制了归因。动态候选暂不采纳，仍保留原实现和回退方式。上述对照均包含静态副本布局，不能当作相对于无副本保留版的单因素收益，也不代表在线 EPLB 已适配。

动态候选的 Triton 缓存共有 16 条融合内核元数据，在首次请求文件时间至该时间加首 token 相对耗时的代理窗口内新增 0 条；静态长度融合版同口径为 47 条。文件时间与 worker 相对计时起点不同，结果支持编译特化参与延迟，但不足以证明其他开销不存在。
