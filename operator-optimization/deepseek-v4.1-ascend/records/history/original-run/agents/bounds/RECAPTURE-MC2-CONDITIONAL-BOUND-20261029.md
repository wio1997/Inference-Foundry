# MC2 两次 GMM 的条件理论界

本记录为 EP8、目标层 14 的已观察 `DispatchFFNCombine` 形状建立**条件模型**：输入 [1023,5120]、两个 INT8 权重导出形状 [24,5120,4608] 与 [24,2304,5120]、top-k 形状 [1023,6]，输出含 INT32[24]。它们不证明当次二进制、路由有效行数或真实计算路径。这里没有测设备，没有修改服务。

## 一、本地专家有效行数

令本 EP rank 的第 `i` 个本地专家的、从全部 EP 来源累加后的路由行计数为 `c_i ≥ 0`，按实现的专家顺序编号，且本次容量为 `C = maxOutputSize`。若确实绑定到 [已审计的 custom INT8 实现](../diagnosis/RECAPTURE-MC2-EXPERT-COUNT-20261029.md)，其各专家实际供 GMM 的逻辑行数可以按下式递推：

`r_0 = min(c_0, C)`；

`r_i = min(c_i, max(0, C - sum_{j<i} r_j))`，`R = sum_i r_i`。

这是固定源码 GMM1/GMM2 对每个 expert 使用 `currentM`、并按之前专家累计值和容量截断的条件表达；计数输出是截断前汇总。每个本地专家可能收到多个来源 rank 的行，不能拿 EP8 的 1,023 行、1,023×6 或平均分配来代替 `R`。目前无该次逐专家 `c_i`、`C` 和源码/二进制绑定，**R 未知**；亦不能假定 24 个专家各不为空，或将本模型直接当作历史实际指令计数。

## 二、固定传统稠密执行的工作账

附加以下完整条件：两次 GMM 对同一批经过上述裁剪的 `R` 行，按每专家执行普通稠密点积，GMM1 是 INT8×INT8 的 5120→4608，GMM2 是 INT8×INT8 的 2304→5120；每个输出元素按完整 K 个独立乘加计数。gate/up 的 4608 经激活组合为 2304 后输入 GMM2；量化、激活、读写、路由和通信不计入此两项工作账。

| 项目 | 每条专家行的逻辑 MAC |
|---|---:|
| GMM1：5120 × 4608 | 23,592,960 |
| GMM2：2304 × 5120 | 11,796,480 |
| 两次合计 | **35,389,440** |

由输出元素数乘每项点积长度，固定稠密工作账为 **`W_dense = 35,389,440 × R MAC`**。若明确采用一个 MAC 记作一次乘法加一次加法的计数约定，等价于 `70,778,880 × R INT8 算术 ops`；这是计数口径，不是声称每个 MAC 是两条指令，亦不是 FP FLOPS。

该公式仅在两个 GMM 有同一个 `R`、完整矩阵与所述精度契约时成立；若实际两阶段分别有 `R1、R2`，应使用 `23,592,960 R1 + 11,796,480 R2`。形状允许此模型，并未证明现有执行一定满足这些前提。

## 三、限定实现域的时间下界和吞吐上界

在进一步证明上述 `W_dense` 在选定同一个算子计时窗口内确实全部由所限定的传统稠密 MAC 路径执行、且 `P_max > 0` 是这台设备在该窗口中**所有允许相关执行资源同时可用时不可超越的 INT8 MAC 总速率上限**时：

`T_compute ≥ 35,389,440 × R / P_max` 秒；

等价地，对于 `R > 0`，`R / T_compute ≤ P_max / 35,389,440` 专家行/秒。

如果比较完整 MC2 任务 elapsed，还须证明该工作完全落在同一任务窗口；通信、访存、调度可与计算重叠，因此该界不把它们的时间直接相加。若把该模型用作推理 token/s 上界，还必须另有已证明的 token 到实际专家行与多个层之间的对应，不能将专家行/s直接称为输出 TPS。此处 `R`、`P_max` 以及计时绑定均 unknown，不能给数值时间界、算子效率或与实测的性能差距。

**该界不是对所有等价算法的普适必要下界。** 若允许利用固定权重或输入预计算、跳过可证明为零的运算、特殊权重结构、算法重排、跨算子融合或其他实现，原始逐项传统乘加次数不一定是不可避免工作。要升格为更广实现域的硬下界，必须对允许的输入、精度/误差、权重状态、复用缓存、预处理及每种执行资源分别证明必要工作和容量；不能用该传统工作账冒充普适证明。若其余模块并行争用同一设备资源，只能在真实总硬容量下统一记账；不能先假定各自均独占满速，再将独占时间当普适事实。

## 四、8,180 × 6：只在证明条件后的跨 EP 示例

若且仅若以下条件全部被实际证据证明：

1. 某一个与该层对应的 EP 组中，调度器报告的 8,180 token 恰好对应该层的 8,180 条互不重复的有效路由输入；不是仅仅形状或调度 digest 相似。
2. 每条有效输入恰好产生 6 个实际专家分配；不存在 padding、无效 mask、丢弃、复制、额外/缺失分配或其他计数变化。
3. 这些分配恰好各由 EP 组内一个被统计的专家处理一次；所有 rank 的专家计数汇总可绑定同一次调用，且没有容量裁剪，GMM 两阶段均处理相同行。
4. 上节每专家的权重维度、计算精度与完整传统稠密执行条件对整个 EP 组均成立，且所计工作覆盖同一个目标层窗口。

那么，**整个该 EP 组**的 `sum_ranks R_rank = 8180 × 6 = 49,080` 专家行，对应两次 GMM 的传统逻辑工作账 `49,080 × 35,389,440 = 1,736,913,715,200 MAC`（按 2 ops/MAC 记为 3,473,827,430,400 ops）。若另证该组所有允许相关计算资源合计硬上限为 `P_EP,max` MAC/s，则对应同一跨 rank 时间窗有条件界 `T ≥ 1,736,913,715,200 / P_EP,max`。

这些条件**尚未证实**；这是可证伪的算术示例，不是本次实际工作量。例：存在一个 padding/无效 token、某 token 不满 6 个有效路由、专家容量发生裁剪、调度 token 被复制到多个行，或 8,180 不等于该层有效输入时，49,080 即不成立。即便组总数成立，专家负载不均仍使单卡 `R` 未知；跨 rank 的时间窗与总体容量也不能自动由单卡 trace 相加或假定时钟同步。

## 六、短时间窗的速率和在途工作边界补充

第三节的无信用式只有在 `P_max` 对同一指定窗口的每个前缀均满足 `W_completed(t) ≤ P_max × t`，或以等价方式证明初态和计数口径没有突发时成立；这里 `W_completed(t)` 指计入本窗口的上述传统 MAC 完成量。仅证明长期平均峰值或稳态发射速率不自动足够。此前第三节已要求窗口总速率硬上限，但没有显式说明这个前缀和初态条件；满足该条件时原式成立。

更一般地，若对本窗口任意 `t ≥ 0`，可以证明 `W_completed(t) ≤ b + P_max × t`，其中 `b ≥ 0` 按同一 MAC 口径覆盖窗口初态和突发，包括之前已发射但仍在途且本窗口完成的工作量；而且窗口结束前至少必须完成 `W_min = 35,389,440 R` 个本窗口计数的传统 MAC，则：

`T ≥ max(0, 35,389,440 R − b) / P_max`。

这仍以实际 R、维度、算法域、任务与窗口绑定、数值契约及证明出的 b 和 P_max 为前提。若把窗口开始之前已完成的工作算作 W_min，就不满足这里的计数条件，不能靠随意选择 b 修补。b 也可能包含计数边界的离散完成或多条并行流水初态，不能未经证明将其设为 0。此公式不意味着历史实例实际存在预先在途 MAC。

反例（抽象流水线而非 169 测量）：稳态每秒最多开始 1 个操作，某操作在窗口之前已开始，且在窗口开始后 0.01 秒完成；如果本窗口只需这个操作的完成，则 `W=1`、`T=0.01 s`，把稳态发射率直接代入 `W/P=1 s` 会得到错误结论。取能够覆盖该初态的 `b=1`，更一般式给出 0。可在 CPU 复算：`python3 -c 'W,P,T,b=1,1,0.01,1; print(T,W/P,max(0,W-b)/P)'`。这不声明 910C 的发射率、延迟或初态。

类似地，归约深度界 `D × δ_F` 需有完整长度为 D 的必要依赖路径从窗口起点后开始且结果在窗口内完成；若部分中间结果已算出或在途，要对初态进行修正，而不是把完整深度强加给所选短窗。相关受限纯 max DAG 及其它假设见 [归约依赖界](mc2-reduction-dependency-bound-20261029.md)。

## 七、面向瓶颈排查的工程理想模型（既有数据、非硬件性能证书）

这里按用户要求建立可用于分析的理想参考：假定对应已保存的 custom INT8 两阶段 GMM 路径，采用当前观察到的输入/权重维度，允许路由、数据传输和计算按块流水；它是工程比较，不声称实际已能达到，亦不把名义容量当物理硬上限。样本为同一 `1b826883…` 摘要的 EP8 第 14、39 层 `DispatchFFNCombine`，各自绑定到所选 scope 和设备任务；profile 中 EP8 两任务为 **160365.956 µs**、**8290.414 µs**。这两个值受采样影响，也不保证两层的有效专家行、路由、权重值和内部阶段相同。

**计算账。** 记本卡收到且在裁剪后真正进入两次 GMM 的有效专家行数为 `R`。假设每行完整进行 `5120→4608` 和 `2304→5120` 的直接 INT8 稠密乘加，则工作 `W=35,389,440×R MAC`。沿用已有 profiler 元数据及昇腾估算公式，假设本逻辑设备 24 个 Cube、1.8 GHz、每核每周期 8192 INT8 MAC，其名义合计 `P_nom=353.8944 TMAC/s`，可写计算段**理想参考**

`T_compute_nominal = W/P_nom = 0.1 × R µs`。

系数来自模型维度和上述名义容量；有效行、物理指令、频率和该公式是否覆盖所有计算资源未绑定。两阶段如实际行数不同，应改为 `(23,592,960 R1 + 11,796,480 R2)/P_nom`。不能拿输入形状的 1023 行直接当 `R`：路由可以接收其他 rank 的行，受 mask、expert 分布及容量裁剪影响。若把 EP8 两个采样时长分别除以 `0.1 µs/行`，得到约 **1,603,660** 和 **82,904 名义专家行当量**；这仅表示“若全部时间被上述名义满速的两次计算填满，对应多少行”，不是这两次实际 R、测得计算量或真实利用率。由于 R 未采到，也不能从时长和比值反推计算占比、可用提速或单点瓶颈。

**访存账。** 按导出的权重逻辑尺寸和 INT8 一字节，单个本地专家的两组权重分别为 `5120×4608=23,592,960 B` 与 `2304×5120=11,796,480 B`；两者合计 **35,389,440 B**，24 组全量逻辑大小 **849,346,560 B**（不含 scale、offset 或额外 metadata）。这只是张量规模；`FRACTAL_NZ` 物理布局、切片/对齐、实际读取路径、活跃专家数、L2/HBM 已有驻留以及跨 token 复用未绑定。为估测可定义 `D_HBM` 为同一任务窗口真实经过所选 HBM 边界的权重、激活、输出与 metadata 总字节，用 `T_mem≈D_HBM/B_HBM,eff` 表示资源服务时间；`D_HBM` 和对应有效带宽 `B_HBM,eff` 均待测，不能将上述全量逻辑大小直接代入。分块越多可能增加重读，也可能通过片上驻留降低权重重复读取，应由实际 tile 和层内专家行分布确定。

**通信账。** 记 `R_remote` 为实际从其他 rank 输入到本卡专家的有效行数。若确认所选 custom 分支确将每行 5120 个激活量化为 INT8，并每行另携一个 FP32 scale，那么只按内容算，输入方向的逻辑载荷为 `R_remote×(5120+4) B`；实际分包、对齐、路由表、重复发送和其他通道均另计，不能等同链路字节。冻结实现中的 per-token scale 类型为 float，具体 task 的 binary、远端行数和链路仍未绑定。专家结果如何按实际 dtype 返回、combine 所需 metadata 和通信服务量也需单独计算，不能忽略返回或重复计算已共享数据。用 `D_link/B_link,eff` 表示同方向或具体 cut 的工程通信服务时间；`D_link`、拓扑和有效带宽未知。配置 TP=8 或 scheduler 8180 本身不证明 MC2 的组成员、实际专家行或同步窗口。

**分块与重叠。** 一个专家行块需先有相关路由与输入，再执行 GMM1、激活/量化、GMM2，并将该块结果按原顺序合并；不同块及不同专家可以在数据就绪且缓冲安全时流水。以 `T_dispatch/T_compute/T_mem/T_return` 表示同窗各资源总工作除以对应有效容量，理想稳定阶段可参考各资源的最大服务需求，并另考虑首块启动、块间依赖与最后一块排空。GMM1 与 GMM2 若共用同一 Cube 池，须先将两者 MAC **相加**计入 `T_compute`；不能把它们假设为两个都独占全部 Cube 的并行池。HBM 读写或通信若共用端口、链路或执行单元，同一资源工作也要合并；仅在资源独立且无依赖时才可重叠。各阶段有不等块、专家倾斜、非均匀资源争用或额外等待时，应以逐块依赖与资源账本替代简单最大值，不能把整个 profiler task 时长减去某个理想项就称为通信或等待。

**下一步要用同一调用补齐的参数。** 按优先级：① 同次每专家 count 与 capacity 得到 `R1/R2` 和专家倾斜；② 同任务 actual binary/tiling、per-token scale 和有效数据类型；③ 定向区分本地/远端输入、返回字节与实际组/路由；④ 同口径获取任务内块级计算、访存、通信和等待的活动或事件，并明确 profiler 开销。若样本本身不能提供这些字段，保留 unknown；不将两层同 shape 当同工作量，也不能以采样间隔或活动比例直接判定根因。离线算术复算：`python3 -c 'w=5120*4608+2304*5120; p=24*1800000000*8192; print(w,24*w,w/p*1e6,160365.956/(w/p*1e6),8290.414/(w/p*1e6))'`。无新 NPU 工作。

## 八、按专家行与活跃专家数变化的工程规模对照

下表是人工选定的 `R`、`A` 场景，**不是 169 任一采样的专家行数或路由分布**。每个场景限定一个 rank 的传统 INT8 两阶段路径，`R` 为两次 GMM 处理的专家行总数，`A` 为至少处理一行的本地专家数；不保证各专家分配均匀。设 `W_e=5120×4608+2304×5120=35,389,440`，则两次 GEMM 的逻辑量 `R×W_e MAC`，在“每个活跃专家的全部 INT8 权重恰从 HBM 读取一次、同任务后续行充分复用”的模型中，权重服务量 `A×W_e B`，每专家平均行数 `R/A`，只计权重读取时的逻辑强度是 `(R/A) MAC/B`。各值使用十进制 MB；scale、激活、输出与额外事务不在这个权重账里，已在缓存时甚至可以无需再次读取全部权重。`0.1R µs` 列仅使用上节 `353.8944 TMAC/s` 的名义满速模型，忽略 fill、tail、竞争与其他阶段，实际频率和有效资源未证。

| 假设 R | 假设 A | 行/活跃专家 R/A | 两次 GMM 逻辑量 GMAC | 名义纯计算 µs | 假设权重各读一次 MB | 只计权重强度 MAC/B |
|---:|---:|---:|---:|---:|---:|---:|
| 24 | 24 | 1 | 0.84935 | 2.4 | 849.34656 | 1 |
| 240 | 24 | 10 | 8.49347 | 24 | 849.34656 | 10 |
| 240 | 4 | 60 | 8.49347 | 24 | 141.55776 | 60 |
| 2400 | 24 | 100 | 84.93466 | 240 | 849.34656 | 100 |

在该简化账里，固定 R=240 而 A 从 24 变为 4，逻辑 MAC 不变，假定需首次读取的权重容量缩小 6 倍，强度增至 6 倍；固定 A=24 而增加 R 则权重能分摊到更多行。但真实专家并行度、拥塞和分块尾部随分布改变，少量专家并不必然更快；`R/A` 也遮蔽倾斜，例如同为 R=240、A=24，可以均匀 10 行，也可以一组 217 行、其余 23 组各 1 行。后者可能有不同的负载平衡与尾块；具体取决于调度与 kernel，不能把平均数直接替代逐专家计数。

**按块看权重复用。** 对第 e 个活跃专家 `r_e>0` 行，若每块最多 m 行，块数 `n_e=ceil(r_e/m)`；采用上述直接稠密算法，计算总量仍按 `R×W_e` 计，不包含硬件尾块填充。如果权重可跨该专家所有块复用，理想权重账为 `A×W_e`；如果相反地每个块都重新从所选 HBM 边界读取该专家完整权重，则该**特定简化实现**为 `W_e×sum_e ceil(r_e/m)`。两者仅是明确策略下的量纲参考，不保证实际落在这两者之间：缓存预驻留可能更少，重复加载、padding 和协议可能更多；真实实现也可按权重片分块并跨行共享，不必每次读完整专家权重。m、逐专家 `r_e`、已驻留权重以及读写带宽目前未知，不能把任一策略的逻辑量直接当实际时间。

**通信场景。** 仅为量化设计，额外假设每条专家行均来自远端、在发送前量化为 5120 个 INT8 值并携一个 FP32 scale，专家结果逐行以 BF16 5120 维发回原 rank，且两方向每条专家行恰发一次、不在通信中合并：dispatch 的逻辑载荷为 `R×5124 B`，返回为 `R×10240 B`。在上述四个 R 场景，对应 dispatch 为 **0.122976 / 1.22976 / 1.22976 / 12.2976 MB**，返回为 **0.24576 / 2.4576 / 2.4576 / 24.576 MB**。这是选定协议的 payload 账，不含路由、包头、padding、重传及额外状态；若同一行发给同一远端的多个专家可以共享输入、远端先合并输出、存在本地路由或已有副本，则不能机械乘 R。相反重复分片及协议开销可能增大物理流量。实际输入的量化类型、返回表示、`R_remote` 与各链路字节均未绑定本次任务，不能据此算带宽时间。

对分块流水，用各已知/测得资源的总服务量除有效容量，考察计算、HBM 和输入/返回链路的最大需求；同一资源的 GMM1/GMM2 工作、共用 HBM 的必要读写以及共享链路的通信先按口径合并，再考虑块间依赖、首块就绪和尾块排空。实际阶段和容量未取到时，本表只能说明 R、A、路由及复用如何改变工作，不能给真实 task 耗时分解、利用率或推断可实现提速。

## 九、按路由槽约束工作量：保留通信组条件

同一摘要 `1b826883…` 中，EP8–15 各 rank 的所选第 14、39 层任务都导出输入 `[1023,5120]`、路由槽 `[1023,6]`。这是各卡所选 scope 和形状一致，不能单凭摘要证明八条记录属于同一 collective 或这八卡是完整 EP 组。另一采集的 EP 组元数据曾显示 16 成员，也不能直接绑定本次。

如果进一步证明目标确实使用保存的 custom INT8 正常路由分支、同一调用的完整来源集合为 S、每源有效行至多物理输入行数且每个路由槽至多贡献一个待处理行、计数无溢出，那么令来源 s 的输入物理行数为 n_s、每行路由槽数为 k_s、本接收 rank 实际容量为 C：

`R <= min(C, sum_{s in S} n_s k_s)`。

该约束无需专家负载均匀，也不要求不同槽的专家 ID 唯一；mask、裁剪和其他无效项会使有效工作量降低。它只约束上述特定逻辑行数，不约束内核 padding、重复搬运、额外计算或总时延。源码依据：`dispatch_ffn_combine_kernel.hpp:365–397,402–431` 与 `moe_v2_fullload_quant_base.h:90–115,170–203`；历史二进制、来源集合、同次 replay、mask 和 C 尚未绑定，当前不能把任一数值当作该调用已证上限。

仅作条件算术例：若完整组确为 16 个来源、且各自同次输入均为 1023 行、6 槽，则一个接收 rank 的上述逻辑行数至多 98,208；沿用第七节 24 Cube/1.8 GHz/8192 MAC 的名义公式，在这种理想满速且忽略其他工作的计算账中，`0.1R` 至多 9.821 ms。它不是实际计算耗时的上限，更不是整个 MC2 的时延下限或可兑现提速。实际 16 来源是否都对应目标 collective 和形状未知，不能将 9.821 ms 和 160 ms 样本作为已匹配工作量的性能差距。
