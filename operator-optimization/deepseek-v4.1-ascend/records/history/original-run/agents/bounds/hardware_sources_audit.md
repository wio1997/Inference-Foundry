# 169 硬件能力证据审计：哪些可用，哪些不能用于严格上界

## 核间同步计数器与短窗信用的边界（2026-10-30）

[Ascend C 的 `asc_sync_block_arrive` 文档](https://asc.gitcode.com/api/SIMD-API/c_api/sync/inter_core_sync/asc_sync_block_arrive.html)列出 Atlas A2/A3 支持，并描述 2201 单个 AI Core 内 AIC 与全部 AIV 的一种同步模式：每个 `flag_id` 有独立的 4 位计数器，计数器最多连续累加至 15；匹配的 wait 检测并消费通知，arrive 不阻塞对应流水后续指令。AIC 等待全部 AIV 时，所有参与 AIV 完成 arrive 才让 AIC 对应计数器加一；不能把每个 AIV 的 arrive 直接当一次该计数器增量。文档同时列出不同核支持的流水类型，以及该接口的执行空间和标记匹配条件。

这是一条**接口特定的正确性上限**：仅当执行确实使用此同步协议、选定计数器、并符合文档约束时，可将该计数器的未消费通知数约束到 15。它不是每张卡或所有核总共最多 15 个在途任务，也不是最多 15 字节或 15 个 tile；每次通知与实际搬运字节、流水深度、其它 `flag_id`、其它同步机制之间没有在此证明的等价关系。即使已证此接口绑定，也不能单凭 15 填入 `Q(t)≤β+Bt` 的字节信用 β、推算通信带宽或全芯片吞吐上界。

这份页面自述来自 `asc-devkit` master 持续开发版，构建标识 `2fbb723e5f18` 且包含未提交修改，不能只凭提交号作为可复现的固定版本；它的历史版本与 169 当时安装的 CANN、具体 kernel 二进制及运行路径尚未匹配。该资料有助于检查允许 AIC/AIV 异步的候选调度和同步约束，但没有证明历史任务真的使用此接口、实际互相重叠，也没有提供 SKU 全部计算路径、跨核共享资源、硬最高速率及短窗初始信用，因此本次真实硬上限、跨核并发容量与 β 仍为 **UNKNOWN**。无需为此重跑设备；后续只有拿到匹配历史版本的静态二进制/源码和正确性合同，才能进一步判断此协议条件是否适用。

## 结论

本地证据能确认板卡查询、profiler 元数据及部分已安装内核中存在的矩阵指令，也能复算厂商工具的 FLOAT16 和 INT8 **条件标称值**。但没有一份证据已证明这些值是 169 全部资源、全部时刻的物理硬上限；BF16、INT4、HBM 与互联也没有同口径硬上限。因此暂不能将其用于无条件理论 TPS 数字。

## 条件公式：不同 dtype 不混用

厂商工具以 `1 MAC = 2 operations` 计数。若**另行证明**适用于 9382、24 AIC 是该池的准确核数、1800 MHz 是该执行域的硬频率上限且无其他计算路径，则可按快照复算每逻辑设备的条件标称容量：

- FLOAT16：`24 × 1800×10^6 × (16×16×16×2) = 353.8944 TOPS`。
- INT8：`24 × 1800×10^6 × (16×32×16×2) = 707.7888 TOPS`，折合 `353.8944 TMAC/s`。

这是两个不同 dtype、同一资源池上的容量口径，不可把二者简单加总；若需要允许其他硬件共同执行，还须证明总资源容量。FLOAT16 和 INT8 的算子混合也不能只用一个 dtype 的峰值计费。该文件没有提供 BF16、INT4 或 FP32 的峰值系数；有相应 `MMAD` 指令只能证明该内核实现路径存在，不能自行造出对应吞吐。INT4×INT4 指令支持不等于原生 INT8×INT4 混合矩阵乘。

数值仅是上述明确条件下的估计器算术，**并未成为本次热态模型的无条件吞吐上界**。此前 Wq_b 和整模型数值依赖更多前提，包括一般输入的必要工作量、无其他资源绕过与跨 rank 资源独立，都应保留条件标签。

## 新增：2201 官方 BF16 并行度与多资源路径（2026-10-28）

上文“没有 BF16 的峰值系数”特指所核对的 `msprof-analyze` 文件，并不表示没有其他官方资料。最新访问的 [Ascend C Cube 指令理论性能附录](https://asc.gitcode.com/api/appendix/cube_instruction_theoretical_perf_summary.html) 对 2201 列出 `Mmad` 的 BF16×BF16 对应 `cube_m/cube_n/cube_k/k0 = 16/16/16/16`，称前三项为硬件真实并行度。页面适用 Atlas A2/A3 系列；所访问页面的具体发布版本未固定，抓取文本丢失公式，因此仅靠表格**不能独立证明 4096 MAC/周期是物理硬上限**。作为需要额外明确假设的模型，可写每 Cube 每周期 `p=16×16×16=4096 MAC`，但完整公式、同一物理资源其他可并发指令及该假设适用本机仍待核对。该页另给 L1→L0A 256、L1→L0B 128 Byte/cycle 作为相应搬运指令的理论性能，不是 HBM 带宽。

[Ascend C 2201 架构说明](https://asc.gitcode.com/guide/programming_guide/advanced_programming/hardware_implementation/architecture_spec/npu_arch_2201.html) 声明 AIC 与 AIV 独立、1:2 配比，可分别加载代码；[2201 的 asc_mmad API](https://asc.gitcode.com/api/SIMD-API/c_api/cube_compute/mmad_compute/asc_mmad.html) 支持 BF16×BF16→FP32 且只在 AIC 上运行。它们说明 Mmad 是一条可用路径、而非已证历史 MatMul 的实际路径；独立 AIV 资源使单独 Cube 模型不能自动覆盖允许混合资源的全部合法实现。单独读取 SKU 配置的 24 与 1800 MHz 再算出来的值，仍只是**在 24 核、频率 1800 MHz、每核每周期 4096 MAC、只使用该 Cube 路径等假设下**的模型值，并非任意实现的严谨上界。

要闭合严格物理界，至少需要：精确 SKU 与历史 rank 的设备资源映射；适用全部运行状态的 Cube/Vector 指令吞吐及最高频约束、可否并发与资源竞争；该型号 HBM 与互联的方向及共享资源物理最大速率；目标实现实际 kernel 和所需运算、搬运不可避免性的证据。优先获取设备供货方对应 SKU 的原厂技术规格，及现有容器内与安装版本一致的官方离线 ISA/硬件手册；若由主控安排读取，仅做静态文件与版本/hash 取证，不进行设备计算。频率元数据与标称典型值不是最高频证明，厂商理论模型本身也不替代设备级硬界证明。

## 2201 单指令公式与受限分块推导（2026-10-28）

官方页面的公式以 SVG 形式渲染，主控通过只读 HTTP 提取并转换图像，本次已直接查看图像：证据为同目录 `cann-mmad-formula.svg` 和 `cann-mmad-formula.png`，可复算 `python3 agents/bounds/recheck_mmad_shape_model.py`，数值及文件 SHA-256 在 `mmad-shape-model-check.json`。SVG 是公式片段，不是整个页面；页面版本与历史运行版本是否一致未确认。以下是文档的**单条 Mmad 理论 Cube 利用率模型**，不是设备物理硬界。

令 `a(x,q)=ceil(x/q)q`，BF16 的 `cube_m=cube_n=cube_k=k0=16`。单指令 `m,n,k` 的有用工作 `w=mnk`，模型周期 `c=Δt + a(m,16)a(n,16)a(k,16)/4096`，其利用率为 `(w/4096)/c`。对于整体逻辑形状 `m=3,n=25600,k=6144`，公式代入得到 `115200/(Δt+614400)`；如果仅作为算术示例令 `Δt=0`，比值为 `3/16=18.75%`。

**整幅单指令不可行。** BF16 左矩阵补齐后需 L0A 196608 字节，右矩阵需 L0B 314572800 字节，FP32 累积矩阵需 L0C 1638400 字节；官方 2201 架构资料中的对应单核容量是 65536、65536、131072 字节。因此必须分块；不能把 614400 当作本次实际单指令耗时。

**更实用的严格条件式。** 假设模型允许 N/K 任意分块、任意合法并行，但每个真实 Mmad 仅处理原始三行内的 `m_i∈{1,2,3}`，不能把其他请求、其他计算的有效行拼入；每个 tile 均遵从该官方单指令公式且 `Δt_i≥0`。令 `w_i=m_i n_i k_i`，`c_i=Δt_i+a(m_i,16)a(n_i,16)a(k_i,16)/4096`，则：

`w_i/c_i ≤ 4096 × m_i/16 ≤ 768 MAC/模型周期`。

其中 `n_i/a(n_i,16)≤1` 与 `k_i/a(k_i,16)≤1`，故各 tile 的形状对齐与头开销只会降低上述比率；加权求和得 `Σw_i ≤ 768 Σc_i`。这对约定的单指令模型、任意 tile 选择成立，是有条件的**有用 MAC / 累计模型周期**上限，非 NPU 实测利用率、单次 wall time 或通用实现的上限。

要进一步推到时间，还必须额外假设：每条 `c_i` 对同一 Cube 的独占工作量可以相加（不允许跨指令的重叠改变服务间隔）；参与的 Cube 至多 `N_C` 个；每个 Cube 全时的频率不超过 `f_max`；所有直接稠密工作都在这组指令内执行，且无跳过、算法变换、预处理、其他资源参与。则 `T ≥ (Σw_i)/(768 N_C f_max)`。对于不重叠、完整覆盖本形状的传统稠密分块，`Σw_i=3×25600×6144=471859200 MAC`；再假设 `N_C=24`，得到 `T ≥ 25600/f_max` 秒。**官方单指令利用率公式并不单独证明多指令的周期可加、最高频率或这次执行域；24 核/1800 MHz 是现存元数据，而非硬界证明**。如果只把 1.8 GHz 当作假设示例，结果是 14.222…微秒，不代表这次算子的实际下界或能达到的延迟。

跨请求拼行、重新组织/融合、改变算法、AIV 协同、不同缓存状态及其他资源都可能脱离上述受限执行域；已有 trace 未证明实际 Mmad 分块方案和上述模型假设。既存 EP8 样本的 `aic_mac_ratio≈0.12` 是按独立 profiler 文档解释的 MAC 周期占总周期比例，`cube_utilization≈0.81` 另是按核数与时间归一的总 AIC 周期比例；两者均不等于这里的 `3/16`，也不能用后者与之做除法得到提速倍数。两个文档版本与真实采集器的内部实现版本尚未闭合。算子形状已确认，Engram 权重身份仍是待验证假设。

## QLI 精确 top-k 的条件数据依赖与 169 缺口（2026-10-28）

已冻结模型配置 `evidence/model-config.json:text_config` 给出 `index_topk=512`、`index_n_heads=32`、`index_head_dim=128`、`candidate_topk_blocks=2048` 和 `candidate_block_size=8`；这些是配置，不是已观测的有效候选数。源码 `models/deepseek_v41/indexer.py:254–290` 在非 packed 路径把 query、key、scale、候选索引等传给自定义 `npu_quant_lightning_indexer_v3`。EP8 已归属第 24 层三次 QLI 任务为约 32.020、498.491、498.170 微秒，但 profiler 形状 `3,1,2048` 仅说明张量容量，无法直接得出逐次有效候选数、实际 key 工作量、请求阶段或分支，见 `agents/diagnosis/indexer-dynamic-metadata-ep8.md`。

厂商 [QLI V2 metadata 官方资料](https://gitcode.com/cann/ops-transformer/tree/master/attention/quant_lightning_indexer_v2_metadata) 指出 `seqused_k` 表示实际参与运算的 key 序列长度，其前置算子据此划分各核任务；它是说明“长度值有必要取证”的一手资料，**不是本次自定义 V3 的语义或实现证明**。该当前主线文档对 A3 的 `num_heads_q` 约束写 64，而本地目标 trace 的某输入为 `[3,32,128]`；不得用此文档直接宣称历史实例遵守当前主线限制或采用相同内核。厂商 [experimental 目录](https://gitcode.com/cann/ops-transformer/tree/master/experimental/attention) 提供块级筛选后 token 级筛选的资料入口，仍需匹配具体版本和本机实现。

**新条件证书：候选 key 的可区分性。** 考虑一个独立接口，输出必须正确给出 C 个可见且互不重复的候选中精确 top-512 的索引集合，其中 `C≥513`。限制一个可证域：32 个 head、128 维 INT8 query/key，选定 query 第一 head 的首元素为 1，其余均为 0；相应第一 head 权重、query 与 key scale 均为 1，其余 head 的贡献为 0；所有候选均通过 mask。按明确假设的打分语义 `score_j = ReLU(q·key_j)`，因此每个候选的分数就是其第一坐标取非负 `0/1/3` 时的值。这是一个用于证明的接口子域，尚未证明本次自定义 V3 和候选过滤满足同一完整语义，也未证明真实模型可以产生该域输入。

在基准输入里让 C 个候选的这个 INT8 坐标全为 1。某个确定性的精确实现返回一个 512 元素集合 T，即使同分时如何择优未规定，这个特定实现的输出也确定。对任意候选 j：若 j∈T，仅把 j 的坐标从 1 改 0，则因 `C>512` 有至少 512 个其他分数为 1 的候选，正确输出必须排除 j；若 j∉T，仅把 j 从 1 改 3，则它成为唯一最高分，正确输出必须包含 j。两种输入仅有该候选的一个位置改变，输出集合必然变化。因此每个候选位置都对接口结果存在可区分见证。

进一步限制所有输入只以互不重叠的原始 key 字节供在线读取，窗口开始前不能存有候选打分/排序摘要、其他副本或携带输入信息的旁路，而且须对上面的基准及每个单点改变均正确，那么在基准输入上，一个确定性实现若完全不读取候选 j 的字节，就无法区分它的对应反例，输出必错。因此至少检查 **C 个不同候选字节地址**；对 `C=513` 的例子为 513 个。允许独立读取并行、读取预取或 fusion；此结论不是 513 次发射、513 cycles、513 字节 HBM 流量或无条件时间界。如果允许 producer 提前附带同次输入的评分摘要、已缓存排序、副本或其他旁路，本访问下界不自动成立；若下游无需保持所选 indices、模型允许误差或有效候选小于等于 topk，结论也不自动成立。

这不是 169 已测负载下界：`C`、精确 topk/掩码与候选去重规则、参与评分的 key 字段、实际值域、对应 kernel 与进入时缓存状态均 UNKNOWN；未找到证据证明构造可由该固定权重模型产生。也没有经证实的跨 cut 硬速率上限，因此不把候选位置数换算为时间、带宽或 TPS。若有多个 query，key 可在片上复用，不能把每个 query 的候选访问数无条件相加。

可离线复算 C=513、k=512 的构造，Python 一般整数排序仅是见证检查，不是 NPU 或浮点精度验证：

```python
C, K = 513, 512
select = lambda values: set(sorted(range(C), key=lambda j: (-values[j], j))[:K])
base = [1] * C
chosen = select(base)
for j in range(C):
    alt = base.copy()
    alt[j] = 0 if j in chosen else 3
    assert select(alt) != chosen
```

**给这条真实形状的热态搬运条件式。** 固定执行窗口及一条从慢侧到快侧的有向边界。若 (i) 执行方式必须直接读取并使用右矩阵全部 314572800 个原始 BF16 字节，不可用重编码、副本、计算摘要或其他结果替代；(ii) 窗口开始时边界快侧最多有 `C_B` 个这类必需字节；(iii) 剩余必需字节只有通过这条边界才能进入快侧，预取也计入该窗口，则不管分块、调度和计算如何重叠：

`Q_B ≥ max(0, 314572800 − C_B)`。若在所选窗口内任意长度为 `t` 的前缀均有累计穿越字节 `Q(t) ≤ B_cut,max × t`，则 `T_move ≥ Q_B / B_cut,max`；若仅有带初始突发的包络 `Q(t) ≤ b + B_cut,max × t`，应改为 `T_move ≥ max(0, Q_B−b) / B_cut,max`。长期平均带宽不能替代逐前缀容量约束。

设 `a_e` 为实际被裁剪后送入本 rank 第 `e` 个专家的行数，`A=Σ_e a_e`，`U=|{e:a_e>0}|`。只考虑**传统直接稠密矩阵乘**的逻辑工作，每个专家有效行 GMM1 是 `5120×4608=23,592,960 MAC`，GMM2 是 `2304×5120=11,796,480 MAC`，合计 `35,389,440 MAC`；所以两次合计逻辑工作为 `35,389,440×A MAC`。这不是算子输出行数，也不是通过本 rank 的网络 token 数；输入在本地为 3 行不意味着 `A=3`、`A=18` 或可与其他 rank 不加证明相加。`A`、`U` 的历史值目前 **UNKNOWN**。

**计算资源条件界。** 若进一步限制执行域为两次直接稠密矩阵乘的全部逻辑 MAC 均必须在同一计时窗口内实际执行、不能借零值跳过/代数变换/缓存结果/移到其他未计资源；并有与该窗口及设备所有并发计算路径匹配的逐前缀硬容量 `F(t)≤P_int8,max×t`，其中 `P_int8,max` 单位为 MAC/s，则总工作守恒给出

`T_MC2 ≥ 35,389,440 A / P_int8,max`。

这个形式允许各专家和两次 GMM 在有数据依赖的条件下分块、跨核和与通信并行；将必要工作除以**共享总容量**，不是将各 core 或模块的时间相加。算子的启动、量化、SwiGLU、通信和写回若需时间只能另行证明并以可重叠方式并入；它们不自动等于该公式之外可加的墙钟时间。采样器的 24 AIC、1800 MHz 和 `msprof-analyze` 估算未证实本机全部合法状态的硬容量，故 `P_int8,max` 仍是 UNKNOWN，不能把 353.8944 TMAC/s 填成物理上限。

**权重搬运的独立受限界。** 每个参与专家的两组权重逻辑上共有 `35,389,440` 个 INT8 元素（同数目的逻辑原始字节；量化 scale 等不包含在内）。必须额外明确限定：对每个参与专家，执行方式**确实逐一读取该专家两矩阵所有原始权重位置**，不因零激活、零权重或其他原因跳过；不同专家和矩阵的这些原始位置在指定 cut 上一一映射为互不重叠、不可共享的字节，不能压缩、重编码或改用副本和摘要绕过。所需字节可从窗口前所有快侧副本获取的总数至多 `C`，其余只能通过该 cut 进入，预取也计入窗口。只有在这些额外前提全部成立时，才能得到必须穿过的字节 `D ≥ max(0, 35,389,440 U − C)`。**此完整读取前提未由源码或历史 trace 证明**；逻辑稠密工作量与权重形状本身不证明物理 cut 字节。对覆盖此 cut 所有并发路径、任意窗口前缀的方向性硬带宽 `B_cut,max`，有 `T_MC2 ≥ D/B_cut,max`；若存在可允许的初始突发或其他旁路，应把它们纳入初态/cut 后重新证明。这里 `C` 是该边界所有有效快侧副本的容量/内容上限，不能将 SDK 的单项 L2 数字直接视作它；`C` 和 `B_cut,max` 目前均 UNKNOWN，`U=0` 时此界为 0。

只有当上述计算和搬运前提同时成立，才能写 `T_MC2 ≥ max(35,389,440 A/P_int8,max, max(0,35,389,440 U−C)/B_cut,max)`；允许异步时不能把两项无条件相加。源码 `operator()<AIC>:215–223` 包含 GMM1→等待→GMM2 的该实现控制链，AIV 的 SwiGLU/同步见 `:919–958`；这支持该实现的依赖排查，但不同专家/切片可流水，不能据此把**全量 GMM1、全量激活、全量 GMM2**各自墙钟耗时相加，也不能证明融合/重算后的模型语义必须保留这些阶段。

这是一份**真实采样形状绑定仍待确认、且执行方式受限的条件证书**，不是允许任意融合、跨层复用、稀疏跳过、预计算和重编码的全局模型 TPS 上界；因 `A,U,C,P_int8,max,B_cut,max` 和有效映射都未知，不能得出本次数值极限或可达提速。最小补证是同版本 tiler 的实际 storage 维度、绑定确切 replay 的匿名逐专家裁剪行数、cache 初态/指定 cut 以及精确 SKU 的方向性物理容量；先查已有固定导出，缺失时记 UNKNOWN，不再用形状猜数据。逐行工作数可只用 CPU 验算：`python3 -c 'k,n=5120,4608; print(k*n,k*(n//2),k*n+k*(n//2))'`。本轮未触卡。

### 16 rank 条件下的专家行守恒与权重读取审计

若再明确假设：**同一次** MC2 调用包含 16 个 rank；每 rank 恰有 3 个有效物理 token 行；每行选择 6 个不同专家；每个选择恰好投递到一个负责该专家的唯一副本，所有选择都成功接收并在两次 GMM 中各处理一次；无 mask、容量或其他裁剪导致丢失，也无额外副本重复计算，那么来源侧有 `16×3×6=288` 个 token→expert 选择，接收侧的专家行数满足 `Σ_rank A_rank=288`。冻结 `GetCumsumForMMAIV:402–432` 将按专家的各来源计数累加，`GMM1/GMM2:454–469,561–576` 使用累加结果并按 `maxOutputSize` 裁剪；这支持上述守恒所描述的实现关系，但代码本身不证明这些前提在那次样本均成立。特别地，“已投递”不自动排除随后 GMM 容量裁剪。

若 16 个本地 GMM 的逻辑维度均确为 `K=5120,N=4608` 且每行都在两个阶段做完整传统稠密计算，则这一组的**固定实现逻辑工作账**为 `288×(23,592,960+11,796,480)=10,192,158,720 MAC`；以 `1 MAC=2 ops` 计为 `20,384,317,440 ops`。多个物理 token 行可能是同一个语义 token 的不同分片或副本，288 不是去重后的模型输出 token 数。若专家沿 rank 分片、每个选择被重复计算、接收发生丢弃或裁剪、有效 mask 包含 false，或这不是同一组 replay，结果都不能直接套用；尤其 TP/CP 的 16 个物理行组不能自动当成 16 组彼此不同的用户请求。

如再约束全部上述 MAC 在**同一组计时窗口起点之后、终点之前**通过被计入的设备执行，并有逐前缀工作容量 `F(t)≤P_group,max×t`，覆盖此窗口各 rank 所有可用计算路径，则 `T_group ≥ 10,192,158,720/P_group,max` 秒。若已各自证明每个设备资源总能力不超过 `P_i,max`，将它们相加是保守的总能力上界，即使设备之间共享资源也不会因重复计入而变得更紧；但不能仅由 16 个 profiler 标称频率把这些数自动视为已证峰值。对组内重叠计算，只按同一 group 窗口计算总工作，不把每个 rank 的时长加起来；任何预先完成或在窗口开始已可复用的工作都不得计作窗口内必要工作。`P_group,max`、同次调用与完整实际输入条件仍 UNKNOWN，因此不能将该条件界代入历史 benchmark，更不是允许算法任意重组的全局界。

**权重读取审计修正。** 上一节的 `35,389,440 U` 是参与专家两矩阵逻辑形状的总位置数，不能单凭它证明实际每个活跃专家要从某条物理 cut 读取全部这些字节。即使不压缩/重编码，零输入或零权重跳过、重复值复用、预计算、预驻留、副本和更广泛的实现路径都可能改变实际读取；逻辑位置也不等于互不重叠的实际存储地址。上一节已补充必须逐一读取全部原始位置、位置与 cut 字节一一对应及初态覆盖所有快侧副本的严格前提；这些条件目前尚未被源代码或样本证明。更宽域中不作该前提时，应以 **0 或另行证明的实际最小量**为搬运下界，不使用 35,389,440 字节/专家当物理事实。

### 独立时窗审计：预取、突发与业务口径

复核上述两组矩阵乘算术：`16×3×6=288`、`5120×4608+2304×5120=35,389,440`、两者之积 `10,192,158,720 MAC` 均正确，前提是前述单次 group、有效行与不裁剪的条件都成立。`A` 的动态值没有采集，16 rank 的采样 ordinal 也未绑定同次 replay；即使将来绑定，它仍是固定实现的逻辑工作，不自动等于宽域内必要工作。两次业务基准各有 8192 个记录的输出 token、对应各自客户端窗口；16 rank profiler 的局部任务窗口不是这两个业务计时窗口，不能拿 288 个专家行作业务输出 token，也不能直接把算子窗口的下界作 8192-token TPS 分母。

本次发现此前 BF16 示例的 `T_move≥Q_B/B_cut,max` 对 B 作为**逐前缀硬容量**的要求不够明确，已在原式处补全；MC2 的逐前缀限制和所有 MAC 必须在同一 group 窗口完成也已写明。可复现反例：令待穿越 `D=100 B`，所谓 `B=10 B/s` 只是一个允许 `b=100 B` 初始突发后的长期速率；有合法传输在 `0.1 s` 内发送全部 100 B，却违反把长期 B 直接代入得到的错误结论 `T≥10 s`。正确的包络下界是 `T≥max(0,D−b)/B`，因此这个例子下仅为 0；若没有突发且对所有前缀 `Q(t)≤Bt` 才能用 `D/B`。已在途的数据、预取与快侧缓存需明确归入初态或突发预算，不能漏算或将同一字节重复扣减。

资源窗口通用公式 `T≥a+Σw/C+b` 经复核在其已声明的非空任务集、任务工作互不重复、共同窗口内发生、必需依赖和任意时刻硬速率约束下成立；如允许初始突发而未把它扣除，则必须改为与其容量包络匹配的形式。SSE 已保存校验中的 8192 token、32,628 / 33,024 UTF-8 字节以及对应客户端计时均是**各自轮次**的观测；其逻辑客户端边界不等于物理网络/HBM 字节或 NPU 算力界。除已补充的容量和窗口条件外，本次未发现已审查公式的其他算术错误；没有执行 NPU 或修改目标服务。

## DSpark 辅助状态通信 cut：可复算的假设实例

以下是说明如何证明**必要信息量**的假设实例，不是 169 历史调用的通信下界。stage230 的 144 个目标窗口各导出一条 `ReduceMean`，输入 BF16 `[3,4,5120]`、axis 1，输出 BF16 `[3,5120]`；另有形状和顺序相容的 `hcom_allGather_` 导出。张量身份、实际 aux 分支、通信内容和请求身份尚未绑定，详见 `agents/fusion/F27-AUX-MAIN-PROJ-PIPELINE-REVIEW.md`。因而这里的数字仅借用观测到的物理形状建立例子，不能称为实际有效行数或实测流量。

固定一次协议、同一个有向物理 cut 和一个明确定义的计时窗口，**同时假设**：

1. 源侧需要将该 `[3,5120]` 的所有均值精确交付给 cut 另一侧，且 3 行均有效。输入域包含 `3×5120=15360` 个位置相互独立取 0 或 1 的全部组合；每个位置的四路 BF16 输入均设成同一个相应值，mean 的结果按假设实现精确为该值。
2. 接收侧在窗口开始前的初态、已缓存副本及其他先验状态对这 15360 个取值不携带信息；所有与之相关的信息在窗口内只能通过该 cut 由源侧向接收侧进入。不存在绕过该 cut 的副本、预传、结果摘要、通信旁路或可用的时间等侧信道。
3. 接收侧必须对上述所有 `2^15360` 个可能输入精确给出各位置的均值。对固定的其余初始状态，穿过该 cut 的方向性消息采用固定长度 `b` 位编码；必要的协议反馈也不能作为绕开上述边界的信息来源。

若 `b < 15360`，最多只有 `2^b` 个不同的定长消息，但所要求区分的输入有 `2^15360` 种，必有两种输入在接收侧形成相同的可用信息，无法同时输出不同的正确结果，矛盾。因此有 `b ≥ 15360` bit，即至少 **1920 字节的信息编码容量**。这是允许将每个 0/1 均值压缩为一位后的界；不能把 BF16 逻辑张量容量 `3×5120×2 = 30720` 字节直接称为任何等价实现的必要物理流量。此处按 8 bit/字节换算；并行链路、编码及协议开销应统一纳入所指定的物理 cut。

如果额外证明计时窗口覆盖这些必须传递的信息，且该 cut 在整个窗口内、所有并行路径合计传输容量满足 `D(t) ≤ B_cut,max × t`，其中 `B_cut,max` 是方向性硬速率上限且没有未计入的初始突发容量，则该条件实例有 `T ≥ 1920/B_cut,max`。若允许窗口前预传、初始缓冲已有信息或突发容量、变长编码与时间侧信道、传输到其他计算位置而无需在该接收侧还原全部均值，须重建模型，不能沿用此式。即使各项前提都成立，通信也可与其他计算重叠；不能把这个耗时无条件加到整个算子的墙钟时间上。

当前没有证据证明 stage230 的那次 gather 搬运此均值、三行有效、上述独立输入组合能由固定模型在该层产生、接收侧必须恢复完整均值或初态不含相关信息，也没有绑定上述 cut 的硬速率。三个辅助层的状态还可能相关、可复用或共同编码，不能把 1920 字节直接乘 3、乘 rank 数或用它估算 TPS。类似地，源码中的 mean→gather→projection 顺序只支持当前实现的静态语义；融合后是否需要完整张量和对应算子次序，取决于最终可观察结果与可达输入的可区分性，而非源码存在该调用本身。本节只提供可证伪的形式化示例，不更改已有 UNKNOWN 状态。

限定某专家全部 Mmad 每条只含最多 `m≤16` 个有效行，不拼入其他专家/请求的有效行，允许任意 N/K 分块；若每条遵循官方所列单指令模型且头开销非负，则 `w_i=m_i n_i k_i`，模型周期 `c_i=Δt_i+align16(m_i)align16(n_i)align32(k_i)/8192`，故 `w_i/c_i≤8192·m/16`；对各条相加也成立。在该模型内，m=1、2、3 的有用 MAC/周期分别不超过完整 8192 的 6.25%、12.5%、18.75%。这是受限执行模型下的分形利用率界，不是指令测时、墙上时间、整芯片 NPU 活动或请求 TPS。合并工作、改算法、不同精度与资源、其他模型和跨请求/专家拼行不属于该结论。

**不能把它直接套用到历史 MC2。** 已导出 `[M,5120]` 的 M 是一个 rank 的输入物理行数，而 dispatch 后一个专家可以接收多个 rank 的行；源码中的 expert 累计与 `currentM` 取决于动态路由和截断。历史每次专家有效行数、执行 Mmad 形状、编译对象和实际 runtime 未绑定；M=1/2/3 的采样并不证明专家 M≤1/2/3。设备频率硬上限、宽实现域的必需工作量亦未知，本次没有形成新的无条件数值性能上界或预测收益。

## INT8 小行数界的复核范围

2201 表中 16×16×32 指 Mmad 模型的计算并行度，不能混成二维存储分形；该单条模型的 M 是该指令的逻辑有效行，不是 dispatch 之前本卡输入行数。达到 m/16 还要求 N/K 对齐和理论头开销为零。多条指令的模型周期转成墙钟下界，还需证明共同资源容量和工作守恒，不能直接相加当耗时或等同 profiler MAC ratio。
