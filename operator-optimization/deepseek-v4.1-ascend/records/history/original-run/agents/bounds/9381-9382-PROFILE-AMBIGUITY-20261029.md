# 9381 / 9382 配置与历史采集的身份区分能力

**结论：**本地已保存的 CANN 两份配置对比显示，`Ascend910_9381.ini` 和 `Ascend910_9382.ini` 的全部 10 个 section 内，解析出的唯一不同项目是 `[version] SoC_version` 本身。24 Cube、48 Vector、1800 MHz、2201、内存容量及 dtype 等配置项均相同。因此，已存 16 个 profile 的 24 AIC、48 AIV 和 1800 字段即使每个都相同，也无法单凭它们区分这两个软件配置目标；不能据此把单个 board0 查询扩展成历史所有 rank 均为 9382 的证明。这是**软件配置反例，不是实测或声称两种芯片物理属性完全相同**。

## 对 BF16 模型的影响

已存 board0 查询有 `NPU Name=9382`，与 9382 名称相容；它不是 16 个历史 rank 各自 runtime SoC 查询，尚需将历史 worker 的 runtime 型号和具体物理设备绑定。已存 2201 官方资料对 BF16 Mmad 有 16×16×16 的单指令模型，并不证明所有指令/资源的完整硬吞吐；profiler 1800 字段和配置 `cube_freq` 也未证明覆盖所有状态的最高频。`24×1.8 GHz×4096 MAC/cycle` 仍只可作为明确假设下的单 Cube 路径模型，不能作为设备不可超越硬上界。

要闭合：获取历史每 rank 的精确 runtime SoC/逻辑设备到物理板卡映射和软件版本，再取得与该实际 SKU/固件匹配的最高频、BF16 各计算路径发行和共享、短窗突发容量的一手规格。即使这些硬容量已证，也还需另证明允许实现域内的必要工作量、时窗初态。当前资料不支持进一步数值收紧；不应为重复读取同一配置或重复查询设备而发起新 NPU 工作。
