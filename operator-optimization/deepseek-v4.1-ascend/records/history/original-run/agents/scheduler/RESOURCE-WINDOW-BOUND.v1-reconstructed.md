# 算子、通信与调度的理想时间下界：依赖 + 资源窗口

这是一个**严格限定了执行域的通用模板**，不是 169 的 TPS 结论。它说明怎样比“分别算访存、计算、通信再取最大”更紧，同时仍然允许可行的重叠、分块流水、抢占、异步调度和不同请求并行。

## 1. 必须先约定什么

固定计时窗 `[0,T]` 和有效输出 `Q`，假设已经证明：

1. 对该执行域内每一个合法实现，某个共同的任务图中的任务都必须发生，图的边代表**完成到开始的必要依赖**，任务可以细分到实际允许的 tile 粒度。不确定的边不要加入；允许改变算法、复用或预计算时，不能直接把现有实现的算子图当共同任务图。
2. 每个任务 i 在明确的资源 r 上必须消耗不少于 `w_i` 的**互不重复**工作量；资源 r 的总处理速率任何时刻不超过 `C_r`。例如严格定义的存储 cut 字节数及该 cut 的读写合计速率上限。必须证明各任务无法用另一条资源通路、共享一个结果或消除工作；资源或工作无法证明就保留 UNKNOWN，不能把实测最好值当硬上限。
3. 每任务有效执行的起点和终点之间有已证实的最短跨度 `d_i ≥ 0`。可令未知 d_i 为 0 以放松模型；不能把测得平均值、软件启动耗时或完全可被融合消除的实现边界当不可避免时延。
4. 计时起点之前已经在缓存、预取、预计算和已有输出中的内容要在模型初态中允许；`w_i` 只能包含进入窗口后仍不可避免的工作。资源可以在任务间任意分配和抢占；不同资源可同时工作。

对应合法调度集合称为 D。若从更宽的用户理想域到这个图的包含关系没有证明，得到的只是在 D 中的条件界，不是全体实现的通用上界。

## 2. 如何算

在图中使用每个 `d_i` 忽略资源争用，得到：

- `a_i`：从时间 0 开始，到任务 i 能开始之前的最长必要前驱路径最短时间。
- `b_i`：任务 i 结束后，到完成所有输出仍必须经过的最长必要后继路径最短时间。
- `L`：从输入到输出的最长必要路径的最短时间。

对任一资源 r、非负阈值 a、b，选出 `S(r,a,b) = {i | resource(i)=r, a_i≥a, b_i≥b}`。则**任何**属于 D 的合法调度，都满足：

`T ≥ a + [Σ(i∈S) w_i]/C_r + b`。

证明：集合内每项工作不可能早于 a 开始；每项工作结束后离最终完成至少还需 b，所以所有这些工作只能占用 `[a,T−b]`。该资源在任何时刻总速率不超过 C_r，而每项工作量互不重复，所以 `Σw_i ≤ C_r(T−a−b)`。整理即得公式。此证明允许集合中的任务交错、抢占，以及与其他资源并行。

求所有 r、a、b 的最大值，再与路径界取最大：

`T_lower = max(L, max_(r,a,b)[a + Σ_(i∈S)w_i/C_r + b])`。

这包含普通资源总量界：令 a=b=0 就得到 `T ≥ Σw_i/C_r`。资源容量、任务量、依赖或精度约束只有在已证实且适用时才允许代入；**可证明的下界越大，其对应 TPS 上界 `Q/T_lower` 越小、越紧**。模型不需要找到达到该值的调度。若 Q=8192 仅限合同中一次完整 8 请求、各输出 1024 token 的计时窗，分母须使用同一个窗，不能套在单次 kernel 或 profiling 窗口上。

## 3. 小例子：为什么依赖和共享资源要一起算

4 个 tile，每个都需要依次搬入 1、计算 3、搬出 1 个时间单位；搬入和搬出共享一个 IO 资源，计算使用另一资源，各自容量为 1。假设这些工作和 tile 边确实都是不可避免的。

- 单条 tile 依赖路径是 5；IO 总工作是 8；计算总工作是 12。单纯取最大得到 12。
- 所有计算至少在首次搬入之后开始，所有计算结束后还要至少一次搬出。取计算资源窗口的 `a=1, b=1`，得到 `T≥1+12+1=14`。
- 示例脚本给出一个合法的 14 单位调度作为算术自检；**理论上界成立不依赖找到这个调度**。不是所有图的下界都能被达到。

换成每 tile 搬入和搬出各 8、计算 3，共用同一个 IO 资源，则仅 IO 的总必要工作就给出 `T≥64`。首搬入 + 所有计算 + 末搬出为 `8+12+8=28`，在此例是更松的下界而非真实最优时间：不能假定全部搬运总能藏在计算后面。

反过来，如果实际提供独立读写路径，必须分别建资源，不能把双向字节强加到单一资源上。若 I/O 和算力共享某个中间硬件，还需有证据才能建立该共享资源 cut。没有证明共享就不做强制相加。

## 4. 一个重要反例：过粗的依赖边会高估下界

如果一个 10 单位读操作可以拆成 10 个 tile，每个读 1 单位后对应计算 1 单位立即开始，读和算资源不同，则流水只需 11 单位。把整个读取和整个计算画成不可拆分、全完成后才能开始的两个节点，会得到 `T≥20`，这是错误地排除了合法流水。对 169，`全量通信→全量计算`、`一整层→下一整层` 等边只有在确实无法逐块就绪时才可加入；同步点和 chunk 粒度应由源码、接口和真实数值语义分别证明。

## 5. 对当前 169 基线怎么使用

候选是从已冻结的 F05 Q 量化/投影、F21 MC2、F23 MoE 输出与残差等边界建立**多种逐步放宽的图**：

1. 先定义实际观察图与理想图；标出已融合的 MC2 内部哪些工作、scale/精度及每个状态写确实需要，保留分片和所有消费者。
2. 不把 graph replay、kernel launch、当前屏障、一次调用的全部输入、通信等待直接画成必然边。对于存在多条实现路径或跨层复用的节点，先证明共同必要子图，不能为方便算数固定现有实现。
3. 每个资源填写**可追溯的硬能力上限**，每个节点填写已证明的最低工作；不知道就写 UNKNOWN。现有 `agents/bounds/` 的条件量和产品规格不能直接当硬上限。
4. 对每个细化版本重新算公式，结果标明合法实现域、初态、时间窗和计量单位。只有证明新的约束对该域内所有实现都成立，才能用于收紧上界；域变窄就只能标“条件界”，不得与宽域无条件界混为一谈。
5. 与基线比较时明确端到端 Q=8192 与实际测量窗；局部 40 层或 profiler 数据不能直接替代端到端时间。

## 复现

在任务根目录执行 `python3 agents/scheduler/resource_window_bound.py`。它采用有理数精确计算拓扑路径和有限阈值资源窗口，生成同目录 `resource_window_bound.json`，校验两个示例及一个合法调度。脚本计算的是输入模型的数学结果，**不会证明输入图、工作量或硬件能力符合 169**。
