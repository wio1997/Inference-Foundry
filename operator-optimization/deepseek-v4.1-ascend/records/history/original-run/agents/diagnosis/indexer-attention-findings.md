# Indexer 与 attention：分层样本

复算结果为 `indexer-attention-by-rank.json`，脚本 `analyze_indexer_attention.py`，均已记录 16 份 kernel CSV 和窗口数据的 SHA-256。它复用 16 rank、各 3 个内部采样轮次、40 层共 1920 个已有 target 窗口，其中 8 层各发现 48 个 Indexer，合计 384 个；均能在相同 rank、model、stream 和模块窗口中找到一个 SparseFlashMla。

| 层 | Indexer 48 个样本耗时中位数 | Attention 48 个样本耗时中位数 | 各 rank 的 3 次 Indexer 均值范围 |
|---|---:|---:|---:|
| 2 | 89.88 μs | 45.48 μs | 65.31–69.90 μs |
| 8 | 90.16 μs | 43.44 μs | 64.89–75.99 μs |
| 14 | 91.26 μs | 45.88 μs | 66.02–75.06 μs |
| 20 | 209.35 μs | 43.48 μs | 144.55–153.53 μs |
| 24 | 494.41 μs | 43.31 μs | 335.09–349.21 μs |
| 28 | 493.66 μs | 44.27 μs | 334.66–341.79 μs |
| 32 | 493.12 μs | 43.57 μs | 334.65–343.69 μs |
| 36 | 494.02 μs | 43.75 μs | 334.88–345.91 μs |

中位数是按 48 个单次样本计算；每 rank 的数字是 3 次的均值，两种统计量不能直接等同。层 24/28/32/36 的 Indexer 明显值得优先追查；这四层各 rank 组的 AIC MAC 代理约 **3.38%–5.22%**，并且采样时间较长，但该指标不是整卡利用率。不同层的输入形状和代码分支不同，不能把层间耗时差直接归因某一个输入或证明可减少的时间。

记录的 Indexer 输入形状有 6 种：每层各有两种、分别覆盖 8 个 rank；第 2/8/14 层的第二个输入中间维度为 64，第 20/24/28/32/36 层为 128，而后四层记录中额外出现 `3,1,2048` 输入。这是 profiler 记录的物理形状，不能直接当作有效序列长度或实际 token 数。

384 对都显示 **Indexer 在同一 stream 上结束后，attention 才开始**。冻结源码 `dsa_v41.py:708–711` 在相应条件分支中将 `_select_sparse_indices` 的输出传给 `_forward_attention`；这支持源码层面的生产者—消费者关系。当前 trace 没有逐调用张量身份和所有事件边，不能只凭时序宣称运行时每个 buffer 已精确匹配、证明可消除耗时或断定端到端关键路径。不同 stream 也可能与它重叠。

下一步可仅用已有 trace 将三个采样轮次分别列出，检查组内均值与整体中位数差异，并结合 `indexer.py:274–285` 对不同 `candidate_mode` 和输入形状做源码分支映射。须先查明实际 metadata／候选长度；没有实际值前，不把分支相关性升级为耗时原因。
