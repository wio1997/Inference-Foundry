## 补充：两个矩阵候选的周期乘积比较（2026-10-30）

复用下文 16 rank × 3 轮同 rank 同轮的 48 对形状相容的 BF16 MatMul 候选，将每条记录的 `aic_total_cycles` 分别乘以 CSV 导出的 `aic_mac_ratio`、`aic_mte2_ratio`，再对每一对取前一区间除以后一区间。三个采样轮次分别为：

| 周期乘积比值 | 第 1 轮最小/中位/最大 | 第 2 轮最小/中位/最大 | 第 3 轮最小/中位/最大 |
|---|---|---|---|
| MAC | 0.994858 / 1.000997 / 1.004328 | 0.993807 / 0.999371 / 1.006564 | 0.994092 / 0.999085 / 1.007973 |
| MTE2 | 1.054437 / 1.079754 / 1.091278 | 1.043320 / 1.062086 / 1.077880 | 1.030172 / 1.064860 / 1.078176 |

在这 48 对中，前者任务总耗时均较长（见下文）；上表进一步说明，**在导出字段的代数口径下**，MAC 乘积相近，而 MTE2 乘积均较大。它缩小了需要解释的现象：仅凭更低的 MAC 比例，不能断言前者的 MAC 乘积更少。这不证明 MAC 指令数相同，也不证明新增耗时由搬运造成：ratio 只有三位小数，历史导出器、核间聚合、频率与算子 binary 未闭合；MTE2 乘积不是读字节、HBM 带宽或可加的独立墙钟阶段。输入有效值、权重及运行请求未绑定，不能认定资源争用、缓存或具体原因。三个轮次来自同次采集，非独立实验；样本只涵盖这两个候选形状，不代表其他矩阵或线上服务。

对同样的逐对字段进一步分解，`aic_total_cycles` 的前/后比三轮中位为 **1.077262、1.061385、1.063780**，`aic_mte2_ratio` 的前/后比中位为 **1.002033、1.001018、1.001016**；后者 48 对范围为 **1.000000–1.005097**。因此先前 MTE2 乘积上升在保存的数字口径下主要随总周期增加，不是除总周期变化以外独立出现的显著比例差异。两者逐对相乘后再取中位，不能用两个中位数之积代替；字段显示精度、硬件事件与误差未知，故这不证明真实搬运比例近乎相同，也不排除真实搬运造成耗时差。复算同一 `recheck_engram_pair_product.py`，脚本校验输入 SHA 和 48 对唯一性。

## 当前判断

在既有 trace 的 16 rank、3 轮 target 图采样中，**第 0→1 层之间的最大间隔并非整段都没有导出任务**：每个样本的主流上都记录到一段 BF16 `MatMulV2` 和一组与 Engram 普通门控计算相符的任务。第 13→14 层也出现相似模式，符合冻结模型的 Engram 层为 1、14 的源码角色；预选的第 12→13 层对照没有相同导出记录。

## 形状与源码的关联线索

两类候选边界各 48 个样本中，每个都出现：

- 主流、model 49 的 `MatMulV2` 输入 shape `[3,6144]` 和 `[25600,6144]`，两个输入 dtype 均 `DT_BF16`。每个候选窗口恰有一条此形状任务，并完全落在该间隔；0→1 的任务时长范围 275.755–293.474 μs，中位数 283.934 μs；13→14 为 257.015–275.775 μs，中位数 267.584 μs。逐卡计算后，大矩阵任务占 0→1 间隔的中位数约 61.19%，13→14 约 59.77%。
- 主流、model 49 的另一条 `MatMulV2`，输入 shape `[1920,32]`、`[32,32]`，dtype `FLOAT;FLOAT`；同窗还有 `Pows`、`ReduceMean`、`Rsqrt`、`ReduceSum`、`Sigmoid`、`MaskedFill` 等记录。
- 预选对照 12→13 的 48 个区间中没有任何 CSV 导出行，也没有这两类 `MatMulV2`。这只说明在该短区间未导出这些行。

冻结 `evidence/model-config.json` 有 `engram_max_ngram_size=4`、`engram_n_heads=8`、`engram_head_dim=256`、`hc_mult=4`、`hidden_size=5120`。`engram/layer.py:23-34` 的 `wkv` 逻辑输入宽度 `(4−1)×8×256=6144`、输出宽度 `(4+1)×5120=25600`；`model.py:1565-1592` 在相应层存在 Engram 且 token mask 非空时等待相关 lookup、调用 `layer.engram`，之后进入该层 decoder。`engram/common.py:61-72` 的普通门控路径包含平方均值、乘法、归约、sigmoid、mask 和加法；需要 rotation 时还包含 32×32 旋转。该数值形状和源码顺序与 trace 特征一致，但 `MatMulV2` 的权重张量地址、调用栈及图内 tensor identity 未被本次查询验证，不能断言这条 task 已被精确绑定到 `wkv` 或精确分解为各语义阶段。

## 对候选解释的判定

1. **“约 465 μs 完全没有任何导出设备任务”**：与这 48 个 0→1 区间的记录矛盾；同卡数字 stream 导出行覆盖了其中大部分。这个排除只针对已导出的记录，不排除 profiler 之外或 kernel 内部的等待。
2. **“整个间隔只是跨 stream HCCL 高层导出行”**：与同窗主流、model 49 的两个具体 MatMulV2 及其他已导出算子不符；未发现 `hcom_` 名称行。不过，通信可能存在于其他任务、内部机制或未记录路径，不能据此排除通信影响。
3. **“Engram 的投影和普通 gate 执行于这两个边界”**：源码条件、两处位置、矩阵 shape/dtype 和后续算子序列均相容，对照提供进一步线索；仍缺 tensor/权重身份及运行分支绑定，所以是优先假说而不是定论。运行中的 rotation、lookup ready 与 mask 状态也未直接观察。
4. **“CPU 调度/等待造成全部或部分耗时”**：不能仅凭设备时间区间排除。已导出任务覆盖多数窗口，反驳的是“整段无导出任务”，而不是“内核/图含等待”或“提交时机影响”。

## 完整性和下一步最小证据

16 份 CSV 的 SHA 与冻结清单一致，48 个候选及对照的窗口来自同一份快照；独立复算全部 144 个窗口的数字 stream、未知 stream、合并并集与补集。它确认分析输入和算术，**不证明 profiler 已捕获全部事件**；不同 API、host、其他进程、内部等待及 PMU 语义仍可能缺失，且 graph replay 的 task ID 不一定唯一。这里没有新设备采样，也没有把类型时长当作性能收益。
