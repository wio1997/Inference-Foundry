# EP8 第 24 层：是否记录动态长度

只读查询 `query_indexer_runtime_metadata.py` 的结果保存在 `indexer-runtime-metadata-ep8.json`，含查询脚本与原数据库的 SHA-256。范围是 EP8、model 49、stream 89 的三个已归属内部采样窗口，每个窗口恰有一个 Indexer TASK：

| 采样轮次 | TASK 耗时 | globalTaskId / connectionId | attrInfo ID |
|---|---:|---|---:|
| 1 | 32.020 μs | 19466 / 184330 | 1303 |
| 2 | 498.491 μs | 19466 / 184330 | 1303 |
| 3 | 498.170 μs | 19466 / 184330 | 1303 |

三次查询取得同一个属性字符串、输入形状和类型字符串；属性字符串包含 `attr_8:2|attr_9:2048|attr_10:8` 等无名称字段。冻结源码与配置中确实有 candidate mode 2、候选块数 2048 和块大小 8；**但本次尚无该 profiler `attr_N` 字段的命名定义，不能把对应关系当成实测已证，也不能把其余大整数猜成有效长度。**

这三条结果**没有提供逐次 query 长度、cache 有效长度、实际候选数量或请求阶段**。输入的 `3,1,2048` 是缓冲区形状，不是其中有效元素数量；相同属性 ID 及全局任务 ID 也不足以证明每次运行的动态输入相同。精确 connectionId 查询 CANN_API 没有行，不能因此声称无上游提交或无通信：图重放中连接可能属于其他记录。

目前结果仍不能解释 run 1 与 run 2/3 的 15 倍左右耗时差。下一步优先只读检索已保存 profiler 导出是否包含 metadata tensor **值**或该任务属性字段的版本定义，再结合请求关联数据；若找不到，应把这些运行值记为未知。是否新增观测要先确定精确缺口和设备占用，不能把一次任务的结论推广到所有层或 rank。
