# MC2 两个整体活动字段不能识别内部等待：构造性检查

只使用已归属的 48 条第 0 层 MC2 汇总中的 EP8、第 1 个内部采样序号这一条：该记录持续 2035.220 μs，`aic_mac_ratio=0.010`，`aic_mte2_ratio=0.078`。选样沿用原记录的身份、profile 扰动及导出局限，不代表整机。前文周期代理比较已表明该组字段与时长的组间变化不相同；本检查回答另一个问题：即使两字段完全正确，是否足以拆分内部活动与等待？

**条件假设**：将这两个字段当成同一个归一化 core-cycle 样本空间上两个精确的 0/1 活动事件比例；历史 exporter 的分母、跨核聚合、计数口径与精度尚未完整证明符合这一假设。以下数学结论不是硬件实际占比或等待时间的测量；实际值仅以三位小数输出。

构造两个均有 1000 个抽象样本的实例，MAC 活动均为 10 个，MTE2 活动均为 78 个。第一种二者完全不重叠，两个字段都不活动的样本数为 912；第二种 MAC 完全包含在 MTE2 活动内，两个字段都不活动的样本数为 922。两个实例的整体字段相同，重叠分别为 0 和 10，但内部时间构成不同。一般地，以 a、b 为两个比例，二者共同活动范围为 `[max(0,a+b-1), min(a,b)]`，二者均未活动范围为 `[max(0,1-a-b),1-max(a,b)]`；将上述显示值作为精确值时分别为 `[0,0.010]` 和 `[0.912,0.922]`。

这只约束**两项事件在抽象样本空间内的联合关系**：两个字段都未活动时，可能执行其他流水/指令、处于控制或同步过程，也可能无工作；AIV、通信引擎和其他核仍可活动。现有两个边缘量本身不能区分上述情况，更不能推算设备空闲、等待比例、有效 MAC 操作数、通信字节、芯片 NPU 利用率或可消除耗时。即使可额外证实该集合解释，不能把 91.2%–92.2% 描述为此算子的等待时间；计数聚合不等于物理时间轴。任何观察到的相关性也无法单独证明低活动原因。

可复算：在任务根执行 `python3 agents/diagnosis/mc2-marginal-nonidentifiability.py`，输出与 `agents/diagnosis/mc2-marginal-nonidentifiability.json` 对照。脚本记录输入摘要 SHA，对选定样本及构造的两组边缘量断言。要进一步辨别原因，至少需要该实际调用的逐专家有效工作量和已绑定可执行对象、计数器的同版本定义，及能关联同一调用内部阶段与等待的直接数据；仅新增更多同口径边缘统计不能补齐这些缺口。本检查只使用已存文件，未修改模型/服务或启动 NPU。

## 路由总量守恒下的条件约束与可行反例（CPU 构造）

这里分析一种**待证的单一解释模型**，不是测得的 expert 行数：假设第 14、39 层属于同一个完整通信组，均有相同总有效路由行数 `S > 0`；假设记录的 EP8–15 是这个组的 8 个不同接收 rank；且各 rank 两层的设备记录耗时均服从相同参数的 `tᵢ,层 = aᵢ Rᵢ,层 + bᵢ`，其中 `aᵢ > 0, bᵢ ≥ 0`，`Rᵢ,层` 是该 rank 本层的有效专家行数。允许不同 rank 有不同 `aᵢ、bᵢ`，但同 rank 的两层不得变化。总量相等可由同一组两层有相同数量有效 token、每 token 恰好 6 个有效专家、没有丢弃/重复/容量截断得到；也可由其他方式成立。上述任一条件尚未通过本次采样证明。

由两层选中的实际设备记录，所有 8 对 `tᵢ,14 / tᵢ,39 ≥ q`，最小值 `q = 19.3435395...`。若上述模型成立，则 `Rᵢ,14 ≥ q Rᵢ,39`：直接展开得到 `aᵢRᵢ,14 + bᵢ ≥ q(aᵢRᵢ,39 + bᵢ)`，即 `Rᵢ,14 ≥ qRᵢ,39 + (q-1)bᵢ/aᵢ`。因此固定的非负截距只会使约束更严格，而不会产生这个观察比值。对已选 8 rank 求和，注意它们 14 层有效行数总和不超过全组 `S`，可得：

`sum_selected Rᵢ,39 / S ≤ 1/q = 5.1697%`。

这提供可以用未来同次 expert-count 测量检验的**必要条件**：一旦满足并证明同组总量守恒和该线性耗时模型，而短层所选 8 rank 的份额大于 5.1697%，此模型不成立。反之份额较低也只能说明该必要条件未被排除，不能证明路由量是根因。这里的 5.1697% 不是任何历史专家分布的测量，也不是严格性能上界；各 rank 通信、共享资源、分组 tile 填充、输入数值、调度或两层参数变化均可使该模型无效。当前尚未绑定该次全部 16 rank 为同一个实际 MC2 组，未绑定这些 EP 与专家实际归属，也不知有效 count、mask 或容量，不能把这个条件当事实。8 张卡是否恰占全部专家的一半，单凭记录也不能断言。

**合成可行性**：构造 16 个 rank，各 24 个可选专家、每 token 选 6 个不同专家，160 个有效 token 在两层无丢弃、无截断。合成短层给前 8 rank 各 114 行、后 8 rank 各 6 行；合成长层给前 8 rank 各 0 行、后 8 rank 各 120 行。每层总数均是 `160×6=960`，后 8 rank 同时达到 20 倍工作行数，短层占全组 5%。每个 token 的 6 个专家都合法地选在其中某个 rank，同一 token 的专家不重复；容量假设每 rank 至少 120 行。此例证明在上述抽象路由约束内，即使全组总量不变，所选 8 个 rank 的工作量也可以同时大幅增长；它不代表真实路由分布或真实 19.34 倍时长确由行数造成。若合成时间取 `aᵢ=1,bᵢ=0`，记录比为 20；`bᵢ>0` 时在相同工作量下比值变小。

复算：`python3 agents/diagnosis/mc2_routing_conservation_counterexample.py`；输入既有 18 签名成对记录 `mc2-l14-l39-matched-tasks.json` SHA-256 `521aef9efc67cc342ed062a97783e17b2847506c268af6ef13f839720b6d23cb`，选中精确 8 对 MC2 记录计算 q；脚本 SHA-256 `87a05a64e76e256158c94e455d25dcec7e6d0941ac6817d74d1c58baf3339230`。脚本只在 CPU 生成合成专家索引并检验唯一性、计数与容量；不读取真实 expert ID，不运行设备。
