# 同批逐卡：MC2 第 14 层和第 39 层的周期与比例分解

这是对已有 profile 的只读 CPU 算术，目的是区分“显示比例变小”与“总周期变大”的关系，**不是根因、代码优化或理论性能上界**。输入是 `diagnostic-20261029/target-layer-mc2-16rank.json`；脚本 `agents/diagnosis/compare_mc2_l14_l39_cycles.py` 要求同一匿名 scheduler digest `1b826883b782ba77814d5bd40fcd3e46c759e380069db2e066ff0e9cb4bce89d`、同一 EP 的两个目标层 scope 各唯一关联一条 `DispatchFFNCombine`，再逐项核对输入/输出 shape、dtype、format、Accelerator Core、block 数相同。8 张 EP8–15 全部满足；这些条件仍**不能**证明两层有效行数、专家负载、mask、通信、权重值、实际 kernel 或内部状态相同。数据来源是目标层同线程提交 scope → flow → 设备任务 → CSV，属于一次开启 profiler 的采样；层号代表提交归属，未匹配任务、其他流及 profiler 扰动需保留。原始行、flow、精确数及输入/脚本 SHA 在 `agents/diagnosis/mc2-l14-l39-cycles-comparison.json`。

所有 8 卡，第 14 层导出时长约为第 39 层 **19.34–19.52 倍**，AIC 总周期字段为 **20.25–24.81 倍**。第 14 层显示的 AIC MAC 比例为 0.001–0.011，第 39 层为 0.050–0.164。这个对照显示：总周期字段变大与比例降低同时发生，但两者增长倍数并不相同，无法用数值相似直接确定时间与周期的单位换算关系或因果。

如果假设显示值正好是被 0.001 最近舍入、且总周期字段精确，单独考虑 ratio 的舍入误差，EP10 的代理比区间约 **3.01–3.34**，EP15 约 **0.14–0.42**，EP9 约 **0.68–1.16**。这是对假设的灵敏度分析：当前未验证导出器的舍入规则、周期字段误差及相应的 9.2 版本统计分母，因此区间**不是已证明的真实硬件误差界**。尤其 0.001 的相对误差可能很大；不能把展示的小数位当成测量精度。

**可以得出的判断**：单看“第 14 层 MAC 比例更小”不足以得出“矩阵工作量变少”。可观察的数值分解中，8 卡总周期都变大，代理在不同 rank 既有更小也有更大；因此“各卡只是同一个固定代理分子，被更大的分母稀释”与显示值不符，且在上述最近舍入假设下 EP10、EP15 的方向仍不同。不能因此反过来声称实际 MAC 指令数或计算量改变：代理的统计口径、时间覆盖、分母与真值关系未闭合，两个 layer 的动态专家行等工作也未证明一致。

**尚不能判断**：空闲、通信等待、访存、路由不均、活跃核数变化、profile 归一化或其他原因哪个导致长时低比例。每张卡近似同步的长时也不能证明它们处于同一个 collective 等待。取得匹配版本的原始高精度 PMU 口径、相同调用内各专家实际行数与核任务分配、融合 MC2 内部的有时间界限阶段证据，才能继续区分；不得把跨流时间或不同 rank 时长加成墙钟，也不能直接拿此 profile 耗时当无采样服务速度。

复现：从任务根目录执行 `python3 agents/diagnosis/compare_mc2_l14_l39_cycles.py`；该脚本只读取上述已存 JSON、写当前分析目录，不启动 NPU、不修改目标实现。

## 同 scope 中选定的 gate 与 MC2：时长差与工作量未知
