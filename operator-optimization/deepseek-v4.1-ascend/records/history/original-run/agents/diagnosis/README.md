# 第 0 层 MC2 持续时间差：已有 trace 的离线复核

本次 Run 对固定的 3 个内部采样轮次（forward ordinal 1、6、7）比较 DP0 与 DP1 对应 TP 编号上的同层 MC2 耗时；数据为 16 个 rank、48 个第 0 层调用。第 1 层用同一轮、相同 rank、同为 physical M=3 的调用作参照。复算命令，在任务根目录执行：

```sh
python3 agents/diagnosis/mc2_duration_contrast.py
```

脚本校验 48 个样本、模型 ID、M、层号及第 0 层原始耗时，并在 JSON 中记录输入 SHA-256。对应 TP 编号是分析配对方式，并未证明两者是通信 peer；不同 DP 的同轮身份仍有 ordinal 配对假设。

| 采样轮次 | 第 0 层 DP0 中位数 | 第 0 层 DP1 中位数 | 配对耗时差 DP1−DP0 中位数 | 第 1 层相同配对差中位数 |
|---|---:|---:|---:|---:|
| 1 | 273.245 μs | 2031.189 μs | +1757.925 μs | −2.860 μs |
| 6 | 392.173 μs | 942.921 μs | +549.859 μs | +4.190 μs |
| 7 | 353.973 μs | 1661.876 μs | +1307.664 μs | +2.169 μs |

三轮全部 24 对中，第 0 层 DP1 更长。每个耗时使用该 rank 自己的开始与结束时间，因此固定时钟偏移不会改变该耗时；时钟频率误差、profile 扰动和跨组配对身份仍有不确定性。更正（2026-10-29）：此前结合跨卡绝对时间提出“DP1 更早进入、早到方等待”的说法，缺少已证明的跨设备时钟误差上界与同次 collective 身份，现撤回该判断；本表只支持各卡自身持续时间的组间差异。第 1 层对照说明这种大幅组间耗时差并非这三个采样轮次中各层都同样出现，但两层语义、专家路由和计算量不同，不能当成受控实验。

**不能判定**其中多少是通信等待、专家负载不平衡、计算、访存或其他原因；不能将差值视为可消除耗时或端到端收益。要区分原因，需要先将请求／collective 身份、各 rank 的发射与设备事件关联起来，再获得 MC2 dispatch、GMM、combine 与同步的可区分阶段记录或可信硬件计数。只有当已授权设备空闲且有明确采集需求时才需要新增采集；该 Run 没有启动 NPU 工作。
