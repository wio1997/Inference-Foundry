# Second, selective binding capture — review only

This directory contains a distinct copy of the previously reviewed controller. Nothing is started by merely viewing it or running the CPU mocks. After independent review, `python3 launch_second_background.py --execute` starts the local detached controller. Its handle, stdout, stderr, watchdog UUID/state and controller outputs remain in this directory. A PID or launched state does not establish capture or baseline recovery success. A durable one-shot controller reservation refuses all duplicate launches; after a crash, inspect controller PID and recovery status before manual intervention.

The new diagnostic container is `wio-vllm-v41-binding-diag2-169-20261029`; the remote task output is `.../diagnostic-20261029/binding-diagnostic-selective2`. It never uses the first diagnostic's container name, runtime, capture, profile, recovery records, watchdog lease or logs. It intentionally takes the first diagnostic's same container-internal ownership fence so the two controllers cannot park/restore concurrently. A launch has a unique UUID, checked against the created diagnostic's label and saved identities. Supervisor status, capture and restore also check that UUID and exact diagnostic ID. Recovery locates the new exact name and validates label/UUID before stopping it.

The startup chain verifies the fixed baseline ID and image, NPU process ownership, baseline health/idle, empirical per-chip HBM references, and a recent watchdog lease; persists and reads back both recovery identity copies before stopping the original; starts only after consecutive empirical release observations; monitors health and runs the existing workload/profile with PROFILE_ACTIVE. It records OFFLINE_EXPORT_REQUIRED, checks the client assertion-complete state, stop-profile status and aggregate success/input/output counters from progress.json, plus 16 readable worker framework/device data roots, then compares counts and sizes in three snapshots approximately two seconds apart. This is an observable stability clue, not proof of a complete flush. Missing/unstable data is preserved as incomplete through summary and restoration; client completion does not imply profile completeness. The probe does not read generated response texts. It does not wait 900 seconds for online export. If another NPU owner appears, it does not appropriate their device. A detached recovery watchdog is active before the service is parked. It retries on owner exit, and success requires original baseline HTTP health 200. Extremely abnormal loss of both saved references may defer recovery for manual intervention; HBM envelope is empirical, not proof that all hidden allocations belong to the owner.

The selective graphgate C source is bundled from this directory into the new runtime and compiled inside the stage container; its source and library hashes are saved in the new task output. It keeps matching launch/function metadata only during PROFILE_ACTIVE; selected graph capture candidates can be retained during warmup in bounded memory for possible replay correlation. Outputs remain candidates, not proven graph-task/kernel bindings; no target record is not evidence of absence. Recorder/profiler overhead and changed semantics remain unverified.
