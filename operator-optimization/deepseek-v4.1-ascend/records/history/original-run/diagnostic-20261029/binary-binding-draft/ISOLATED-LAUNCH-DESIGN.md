# 独立启动记录器：待审查方案（不执行）

## 为什么启动记录不等于任务绑定

只在启动期记录到某个 `load_data` 的 pre-call SHA、成功的 binHandle 和函数名，可验证**这个隔离进程观察到的加载/查询**，例如是不是出现三个安装对象之一的完整 `kernelName`，以及对应摘要是否与文件摘要相同。这个结果能为候选路径、API 取证覆盖和未来匹配提供信息；它不能证明当前 baseline 曾使用同一对象，也不能证明启动时看到的函数在目标 layer、相应 rank/step 确实执行。二进制可能预加载、被缓存或仅供其他分支使用，pre-call bytes 也不是 runtime 实际读取内容的证明。

如果需要把新实验的“目标层一次调用”关联到对象，最小链应是：

1. 每个目标 rank 的一次成功 data/file 加载时所观测内容摘要与 binHandle；若不等于原文件，需要确认容器封装/转换；
2. 与该 handle 同进程、同生命周期的成功 GetFunction 名称或 entry → funcHandle；处理 unload、重复注册、缓存、fork、句柄复用；
3. 在某个真实目标层的调用提交或 graph capture 中观察到此 funcHandle→stream/图节点，并由已验证的 tracer 将该节点或发射连接到特定 model/physical stream/task 与层标记；对 replay 单独验证 graph 节点身份和每次 replay；
4. 完整保存 `hook 路径覆盖/缺失`、日志丢失、版本、PID、进程生命周期与否定情况。仅有 Load / GetFunction 或仅有 profiler generic name 不构成上述链。未观测到发射不能推断没有执行。

现有 hook 只有 `LaunchKernelWithHostArgs`，缺捕获 modelRI/线程 task ID 等记录，且这些值与 profile 的物理 ID 是否对应未证。现有 `sitecustomize.py` 和 profiler 能提供层→设备 task 的证据，但它没有记录本 hook 的 funcHandle，因此不能直接用时间近似硬拼成唯一匹配。只有启动期加载是**低成本能力探针**，对闭合目标层身份是未完成；不应为单纯碰运气而停基线。

## 与现有启动脚本的关系

- `../start_recapture.py` 已检查固定 baseline 容器 ID/image、所有 NPU PID 属于 baseline、health/metrics 空闲；复制自己的独立 runtime，原模型/权重只读挂载，并在停止原 baseline 后再次检查卡、创建隔离诊断。`../run_capture_and_restore.py` 在 `finally` 内停诊断并尝试启动原容器。应复用其镜像、挂载和已冻结 workload 配置，不修改原文件。
- 这些现有检查是**快照而非锁**：两次采样间其他用户可能开始 NPU 任务，health/metrics 零也不阻止新的外部请求进入；`finally` 无法覆盖主控进程 SIGKILL、主机掉电、网络断开、Docker daemon 故障，baseline restart 命令成功不等于服务健康。不能把脚本的存在描述成绝对安全或保证无条件恢复。
- 若其他任务在原 baseline 已停止后占用卡，立即重启模型会违反“不影响别人”的约束；应停止诊断并记录 `RESTORE_DEFERRED_OTHER_NPU_OWNER`、保留自动恢复的清晰条件。诊断停止失败、卡仍占用、设备不可用或 daemon 故障也可能暂时无法恢复。所谓失败后无条件恢复应落实为**无条件执行恢复流程和告警**，但不能承诺忽略其他任务强行启动。

## 启动前必须解决的门槛

1. **空间总限额**：当前草稿每进程有条目上限，但十多个进程共享文件无全局大小上限、跨进程无日志锁。需先实现或配置任务专用目录的硬总空间上限且避免触发目标进程 SIGXFSZ；同时可报告丢失/截断。仅 `ulimit -f`、每进程条目数、定时 `du` 或单线程互斥都不足以保证总字节上限。实现后在多进程并发、部分写、错误/空间满和 fork mock 验证；正式诊断前核对其运行环境和挂载。在当前草稿未具备此门槛时不能启动模型。
2. **明确可观测的关联**：至少有运行时函数加载记录与基于相同进程/生命周期的使用证据，以及区分图 capture 与 replay 的依据；对不可闭合的关联提前定义结果为 UNKNOWN。想追求目标 task 身份则还需上一节第 3 点的实证机制，不能将时间接近当作身份。
3. **独立回滚监督**：诊断生命周期需由不随本地 SSH 会话退出而消失的受控监督器维护原容器身份、停止/恢复状态和 deadline，恢复前二次验证其他占卡情况；在容器不可用、超时或监督器重启后可重试并有可见告警。需要证明其进程身份与持久化状态是实际活体、停止条件可靠，并明确 daemon/机器宕机等不可保证的情况。当前脚本的 `finally` 单独不足。
4. **流量与空闲**：核实排队与在途采样覆盖所有引擎与 frontend；停止原服务前后尽可能安排用户侧流量静默或有明确的仅限本服务的入口控制。光靠瞬时 metrics 不能证明停机不会碰到随后到来的请求。无可靠控制时不得宣称完全无请求损失。
5. **调用覆盖与行为**：确认同镜像同 runtime 的符号解析方式和该 interposer 的覆盖，先在 CPU mock 验证后，再在允许的独立诊断中评估模型启动与记录丢失；留出原始实现未插桩基线作为参考。不能假定 `LD_PRELOAD` 对 `dlsym`、深绑定、其他发射 API 或每次 graph replay 都有效。仅诊断容器设置环境，需先核对并保留原容器已有 `LD_PRELOAD` 配置，禁止覆盖系统/原容器全局设置。

## 未来拟执行的状态机（非代码、未启动）

1. 生成任务目录内不可覆盖的新 run ID；准备只读的原镜像及独立 runtime 副本、已经审查和 CPU 验证的 recorder、明确受限日志目录；记录构建 SHA、镜像 ID、原服务精确配置和待恢复 ID。提前检查 health、所有 baseline 分片的空闲值、docker 容器 ID、NPU PID 映射和端口冲突，未知即不执行。评估其他进程产生的竞争窗口，不能把一次 PID 快照当资源预留。
2. 启动受控恢复监督并确认其可响应、持久记录已落在任务目录。临近停止基线前再次查所有占卡 PID、每个引擎与 frontend 在途/排队、baseline ID 和用户入口条件；不满足就终止，原服务继续运行。
3. 仅停本人的 baseline；确认它已停、卡进程为空后再启动新诊断容器。诊断容器使用原基线镜像与只读权重，独立配置、缓存与日志，限定私有端口和用户空间，不修改基线 mount；将 recorder 和专用记录路径仅注入这个容器。
4. 先观察启动的成功/失败、记录器覆盖、资源预算；如执行目标请求，必须使用冻结的诊断负载和已核验的层→task 采集链，所有过程只在独立容器中；结果只认符合关联证据的部分。对丢失、缓冲变化和不可识别的 graph 节点报告 UNKNOWN，不为凑结果扩展到他人服务。
5. 不论正常、异常或超时都触发恢复流程：验证诊断容器 ID 再停止，确认无自己的诊断设备进程；重新检查所有设备与他人进程。无人占卡时启动原 baseline 并等待 health/metrics 达到已知正常；有他人占卡、设备故障或原服务健康检查失败时记录未恢复状态与告警，不能假称成功。监督器在允许条件满足时重试。全部状态、摘要与截断标志落在 `/data/tiankuan/wio/main` 任务目录。

本文件为只读设计，无 NPU 操作，也没有修改现有启动脚本或运行中的容器。
