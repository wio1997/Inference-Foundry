## 表述和理论口径

- 当前文稿已明确不能识别全模型“利用率最低模块”，这一边界应保留。PipeUtilization、MAC 活动代理、npu-smi AICore%、算子占时和芯片总利用率不是同一指标。通信事件持续时间、跨流相交、真实关键路径等待和 host gap 也不是同一个量；不能由时间相交推出有效隐藏，更不能从未匹配区间推断空转。
- `README.md:53–65` 的 Q_b 纯计算约 0.356 µs 与 MoE `0.1×R µs` 应在首次出现时紧挨着标注采用的名义 353.8944 TMAC/s、直接 MAC 账及该假设的适用范围。后文已说它不是已认证硬容量；不能据此把 `42/0.356` 称作可兑现加速或不可超越的硬上界。冷权重完整读一次的 `bytes/B` 也是带初态和读取假设的条件参考，不是已测 HBM 流量。
- 不把“真实请求已完成”“导出目录稳定”“16 rank 各有两条元数据”升级为“所有模块和窗口已完整剖析”，也不把混合 prefill/首个非空文本时刻当作精确设备侧 prefill 结束。profile 会引入扰动；同输入、同流式方式并不等于两个运行的每个 DP 请求绑定和 draft 工作量完全相同。
- `README.md` 的历史两轮无 profiler 519.84 tokens/s 与本次诊断同场景配对结果分别标识来源、重复次数、计时边界、profile 开关和变更；仅在本次配对的实际数据可核验后报告本次扰动，不混用其他轮次算百分比。
- 实例级复现目前有限：公开融合清单已明确原始 `fusion-scan.json` 等未随公开摘要提供；`verify_summary.py` 只复算匿名摘要算术。报告应提供允许公开的哈希、输入范围、脚本及原始证据索引，不能将算术验证宣传为第三方可独立复采或证明语义/因果。
- 版本记录区分实际 `profiler_info` 中 CANN/torch_npu 字段、toolkit 真实路径与 MS Service Profiler 的 `version.info`；后者是组件信息，且本次未叠加该采集器，不是 CANN 版本或已完成的 engine-core 采集证明。
