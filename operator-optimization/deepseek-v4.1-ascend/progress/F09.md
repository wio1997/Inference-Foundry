## 算子与原有流程

Indexer project_query→inplace_partial_rotary_mul→quantize_indexer_query；归档32head×128，RoPE尾64，非packed INT8/FP16 scale域。

投影BF16 query→原位尾64旋转/BF16舍入→整128 custom quant（amax/FP16比例/INT8已融合）→QLI选择位置。

## 候选改动及其意义

本轮保留Indexer投影，仅在量化核读取整head后接入部分RoPE并保持原精度；仍需的BF16输出保留。

减少独立旋转的tail读取和任务交接；所有必要旋转/统计/量化保留，量化内部已有融合不重复计价。

## 成立条件与证据边界

原BF16旋转舍入、整128 amax、先FP16 scale舍入、div_rn/nearbyint/clip/min2^-24、所有读者/scale写所有权/事件保持；不套key或packed MXFP4量化规则。


## 第九条：索引查询的RoPE＋量化

本轮选择 **F09-ROPE-QUANT**。这是此前“先选哪些缓存位置”的Indexer小分支，不是主Attention的Q，也不是F05投影前1280维QR的量化。前面的Indexer投影保持原算子，先研究后面两个操作。

### 算子与算法

|操作|接口|作用|
|---|---|---|
|索引查询投影|`indexer.project_query / indexer.wq_b`|从qr生成索引查询；归档case为32个head，每head128维|
|位置旋转|`inplace_partial_rotary_mul`|只旋转每head末尾64维，前64维保留|
|每head量化|`quantize_indexer_query`|按完整128维求比例，用INT8数据＋FP16比例表示查询值|

量化可以理解为用整数和比例近似表示数值，例如整数3配比例0.1表示约0.3。这是模型原本就做的转换，融合不新增量化或额外降低精度。结果交给`npu_quant_lightning_indexer_v3`继续索引打分/选位置，选位置本身不在本轮。

### 怎么接起来

```text
原来：
索引查询投影 → BF16 query
                    ↓
         独立RoPE读尾64 → 旋转并BF16舍入 → 原位写回
                    ↓
         量化读取整128 → 求比例并转INT8 → INT8＋比例

候选：
索引查询投影 → BF16 query
                    ↓
[读取整128 → 旋转尾64 → 原BF16舍入 → 求整128比例 → 转INT8]
                    ↓
             INT8＋比例（保留仍需的BF16结果）
```

原量化kernel本来就要读取整128维，可以研究把旋转放入同一次处理，减少独立旋转的读取及任务交接。原量化内部已经融合amax、scale和转整数，不能再计一次首次融合这些基础操作的收益。

### 比例和精度不能换顺序

原量化先用整128维的绝对值最大值除127，将比例舍入成FP16，再以这个比例除数值，按nearbyint舍入并夹到[-127,127]。零值head使用最小正FP16次正规数2^-24作比例下限。

因此融合必须保留：投影原BF16结果→旋转→旋转结果BF16舍入→整128统计→比例先FP16舍入→原INT8舍入。不能拿未舍入旋转临时值量化，不能只对末64求比例，也不能套Indexer key的“先FP32比例量化、再缓存FP16比例”规则。

### 中间BF16结果和执行条件

当前prepared.query仍传给select_projected；所选INT8分支有形状读取，packed等其他路径仍可能消费BF16值。保守方案保持旋转后的BF16输出，只省一次独立tail读取。若M3/32head/tail64，该读取为12,288B（12KiB）；只有额外证明无须BF16输出后，才可研究连tail写入一起省24KiB。这不是实测HBM或峰值显存减少。

原RoPE在prepare阶段，量化后续由aux stream提交并通过quantize_done同步。融合还需决定执行时刻、保留原行/连续性/写scale所有权及其他读者，不能仅因两步有数据依赖就随意提前或推迟。空query、没有历史cache、不需要量化、packed MXFP4等条件按原路径保留。

### 当前判断

**这是适合先评估小范围原型的候选：投影不重写，已有量化核中接入局部旋转，必要计算保留。** 是否更快仍需比较整个Indexer查询/位置索引就绪时间、原有重叠、图内存和正确性。没有新实现、native精度测试或提速结果；Q_B/IndexQ联合投影等更大F09交叉变体不在本轮关闭。

## 手算例子：同一份数据如何从旋转走到INT8

为便于理解，用4维代替真实128维：前2维不转、后2维转90度。真实模型的维度/角度仍按前述源合同，此例不是native精度或性能证明。

```text
输入：[8, 2, 3, 4]
前两个不变；后两个[3,4]转90度变[-4,3]
旋转后：[8, 2, -4, 3]

完整行绝对值最大值：8
比例：8/127，按原FP16规则舍入后约0.063
原INT8规则得到：[127, 32, -64, 48] ＋ 比例
```

如果错误地仅用旋转后的两个数求最大值，会得到4，比例约0.0315；原来的8饱和后只能表示约4，结果明显改变。融合只能减少数据交接，不能删掉全head统计。

原来RoPE读取尾部、写回BF16，量化再读取整行。保守融合让量化核本来就要做的整行读取同时服务旋转，然后保留原BF16舍入和仍需的BF16写回，再做统计/INT8输出；少一次独立tail读取和设备任务边界，不声称所有写回消失。

算子内部暂存的是当前小批数据，处理完就输出，不要求把整模型或整份请求放入片上。必要的旋转、最大值、求比例、除法/舍入都还在。图模式即使已经减少Host下发开销，图内设备任务边界仍存在；省掉一个设备任务不等于主机开销或图显存按比例下降。

新实现还会增加cos/sin读取、配对运算和暂存压力，可能改变原aux重叠。应在原量化核基础上做最小变化，比较完整索引就绪时间与内存；没有收益则停止，不继续扩大融合范围。

精确手算数据及错误反例见[解释用数值例子](evidence/F09-rope-quant-worked-example-20261104.json)。例中整数能被BF16准确表示；真实小数的BF16边界仍必须按原规则保留，例子不能证明省掉舍入合法。
