## 本次回答：MoE路由TopK还能怎么优化

用户点名检查本族。本次选定的低成本子方案是 **F20-I64-NATIVE-NO-SANITIZER**：保留原INT64接口，让原生TopK中已有的编号处理承接调用方重复清理。另讨论部分选择和打分矩阵乘法融合，但不将它们升级为已验证方案。原F05顺序讨论位置不因此关闭。

### 当前已经融合了什么

固定调用为 `torch.ops._C_ascend.moe_gating_top_k_hash`，`norm_type=2`、`out_flag=False`。所查without-group源码内部已有：

```text
路由矩阵乘法 → 每个专家的原始分数
                  ↓
现有TopK：[按原规则变换分数 → 按token类型加bias → 全排序并选前K
          → 取未加bias的选中分数 → 归一化/缩放权重]
                  ↓
专家编号＋合并权重 → 既有dispatch/FFN/combine接口
```

这里分数变换是原FP32的Exp→+1→Ln→Sqrt，不直接替换为普通Softmax。用来选专家的加bias分数，与最终合并权重所用的未加bias分数不能混淆。此处已有融合不再计一次“首次融合”收益；目标已加载二进制/171当前分支仍未在本侧聊重新绑定。

### 推荐先看：TopK前面的输入编号清理

这处理的是**输入token编号，不是TopK输出的专家编号**。原调用会转换为INT64、对齐行，再把-1改为0；所选旧图中清理对应Equal、Fill、SelectV2三个任务。已钉原生IsImageRow内部也做-1→0。

```text
原来：转换/对齐编号 → [比较-1 → 准备0 → 选择替换结果] → 原生TopK再处理-1
候选：转换/对齐编号 ────────────────────────────→ 原生TopK处理-1
```

在已证明的无hash、without-group原生分支中，两次相同清理满足C(C(ID))=C(ID)，因此可研究省掉外面一次，可能只需调整调用，不需新增kernel源码。不是删除全部输入准备：INT64转换、行映射、通信/pad、原ID及其其他读者仍保留。Torch fallback、有hash或其他分组分支不能直接套用，加载实现和实际输出尚未验收。

### 第二个方向：只选前6，不把384个分数全部排好

所查主模型E384/k6源码对完整E做Sort，然后取前6。部分选择可能少做比较，但并非只计算6个专家分数；偏置及原评分规则仍须满足。硬件已有Sort可能比新选择算法高效，因此“理论比较量少”不是实测提速。

同分顺序、NaN/Inf、精度和原路由权重必须保留；改K或换评分公式属于改变模型规则，不算当前等价优化。

### 真正跨算子融合：路由打分矩阵乘法＋TopK

可以研究同一实现算出整行专家分数后直接选择，减少logits写出和再读取。E384/FLOAT时逻辑一写一读是3072B/行，M3合计9216B（9KiB）；这不是已测HBM差值，也不删除矩阵计算。

难点是矩阵乘法可能分块产生分数，TopK要得到全行一致结果。整行交接、局部候选合并和临时空间必须一起计价。例如列宽16时产生144个局部候选；每项12B的一写一读为3456B/行，比原3072B/行更大。融合范围更大未必更省显存或更快。

### 旧profile支持什么

以下来自旧166归档，不能当171新测量、不能将独立中位数相加为整段中位数：

|范围|样本数|观测中位任务耗时|
|---|---:|---:|
|M3、E384、k6的root-bound TopK整算子|2560|4.82微秒|
|同一批root-bound链中的Equal＋Fill＋SelectV2任务耗时之和|2560|6.14微秒|
|M816、E384、k6的direct TopK整算子|640|35.191微秒|

清理三步不比整TopK轻，支持优先验证低成本的重复消除。6.14微秒是观测任务耗时之和，不是承诺可节省的请求延迟。TopK任务内排序、非线性和其他阶段没有单独计时，不能把4.82微秒全归为排序。

## 条件分支融合：共同前缀A与互斥B/C

用户明确提出两种变换，均纳入候选分析；它们和此前A同时给B、C两个消费者不是同一种情况。

```python
# 原来：每次算A，再选B/C中的一个
t = A(x)
if p:
    out = B(t)
else:
    out = C(t)

# 候选1：条件可提前获得、重排不改语义时，选一个专用融合算子
if p:
    out = AB(x)
else:
    out = AC(x)
```

候选1虽然AB、AC代码都包含A，**每次只走一支，因此A仍只计算一次**。在A/B/C原来各一次底层执行的简化模型中，每次是A＋所选B/C两次，候选可变成一次。两种实现不表示每次都启动两个算子，也不等于每张capture图都保存两支。若B、C都要执行，则AB和AC会重算A，属于此前另一个取舍。

候选2把共同前缀和判断都放进一个真正的底层算子：

```python
# 表示候选kernel内部逻辑，不是用Python函数包装即可实现
t = A_inside(x)
if p:
    out = B_inside(t)
else:
    out = C_inside(t)
```

如果p依赖A的结果，就不能在A前凭空选择AB/AC；可研究在内部先算A，再得到p并选择。能否成为一个高效kernel还取决于全行统计、跨块同步、容量和支路操作兼容性，不能只靠伪代码定案。

### 当前TopK已有实际源码例子

所查原生TopK在同一kernel内部做：按token编号判断类型→选图像bias或文本bias（或无bias）→继续专家选择和权重计算。Process里另有hash与排序路径的条件；旧所选无hash观测不代表hash分支执行过。归档v76已经保留相关条件清单，但不是全部模型条件分支已关闭。

### 何时更值得融合

- 条件在host已知且长期固定：可比较分支专用实现；需核对是否因此保留更多capture图/内存池。
- 条件来自设备数据：内部判断可能避免额外数据交接；不得默认需要或已经存在CPU往返。
- 一批不同行走不同分支：需要按实际行/块的执行方式计价，不把统一条件的成本直接套过来。
- 不用`where(p, B(t), C(t))`就认定只算一支；eager实参求值可先算两边，编译后的真实行为需检查。

### 内存和语义约束

选中一支不保证只分配该支临时空间；需看实际buffer生命周期、工作区和图池。反过来，两份代码也不意味着中间结果必须两份常驻。所有原读者、数值舍入、状态和通信参与要求保留，不得误执行原先未选分支的副作用。

**本次补齐的是候选生成与解释中的条件分支视角，没有新kernel、性能或全覆盖结论。** 同一条件/源域复用已有合同，不重新穷举无关算子配对。详见[条件融合记录](evidence/F20-conditional-fusion-review-20261103.json)。
