# 逐条进展记录规范

每个既有候选保持一个稳定编号和一页记录。日常先看总览和当前候选页，不重读历史目录。F01 这样的候选族还要指定本轮子方案，不能把族内不同方案混成一个已证结论。

## 每页必须回答

1. 算子或操作叫什么？名称是语义名称、模型方法、自定义 API 还是已绑定的 profile 名称？
2. 原来如何计算、输入输出是什么、全部消费者在哪里？
3. 本轮到底改什么，属于融合、拆分、复用、状态重组还是调度？
4. 底层算法、依赖和数值/状态条件是什么？哪些已有事实可以复用？
5. 已有证据来自哪个源版本、机器、采集批次、shape/dtype 和度量口径？
6. 还缺什么，以及它会改变哪个决定？下一步的接受、否定或停止条件是什么？
7. 本轮新增了什么事实、反例或纠正？没有决策增量时，不启动重复取证。

## 状态必须分开

|维度|允许表达的意思|
|---|---|
|历史分析|沿用原归档条件分析，不代表新实现或新复核|
|本轮逻辑复核|说明具体子方案和源码适用域；不能替代 native 执行证据|
|独立复核|只有实际收到独立审查结果并引用产物后才完成；请求过代理不等于启动过|
|实现|有可追溯代码和构建/运行记录，才能从“未实施”升级|
|正确性|候选路径确实执行且用例/数值/状态判据通过后才接受|
|性能|同 case、同采集口径、同完成边界，并说明重复测量与噪声；不能用算子时间之和作端到端收益|

登记 42 页只说明入口覆盖。F01 的 EARLY-Y 源码依赖澄清不代表 F01 全族验证完成，也不改变历史 v180 的原始归档文件。

## 更新方式

1. 修改 `candidates.json` 对应候选的当前状态、逻辑、证据和下一步。保留稳定 ID。
2. 向 `events.jsonl` 追加唯一事件：日期、候选 ID、依据和决策增量。纠正必须写明旧说法、正确范围及原因；不悄悄覆盖历史事件。
3. 执行 `python tools/render_progress.py`，生成 42 个可读页、总览和变更记录；`--check` 只检查，不写文件。
4. 涉及当前 Task 时，用 Task/Loop/Run 记录一次有边界的复核或实验。未运行的实验只保留待办，不创建虚假 benchmark Run。
5. 检查本次改动及链接后提交到现有分支。Git 提交记录保留每次更新，可用页面 History 和提交 diff 回溯。

日常不要全量扫描/rehash 历史归档。更新的实际源码、配置或假设只使相关证据失效。对“未知”和失败同样记录重开条件，不因对话恢复重跑同一问题。
