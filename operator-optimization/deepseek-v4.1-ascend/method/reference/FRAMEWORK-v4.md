# 推理框架的理想吞吐上界 — PEAK-CEILING-v4

本文是框架范围的理论分析参考；算子/子图/模块性能与极限对比按当前流程固定执行。当前执行顺序见 ../PROTOCOL.md，模块诊断见 ../MODULE_DIAGNOSIS.md；当前阶段不推进到解决方案或实现。

## 对象：整个推理工作，不是框架调用序列

给定硬件、模型/数值语义、允许算法和负载，研究任何合规框架实现的天花板。SGLang/DeepInfer 的代码提供计算与状态语义，也帮助识别可消除开销；当前 Python、kernel 边界、提交顺序和同步不被默认继承。

理想 model 是“没有框架开销的推理机”：零调度/元数据/提交/回读/分配/HTTP 成本，允许最佳融合、布局、批处理、负载均衡和域内任意重叠。存储/通信/容量可以先进一步放宽，不先要求开发者实现这些理想条件。

## 固定口径

合同明确以下条件，缺项查资料或保留未知：

- 模型与权重身份、W8A8/混合精度、准确性与采样语义。
- 输入/输出长度、请求内容或分布、到达与并发、TTFT/TPOT 等服务约束。
- 初始 prefix/KV/权重/Engram 驻留，冷热与命中依据；输出答案缓存是否允许。不能预先注入目标答案。
- 普通解码、DSpark 或 prompt lookup 等允许算法，候选/验证和最终接受 token 的计数；随机条件与 trace 身份。
- TP/EP/DP、放置和重分片是固定限制还是允许自由选择。自由选择时，不能把某分片方案的通信当成所有实现必需。
- 模型已驻留后的服务时间，还是包含加载/建图等启动时间。不能把不同时间范围的数据混算。

## 第一层：必要计算的理想资源负载

对固定有效工作 Q，推导全程至少必须完成的资源工作 W_min[r,Q]。包含必要的线性/attention、路由/MoE、归一化、量化/反量化、采样/验证等；只有在允许域内证明不可避免的部分才计入。不照搬当前算子个数或逐算子时长。

对每个资源已知容量上限 C_max[r]：

    L_compute = max_r W_min[r,Q]/C_max[r]
    U0 = Q/L_compute

“每个 token 平均多少工作”可能依赖批量、复用、专家并集、上下文和接受率；优先推导全程总量，不机械乘平均。跨多个设备时使用实际可用容量的乐观上限，必要时先允许完美平衡；不把设备数与物理卡/die 混淆。

若必要计算量或资源峰值缺证据，只给条件/符号模型。工作量对固定算法成立时，写“该算法域上界”，不声称所有精确算法都不可能更快。

## 第二层：必要数据与资源守恒

逐步加入证明必要的 HBM/片上、CPU 内存、主机互联、片内/片间链路及拓扑割负载：

    L_resource = max_r NecessaryWork[r,Q]/CapacityUpper[r]
    L = max(L_compute, L_resource)

同一物理资源的必要负载累计。权重在片上/缓存的复用、KV 布局、专家并集、批次共享、压缩和重算会改变字节数，不能按整个模型大小/token 推界。

Engram/CPU 卸载只按真正必需的访问量、带宽和容量收紧；不要把当前 CPU 查询/同步实现直接加入不可消除的时间。查询接口无法证实最小流量时保留条件界。

## 第三层：必要因果

单请求同一数据的生产消费、attention/归约、采样后状态推进，可能提供不可突破的链或循环下界。但模型层级依赖不等于完整 kernel 必须串行，需允许块级发布与跨层流水。

投机算法可以一次验证多个候选，不能用“每 token 一次完整串行前向”约束更宽域。接受率已知 trace 只支持该 trace 条件结论；未知时可用允许的乐观包络，但必须纳入对应必要验证工作。使用不可实现的接受 oracle 作为松弛时明示，不声称真实模型支持该接受率。

不同请求之间可重叠，但有共同计算/存储/链路预算。无限并发或放宽延迟可作为明确松弛，给固定 C8/延迟条件下仍有效但较宽的上界；不能把它称为原问题的精确极限，恢复原条件时需另有收紧依据。

## 指标分别推导

TTFT：从声明起点到首个有效输出的时间下界。prefill 依实际缓存初态处理；32K 总 prompt、其中 90% 已缓存的场景不代表冷 32K。

TPOT/II：确定是相邻 token 间隔、首末 token 平均间隔，还是验证组循环间隔。允许突发输出时不能把一个验证组的间隔直接当每 token 的硬下限。

有限批次 TPS：固定请求集合的最终接受输出 Q 除以完整声明计时窗口，以该窗口的有效时间下界给上界。输入处理已经含在时间中时，不能再把独立 prefill/decode 峰值随意相加。

稳态输出 TPS：可用累计资源守恒直接约束。若对任意合规稳定执行，资源 r 的长期必要消耗率至少为输出率 λ 乘 w_min[r]，则 λ≤C_max[r]/w_min[r]；必须证明 w_min 包含所要求输入到达、批次复用和输出比例。无限批量得到的上界不要称为固定并发/延迟条件下精确极限。

## 框架调度怎样处理

不先估算 Python 调度能缩短多少，而是把它从 L0 中放宽为零。接口、源码与历史 trace 用来理解哪些状态依赖是真实的，哪些开销只是实现选择。除非已证明必要，CPU 时延、固定 microbatch、event 次数和 graph 调用次数都不收紧通用上界。

例如可查 [SGLang 的 overlap/future-token 说明](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/) 和 [DeepInfer ZOS 元数据源码入口](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py)。它们帮助定位异步状态边；不是 Ascend 硬件成本证据，使用时固定实际版本并核对源码。

理论上给开发 Agent 的要求是“不论怎样调度都受这些必要负载/因果约束”；怎样隐藏其他工作由开发任务实现，本评估不需要给它一份最优调度。

## 最终交付给开发 Agent

逐层 U0≥U1≥…；每层假设/必要性证据；支配限制；有效工作和缓存/算法/精度条件；被放宽为零的开销；缺失参数。

可以附已有同口径成绩/上界比例，但不是可达提速承诺。开发成绩超过声称严格界时，应审查界或条件，不把成绩压回去。不给可达方案仍能完成本评估。
