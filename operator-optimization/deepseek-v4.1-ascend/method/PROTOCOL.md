# P1–P7：先找融合机会，再定位模块低利用率

本流程只做发现与诊断。候选结构在分析图中调整，不改目标实现，不给优化解决方案，不执行优化实验。固定主线：范围与基线 → 融合扫描及停止 → 模块实际表现 → 理论极限与实测对比 → 最低利用率模块原因定位 → 交付。

## P1 固定范围与原图

在 runs/任务名/ 复制 templates/ 中的合同、记录、扫描、模块分析、状态和报告。将 workflow-state.json 复制为该任务的 STATE.json。固定源码版本、模块定义、输入/输出、shape/dtype、精度、图边界及可读资料；未知项保留 UNKNOWN。

提取已声明范围的计算图，记录节点、数据边、全部消费者、别名/原地更新、控制/通信边和模块归属。动态分支、不同 Case 分别记覆盖情况。冻结原图 G0；后续候选图都能映射回 G0。只拿到一个算子时写明图不完整，不能声称完成了全模型扫描。

## P2 首轮融合与拆分重组扫描

按 FUSION_SCAN.md 扫描整个范围：两两、三个、更多算子、共享输入/生产者的分支、跨模块边，以及拆开后重新组合。每个机会记录原图与候选图、语义条件、所有消费者、可消除的计算/物化/搬运、资源顾虑和证据。

先发现候选，不要求现有 API 已支持，也不要求先实现或跑分。不能因两两融合没有候选就跳过三算子和拆分重组。候选间互斥、依赖或重叠要记录，不能宣称可以同时全部采用。

## P3 扩展、复扫与停止

对已发现候选继续尝试扩大子图或拆分重组；对发生变化的邻域复扫，最后对声明规则和范围完成一次覆盖检查。保存图指纹和候选去重记录，防止拆开/合并来回循环。

本阶段完成条件是声明范围、Case 和改写规则下的一整轮不再出现新的非等价候选，且每个扫描项均有结论。标 SCAN_COMPLETE_IN_SCOPE，并给出仍有条件的候选数；这不证明所有可能算法均已穷尽。资料、权限或预算不足时标 PAUSED_WITH_GAPS，保留未扫描项和具体原因。

无论是完成还是有明确缺口的暂停，都保存 fusion-scan.json 后进入模块诊断；阶段暂停不是“没有融合机会”。

## P4 按模块分析 NPU 利用率

先按 PROFILING.md 检查数据是否足够；有现成数据就离线汇总，缺证据时填 profiling-plan.json，在已授权设备范围执行有限诊断采集。保留独立无 profiler 基线。交付 profile-index.json、全量聚合表和有界 profile-summary.json，模型先读摘要再按模块/rank/step/时间窗取局部证据；不直接通读大 trace。

分析当前可观察的实现图 G0，或明确标识的已有实现版本。候选图未经实现，不能为它填写实测利用率。按 MODULE_DIAGNOSIS.md 先固定指标定义、设备/核心、分母、时间窗、Case 和采样来源，再汇总每个模块的利用率、耗时、调用次数、等待及资源活动。

在同口径有效数据中升序排列，明确指出最低模块或并列最低集合，并报告覆盖率。没有数据就保留 UNKNOWN，不用 FLOPs 推测值或整卡采样替代模块测量。重叠活动、嵌套模块和共享 kernel 无法归属时单列，不能重复计入后强行排名。

## P5 理论极限与实际性能对比（固定环节）

对声明范围内的算子、子图和模块，按 OPERATOR_MODEL.md 和 reference/ 中的方法建立必要计算、逐层 I/O、资源争用和依赖的模型；自主取证并保存快照/哈希。先允许理想融合与重叠，再以有证明的必要约束收紧，L[k]=max(L[k-1], 新下界)，U[k]=Q/L[k]。

严格界使用工作量下界和能力上界；实测有效速率只支持相应观测或估计。模块和融合子图整体重新计数，不相加独立算子下界。固定硬件、Case、精度、输入域、初态、有效工作 Q、计时范围及允许实现域；不匹配的实测与界不计算比值。

每个对象必须有对比记录：实际耗时 T、时间下界 L、实际吞吐 Q/T、吞吐上界 U、实测/上界比 L/T、差距倍数 T/L、NPU 利用率、支配约束、证据和界的状态。仅在 T、L、Q 均为同口径有效正值时计算相应比值；差距不是可达提速承诺，L/T 也不是设备活动率。若实测突破声称严格的界，先审查口径、前提和计数。

融合候选另列必要工作/I/O 变化和理论界，实测字段留空，不能把不同实现域的上界变化当成已证收益。缺少参数保留符号或条件界；缺实测、无法证明必要工作或硬件容量时，记录 UNKNOWN/INCOMPLETE 和缺口，仍进入原因分析，不省略本环节或编数字。

填 bounds-input.json，多个对象分别保存输入和对象映射；有可复算内容时运行计算器并保存原始输出。结果同步写入 module-analysis.json 的 performance_comparisons 和报告对照表。

## P6 结合极限对比定位最低模块的原因

从最低模块出发检查调用链和时间线，分别列出供给/调度空洞、数据/通信/同步等待、访存压力、并行度不足、负载不均、执行路径或统计口径等竞争解释。每条记录症状、机制、支持证据、反证、受影响 Case、缺失证据和置信程度。

结合 P5 对照判断低利用率是否与计算/访存/依赖约束相符，或仍存在无法解释的差距。仅凭远离一个较松的界不能确认存在可消除开销，必须有时间线、源码或硬件证据。再检查模块耗时占比及端到端暴露时间，解释问题影响；最低利用率不自动等于最大瓶颈。

当前阶段不提出修复策略、内核实现或调优方案。无法区分的原因标 HYPOTHESIS，不把症状改名当结论。按 REVIEW.md 审核发现、归属、对比、诊断和理论结论。

## P7 交付并停在定位结果

REPORT.md 依次回答：发现哪些融合/重组机会；扫过什么、遗漏什么、为何停止；哪个模块利用率最低；各对象实际性能与理论极限的差距及其依据是什么；低利用率的可能或已支持原因是什么、还有哪些未知。

交付合同、原图/候选图、fusion-scan.json、module-analysis.json（含性能对比）、records.json、任务 STATE.json、profile-index.json、profile-summary.json、采集计划/已有测量及 bounds-input.json；做过数值复算时再附原始计算输出。大原始数据保留原路径与哈希，不并入交付小摘要。没有实现/解决方案/提速结果不影响此阶段验收；缺失的利用率、界或原因证据必须明确标注。
