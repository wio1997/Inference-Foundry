# 模块 NPU 利用率与原因定位

## 固定正在观察的实现

融合候选尚未实现时，诊断仍对应原图 G0 或已有 trace 的确切版本。模块到 kernel/event/stream 的映射、源码版本、Case、设备数量和采样时段必须保存。不能将候选图的估算字段标成融合后的实测。

优先用已有 trace、profiler 导出和无 profiling 的基线。采集与大文件处理按 PROFILING.md：先读索引/摘要，缺什么证据才定向提取或补采。无采集授权时只准备计划；已有授权范围内的诊断取证继续执行，不重复请求权限。模块映射、kernel 耗时统计、设备活动率和 MFU 分别核对，不把官方模块统计表直接当利用率排名。

## 利用率口径

“NPU 利用率”必须写清具体定义。分别保存设备忙碌率、Cube/Vector 活动率、有效计算吞吐/相应峰值比、带宽利用率等可用指标，不能混成一个百分比。计算效率估计不自动等于活动率。

排名使用合同中指定的主指标；未指定时，选数据可得且在模块之间定义一致的设备/核心活动指标，并明确名称。必须保存分子、分母、单位、统计时间窗、核心/设备集合、样本数、聚合规则和来源定义。无法统一时分组排名，报告不存在一个可信的全体最低值。

模块窗口内的设备活动与 kernel 执行期间的引擎活动应分开：只看 kernel 内部可能漏掉提交和等待空洞；整卡其他任务或模块的活动也不能归给当前模块。多次调用按匹配的时间或核心时间加权，不能直接平均各调用百分比。若指标本身有别的聚合定义，遵循并引用该定义。

嵌套模块固定同一层级或明确 inclusive/exclusive 口径；不同 stream/模块重叠时，按来源可支持的区间并集和归属计算。不能归属的共享 kernel 或重叠区间单列，计入覆盖缺口，禁止重复相加。

## 找到最低者并说明影响

每个模块记录主利用率指标、有效样本、调用次数、窗口/执行耗时、等待、可得的引擎/访存/通信指标及端到端关键路径暴露。无法确定的字段使用 null/UNKNOWN，不填 0；未执行的模块不参加排名。

对同 Case、同口径且有效的模块升序排序。若缺模块数据，结论写“已测 N 个模块中最低”，同时报告总模块数和缺失名单；噪声或分辨率无法区分时给并列最低集合。不同 Case 的最低者可以不同，聚合权重必须声明。

低利用率模块仍必须诊断。耗时和关键路径影响用于说明问题的重要程度，不能直接用低利用率替代端到端瓶颈判断。

## 先完成理论极限对比

按 PROTOCOL.md 的 P5 为算子/子图/模块建立时间下界、吞吐上界与实测对照，记录同口径的 L/T、T/L、支配约束和界的状态；缺数据也保留对照行并标未知。候选结构只有理论项，不能虚构实测。结合对照和下面的原因证据定位问题；较大的理论差距本身不证明存在可消除开销。

## 原因定位表

以下是待核对的竞争解释；不能仅凭低百分比认定任何一条。

| 可能原因 | 用于支持或排除的已有证据 |
|---|---|
| Host/调度供给不足 | 提交间隔、队列状态、CPU 与设备时间线是否对应空洞 |
| 数据、同步或通信等待 | 依赖事件、等待区间、数据到达时间与资源活动是否对应 |
| 访存/数据路径限制 | 传输量、带宽活动、停顿与算术强度；不能只看 Cube 低 |
| 工作量或并行度不足 | Case 大小、任务块/活跃核心分布、尾块时间 |
| 负载不均或长尾 | 核心/设备/分片完成时间和工作量分布 |
| 执行路径与预期不符 | 实际 kernel/指令/回退路径、dtype/layout 转换记录 |
| 测量归属或口径问题 | 采样精度、重叠、嵌套、多任务干扰、计时窗口和 profiler 扰动 |

每条原因分别记录 observed_symptom、mechanism、supporting_evidence、counter_evidence、missing_evidence、affected_cases 和结论。用 SUPPORTED 表示有证据支持，HYPOTHESIS 表示尚未区分，REFUTED 表示被现有证据否定；相关性不足以自动证明因果，多个原因可以并存。

分析到“哪个模块、为什么低、依据和未知是什么”即结束。缺证据时记录下一项需要读取的资料，不设计解决方案、实施修复或运行对照实验。
